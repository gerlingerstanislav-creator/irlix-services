# Migration frontend

Самостоятельный web сервис на `/migration/`, отдельный от Dashboard/Portal. Единственная страница и пункт меню — «Пульт переноса» на `/migration/`. Прежний интерфейс полностью удалён; ссылки `/migration/console` и `/migration/console/` после OIDC заменяются основным адресом с сохранением параметров и hash. Общая оболочка и переключатель сервисов — `@irlix/ui`; OIDC — `@irlix/auth` с отдельным storage prefix. Только platform-admin; права проверяются через Employees и повторно в Migration API.

`npm ci`, `npm run build`; локальный preview `npx vite --host 127.0.0.1`. API использует абсолютный `/api/migration/`. Production host nginx удаляет `/migration/` при проксировании на контейнер `migration-web` (8099); Vite asset base сохраняет внешний prefix.

`node --test tests/*.mjs`. Browser fixture `tests/migration-console.browser.cjs` принимает `MIGRATION_PREVIEW`, `PLAYWRIGHT_MODULE`, `CHROMIUM_EXECUTABLE`; все identities и API синтетические. Проверяет отдельное меню, admin boundary, queue lock, mobile overflow и сохранность value/DOM/focus/caret при polling без запущенного Portal.

Run/rollback orchestration, read-only credentials и контрольные точки: [docs/MIGRATION.md](../../docs/MIGRATION.md).


### Clients: legacy-статусы, причины закрытия и диагностика подготовки · 2026-10-08

Старые коды лидов поддерживаются наряду с русскими статусами: `new → Новый лид`, `initial → Первичный контакт`, `clarification → Уточнение потребностей`, `ignore → Клиент в игноре`, `failed → Сделка закрыта - Отказ`. Другие неизвестные коды остаются конфликтами. Исходная запись сохраняется в приватной metadata.

`attempt_result → results.title` содержит также причины отказа, а не только успех/неудачу. Известные причины из действующего `RequestWorkflowController::FAILURE_REASONS` означают `Закрыт: неудача` и сохраняются в обычном `failure_reasons`; несколько причин одного отрицательного результата допустимы. Явные успех/неудача поддерживаются. Сочетание успеха и отказа, отсутствие результата и неизвестный title блокируют перенос. Комментарий сохраняется отдельно; даты и причины не выдумываются.

Диагностика условий различает отсутствующую сумму, нечисловое значение, диапазон/точность, отсутствующий грейд и ссылку на справочник; указывается конкретное поле без исходной суммы или шифртекста. Нечисловое значение само по себе не доказывает шифрование. Ошибки зависимых строк Clients имеют `DEPENDENCY_BLOCKED` с таблицей, ID и причиной зависимости; `blocked_count` является подмножеством ошибок, а не дополнительным числом ошибок.

Dry run для адаптеров SchemaMigration считает `ready_count` и `processed_count`, но не `success_count`: проверенная строка не является импортированной. Повторная обработка и сохранение дополнительных полей той же строки в metadata не увеличивают число обработанных строк. Пульт показывает «Готово к переносу» и «Только metadata», счётчик готовых строк и зависимостей, до 40 групп предупреждений по таблице/коду/причине; полный журнал с ID и исходной metadata сохраняется. Старые отчёты не пересчитываются: для новых счётчиков нужен новый Dry run.

Ручное сопоставление пользователей доступно также для Clients через существующие `employee-match` / `employee-map`. Проверяются последний ошибочный Dry run, подтверждение, fingerprint email/external_key, уникальный текущий login Employees, UUID, отсутствие активных операций и запрет перепривязки уже импортированного user к другому Employees ID. Постоянные login-связи разделены по сервису и источнику; решение Clients не влияет на Vacations и переживает бизнес-откат. Внешние участники без проверенной личности остаются конфликтами; этот экран сопоставляет users, а не создаёт фиктивных сотрудников/подрядчиков.

Offline SQLite/HTTP regressions проверяют коды лидов, несколько причин отказа, неоднозначность, числовые поля, отсутствие target writes в Dry run, идемпотентность, точные счётчики, группировку предупреждений и изоляцию identity-связей Clients/Vacations.
