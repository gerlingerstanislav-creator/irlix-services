# Migration frontend

Основной production URL — `/system/migration/` в существующей оболочке System. По умолчанию открывается «Пульт переноса», вкладка «Контроль переноса» доступна по `/system/migration/?view=control`. Host nginx перенаправляет `/migration/` в System. Standalone frontend сохраняется для локальных проверок и совместимости: `/migration/` и `/migration/?view=control`. Параметры `service`, прочие query и hash сохраняются при переключении вкладок; back/forward восстанавливает выбранный вид.

Публичный компонент `MigrationConsole.vue`, который System уже импортирует с `embedded:true`, содержит обе вкладки без дополнительной оболочки. Исходный пульт сохранён в `MigrationConsoleLegacy.vue`; standalone `MigrationWorkspace.vue` использует его напрямую, чтобы не дублировать вкладки или shell. Общая оболочка и элементы управления — `@irlix/ui`; OIDC standalone — `@irlix/auth` с отдельным storage prefix. Только platform-admin; права проверяются через Employees и повторно в Migration API.

`npm ci`, `npm run build`; локальный preview `npx vite --host 127.0.0.1`. API использует абсолютный `/api/migration/`. В production экран поставляется сборкой `apps/system` через `/system/`; standalone сборка использует Vite asset base `/migration/`.

`node --test tests/*.mjs`. Browser fixture `tests/migration-console.browser.cjs` принимает `MIGRATION_PREVIEW`, `PLAYWRIGHT_MODULE`, `CHROMIUM_EXECUTABLE`; все identities и API синтетические. Проверяет отдельное меню, admin boundary, queue lock, mobile overflow и сохранность value/DOM/focus/caret при polling без запущенного Portal.

Run/rollback orchestration, read-only credentials и контрольные точки: [docs/MIGRATION.md](../../docs/MIGRATION.md).


### Clients: legacy-статусы, причины закрытия и диагностика подготовки · 2026-10-08

Старые коды лидов поддерживаются наряду с русскими статусами: `new → Новый лид`, `initial → Первичный контакт`, `clarification → Уточнение потребностей`, `ignore → Клиент в игноре`, `failed → Сделка закрыта - Отказ`. Другие неизвестные коды остаются конфликтами. Исходная запись сохраняется в приватной metadata.

`attempt_result → results.title` содержит также причины отказа, а не только успех/неудачу. Известные причины из действующего `RequestWorkflowController::FAILURE_REASONS` означают `Закрыт: неудача` и сохраняются в обычном `failure_reasons`; несколько причин одного отрицательного результата допустимы. Явные успех/неудача поддерживаются. Сочетание успеха и отказа, отсутствие результата и неизвестный title блокируют перенос. Комментарий сохраняется отдельно; даты и причины не выдумываются.

Диагностика условий различает отсутствующую сумму, нечисловое значение, диапазон/точность, отсутствующий грейд и ссылку на справочник; указывается конкретное поле без исходной суммы или шифртекста. Нечисловое значение само по себе не доказывает шифрование. Ошибки зависимых строк Clients имеют `DEPENDENCY_BLOCKED` с таблицей, ID и причиной зависимости; `blocked_count` является подмножеством ошибок, а не дополнительным числом ошибок.

Dry run для адаптеров SchemaMigration считает `ready_count` и `processed_count`, но не `success_count`: проверенная строка не является импортированной. Повторная обработка и сохранение дополнительных полей той же строки в metadata не увеличивают число обработанных строк. Пульт показывает «Готово к переносу» и «Только metadata», счётчик готовых строк и зависимостей, до 40 групп предупреждений по таблице/коду/причине; полный журнал с ID и исходной metadata сохраняется. Старые отчёты не пересчитываются: для новых счётчиков нужен новый Dry run.

Ручное сопоставление пользователей доступно также для Clients через существующие `employee-match` / `employee-map`. Проверяются последний ошибочный Dry run, подтверждение, fingerprint email/external_key, уникальный текущий login Employees, UUID, отсутствие активных операций и запрет перепривязки уже импортированного user к другому Employees ID. Постоянные login-связи разделены по сервису и источнику; решение Clients не влияет на Vacations и переживает бизнес-откат. Внешние участники без проверенной личности остаются конфликтами; этот экран сопоставляет users, а не создаёт фиктивных сотрудников/подрядчиков.

Offline SQLite/HTTP regressions проверяют коды лидов, несколько причин отказа, неоднозначность, числовые поля, отсутствие target writes в Dry run, идемпотентность, точные счётчики, группировку предупреждений и изоляцию identity-связей Clients/Vacations.

### Clients: общий список логинов и второй разбор preflight

По решению пользователя Clients использует подтверждённый список Vacations для того же нормализованного старого корпоративного логина. Читается реестр текущего настроенного источника Vacations; legacy numeric user ID не переносится между сервисами. Собственное сопоставление Clients сохраняется отдельно. Если оба реестра указывают разные текущие логины, возникает `IDENTITY_ALIAS_COLLISION` с обоими значениями: ни одно не выбирается автоматически. Текущий login должен единственным образом разрешаться в Employees и согласовываться с UUID. Если уже импортированный users mapping указывает другой Employees ID, `IDENTITY_MAPPING_COLLISION` запрещает тихую перепривязку и требует проверки/отката Clients.

Дополнительные legacy статусы: `leads.active → Активные переговоры`, `leads.proposal_sent → КП отправлено`. `positions.under_consideration/waiting/no_candidates → Открыт`: позиция без closed_at остаётся открытой, а отображаемое «В работе» новый Clients вычисляет по попыткам; эти коды не создают выдуманных попыток или закрытий.

Закрытые попытки без attempt_result имеют `MISSING_ATTEMPT_RESULT`; сочетание успеха и отказа — `AMBIGUOUS_ATTEMPT_RESULT` с названиями результатов. Даты started_at/closed_at не заменяют отсутствующий исход. Нечисловая сумма с распознаваемой base64 JSON-структурой Laravel iv/value/mac имеет `ENCRYPTED_AMOUNT`; распознавание формата не расшифровывает и не доказывает валидность payload. Ключи, суммы и шифртекст не включаются в журнал. Остальные нечисловые значения сохраняют `NON_NUMERIC_AMOUNT`.

`EXTERNAL_MEMBER_UNRESOLVED` показывает исходные memberable_type/memberable_id без создания фиктивного сотрудника. `SOURCE_PERIOD_OVERLAP` показывает ID и границы обеих пересекающихся исходных записей; периоды не обрезаются и не объединяются автоматически. Эти подробности доступны только через приватный журнал с существующей авторизацией.

Открытые вопросы для завершения переноса: восстановление отсутствующих результатов попыток; доступ к старому ключу Clients или расшифрованному числовому экспорту; проверенные грейды/технологии отсутствующих ссылок; идентичности внешних участников; выбор корректных исходных записей пересекающихся периодов. До получения достоверных данных полный preflight блокирует Import и не изменяет target. После выпуска нужен новый Dry run; количество оставшихся ошибок заранее не обещается.

Синтетические offline regressions проверяют общий список при разных legacy ID, коллизию двух реестров, UUID, запрет перепривязки импортированного пользователя, дополнительные статусы, разделение отсутствующего/противоречивого исхода, распознавание encrypted payload и обе границы пересечения.


Во время Clients restore сначала опрашивается `/console/state`; при `restore_status` maintenance чтение `/state`, runs и журналов приостанавливается. Пульт остаётся доступным через Migration API, который не выключается вместе с worker. Завершение восстанавливает обычное чтение; post-COMMIT ошибки показываются по состоянию ops без обращения к заменённой SQLite.

## Старый APP_KEY Clients и согласование исторических ТШ · 2026-10-12

В настройках подключения Clients добавлены защищённый APP_KEY и выбор алгоритма старого config/app.php (AES-256-CBC по умолчанию, также AES-128-CBC/GCM и AES-256-GCM). Пустой ввод сохраняет существующий ключ; явный флажок удаляет его. Ключ хранится только зашифрованным MigrationCredentialCipher в migration_connections, API возвращает только признак наличия и алгоритм. Значения ключа и ciphertext не выводятся в диагностике. Настройки доступны только platform-admin, изменения требуют повторного Verify.

При заданном ключе импортируются rates.rate и attempts.rate: проверяется MAC/tag Laravel и поддерживаются plain numeric строки и сериализованные числовые scalars без unserialize объектов. Ошибка ключа/алгоритма/формата даёт RATE_DECRYPTION_FAILED, весь preflight блокирует целевую запись. Без ключа суммы по-прежнему отложены; известные суммы не стираются. Legacy APP_KEY не заменяет APP_KEY/MIGRATION_APP_KEY новой платформы. После релиза оператор сохраняет ключ, выполняет Verify, Dry run и повторный перенос Clients; реальный перенос не запускается самим релизом.

Проверена схема shema_timesheets.sql: коммерческие часы находятся в timesheets.hours, связь rate_id ведёт через rates.member_id к members; time_records.minutes — отдельное личное время без проекта. Тест переноса 7.5 часа и повторного запуска проходит. Пользователь отменил сообщение об ошибке нулевых часов: перенос Timesheets ещё не запускался.

Отправленные клиенту отчётные периоды (ТШ на согласовании и все последующие статусы) дают эффективное согласование аккаунта для активных подключений в своих границах. На /mine и в управлении такие дни зелёные и заблокированы; замок в управлении использует то же правило, что зелёный цвет. Workspace возвращает клиентские периоды только для собственных подключений и выбранного месяца. Финальное согласование не расширяется на другого клиента или дни вне периода. Исторические approved_by/approved_at не выдумываются: правило выводится из авторитетного статуса Clients, без фиктивного события финального согласования. Новый период не получает согласования автоматически; существующие ручные final approvals продолжают действовать.


## Контроль переноса

По умолчанию `/system/migration/` открывает существующий пульт. Отдельная вкладка **Контроль переноса** доступна по `/system/migration/?view=control` (standalone: `/migration/?view=control`); исходный пульт сохраняет подключение источников, бэкапы и ручные действия. Контракт: [docs/MIGRATION_CONTROL.md](../../docs/MIGRATION_CONTROL.md).

Контроль запускает новую операцию через `/control/start`, допускает повторный перенос после частичного результата и запрашивает остановку между этапами с обязательной причиной. Остановка не выполняет откат. Этапы, сгруппированные причины, результаты записи и инвентаризация полей показаны отдельно. Отсутствующие значения отображаются как «Нет данных».

Опрос последовательный, запросы состояния и отчёта имеют таймаут; при потере связи сохраняется последний отчёт. История выбирается по идентификатору операции, независимо от повторно использованных run ID. Полный JSON скачивается с серверного endpoint `?download=1`, независимо от фильтров и отображённых примеров. Краткий отчёт имеет резервное ручное копирование. Подтверждение позднейшего отката показано отдельно от неизменяемого исторического результата переноса.

Проверки: `node --test apps/migration/tests/*.test.mjs`, `npm --prefix apps/migration run build`; браузерные синтетические сценарии — `apps/migration/tests/migration-control.browser.cjs` и `migration-console.browser.cjs`.

Для проверки production-входа собирается `apps/system`, затем запускается его Vite preview. Тот же сценарий контроля выполняется с `MIGRATION_EMBEDDED=1 MIGRATION_PREVIEW=http://127.0.0.1:5199 node apps/migration/tests/migration-control.browser.cjs`; `PLAYWRIGHT_MODULE` и `CHROMIUM_EXECUTABLE` при необходимости задают путь к установленным Playwright и Chromium. Сценарий использует `/system/migration/?view=control`, синтетическую сессию `irlix.system.auth` и API fixtures; проверяет единственную оболочку, вкладки, старый пульт с настройками/бэкапами, сохранение query, историю браузера, мобильный экран и отказ доступа. Это проверка реальной сборки System с синтетическими данными, а не production smoke.
