# CV конвертер frontend

Iteration 2 сервиса: загрузка произвольного текстового PDF/DOCX, LLM-нормализация в canonical CV и генерация IRLIX CV по выбранному шаблону.

## Доступ

CV Converter доступен по эффективному `services.cv-converter` из `GET /api/employees/access/me`: администраторам платформы и руководителям производственных подразделений, назначенным в `departments.manager_id` при `is_production=true`. Само название должности, принадлежность к производственному подразделению без назначения руководителем или роль `platform-tester` права не предоставляют.

- frontend после авторизации проверяет эффективный доступ, как Dashboard и launcher; отсутствие grant = 403 при прямом открытии `/cv-converter/`;
- frontend дополнительно проверяет локальное `cv.convert` через `GET /api/cv-converter/permissions/me`: общего допуска Employees недостаточно; при отсутствии permission возвращается 403;
- страницы `/cv-converter/settings/` (LLM-провайдеры и секреты) и `/cv-converter/permissions/` (локальная матрица ролей) доступны только `platform-admin`, включая API; пункты скрыты для руководителей, прямой переход закрыт 403;
- в JWT-режиме backend проверяет подписанные `service:cv-converter`, `employee-id:<id>` и актуальные `head:<alias>`; CV независимо проверяет собственную сохраняемую матрицу с приоритетом запрета, а стартовый `head:*` применяется только к подтверждённым производственным руководителям;
- health endpoints остаются доступны инфраструктуре для readiness/deploy-проверок.

## Пользовательский сценарий

- route `/cv-converter/`, рабочий экран `/cv-converter/convert/`;
- настройки LLM доступны администратору на `/cv-converter/settings/`, а редактирование матрицы — на `/cv-converter/permissions/`;
- пользователь одним действием загружает PDF или DOCX;
- исходник отображается слева;
- файл отправляется в `cv-converter` backend только на время запроса и не сохраняется;
- backend извлекает текст и передаёт его выбранному `CvExtractionProvider`;
- результат валидируется как canonical CV;
- справа автоматически появляется PDF-preview выбранного шаблона `Irlix CV` или `Irlix CV AN`;
- DOCX и PDF для выбранного шаблона генерируются из одной canonical-модели и одного DOCX-based renderer; смена шаблона перестраивает PDF без повторного обращения к LLM.

## LLM providers

Основной локальный режим стенда:

- `llama.cpp` CPU server;
- `Qwen3-4B-GGUF:Q4_K_M`;
- 6 CPU, до 4000 MB RAM;
- внешний API не нужен.

Через страницу настроек можно без restart переключить provider для следующих конвертаций:

- `local` — OpenAI-compatible локальный endpoint;
- `gigachat` — GigaChat API с OAuth credentials;
- `yandex` — Yandex AI Studio;
- `openai_compatible` — произвольный совместимый endpoint, включая MWS.

Для GigaChat доступны credentials, scope, model, API URL и OAuth URL. Секрет после сохранения не возвращается frontend: UI получает только признак `credentials_configured`. Пустое поле секрета при повторном сохранении означает «оставить текущее значение».

Настройки сохраняются backend в отдельном persistent volume и применяются на каждый новый parse request, поэтому перезапуск контейнеров для переключения provider не требуется.

## Тайминги

Во время parse frontend показывает один честный таймер серверной обработки: backend выполняет внутренние этапы последовательно и возвращает их фактические длительности после завершения запроса.

После успешной конвертации нижняя панель показывает шесть измеренных этапов:

1. `Извлечение текста` — чтение PDF/DOCX и получение исходного текста;
2. `Структурный разбор` — deterministic structural pre-parser;
3. `GigaChat` / `Локальная LLM` / `LLM` — фактическое время inference-запросов к выбранному provider;
4. `Валидация ответа` — JSON parsing и проверка результата через `CanonicalCv` schema;
5. `Объединение данных` — header fallback + completeness merge с результатом pre-parser;
6. `Генерация PDF` — серверный renderer, включая создание DOCX-представления и конвертацию в PDF.

Если GigaChat вернул синтаксически некорректный JSON или объект, не проходящий `CanonicalCv`, backend автоматически выполняет repair/recovery. Подпись LLM-этапа показывает фактическое число попыток, а время содержит сумму inference-запросов. Валидация считается отдельным таймером.

Для PDF используется серверный `X-CV-Render-Ms`, поэтому нижняя панель показывает именно время renderer, а не сетевую задержку браузера. DOCX-download остаётся отдельным пользовательским запросом и не добавляется как фиктивный самостоятельный этап в автоматическую конвертацию.

## Layout

CV использует общие `UiAppSidebar` и `UiAppTopbar` из `@irlix/ui`. Рабочая область начинается ровно после `--irlix-sidebar-width`; локальный legacy-offset `--irlix-sidebar-collapsed-width` не используется. Поэтому верхняя панель и контент вплотную примыкают к правой границе общей левой панели без промежуточного зазора.

- рабочая зона занимает оставшуюся высоту viewport;
- левая и правая области не выходят ниже окна браузера;
- исходник и результат прокручиваются независимо;
- на mobile shared sidebar становится горизонтальным, поэтому локальный left offset сбрасывается в `0`;
- preview результата — PDF, сгенерированный тем же backend renderer, который используется для скачивания.

## Ограничения iteration 2

- legacy `.doc` пока требует предварительного сохранения в `.docx`;
- PDF scan без text layer требует OCR и пока возвращает явную ошибку;
- оригиналы, canonical JSON и renders не сохраняются после запроса;
- при выборе внешнего provider текст CV передаётся соответствующему поставщику;
- локальный `cv-llm` остаётся запущенным при выборе внешнего provider, чтобы переключение обратно было мгновенным;
- интеграции с Clients/Recruitment пока отсутствуют.

## Локальный запуск

При запуске всей платформы используется дополнительный overlay `docker-compose.cv.yml`. `cv-web` публикуется на `127.0.0.1:8096`, backend — на `127.0.0.1:8097`, а `cv-llm` доступен только внутри Docker network.

Host nginx маршрутизирует `/cv-converter/` на frontend и `/api/cv-converter/` на backend. Старый `/cv/*` перенаправляется на `/cv-converter/`.
