# IRLIX Services — обязательная точка входа

**Цель:** выполнить задачу с минимально достаточным контекстом, сохраняя все действующие ограничения. Полные регламенты обязательны **при соответствующем действии**, но не должны читаться целиком «на всякий случай».

## Выбор контекста

1. Назови сервис, конкретный сценарий и тип работы. Начни с [матрицы](docs/context/MATRIX.md) и [маршрутов](docs/context/MANIFEST.json) **только в относящейся части**; границы — [CONTEXT_SCOPE.md](docs/CONTEXT_SCOPE.md). Для узкой задачи ищи нужный файл, символ и раздел без загрузки всего сервиса.
2. Выбери **затронутые** горизонтали: [Frontend](docs/horizontal/FRONTEND.md), [Backend](docs/horizontal/BACKEND.md), [Database](docs/horizontal/DATABASE.md), [Security](docs/horizontal/SECURITY.md), [Integrations](docs/horizontal/INTEGRATIONS.md), [Governance](docs/horizontal/GOVERNANCE.md); QA/CI — по фактическому шагу. Вертикальные индексы — [docs/context/](docs/context/README.md), продуктовые требования — приватный `ideas/company-internal-services-81-2.4/`.
3. Не обходи зависимости рекурсивно. Соседние сервисы — только через конкретные API, события, permission/scope и модели данных; уточняй scope при реальном конфликте. Режимы Fast/Standard/Deep масштабируют объём чтения, **не отменяют QA, security и правила Git**.

## Инварианты для всех задач

- **Git:** новая рабочая ветка только от свежей `development`, законченная задача — PR обратно в `development`; промежуточную работу не интегрировать. Параллельные изменения сохранять, force-push общей истории запрещён. [BRANCHING](docs/BRANCHING.md), [GIT_RELEASE](docs/policies/GIT_RELEASE.md).
- **Production:** `main` меняется **только по прямой команде владельца** накопительным проверенным fast-forward из `development`. Не считать merge/push успешным deploy. После изменений дождаться относящихся к точному SHA CI/QA; не выдавать непроверенные E2E и smoke за PASS.
- **Безопасность:** `irlix-services` публичный, `ideas` приватный. Не публиковать реальные персональные/коммерческие данные, секреты и приватные ТЗ. При auth/permissions читать [Security](docs/horizontal/SECURITY.md).
- **Границы:** shared UI из `@irlix/ui`; владение данными за сервисом; чужие таблицы недоступны напрямую; интеграция через API/события. Для структурных изменений обновить [service map](docs/SERVICE_MAP.md). [Точные инженерные правила](docs/policies/ENGINEERING.md).
- **Критическое мышление:** самостоятельно оценивать существенные предложения, риски и альтернативы; не соглашаться автоматически. Не выдумывать неизвестные бизнес-правила и не менять конфликтующие требования молча. Принятые решения и изменения поддерживать в актуальной документации.
- **Роли и память:** применяй [TEAM_RULES](docs/policies/TEAM_RULES.md) по режиму Chat/Work, только нужные роли; **кастомные Skills временно отключены**. По [Kaizen](docs/CONTINUOUS_IMPROVEMENT.md) ищи только относящиеся к задаче прошлые сигналы и фиксируй доказательные новые; не читай историю целиком.
- **Отчёт:** [REPORTING.md](docs/REPORTING.md). Разделы: «Что реализовано», «Что требуется от тебя», внизу «Сборка и деплой»; **отдельная строка для каждого Git-репозитория**. Для production — полный состав накопительного релиза, только проверенные статусы.

Остальные канонические документы (CI, deployment, issues, архитектура, роли, регламенты) открывать по конкретному событию через [docs/README.md](docs/README.md), а не как стартовый комплект.
