# IRLIX Services — правила работы с проектом

Этот файл обязателен к прочтению перед изменениями в репозитории.

## Источники истины

1. Реализация хранится в этом репозитории `irlix-services`.
2. Продуктовая и полная исходная документация проекта хранится в репозитории `ideas`, каталог `company-internal-services-*`.
3. Чат не является спецификацией. Подтверждённые решения, требования и правила должны быть перенесены в репозиторий.
4. При расхождении кода и документации расхождение должно быть устранено в рамках той же задачи либо явно зафиксировано как открытый вопрос.

## Scope рабочего контекста

- Перед любой задачей сначала определить затрагиваемые сервисы, платформенные компоненты и интеграции.
- Первое чтение: этот файл и `docs/CONTEXT_SCOPE.md`, затем только документы по текущей задаче. Индексы документации и списки сервисов — навигация, а не список обязательного чтения.
- По умолчанию запрещено загружать полную документацию и код всех сервисов платформы «на всякий случай».
- Всегда используется минимально достаточный контекст: общие правила проекта + документация/код затрагиваемых сервисов + только те соседние сервисы, чьи API, события, permissions или данные реально участвуют в задаче.
- Наличие технической зависимости не означает необходимость читать соседний сервис целиком: сначала изучается только соответствующий контракт интеграции.
- Не обходить зависимости рекурсивно и не загружать все README/ТЗ одним пакетным чтением. Поиск имён файлов и точечных ссылок допустим; найденные документы читаются только после проверки их отношения к задаче.
- Полный проектный контекст допускается только для действительно сквозных задач (архитектурный/security-аудит, общая auth/permissions/design-system миграция, глобальная инфраструктура/CI, реорганизация монорепозитория) или по явной просьбе пользователя.
- При старте нового чата не восстанавливать историю всех сервисов. Определить scope из текущей задачи и расширять его только при обнаруженной необходимости.
- Детальная политика и карта прямых зависимостей находятся в `docs/CONTEXT_SCOPE.md` и обязательны к применению вместе с этим файлом.

## Правила разработки

- Пока проект является монорепозиторием.
- Общая Vue SPA является frontend-shell платформы. Бизнес-сервисы не должны дублировать глобальную навигацию и дизайн-систему.
- Любой новый или изменяемый интерфейс обязателен к реализации через нашу дизайн-систему: `@irlix/ui`, shared styles и design tokens из `packages/ui`. Перед UI-задачей прочитать относящийся к ней раздел `packages/ui/README.md` и найти существующий компонент/паттерн; не загружать остальные сервисы ради визуального примера.
- Запрещено создавать локальные аналоги существующих общих Button/Badge/Tabs/Select/Drawer/Sidebar/TreeToggle и переопределять их базовый вид в сервисе. Локальный CSS допускается для бизнес-композиции и раскладки; повторяемый новый UI-паттерн добавляется в `packages/ui` с примером в `apps/design-system` и описанием в той же задаче.
- При изменении shared UI одновременно обновлять живую витрину `/design-system/`, `packages/ui/README.md` и соответствующую спецификацию `ideas/.../design/`. Проверить состояния и responsive layout, собрать затронутые frontend. Скрин сервиса — референс: актуальный визуальный контракт хранится в компонентах и токенах, а не копируется из его CSS.
- Стандартная оболочка нового сервиса — `UiAppShell` из `@irlix/ui`: она автоматически включает `UiAppSidebar` и `UiAppTopbar` с названием сервиса и breadcrumbs активного раздела. Сервис передаёт навигацию и действия, не копирует оболочку. Контракт, токены и примеры: `packages/ui/README.md`, `apps/design-system` и `ideas/.../design/DESIGN_SYSTEM.md`.
- Существующие сервисы при поэтапной интеграции используют те же `UiAppSidebar` и `UiAppTopbar`; отдельные реализации меню/верхней панели запрещены. Все подробности их внешнего вида и поведения принадлежат дизайн-системе, а не этому файлу.
- Каждый backend-сервис имеет собственную доменную границу, API и жизненный цикл.
- Прямое чтение или изменение таблиц другого сервиса запрещено.
- На первом этапе допускается одна физическая PostgreSQL, но каждый сервис владеет своей schema и работает через отдельного DB user.
- Межсервисные синхронные запросы выполняются через API; события и фоновые процессы — через RabbitMQ.
- Обработчики событий должны проектироваться с учётом повторной доставки, retry и dead-letter.
- Employees является source of truth для сотрудников и оргструктуры.
- LDAP/Keycloak отвечает за corporate identity, а не за бизнес-сущность employee.
- Авторизация проектируется как permission + scope.
- `platform-admin` является платформенным суперпользователем: по умолчанию он имеет доступ ко всем функциям и данным всех сервисов, включая новые функции, даже если это отдельно не проговорено в конкретном ТЗ. Исключение действует только если для конкретного сценария явно зафиксировано обратное ограничение.
- При проектировании нового permission/scope или пользовательского сценария разработчик обязан учитывать `platform-admin` автоматически и не требовать отдельного подтверждения его доступа, если в требованиях нет явного запрета.
- Навигация каждого сервиса строится по эффективным `*.view` разрешениям: страница без права просмотра не должна отображаться в левом меню. Скрытие пункта меню не заменяет серверную проверку permission и scope.
- В контуре клиентов роли поступают из оргструктуры Employees и со страницы специальных ролей, а эффективные разрешения Clients/Timesheets вычисляются общей матрицей Clients. Наследуемые права руководителя не могут быть уже прав базовой роли.
- Секреты не коммитятся. В репозитории хранятся только `.env.example` и безопасные значения для локальной разработки.

## Выбор сотрудников на всей платформе

- Любое поле выбора сотрудника во всех сервисах обязательно строится как дерево подразделений с сотрудниками внутри через общий `UiSearchSelect` из `@irlix/ui` (не плоский native select).
- Подразделения — невыбираемые заголовки групп; вложенность передаётся через `depth`, выбранное значение — ID сотрудника. Поиск сохраняет родительские группы. Сотрудники без подразделения отображаются отдельной группой «Без подразделения».
- Сервис сохраняет свои eligibility/permission/scope-ограничения и получает сотрудников/подразделения через API Employees. Группировка не расширяет доступ и не даёт права читать чужую БД.
- Этот стандарт применяется сразу при создании любого нового поля выбора сотрудника и при доработке существующего. Канонический UX, контракт options и пример находятся в `packages/ui/README.md`, витрине `/design-system/` и `ideas/.../design/SEARCHABLE_FILTERS.md`.

## Демонстрационные и реальные данные

- Скриншоты существующих внутренних систем используются только как источник требований к UX, структуре экранов, полям, состояниям и бизнес-процессам.
- Запрещено переносить со скриншотов или из любых других реальных источников конкретные данные сотрудников, кандидатов, клиентов, контактов, проектов, ставок, зарплат, отпусков, таймшитов, фидбеков, заявок и иных бизнес-сущностей в код, seed-данные, fixtures, тесты, документацию или примеры API.
- Любые демонстрационные данные должны быть явно синтетическими и не должны позволять идентифицировать реального человека, клиента, проект или коммерческое условие.
- Если для воспроизведения сценария нужен реалистичный пример, создаются новые вымышленные имена, компании, контакты, суммы и идентификаторы, не копирующие исходные данные.
- Это правило действует на весь проект и все сервисы без исключений, включая будущие сервисы.

## Документация

При добавлении или изменении функциональности разработчик обязан обновить относящуюся к ней документацию.
Подтверждённые в диалоге правила доступа и бизнес-переходов фиксируются в этом репозитории вместе с кодом и в соответствующем ТЗ репозитория `ideas`; нельзя считать ответ в чате заменой документации. Выдача permission для существующего действия не означает разработки нового действия: если самого действия нет или его смысл неясен, сначала уточнить сценарий.

В кодовом репозитории храним документацию, необходимую для запуска и поддержки реализации:

- `README.md` — быстрый старт и текущее состояние;
- `docs/ARCHITECTURE.md` — фактическая архитектура реализации;
- `docs/DEVELOPMENT.md` — правила локальной разработки;
- `docs/DEPLOYMENT.md` — устройство стенда и выкладки;
- документацию конкретного сервиса рядом с сервисом, если она относится к деталям реализации.

Продуктовые требования и полные ТЗ продолжают поддерживаться в `ideas/company-internal-services-*`.

## Git и CI/CD

- `main` — развёртываемая ветка стенда; прямые промежуточные изменения в неё не вносятся.
- `development` — рабочая интеграционная ветка. Все промежуточные коммиты текущей задачи сначала попадают в `development`.
- Любая разработка независимо от того, где она ведётся (отдельный чат, временная ветка, локальная рабочая копия или иной рабочий контекст), обязана сначала быть полностью интегрирована в актуальный `development`, пройти проверку результата там и только после этого может переноситься из `development` в `main`. Прямой перенос рабочих изменений, commit, merge или cherry-pick из временной ветки/рабочего контекста сразу в `main` в обход `development` запрещён.
- Постоянно существующими ветками репозитория являются только `main` и `development`.
- Временная ветка допускается только на время конкретной технической операции или изолированной разработки. Сразу после безопасной интеграции результата она должна быть удалена локально и удалённо. Перед удалением обязательно убедиться, что в ней нет уникальных нужных коммитов и что ветка не используется параллельной активной работой.
- После завершения задачи разработчик обязан убрать созданные им временные ветки; накопление завершённых `feature/*`, `fix/*`, `tmp/*` и аналогичных веток запрещено.
- После закрытия или слияния PR нужно проверить, что полезные изменения сохранены в `development` и `main`, и удалить связанную временную ветку. Нельзя закрывать PR как устаревший только по совпадению названия функции: сначала проверить, доступна ли она на действующем экране.
- После завершения логического блока изменений выполняется итоговая проверка diff и только затем `development` сливается в `main`.
- Автоматический CI единый: push в `development` проверяет registry/Compose и собирает только изменённые компоненты с публикацией проверенных образов; push в `main` переиспользует эти образы и выкатывает только затронутые контейнеры. `development` и ручные сборки не имеют deploy-действий. Подробная обязательная политика: `docs/CI.md`.
- Временные рабочие ветки/PR не запускают автоматические image builds; предварительные проверки выполняются локально, при необходимости один ручной запуск CI. Отдельные service-specific PR/push build workflows запрещены без обоснованной новой потребности: они дублируют общий pipeline.
- Завершённый логический блок интегрируется в актуальный `development` одним push; после успешного `CI verified` переносится в актуальный `main`. Не создавать PR/dispatch ради повторения уже успешной сборки. `main` собирает компонент только если отсутствует проверенный image для точных финальных build inputs.
- Новый deployable сервис обязательно регистрируется в `infra/ci/services.json`; image overlay генерируется `python3 scripts/ci/service_plan.py images --write`. Контекст, worker aliases, migrations и smoke endpoint идут через общий planner/build/deploy. Не добавлять ручные списки сервисов в workflow/deploy и не включать full build для неизвестного пути.
- Изменения только frontend/shared UI не должны пересобирать backend или запускать Keycloak bootstrap. Compose/.env изменения сравниваются по итоговой конфигурации каждого сервиса; диагностические скрипты не вызывают platform deploy. Полный build — явный ручной запрос либо initial bootstrap без успешного baseline.
- Перед публикацией GHCR image проходят Dockerfile/offline image tests. Теги по hash build inputs неизменяемы; нельзя публиковать непроверенный image под reusable tag. Каждый image использует общий Buildx cache, новые приложения используют lock files. Сборки приложений на стенде запрещены.
- Не отменять начатую main-выкладку новым push. Failed/cancelled изменения должны входить в следующий план; baseline — последний успешный CI/release той же ветки, а не последний push.
- `main` должен оставаться развёртываемым.
- Одна логическая или бизнес-задача должна оформляться отдельным коммитом. Не смешивать в одном коммите независимые продуктовые, инфраструктурные, UI и документационные изменения.
- Технически связанные изменения, без которых одна задача неработоспособна, допускается объединять в один коммит.
- Сообщение коммита должно отражать конкретную задачу (`feat(auth): ...`, `feat(dashboard): ...`, `perf(ci): ...`).
- Любое изменение инфраструктуры должно проходить `docker compose config`.
- Для backend/frontend по мере появления тестов и линтеров они становятся обязательной частью CI.
- После push в `main` необходимо дождаться результата CI/deploy и проверить причину ошибки, если pipeline упал.
- Задача, включающая выкладку на стенд, не считается завершённой только потому, что код закоммичен.
- Не отключать проверки ради прохождения CI без устранения причины.

## Параллельная разработка и защита изменений

Проект разрабатывается многопоточно: одновременно могут выполняться независимые задачи в разных чатах или рабочих контекстах. Любую работу с репозиторием нужно вести с предположением, что после последнего чтения ветки другой поток уже мог внести изменения.

- Перед началом изменений и повторно непосредственно перед записью, commit, merge или разрешением конфликта необходимо получить актуальное состояние целевой ветки и проверить, не появились ли параллельные изменения в затрагиваемых файлах.
- Запрещено записывать целый файл поверх более новой версии, используя устаревший снимок. Свои изменения нужно переносить на актуальную версию файла, сохраняя чужие независимые доработки.
- Запрещены `force push`, принудительный reset общей ветки, переписывание общей истории и другие действия, способные удалить уже опубликованные коммиты, если это явно не согласовано отдельно.
- При merge/rebase/cherry-pick конфликт нельзя разрешать механическим выбором только одной стороны (`ours`/`theirs`), если обе стороны содержат функциональные изменения. Нужно объединить независимые изменения и убедиться, что результат сохраняет поведение обеих задач.
- Если параллельные изменения затрагивают одну и ту же бизнес-логику и их нельзя безопасно совместить автоматически, конфликт считается смысловым: нельзя молча отбрасывать одну реализацию. Нужно сохранить обе исходные версии до принятия решения и явно зафиксировать конфликт.
- Перед переносом `development` в `main` необходимо учитывать актуальный `main`, а не состояние `main` на момент начала задачи. Интеграция не должна откатывать изменения, которые попали в `main` из других параллельных задач.
- После интеграции необходимо проверить итоговый diff/историю: изменения текущей задачи присутствуют, а параллельные изменения других задач не исчезли.
- Удалять временную ветку другого потока только потому, что она не `main`/`development`, запрещено. Сначала необходимо убедиться, что работа завершена или полностью интегрирована; правило двух постоянных веток не должно приводить к потере активной параллельной работы.

## Принцип итераций

По умолчанию за одну продуктовую итерацию добавляется один новый бизнес-сервис. Первая итерация включает инфраструктуру, Platform Core, общий frontend-shell и Employees как эталонный бизнес-сервис.

## Работа с неоднозначностями

- Если формулировка пользователя непонятна, неточна, допускает существенно разные реализации или нелогично меняет имеющуюся логику, разработчик обязан задать уточняющие вопросы до реализации зависимой части. Нельзя молча выбирать трактовку или заменять требование собственным предположением; понятные независимые части задачи можно продолжать. Это правило относится ко всем требованиям, включая UI/UX, а не только бизнес-правила.

- Если запрошенное изменение выглядит противоречащим текущей реализации, актуальной документации или уже зафиксированным бизнес-правилам, не выполнять его автоматически: сначала описать обнаруженное расхождение и запросить у пользователя явное уточнение или подтверждение.
- Не придумывать неизвестные бизнес-правила. Если решение влияет на доменную модель, безопасность, permissions, внешний контракт или необратимо усложняет архитектуру — сначала уточнить его. Технические детали, которые обратимы и следуют уже принятым решениям, можно выбирать самостоятельно и документировать.
