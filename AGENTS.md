# IRLIX Services — правила работы с проектом

Этот файл — **обязательная точка входа** для человека, ChatGPT Chat и ChatGPT Work. Подробные требования перенесены в отдельные документы **без отмены их действия**. Весь проект и роли не нужно загружать целиком.

## Первое чтение и область задачи

1. Прочитать этот файл и [docs/CONTEXT_SCOPE.md](docs/CONTEXT_SCOPE.md); установить затронутые сервисы и прямые зависимости.
2. Затем прочитать **только относящиеся к работе** политики ниже, код/контракты сервиса и нужные документы приватного `ideas/company-internal-services-*/`.
3. Вне репозиториев переписка с ассистентом **не заменяет** утверждённого ТЗ. Изменения бизнес-правил и процессов документируются вместе с реализацией.

## Неприкосновенные ограничения

- Только feature-ветка **от свежей `development`**, PR обратно в `development`; перед merge повторно проверить `development` и сохранить параллельные изменения. Никаких force-push/reset чужой работы.
- **Production/`main` — только по прямой команде владельца**, исключительно проверенный накопительный релиз из `development` по правилам Git. Создание PR/зелёный CI не даёт разрешения на production.
- После push/merge ждать **терминальных** результатов релевантных checks **точного SHA**. После финального merge в `development` обязательны `CI verified` и `Development release candidate`; FAIL исправить и проверить повторно. Без фактического TEST нельзя объявлять реальный E2E PASS.
- `irlix-services` публичный, `ideas` приватный: не публиковать реальные/персональные/коммерческие данные, секреты, приватные ТЗ в коде, PR или CI.
- Общие UI-контролы — из `@irlix/ui`; не копировать shell, topbar или компоненты локально. У сервисов отдельное владение данными, никаких прямых запросов к чужим таблицам; интеграции через контракты/API; авторизация `permission + scope`, `platform-admin` имеет полный доступ, если явно не задано исключение. Подробные исключения и все UX-контракты — в ENGINEERING.md.
- **GitHub Issues только для незавершённого или запланированного**: не создавать Issue на каждое изменение или успешно исправленный дефект. `ideas` не ведёт копию backlog.
- Не менять спорные бизнес-правила молча; при конфликте с ТЗ спрашивать владельца. Любые тесты отмечать `PASS / FAIL / NOT TESTED` исключительно по доказательствам.

## Режим команды и наблюдаемость

- **Обычный Chat: один ассистент последовательно** выполняет PM → Analyst → Designer (при UI) → Developer → PlatformEngineer (при необходимости) → QA → PM, **без изоляции контекста**. Ролевые отметки — не отдельные агенты.
- **ChatGPT Work (если действительно доступны subagents):** PM запускает отдельные роли с ограниченным контекстом, ждёт их результата, при QA FAIL поручает исправления и повторную независимую проверку. При недоступности subagents сообщает об этом, не имитирует запуск.
- **Skills:** когда в Git действительно существует `skills/<slug>/SKILL.md`, роль читает полную версионированную методику и необходимые вспомогательные файлы из `skills/`, соблюдая [docs/AGENT_SKILLS.md](docs/AGENT_SKILLS.md). Архивы переносим через проверяемый `scripts/skills/import.py`; пока ZIP не внесены, наличие одного `skills/README.md` **не означает установку** навыков. Если git-копии нет, продолжаем по профилям ролей или доступным личным Skills.
- **Skills (условие доступности):** используем назначение профессиональных ChatGPT Skills по [docs/AGENT_SKILLS.md](docs/AGENT_SKILLS.md), если они фактически доступны в текущей сессии. Репозиторные инструкции самодостаточны; наличие установленных Skills в аккаунте не означает автоматически доступность для Work subagents. Нельзя заявлять, что Skill применён, если это не проверено.
- На существенных этапах показывать короткие `[PM]`, `[Аналитик]`, `[Дизайнер]`, `[Разработчик]`, `[Platform]`, `[QA]` обновления (не скрытые рассуждения).
