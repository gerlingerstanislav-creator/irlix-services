# Specialists

Backend сервиса профессиональных профилей специалистов.

## Ответственность

- хранит грейд, технологии и компетенции специалиста;
- хранит профессиональный профиль уволенного сотрудника;
- является source of truth каталога технологий и компетенций;
- получает сотрудника, кадровый статус и оргструктуру только через Employees API;
- не читает схему Employees напрямую;
- проверяет область доступа руководителя на backend для каждого профиля.

## MVP API

- `GET /api/health` — healthcheck;
- `GET /api/workspace` — scoped список специалистов, подразделений и каталог компетенций;
- `GET /api/people/{employee}` — карточка специалиста в доступной области;
- `PUT /api/people/{employee}` — изменение профессионального профиля;
- `GET /api/catalog` — технологии и компетенции;
- чтение каталога доступно любому авторизованному пользователю платформы, чтобы селекты технологий в других сервисах работали независимо от его роли; создание, редактирование и удаление технологий разрешены только роли `platform-admin` (на backend проверяются через Employees `/api/access/me`); остальные роли сохраняют просмотр каталога и выбор технологий в профилях;
- `POST /api/catalog/technologies` — добавить технологию;
- `PUT /api/catalog/technologies/{technology}` — изменить технологию;
- `DELETE /api/catalog/technologies/{technology}` — удалить технологию.

Employees предоставляет внутренний контракт `GET /api/specialists-directory`. Для обычного пользователя он доступен только руководителю подразделения и возвращает его department tree; `platform-admin` получает полный scope. Уволенные не фильтруются.

Корпоративным каталогом технологий управляет только администратор платформы (`platform-admin`). Остальным пользователям доступен просмотр технологий и использование каталога для выбора технологий специалиста. UI скрывает действия изменения для не-администраторов, а POST/PUT/DELETE API возвращают 403 независимо от UI. При недоступной проверке роли изменения запрещены.

## Данные

Собственная PostgreSQL schema: `specialists`.

Таблицы первой версии:

- `specialist_profiles`;
- `technologies`;
- `competencies`;
- `specialist_technologies`;
- `specialist_competencies`.

`last_department_id` сохраняет последнюю известную организационную принадлежность вместе с профессиональным профилем.

### Каталог технологий

Начальный каталог технологий засеивается миграцией `2026_09_27_000002_seed_technologies.php` по данным из предыдущей реализации.

Поля каталога:

- `name` — отображаемое название технологии;
- `alias` — короткое название из предыдущей реализации; пока сохраняется как справочное и не участвует в бизнес-логике;
- `category` — прежняя привязка к направлению (`Backend`, `Frontend`, `Mobile`, `QA`, `Analytics` и т. п.); пока сохраняется как справочная и не используется для разграничения доступа;
- `parent_id` — иерархия технологии/подтехнологии, например `JS → Node.js/React.js/Vue.js`, `Python → Django/FastAPI`, `QA → QAA/QAM/QAMM`;
- `active` — доступность записи в каталоге.

В UI каталог отображается как раскрываемое дерево. Для каждой технологии доступны добавление дочерней записи, редактирование и удаление; новая запись также может создаваться на верхнем уровне.

Backend не разрешает циклическую вложенность и удаление технологии, пока у неё есть дочерние технологии, привязанные компетенции или она используется в профиле специалиста.

Текущий стартовый каталог: 1C, Android, Business analyst, C#, Design, DevOps, Flutter, GO, JS (Node.js, React.js, Vue.js), Java (Spring), ML (Computer vision, NLP), PHP (Laravel, Symfony), Product owner, Project manager, Python (Django, FastAPI), QA (QAA, QAM, QAMM), System analyst, iOS.

## Пока не входит

- история развития;
- assessments workflow;
- обучающие программы;
- performance review;
- полноценное управление каталогом компетенций (CRUD технологий уже реализован).


Миграция `2026_10_09_000001_complete_technology_tree.php` дополняет публичный каталог до 32 записей, включая Design → UX/UI, и синхронизирует родительские связи. Существующие IDs, active, alias/category и привязки специалистов сохраняются; создаются только отсутствующие имена. Название 1C используется в латинице; legacy 1С нормализуется при переносе позиций. Clients получает дерево через GET /api/specialists/catalog, не из своей копии каталога.

## Независимые разрешения Specialists V2 — подготовка 28.10.2026

У Specialists собственные `specialists_role_permissions`, журнал `specialists_permission_audit`, администраторская матрица `GET/PUT/DELETE /api/specialists/role-permissions` и эффективные `GET /api/specialists/permissions`. Роли `org:*`, `head:*`, `special:*` поступают из проверенного JWT, сверяются с текущими назначениями Employees, затем применяется **только локальная** матрица. Права: `specialists.profiles.view/manage`, `specialists.catalog.view/manage`. Действия с профессиональными профилями проходят одновременно через локальное permission и серверный Employees Directory по *текущему* `manager_id` производственных подразделений и их дочернему дереву. Это исключает доступ к соседним направлениям и уволенным из чужой последней оргструктуры. Каталог для выбора технологий имеет отдельное право чтения и отдельное право изменения. При объединении нескольких ролей явный deny перекрывает allow для одного permission, отсутствие правила запрещает.

Встроенный Employees `/specialists-directory` остаётся безопасной ролевой проекцией оргструктуры и **не** должен раздавать сотрудникам Employees.read или произвольные разделы Employees; выбор бизнес-действий принадлежит Specialists. В локальном режиме `team` для профилей ограничивается текущим управляемым производственным деревом, `all` по-прежнему не преодолевает собственные безопасные ограничения Directory для обычного руководителя. Роли каталога поддерживают только `all/none`.

Режим `IRLIX_SPECIALISTS_LOCAL_AUTHZ_ENABLED=false` остаётся выключенным. Переход требует перенос существующих прав и ручных назначений, проверки действительных JWT на руководителях разных подразделений, уволенных и platform-admin, подтверждения просмотра каталога из Clients и явного rollback. Старые права и данные не изменены.


## Матрица ролей и экран разрешений · 06.11.2026

Экран `/specialists/role-permissions` использует роли и дерево оргструктуры из канонического каталога Employees (только метаданные ролей, без чужих карточек). Выбор роли — поисковый селект, новые колонки создаются **без разрешений**. Владелец матрицы может задавать `Не назначено`, `Явный запрет`, `Команда` (только профили), `Все`; порядок столбцов меняется перетаскиванием или клавиатурно доступными кнопками и хранится локально только для отображения.

API `POST /api/role-permissions/roles` добавляет колонку; `DELETE /api/role-permissions/roles/{role}` атомарно отзывает все прямые разрешения и скрывает колонку. Таблица `specialists_permission_roles` хранит выбранные роли и **неактивные tombstone** удалённых ролей, чтобы историческое правило `head:*` не вернуло доступ после удаления. Старые персонализированные правила руководителей при миграции дополняются только отсутствующими историческими grants; явные запреты не затираются. Legacy `head:*` выводится как заблокированная колонка до отдельного безопасного перевода действующих руководителей на точечные роли. Разрешения других ролей пользователя не удаляются.

Обновление матрицы по-прежнему доступно только проверенному `platform-admin`, независимо от визуального состояния интерфейса. Активация `IRLIX_SPECIALISTS_LOCAL_AUTHZ_ENABLED` **не происходит автоматически**: условия и требуемые проверки перед включением перечислены выше.

Навигация также ориентируется на ответ `GET /api/permissions`: `profiles_view` открывает дашборд и список, `catalog_view` — каталог, а управление разрешениями остаётся отдельным администраторским экраном. Для пользователя с единственным `catalog_view` фронтенд получает каталог напрямую, не запрашивая защищённый `/api/workspace`. Право `profiles_manage` отдельно управляет доступностью формы и кнопки сохранения; все фактические запреты остаются на backend.

## Обновление интерфейса и источника проектов (06.11.2026)

- Каталог технологий занимает высоту рабочего окна; пустая нижняя таблица компетенций не показывается. Добавление технологии выполняется компактной кнопкой в общей верхней панели.
- Фильтр направлений дашборда множественный, его выбор сохраняется на стороне браузера отдельно для каждого авторизованного сотрудника. Применяется только к уже полученному от Employees разрешённому дереву: выбор родительского направления включает его дочерние. Фильтр виден администратору и руководителю с несколькими доступными направлениями.
- Профиль открывается в общем правом `UiDrawer`, значения грейда выбираются из фиксированного списка; исторические значения не стираются при редактировании других полей.
- Проекты поступают из Clients через `GET /api/clients/specialists/people/{employee}/projects`. Клиентские тарифы и договорные сведения не передаются. Endpoint допускает только подписанную роль сервиса Specialists; Clients повторно проверяет актуальную область доступа к сотруднику в Employees и не предоставляет общего доступа к Clients.
- «Разрешения» размещены в нижней системной зоне боковой панели. Автоматическая собирательная роль руководителей производственных направлений **не включена** — требует отдельного решения по изменению платформенной ролевой модели.


## Собирательная роль для руководителей производственных направлений (06.11.2026)

Каноническая роль `special:production-direction-head` автоматически вычисляется Employees из прямых `manager_id` подразделений с `is_production = true`. Она отображается отдельной колонкой на существующей странице разрешений Specialists и доступна в общем каталоге ролей; миграция создаёт только видимую колонку без каких-либо разрешений, а настроенные администратором значения сохраняются. Для пользователей без явных разрешений действуют действующие политики и их ограничения. Организационный scope проверяется отдельно и никогда не становится общим для всех производственных направлений; изменение менеджера автоматически отражается в подписанной роли после Keycloak-синхронизации. На странице **Employees → Роли** состав виден, но ручное назначение/снятие исключено.


## Профиль специалиста, история и дерево подразделений (06.11.2026)

- Один общий фильтр подразделений на верхней панели страниц со списками сотрудников (дашборд и реестр), в виде дерева `parent_id` с множественным выбором. Выбранные ID сохраняются в `localStorage` отдельно по сотруднику и применяются как пересечение с разрешённым Employees scope; фильтр по другим свойствам списка остаётся локальным. Плашка контекста над дашбордом убрана, размеры соответствуют общим токенам UI. Для новых employee-centric страниц используется тот же фильтр и helper `@irlix/ui`.
- В карточке две вкладки: **История** и **О специалисте**. История совмещает scoped датированные кадровые события (Employees `/specialists-history/{employee}`), проектные подключения/отключения и фидбеки (Clients `/specialists/people/{employee}/history`), а также собственные изменения профессионального профиля и комментарии (Specialists `/people/{employee}/timeline`). Отказ одного источника отображается как неполная история, а не «история пуста». Зарплаты, ставки и прочие поля других сервисов не копируются и не передаются. Данные ассесментов добавляются **только по мере появления реального источника событий**; никаких синтетических прохождений не создаётся.
- **О специалисте**: основная технология + её грейд по каждой записи (`Junior/Middle/Middle+/Senior`), вспомогательные технологии без грейдов и проектная история. Основная запись редактируется по карандашу или добавляется кнопкой; вспомогательные выбираются одним мультиселектом с созданием технологии без смены экрана. Общий справочник общий для всех авторизованных редакторов; дубликаты имени без учёта регистра/пробелов блокируются уникальным индексом. `/specialists/technologies` показывает его в алфавитном порядке, `/specialists/competencies` сохраняет существующее иерархическое редактирование.
- Миграция сохраняет существующие `specialist_technologies` как `secondary` **без выдуманного грейда**. Общий грейд сотрудника хранится отдельно для совместимости со старыми дашбордом/реестром. Старые `manager_note` и `specialist_competencies` не удаляются из базы, но соответствующие блоки карточки скрыты; новые комментарии идут в append-only историю. Изменение технологий атомарно и журналируется только при фактической разнице.
- Новые endpoints Specialists используют `route → Controller → Service → Eloquent` и проверяют актуальную область доступа Employees на каждом запросе конкретного сотрудника. Clients и Employees выполняют независимые read-only scope проверки; role preview не предоставляет доступ к персональной истории. Для production требуется smoke + проверка реального JWT и миграции.


## Компактные селекты и автосохранение карточки (06.11.2026)

В `@irlix/ui` для `UiSearchSelect` доступен необязательный `compact`: размеры текста и элементов используют токены дизайн-системы также у телепортированного меню (под `body`). `UiDepartmentTreeSelect` всегда использует его; селекты технологий и грейдов в карточке Specialists — тоже.

Редактирование основных технологий по паре `технология + грейд` (локальная кнопка «Применить»), удаление записи, изменение списка вспомогательных и inline-создание технологии инициируют **автосохранение** текущего профессионального профиля без отдельной глобальной кнопки. Клиент объединяет быстрые изменения, отправляет полные снимки строго последовательно, сохраняет последний снимок при ошибке, предлагает повторную отправку и сбрасывает отложенный таймер при уходе со страницы, не теряя последнюю правку. Список сотрудников после успешного сохранения обновляется отдельно, без перезаписи редактируемой карточки устаревшими данными.

Поле «Общий грейд» удалено **только из карточки**, его legacy-данные остаются в базе и не изменяются новым автосохранением; остальные экраны старого грейда остаются совместимы. Убраны визуальные разделители между блоками карточки и внутри списков её технологий и проектов. Комментарии руководителя, как и раньше, отправляются отдельным явным действием в append-only ленту истории.


## Отдельный каталог дополнительных технологий и карточка (06.11.2026)

- Основные технологии по-прежнему лежат в `technologies` и связываются с сотрудником через `specialist_technologies` (только `kind=primary`, у каждой — собственный грейд). Дополнительные технологии теперь принадлежат **отдельному** справочнику `additional_technologies`; назначения живут в `specialist_additional_technologies`. API профиля возвращает две независимые коллекции: `professional.technologies` и `professional.additional_technologies`; `workspace.people[].technologies` содержит только основные. Сотрудники не получают посторонних технологий из дополнительных связей.
- Миграция `2026_11_06_000004_separate_additional_technologies` атомарно переносит все ранее сохранённые `kind=secondary` назначения и даты: имена общего каталога копируются **только если реально использовались как дополнительные**, а исходные вторичные строки удаляются из основной таблицы после успешного копирования. Исходный ID основной технологии сохраняется как `origin_technology_id` для безопасного восстановления. Откат пытается восстановить оба вида связей, включая созданные после миграции, и отказывается без потери данных при конфликте одинаковой технологии как основной/дополнительной у одного человека.
- Основной селект читает только главный каталог, дополнительный селект — только дополнительный. У одного человека одинаковое нормализованное имя не разрешено в обоих списках; сервер дополнительно валидирует это при автосохранении. Одинаковое имя в двух глобальных каталогах допускается для разных сотрудников и не означает общую запись. Inline создание дополнительных технологий доступно через `POST /api/catalog/additional-technologies/quick`; проверка прав сохранена. Устаревший `PUT /people/{id}` с `technology_ids` явно отвергается, чтобы не стирать новые данные через старый формат.
- В карточке основные технологии расположены горизонтально с переносом строки; компактный плюс находится сразу после последней технологии, карандаш и крестик показываются рядом с технологией по hover или keyboard focus (на сенсорном устройстве — всегда). В реестре отображаются только основные технологии, и технологический фильтр также проверяет только их. Раздел `/specialists/technologies` переименован в **«Дополнительные технологии»** и показывает исключительно дополнительный каталог. Прежний иерархический основной каталог остаётся под `/specialists/competencies`.
- Общий `UiDrawer` обеспечивает `min-height: 0`, собственный `overflow-y: auto` и свободный wheel-scroll при высоком содержимом карточки; блокировка скролла применяется только к подложке. В UI-контурах и при реальных правах сотрудников автоматические проверки не подменяют ручной визуальной приёмки.
