# Finance — рабочая реализация, в процессе финансовой приёмки

Обязательные продуктовые источники: приватный `ideas/company-internal-services-81-2.4/services/finance/`: `README.md`, `FINANCIAL_MODEL.md`, `UX_WORKFLOWS.md`, `UI_SPEC_9_SCREENS.md`, `TECHNICAL_SPEC.md`. Код не должен переопределять открытые бизнес-решения.

**Статус:** draft [PR #413](https://github.com/gerlingerstanislav-creator/irlix-services/pull/413), ветка `feature/finance-service-foundation-20261020`. CI может быть зелёным, но это **не production acceptance**. Никаких личных/коммерческих данных и секретов в публичном репозитории.

## Реализованные рабочие контуры

- Backend Laravel: собственная схема PostgreSQL `finance`, отдельный DB-пользователь со случайным серверным секретом, Keycloak RS256 JWT, эффективные finance.permissions из Employees. Доступы: бухгалтерия, явно назначенные finance directors, platform-admin; руководители остальных направлений **не получают Finance**.
- Интеграции по защищённым read-only контрактам: Clients.ReportingPeriod / исторические условия Client.MemberTerms, Timesheets подтверждённые часы, Employees (зарплатные условия и безопасный персональный справочник), Platform Core календарь. Finance не читает чужие схемы БД и не пересчитывает оклад по факту выплаты.
- Ручные денежные/банковские счета, начальные остатки; `cash_transactions` со статусом подтверждения, устойчивым `request_id`, датой и cashflow-категорией. Атомарные внутренние переводы создают ровно две противоположные записи, **не** являются внешней клиентской оплатой и не закрывают расходное обязательство.
- Счета: черновик / выставлен / отменён, независимо от не оплачено / частично / оплачено. Выписка через проверку согласованного акта Clients; подтверждённые поступления и их распределения на несколько выставленных счетов с блокировками/лимитами/аудитом. Ровно когда все выставленные счета периода оплачены, Finance отправляет доверенное идемпотентное подтверждение в Clients; Clients окончательно запрещает изменения оплаченного ReportingPeriod. Отдельный чек «комплект счетов» не вводится.
- UI «Распределить оплату» поддерживает несколько строк `invoice_id + amount` для **одного** подтверждённого внешнего поступления. Финансовый остаток приходит из отдельного `allocated_amount` по всей базе, а не из ограниченного списка последних разнесений. Проверки дубликатов счетов, остатка поступления, статуса и остатка каждого счёта выполняются в интерфейсе и повторно под транзакционной блокировкой на backend. Активные отменённые разнесения не списывают остаток.
- Начисления: вручную внесённые gross, премии, налоги работодателя, отпускные, больничные, подрядчики, прочие статьи. Денежная выплата привязывается к начислению отдельно, с лимитами и без повторного P&L/ДДС. Сторно ошибочного **неоплаченного** начисления — отдельная отрицательная операция с причиной/аудитом/ссылкой на оригинал. Оплаченные обязательства нельзя молча сторнировать без отдельного протокола возврата.
- 9 страниц Vue на `@irlix/ui`, `UiAppShell`, `UiDrawer`, `UiPeriodPicker`, `UiSearchSelect` для дерева сотрудников. Фильтры счетов, просрочки, два статуса оплаты, таблицы расходов, выручки, рентабельности и планирования.
- Разграничение реестра расходов: `finance.view` позволяет читать **только** записи `contractor/other` без `employee_id`; `finance.salary.view` дополнительно открывает индивидуальные начисления, выплаты и остальные виды начислений. Эта фильтрация выполняется SQL-запросом, а не скрытием полей в Vue. Создание, разнесение и сторно работодателевых взносов (`contribution`) тоже требуют `finance.salary.view`. При отсутствии прав фронтенд не запрашивает закрытые API и не предлагает недоступные виды начислений/экран рентабельности; прямой URL проверяется backend.
- При обновлении отчётного месяца frontend инвалидирует незавершённые запросы предыдущего месяца, не показывает прежние месячные суммы во время загрузки и не применяет устаревшие ответы даже если они пришли последними. Проверка регрессии — `apps/finance/tests/finance-ledger.test.mjs`.
- Вкладка «Настройки» дополнена защищённым реестром аудита: `GET /api/finance/audit` с курсором `before_id` и ограниченным `limit`. Для просмотра всего аудита требуются **одновременно** `finance.view` и `finance.salary.view`, поскольку причины корректировок и метаданные операций могут раскрывать начисления; скрытие UI не заменяет backend guard. Проверены отрицательные сценарии прав доступа и выдача следующих страниц.
- Revenue: по коммерческим часам/версии ставки за месяц услуги, отдельная предварительная/согласованная сумма, отметка неполноты для незакреплённых клиентских override и неоценённых переработок. Profitability: **только прямая подтверждённая трудовая маржа**, а не полная рентабельность. P&L: частичный по введённым начислениям, **не считать достоверной полной прибылью при неизвестных компонентах**. Budget: сценарии и версии, утверждение директором.
- В `GET /api/finance/pnl` поле `result` и в `GET /api/finance/overview` поле `pnl` всегда `null`, пока нет подтверждённого механизма учётной полноты по месяцу. При достоверно согласованной выручке и хотя бы одном введённом начислении API выдаёт отдельное `known_recorded_difference` — **только арифметическую разницу известных сумм, не прибыль**. В Vue подписано явно; `partial_manual_accruals` не означает, что затраты полностью внесены. Регрессия выполняется в runtime PostgreSQL через реальные HTTP routes с mock commercial contracts.
- Finance **не закрывает бухгалтерские месяцы**, не имеет такой кнопки и отдельного lock. Бухгалтер делает это в 1С; интеграция 1С позже.

### Защита источников коммерческой выручки (20.10.2026)

При расчёте `RevenueReport` некорректные значения часов или ставки (включая отрицательные, нечисловые и неограниченные числа), а также пересечение нескольких ReportingPeriod одного клиента на одну дату отмечаются `quality=incomplete`. Не выбираем произвольный период и не превращаем повреждённую ставку в подтверждённую нулевую выручку. Явная нулевая согласованная ставка допускается. Отдельный runtime-контракт `tests/finance_revenue_runtime.php` проверяется в Finance validation вместе с PostgreSQL-тестами.

## Остаточные блокеры до production

1. **Алгоритм переработок**: известен факт коммерческих часов сверх общей месячной нормы. Не определены/не хранятся подтверждённые клиентский и сотруднический коэффициенты и распределение сверхчасов между несколькими клиентами/проектами; не придумывать правила, а оставлять `quality=incomplete`.
2. **Клиентские корректировки часов** и утверждённые клиентом overrides по периодам, пересекающим календарные месяцы: пока отчёт помечает неполным, потому что не утверждено распределение по месяцам/подключениям.
3. **Полная управленческая себестоимость**: разделить обычную зарплату, дополнительную выплату за переработку, отпускные/больничные, прямые расходы, начисления/взносы, налоговые последствия без задвоений и раскрытия персональных зарплат неподходящим ролям; актуальная рентабельность ограничена прямым трудом.
4. **Финансовые коррекции после оплаты**: документированный отдельный безопасный возврат/chargeback/сторно + идемпотентность, reconciliation и неизменность Clients после terminal paid. Автоматическое снятие блокировки запрещено.
5. **Полный реальный E2E**: сервисы Clients/Timesheets/Employees/Keycloak, runtime permissions, финансовые суммы в реальном контуре, 1300px visual/UX-аудит, настоящий staged DB/bootstrap и smoke. Текущая Finance validation в GitHub Actions использует PostgreSQL runtime тесты и **mocked HTTP-интеграции**, не заменяет независимый E2E.
6. Полный сценарий генерации счёта/PDF/отправки (F25) **отложен** до ознакомления с бухгалтерским процессом, не является блокером **ручной** выписки; импорт 1С, внутренние проекты, Equipment link и AM-счета — отдельные TODO, не включаются сейчас.

## Локальный запуск

```bash
export FINANCE_APP_KEY="base64:$(openssl rand -base64 32)"
export FINANCE_DB_PASSWORD="$(openssl rand -hex 32)"
# Для внутренних контрактов настройте стабильные независимые токены в
# локальном .env (не коммитьте); с отсутствующим токеном контракт fail-closed.
docker compose -f docker-compose.yml -f docker-compose.override.yml -f docker-compose.finance.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.override.yml -f docker-compose.finance.yml exec -T finance php artisan migrate --force
```

Проверки: `Finance validation` (Vue/Vite, PHP lint, Compose, реальный PostgreSQL migrate+runtime), `QA` и общие UI/navigation workflows на **точном SHA**. В скриптах `finance_runtime.php` и `finance_routes_runtime.php` с 20.10.2026 явно переопределён CLI exception handler с `exit(1)`, чтобы падение assertions действительно завершало CI с ошибкой. Тестовые запросы идут по реальным backend-маршрутам `/api/...` (внешнее `/api/finance/...` переписывается nginx), а не по несуществующему `/api/finance/...` внутри контейнера. Для синтетического роутинга `Request` с тестовыми permissions передаётся также в Laravel container (`app()->instance('request', $request)`), иначе инъекция зависимостей контроллера получает пустой actor, даже если `Route::bind` выполнен. Предшествующие зелёные container jobs **не доказывали** прохождение HTTP route-regressions; их статус пересматривается после нового прогона. После feature-merge в `development` проверить `CI verified` и `Development release candidate`; production только по подтверждённому накопительному релизу, без выборочного main.
