# Timesheets backend

Laravel-сервис коммерческого рабочего времени, владеющий PostgreSQL schema `timesheets`. Интеграции с Clients, Employees и Vacations выполняются через API.

## Факты и идентичность

Рабочая запись — `client_member_id + work_date + hours + description`, уникальная на подключение и дату. Clients определяет постоянную личность ClientMember и действующие MemberTerms; проекты не ограничивают ввод часов. Для штатного сотрудника `employee_id` проверяется по каталогу Clients, для партнёра остаётся NULL. Корпоративный автор партнёрских действий записывается отдельно в аудит.

Новые суммы вводятся с шагом 0,25, от 0 до 24. Исторические значения, например `7.33`, сохраняются точно; описание такого факта можно изменить без округления часов. Нулевой факт с описанием сохраняется. Совокупный предел 24 часа проверяется для сотрудника по всем фактам дня, включая ещё не преобразованные legacy-записи, а для партнёра — по всем ClientMember одной партнёрской личности. Проверка и запись сериализованы PostgreSQL advisory transaction locks, в том числе при первоначально пустом дне.

## Пользовательские маршруты

| Маршрут | Назначение |
|---|---|
| `GET /workspace` | Собственные условия, факты, подтверждения, блокировки и отсутствие; `members` включает исторические личности без условий |
| `PUT /entries` | Собственная запись с `client_member_id`, без проекта |
| `POST /confirm`, `/unconfirm` | Общее предварительное подтверждение сотрудника по дате |
| `GET /management` | Матрица сотрудник/клиент в рамках permission + scope |
| `PUT /management/entries` | Одна запись либо атомарный `entries:[{client_member_id,hours,description}]` за день сотрудника |
| `PUT /management/bulk-hours` | Один ClientMember, до 31 даты одного месяца; описания сохраняются из БД под блокировкой |
| `POST /management/final-approval` | Подтверждение/отмена по ClientMember и месяцу |
| `GET /partner-hours`, `PUT /partner-hours` | Просмотр и ввод за партнёра корпоративным оператором |
| `POST /partner-hours/confirm`, `/partner-hours/final-approval` | Отдельные партнёрские предварительные и финальные подтверждения |
| `GET /analytics`, `/audit`, `/attention` | Коммерческая загрузка, история и задачи |

`GET /analytics` включает только сотрудников подразделений, помеченных `is_production=true` в каталоге Employees; scope проверяется отдельно. Норма для включённых сотрудников не зависит от наличия подключений. В официальные коммерческие часы входят только финально подтверждённые записи (с учётом дневных исключений и эффективного подтверждения отправленным клиентским периодом). Неподтверждённые и конфликтные часы возвращаются отдельно, в KPI не входят. Табличный показатель `absence_hours` суммирует подтверждённые отсутствия всех видов; разбивка `absences` остаётся для диаграммы. Агрегаты employees/departments/totals формируются из одного и того же отфильтрованного набора.

AM/временный делегат действует в рамках своего клиента, РН — своих штатных сотрудников в дереве подразделений, platform-admin — всех. РН не получает партнёров автоматически; текущая управляемая связь — AM/делегирование клиента. Партнёрский просмотр требует `timesheets.management.view`, изменение — `timesheets.management.manage`. Самостоятельный вход партнёров в этом релизе отсутствует. Аудит ограничен конкретными ClientMember, поэтому доступ к сотруднику одного клиента не раскрывает его события у другого клиента.

Изменение любого часа сотрудника снимает предварительное подтверждение всего его дня. Изменение менеджером оставляет финальное подтверждение остальных дней и создаёт исключение изменённой даты. Партнёрское изменение аналогично снимает отдельное предварительное подтверждение и создаёт финальное исключение. Повторное финальное подтверждение/отмена месяца очищает исключения. Партнёрский месяц нельзя подтвердить до предварительного подтверждения каждого дня с фактом. Конфликт личности или условий запрещает новое подтверждение. Историческое финальное подтверждение можно отменить и после удаления всех условий, если период не защищён.

## Каталог, конфликты и сохранность

`ClientMemberDirectory` читает `GET Clients /internal/system/timesheet-memberships` с `X-Irlix-Timesheets-Token` (`IRLIX_TIMESHEETS_INTEGRATION_TOKEN`, не менее 32 символов). Требуются `complete/count/revision`, полный список блокировок и корректные типизированные идентичности, даты, делегаты, непересекающиеся условия и уникальные term IDs. Неполный/невалидный ответ и отказ Clients запрещают изменения с 503.

`GET` пользовательских страниц не удаляет факты и подтверждения. Worker `bin/reconcile-assignments.php --once` только выставляет/снимает `term_conflict` с аудитом перехода; исторические часы и подтверждения не удаляются. Защищённые локальным freeze факты worker не меняет. Непокрытые условиями факты требуют ручного решения и не допускаются к финальному подтверждению. Сервис запускает worker повторно после ошибки каталога.

## Отправка клиенту: freeze и revision

Обычная проверка блокировок Clients дополняется устойчивым локальным freeze. Все мутирующие транзакции и коммерческие выписки используют общий PostgreSQL advisory gate `timesheets:reporting-snapshot`; freeze начинает действовать после завершения уже выполнявшихся изменений. Он хранится без TTL и переживает сетевой отказ/перезапуск.

1. Clients вызывает `POST /internal/system/reporting-freezes` с серверным `X-Irlix-Timesheets-Token` и `{reporting_period_id,client_id,from,to}`.
2. Timesheets атомарно создаёт freeze и возвращает `{freeze_token,revision}`. Повторный запрос того же периода/границ идемпотентен; смена границ даёт 409.
3. Clients получает `GET /internal/commercial-data?from=...&to=...&client_id=...&freeze_token=...`, с bearer и тем же серверным заголовком. Ответ содержит `entries`, `final_approvals`, `final_approval_exceptions`, `complete/count/schema_version=2`, `revision` и `membership_revision`. Token/границы и неизменность revision проверяются сервером. Каталог не передаёт ставки.
4. Clients сверяет revision и сохраняет снимок при отправке. Freeze остаётся до возврата периода в «Новый»; освобождение — `DELETE /internal/system/reporting-freezes/{id}` с `{freeze_token}` после фиксации возврата. Неуспешная отправка освобождает только свой freeze после отката. Неопределённый результат оставляет период закрытым до безопасного повторения.

`membership_revision` отражает данные подключений; статусы блокировок не меняют его. Локальный `revision` отражает факты, финальные подтверждения и исключения выбранного клиента/диапазона. Существующие защищённые периоды до появления freeze по-прежнему блокируются авторитетным каталогом Clients. Период со статусом отправки даёт эффективное согласование в своих границах без выдуманного исторического approved_by/approved_at.

`GET /internal/system/finance/commercial-data` использует отдельный `X-Irlix-Finance-Timesheets-Token`. Возвращается тот же полный контракт с nullable employee, партнёрской идентичностью и исключениями; диапазон может пересекать месяцы. Finance распределяет полный отчётный период перед фильтрацией нужного месяца.

Обычный internal employee purge не удаляет защищённые финансовые факты и не меняет автора защищённого подтверждения: возвращает 423 без частичных изменений. Для таких данных требуется отдельная согласованная процедура.

## Преобразование уже сохранённых проектных часов

`php bin/convert-project-hours.php` — read-only dry-run. Применение только при согласованном обслуживании с `TIMESHEETS_MAINTENANCE_LOCK=1 ... --apply`; boot/deploy его не запускает. `ProjectHoursConverter` сводит проекты одного клиента/сотрудника в ClientMember/день, сохраняет точную сумму, все описания и исходные IDs в `timesheet_legacy_sources`. Неоднозначная личность, условия, состояние подтверждений, существующий целевой факт, >24ч или защищённый период блокируют применение.

Факты, lineage, месячные approvals (включая месяцы без часов), дневные exceptions и аудит коммитятся одной транзакцией. Сбой между фактами и approvals откатывает весь перенос; повторение восстанавливает контекст по durable lineage и не переписывает исторические даты/авторов. Различные авторы/времена исходных approvals требуют ручного разрешения. Полный перенос внешнего legacy-источника выполняет отдельный Migration service с validate/dry-run/checkpoints; этот скрипт предназначен только для уже существующих фактов Timesheets.

## Проверки

Docker build запускает `tests/runtime_contract_smoke.php` и `tests/project_conversion_smoke.php` на синтетической SQLite БД. Первая проверка выполняет реальные Laravel routes: собственный и управленческий workflow, AM/RN/delegate/admin, partner identity/24ч, отказ неполного каталога, конфликт, точные 7.33, freeze/revision и защищённый purge. Вторая проверяет точный rekey, все описания, lineage, approvals/exceptions, crash rollback и повторение. `assignment_reconciliation_smoke.php` дополнительно проверяет сохранение/пометку конфликтных часов и источник ClientMember. PostgreSQL schema/concurrency и интеграционное QA выполняются отдельно; SQLite smoke не заменяет их.

Схема ClientMember, проектно-независимые факты, freeze/revision/snapshot, ручные конфликты и безопасная координированная процедура восстановления описаны в [docs/CLIENT_MEMBER_CUTOVER.md](../../docs/CLIENT_MEMBER_CUTOVER.md). Partner self-service в текущем интерфейсе не реализован.
