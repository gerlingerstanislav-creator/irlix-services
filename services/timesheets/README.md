# Timesheets backend

Laravel-сервис учёта коммерческого рабочего времени.

MVP поддерживает ввод часов по активным подключениям Clients, предварительное подтверждение сотрудником, финальное подтверждение руководителем/аккаунтом, редактирование из управления, блокировку периода, аудит и аналитику коммерческой загрузки.

Интеграции выполняются только через API Employees, Clients и Vacations. Timesheets владеет своей PostgreSQL schema `timesheets`.

Три этапа защиты ТШ: предварительное подтверждение сотрудником (сотрудник может редактировать с повторным подтверждением), финальное подтверждение на странице управления (блокирует редактирование сотрудником, уполномоченный руководитель может снять), отправка клиенту в Clients (блокирует редактирование и снятие обоих подтверждений для всех ролей). Сотрудник не может снять собственное подтверждение дня, если хотя бы один активный проект этого дня уже финально подтверждён руководителем или аккаунт-менеджером; снять финальное подтверждение необходимо на странице управления. Clients не позволяет отправить период клиенту, пока все его действующие заполненные ТШ не получили финальное подтверждение. При изменении записей, подтверждений сотрудника или финальных подтверждений Timesheets проверяет статус соответствующего отчётного периода в Clients. После перехода в «ТШ на согласовании» и на всех следующих этапах единственный путь к редактированию — последовательный откат отчётного периода в «Новый». Старый механизм закрытия всего месяца отключён; ранее сохранённые `period_locks` не влияют на редактирование, API закрытия удалён, миграция и исторический аудит сохранены. Роль `platform-admin` читается из Employees `/access/me` и даёт полный обзор всех сотрудников и проектов на странице управления.

На странице управления матрица разделена по специалисту и клиенту; двойной клик по дню открывает только проекты этой пары. Одна кнопка сохраняет все проекты клиента за день, закрывает окно и показывает уведомление. Финальное подтверждение месяца управляется двумя постоянно видимыми кнопками: галочка устанавливает подтверждение, крестик снимает его. Галочка неактивна, когда подтверждены все активные дни месяца, а крестик — когда не подтверждён ни один день. Стандартные фильтры включают специалиста и клиента. Ссылка `/timesheets?section=management&month=YYYY-MM&client_id=ID&employee_id=ID` открывает именно управление с предустановленными фильтрами. Навигация синхронизирует текущий раздел и месяц с URL.

Доступ к страницам и действиям Timesheets берётся из общей матрицы контура Clients. Account Manager видит и изменяет ТШ своих проектов, руководитель направления — сотрудников своего дерева подразделений, `platform-admin` — все ТШ всех сотрудников, направлений, клиентов и проектов. Проверка остаётся серверной; страницы без `*.view` не отображаются в меню.

Отсутствия отображаются оранжевой штриховкой: бледной для неподтверждённых и яркой для подтверждённых. При наличии активного проекта зелёные состояния подтверждения ТШ сохраняются под штриховкой. Если отсутствие приходится на день без активного проекта, ячейка получает серый фон с оранжевыми полосами. Дни без активного проекта не подлежат предварительному подтверждению; массовое подтверждение пропускает их, а ранее созданные ошибочные подтверждения удаляются при синхронизации рабочего пространства.

Интерфейс Timesheets использует полноширинную рабочую область без боковых отступов контейнера. На страницах «Управление», «Коммерческая загрузка» и «История действий» фильтры, показатели и остальные элементы над таблицей остаются неподвижными, а прокрутка выполняется внутри области таблицы; заголовок таблицы закреплён. На странице «Мои таймшиты» прокручивается весь контент. Календарные дни на ней уплотнены по высоте, а штриховка отсутствий накладывается поверх бледно-зелёного или зелёного фона подтверждения так же, как в матрице управления.


## Сохранность ТШ и синхронизация подключений (08.10.2026)

### Отображение ячеек управления (08.10.2026)

В месячной management-таблице часы внутри календарных ячеек отображаются без конечных нулей (8 вместо 8.00, 7.5 вместо 7.50, 7.25 без изменений); это не меняет сохранённые часы. Правый верхний уголок согласования клиентом не отображается; статусы отчётных периодов и серверная блокировка отправленных ТШ остаются неизменными. Левый верхний уголок отсутствий и правый нижний уголок описания сохраняются.

### Все отсутствия: две равные горизонтальные половины (08.10.2026)

На странице «Управление» все типы отсутствий отображаются одинаково: верхние 50% активной дневной ячейки занимают цвета отсутствия (оранжевый для подтверждённого, бледно-оранжевый для неподтверждённого), нижние 50% сохраняют стандартный фон ячейки (рабочий/выходной, предварительное/финальное подтверждение). На выходных и праздниках оранжевая верхняя половина приглушается аналогично зелёному фону. Часы находятся по центру ячейки поверх границы половин. Вне подключения — только тонкая серая штриховка без цифр и без индикации отсутствия. Размеры ячеек, нижний правый маркер описания и логика управления не меняются. Старые точка, полоска, уголок, круг и диагональный сектор не применяются.

### Управление: диапазон дней и описания

Frontend передаёт `Accept: application/json` при всех API-запросах, чтобы Laravel возвращал объяснение ошибок, включая 423, в JSON вместо HTML. При блокировке после отправки клиенту интерфейс показывает серверную причину; если тело ответа недоступно, используется понятное сообщение о блокировке с указанием проверки подтверждения и отчётного периода в Clients. Порядок разблокировки остаётся прежним: возврат отчётного периода в «Новый». Финальное подтверждение само по себе не блокирует редактирование руководителем.

В правом нижнем углу ячейки с непустым описанием отображается закрашенный уголок. При наведении без задержки появляется описание проекта этой строки или «Описание не заполнено». Двойной клик сохраняет существующую форму проектов клиента и сразу фокусирует часы проекта, по которому кликнули.

Перетаскивание с зажатой левой кнопкой выделяет диапазон в одной строке специалиста/проекта в любом направлении. После отпускания открывается «Массовое заполнение» с фокусом на часах. Enter и «Заполнить» задают одинаковые часы каждому выбранному активному дню; дни вне подключения пропускаются. Один клик не открывает форму диапазона. Escape и закрытие отменяют выделение. Подсветка выходных/праздников использует `GET /api/vacations/production-calendar?year=YYYY`, включая перенесённые рабочие субботы; при недоступности календаря используются субботы и воскресенья с уведомлением об ошибке. Зелёные состояния подтверждения и штриховка отсутствий сохраняются поверх календарного фона.

`PUT /management/bulk-hours` принимает `{employee_id, project_id, dates:[YYYY-MM-DD], hours}`: до 31 уникальной даты одного месяца, часы 0–24 с шагом 0,25. Проверяются `timesheets.management.manage`, scope AM/RN/admin, активность подключения и блокировка отчётного периода каждой даты. Весь диапазон сохраняется одной транзакцией; лимит 24 часа проверяется с учётом других проектов каждого дня. Описания не передаются браузером и не обновляются сервером. При нуле существующая запись остаётся вместе с описанием, новая пустая запись не создаётся. После успешного сохранения снимаются предварительные подтверждения выбранных дней и финальное подтверждение проекта за месяц; пишется аудит каждого дня. Ошибка любого дня откатывает весь диапазон, аудит и изменения подтверждений.

Timesheets получает подключения из `GET http://clients:8000/internal/timesheet-assignments` с серверным заголовком `X-Irlix-Timesheets-Token`. Отдельный `IRLIX_TIMESHEETS_INTEGRATION_TOKEN` известен только Clients, Timesheets API и его worker; deploy генерирует случайный secret один раз и сохраняет в server `.env`. Пользовательский `/overview` не используется как полный каталог. Внутренний ответ содержит `data`, `complete=true`, `count`, действующие и исторические периоды, но не коммерческие ставки. Неполный/невалидный ответ или ошибка зависимости приводит к отказу операции без удаления данных.

`GET /workspace`, `/management`, `/analytics` не изменяют записи и подтверждения. Полный внутренний каталог не расширяет пользовательский доступ: AM получает свои проекты, РН — дерево своих подразделений, администратор — все данные. Доступ проверяется и при изменении ТШ.

Контейнер `timesheets-reconcile` использует тот же проверенный образ и выполняет синхронизацию каждые 60 секунд. `php /app/bin/reconcile-assignments.php --once` запускает одну проверку. Worker блокирует существующие кандидаты, получает достоверные подключения и удаляет только записи вне их периодов; изменения и аудит выполняются одной транзакцией. Новые строки, созданные после отбора кандидатов, не затрагиваются. Ошибка или неполный ответ Clients откатывает всю проверку; следующий цикл повторяет попытку. Истинное сокращение подключения по-прежнему снимает утратившие актуальность подтверждения.

`PUT /management/entries` принимает старый формат одной записи либо `{employee_id, work_date, entries:[{project_id,hours,description}]}`. Новая форма сохраняет все проекты дня одной транзакцией, проверяет конечную сумму часов и возвращает сохранённые записи. Валидация/ошибка одного проекта не оставляет частично сохранённый день. Подтверждения снимаются только после успешного сохранения.

Регрессионные проверки в Dockerfile: сохранение/подтверждение двумя AM, просмотр AM/RN/admin без изменения БД, дерево подразделений РН, недоступный/неполный каталог, истинное сокращение периода, идемпотентность очистки и атомарность сохранения.

### Ранее удалённые записи

Исправление предотвращает новые ошибочные удаления, но не восстанавливает автоматически исторические данные. Для расследования использовать `timesheet_audit.action=entry_deleted_outside_assignment` и сохранённый `before`. Перед восстановлением конкретных записей проверить актуальный период подключения, отсутствие более новых изменений и блокировку отчётного периода в Clients. Не восстанавливать массово все удаления: часть из них соответствует реальному сокращению подключений.
