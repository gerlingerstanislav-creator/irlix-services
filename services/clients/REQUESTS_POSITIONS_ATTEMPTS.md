# Запросы, позиции и попытки подключения

## Иерархия

`ClientRequest → Position → ConnectionAttempt → AttemptInterview`.

- аккаунт-менеджер создаёт запрос и одну или несколько позиций;
- руководитель производственного направления видит позиции своего подразделения и всего его дочернего дерева и создаёт попытку подключения;
- руководителю производственного направления в Clients доступны только страницы `Позиции` и `Попытки подключения`; страница `Запросы` доступна клиентской службе;
- при создании внутренней попытки руководитель выбирает сотрудника только из подразделений с `is_production` внутри своего дерева; сотрудники непроизводственных подразделений в этот селект не входят;
- попытку нельзя создать без выбранного сотрудника либо ФИО внешнего специалиста и CV (`pdf`, `doc`, `docx`, до 15 МБ);
- новую попытку можно удалить до отправки CV; общего редактирования попытки нет, поля будут редактироваться отдельными действиями;
- отправку CV и дальнейшие этапы ведёт аккаунт-менеджер;
- `platform-admin` имеет доступ ко всем действиям.

## Статусы запроса

У запроса только два состояния:

- `Открыт` — значение по умолчанию для нового запроса;
- `Закрыт`.

Запрос остаётся открытым до явного закрытия менеджером. Дедлайн и успехи попыток его не закрывают. У открытого запроса с хотя бы одной позицией `В работе` отображается вычисляемый `В работе`; API возвращает его в `display_status`, базовый `status` остаётся `Открыт`. Закрытый запрос всегда отображается как `Закрыт`.

## Статусы позиции и закрытие родителей

Позиция также хранит только `Открыт` или `Закрыт`. У открытой позиции с хотя бы одной незакрытой попыткой (включая новую) отображается вычисляемый статус `В работе`; это не отдельное хранимое состояние. Количество успешных попыток не закрывает позицию автоматически.

Закрытие запроса или позиции выполняет аккаунт-менеджер. Если в их дереве есть незакрытая попытка на этапе `CV отправлено`, `Интервью назначено`, `Интервью пройдено` или `Ожидает подключения`, сервер отклоняет всю операцию с сообщением `Сперва закройте активные попытки`.

Если блокирующих попыток нет, все новые попытки закрываются как `Закрыт: неудача` с единственной причиной `Запрос закрыт` и датой закрытия. Закрытие запроса закрывает и его позиции. Проверка, закрытие новых попыток и родителя происходят одной транзакцией; создание попытки и отправка CV используют тот же порядок блокировок. Закрытые успешные/неуспешные попытки и интервью остаются в истории.

В закрытый запрос нельзя добавить позицию, в закрытый запрос или позицию — попытку. Для повторного открытия позиции сначала должен быть открыт её запрос. Успешная попытка по-прежнему позволяет создать отсутствующее подключение даже после закрытия родителя.

При переходе на эту модель прежние вычисляемые статусы позиций сбрасываются в `Открыт`: они не подтверждали ручное закрытие менеджером.

## Идентичность направления

`Position.direction_department_id` ссылается на ID подразделения Employees, а `direction` хранит его название для отображения. Сервер проверяет выбранный ID по актуальному списку производственных подразделений. Для старых позиций без ID доступ возможен только при однозначном совпадении названия среди всех подразделений; неоднозначная или устаревшая запись не расширяет доступ руководителя и требует выбора направления аккаунтом. При редактировании сохраняется ID.

Роль производственного руководителя вычисляется по `manager_id + is_production`, а не по названию должности или общему признаку manager. Права этой роли в Clients ограничены `positions.view`, `attempts.view`, `attempts.manage`; права Timesheets сохраняются отдельно. Область аккаунтов и сейлзов не расширяется за счёт производственного дерева. Дополнительные клиентские роли пользователя сохраняют собственные права, а `platform-admin` имеет полный доступ.

## Статусы попытки

Рабочая цепочка:

`Новая → CV отправлено → Интервью назначено → Интервью пройдено → Ожидает подключения → Закрыт: успех`.

Правила:

- отправить CV можно только из `Новая` и только при наличии файла;
- интервью назначается из `CV отправлено`, `Интервью назначено` или `Интервью пройдено`;
- каждое интервью хранится отдельно с порядковым номером, датой/временем, оценкой и фидбеком;
- если после заполнения итогов остаётся другое незавершённое интервью, попытка остаётся в `Интервью назначено`;
- подключение назначается только из `Интервью пройдено`;
- из `Ожидает подключения` попытку можно закрыть успехом отдельным действием без создания подключения;
- создание `ProjectMember + MemberTerms` также автоматически переводит попытку в `Закрыт: успех`;
- если попытка закрыта успехом без `ProjectMember`, действие создания подключения остаётся доступным после закрытия;
- из любого незакрытого статуса попытку можно перевести в `Закрыт: неудача` с одной или несколькими уникальными причинами.

## Причины неудачи

Общие причины доступны из любого незакрытого статуса:

- Запрос закрыт;
- Заведомо не подходил по уровню;
- Отказ специалиста;
- Специалист уволился;
- Подключение не состоялось.

Только в текущем статусе `CV отправлено`:

- CV: Недостаточно отраслевого опыта;
- CV: Нет ОС;
- CV: Недостаточно ком. опыта;
- CV: Не пройдено;
- CV: Недостаточно информации для положительного ответа;
- CV: Нет опыта в требующейся технологии.

Только в текущем статусе `Интервью назначено`:

- Интервью: отрицательная ОС;
- Интервью: Положительная ОС без подключения;
- Интервью: отменено;
- Интервью: не прошел тестовое.

Backend повторно проверяет доступность каждой причины и не доверяет состоянию frontend.

## Интерфейс

- клик по названию запроса, позиции или попытки открывает правый drawer с деталями и допустимыми действиями;
- drawer любого вложенного действия, включая создание подключения, открывается поверх карточки сущности;
- страница попыток отображается канбаном по всем семи статусам;
- на странице попыток доступен фильтр по технологии позиции;
- на иерархической странице сущности не имеют рамок и собственного фона;
- в иерархии остаются только название сущности и одинаковая по ширине крайняя правая колонка статуса;
- клиент показывается серым текстом в скобках после названия запроса, затем сразу располагается ссылка `+ позиция`;
- уровни различаются отступами, типографикой и тонкими разделителями; пунктиров дерева и точек у попыток нет;
- стрелка каждого Request помещена в квадрат со светло-голубым фоном для `Открыт`/`В работе` и бледно-красным для `Закрыт`; стрелки позиций сохраняют прежний паттерн;
- три кружка индикатора стоят перед названием каждой попытки, начиная с прежнего места точки; пунктир между самими кружками сохраняется;
- разделитель принадлежит полной строке, чтобы границы не смещались в колонке статусов;
- при первом открытии страницы все запросы и позиции с дочерними элементами раскрыты;
- в названии позиции после технологии и уровня показывается количество в формате `xN`;
- стрелки раскрытия используют тот же паттерн, что дерево клиентов;
- действие `+ позиция` отображается небольшой текстовой ссылкой;
- отдельной кнопки `+ попытка` в дереве нет: попытка создаётся из drawer позиции.

### Карточка запроса

Карточка визуально следует согласованному референсу существующей системы, но выводит только реализованные в новой системе данные.

В верхнем клиентском блоке показываются:

- название клиента;
- Sales (`S`) из `clients.sales_employee_id`, если назначен;
- Account Manager (`A`) из `clients.account_employee_id`, если назначен;
- сфера/сектор из `clients.sector`, если заполнен;
- тип клиента из `clients.type`, если заполнен.

Логотип клиента пока не выводится. В карточке запроса также показываются статус, дата запроса и дедлайн, описание запроса и блок его позиций. Вкладка заметок пока не реализуется.

### Карточка позиции

Карточка визуально следует согласованному референсу позиции и использует тот же клиентский блок. В ней показываются реализованные поля Position и контекст Request: статус, ответственный запроса, направление, технология, уровень, количество, дата создания, дедлайн запроса, ожидаемое время подключения, допустимый формат ТУ, описание запроса, описание позиции и попытки подключения.

## Создание запроса

Форма компактна, использует контролы дизайн-системы и содержит поля в порядке:

1. название;
2. клиент;
3. ответственный за запрос — текущий сотрудник, подставляется автоматически и может быть изменён;
4. дата запроса;
5. время жизни — 1, 2, 3 или 4 недели;
6. описание запроса;
7. одна или несколько позиций.

Каждая позиция содержит:

- технологию из древовидного каталога Specialists;
- производственное направление из Employees;
- уровень `TechLead`, `TeamLead`, `Senior`, `Middle+`, `Middle`, `Junior+` или `Junior`;
- целое положительное количество;
- ожидаемое время подключения: `Неизвестно` по умолчанию, `Месяц`, `Квартал`, `Пол года`, `Год`;
- допустимый формат ТУ: `Не важно` по умолчанию, `Штат`, `Штат / ГПХ`;
- описание позиции.

Те же два новых поля доступны при отдельном создании и редактировании Position.

Запрос и все его начальные позиции создаются одной транзакцией. Дата окончания вычисляется как дата запроса плюс выбранное время жизни; частично созданного запроса при ошибке быть не должно.

## API

- `PATCH /requests/{id}` — редактирование запроса;
- `POST /requests` — атомарное создание запроса с `description` и массивом `positions`;
- `PATCH /positions/{id}` — редактирование позиции, включая `expected_connection_time` и `acceptable_tu_format`;
- `POST /requests/{id}/positions` — создание отдельной позиции;
- `POST /positions/{id}/attempts` — создание попытки с CV (`multipart/form-data`);
- `DELETE /attempts/{id}` — удаление попытки, пока она находится в статусе `Новая`;
- `GET /attempts/{id}/cv` — скачивание CV;
- `POST /attempts/{id}/send-cv` — фиксация отправки CV;
- `POST /attempts/{id}/interviews` — назначение следующего интервью;
- `POST /attempts/{id}/interviews/{interview}/complete` — итоги интервью;
- `POST /attempts/{id}/schedule-connection` — дата планового подключения;
- `POST /attempts/{id}/close-success` — успешное закрытие из `Ожидает подключения` без обязательного создания подключения;
- `POST /attempts/{id}/close-failure` — закрытие с причинами.

## Уточнения интерфейса и модели попытки — 30.09.2026

На страницах запросов и позиций фильтр по умолчанию — `Открыт`; для обеих сущностей он включает вычисляемый `В работе`. Запросы и позиции сортируются по `created_at DESC, id DESC`, в том числе внутри запроса. Отдельный фильтр статусов попыток в дереве скрывает только строки попыток, сохраняя все подходящие запросы и позиции.

На desktop ширины вложенных карточек убывают: Request `50vw`, Position `40vw`, Attempt `30vw`; это начальные размеры, каждое окно можно растягивать за левую границу. Их z-index последовательно 1000/1050/1080. На мобильном карточки полноэкранные. Действия открываются поверх карточек.

`Назначить интервью` сразу открывает календарь с выбором времени и кнопкой `Применить`; дополнительных drawer и клика по input нет. Результаты используют `UiSearchSelect`, feedback — textarea высотой минимум 160px. Шрифт деталей попытки — 14px.

Три кружка CV → интервью → подключение соединены пунктиром. Новый этап белый, текущий жёлтый, завершённый зелёный. При неудаче `closed_from_status` хранит исходный статус: соответствующий кружок красный, будущие белые. `Новая` и `CV отправлено` соответствуют первому кружку, оба статуса интервью — второму, `Ожидает подключения` — третьему. Успех — все зелёные. Для старой неудачи этап восстанавливается миграцией по дате подключения, интервью или отправке CV; без фактов только третий кружок красный, прошлые белые. Индикатор с tooltip текущего статуса показывается в дереве запросов, сверху Attempt и в списке попыток Position.

Новая форма попытки содержит только сотрудника, флаг `Внешний специалист`, обязательный CV и необязательный комментарий. Сотрудники группируются деревом производственных направлений, направления и сотрудники сортируются по алфавиту. Внешний вариант заменяет селект полем ФИО, хранит `is_external=true`, `specialist_id=null` и не создаёт сотрудника Employees. CV выбирается кликом или перетаскиванием в широкую пунктирную зону. Дальнейшее создание ProjectMember использует существующую форму с выбором зарегистрированного сотрудника.

В списке попыток Position вертикальное меню `⋮` содержит только доступные роли и текущему статусу действия: отправка CV, новое интервью, завершение каждого незавершённого интервью, дата подключения, создание подключения, успех, неудача и удаление новой попытки. API повторно проверяет роль, scope и переход.

Проверки: `npm test` в `apps/clients` и Laravel smoke в `services/clients/tests/workflow_smoke.php`; обе включены в сборки соответствующих Docker-образов.


## Поля и действия карточек — 30.09.2026

Отдельных окон общего редактирования Request, Position и Attempt нет. В Request карандашами редактируются название, ответственный, дата, время жизни и описание; в Position — направление, технология, уровень, количество, ожидаемое время подключения, формат ТУ, ответственный РН и собственное описание. Сохранение отправляет PATCH только изменённого поля; ошибка сохраняет черновик, отмена не делает запрос. Открытие/закрытие выполняется через меню статуса. Формы создания сущностей и отдельные действия воронки сохраняются.

Описание Request можно независимо свернуть. В Position последовательно показаны сворачиваемые описание родительского запроса (без редактирования) и собственное описание (с карандашом).

Создатель Request автоматически подставляется ответственным, но при создании и в карточке можно выбрать другого сотрудника Employees. Position всегда показывает актуального ответственного родительского Request, отдельная копия не хранится. `responsible_rn_employee_id` — отдельный ответственный производственный руководитель: автоматически manager выбранного производственного подразделения, либо вручную выбранный руководитель из списка производственных направлений. Смена направления автоматически назначает его руководителя; аккаунт может затем сменить РН карандашом. Старые позиции без сохранённого РН отображают актуального руководителя своего направления. Назначение не расширяет права и scope дерева.

В реестре запросов Position имеет заголовок `Технология, Уровень xN`, справа два серых скруглённых тега ожидаемого времени подключения и допустимого формата ТУ. Attempt имеет ссылку `Скачать CV` справа; её нажатие скачивает файл соответствующей попытки без открытия карточки. После статусов — меню ⋮ для каждого уровня: открыть/закрыть Request или Position, для Attempt — те же доступные действия воронки, что в карточке. Сервер повторно проверяет права и переходы.

В строке Request после стрелки показан логотип Client в маленьком скруглённом квадрате. При отсутствии клиента, логотипа или ошибке загрузки — первая буква названия запроса. Логотип можно загрузить/заменить/удалить в карточке Client при `clients.manage` и доступе к клиенту. Поддерживаются PNG/JPEG/WebP до 1 МБ, SVG не принимается. Файл хранится в существующем volume `clients_files` в `logos`, API не выдаёт путь хранилища. GET `/clients/{id}/logo` требует права просмотра соответствующей страницы и доступного клиента или позиции своего производственного дерева; POST/DELETE требуют управления клиентом. Логотип не становится публичным файлом.

Progress Attempt стоит в заголовке справа. Поле `proposed_rate` удалено миграцией из ConnectionAttempt; новые запросы с ним отклоняются. Ставка задаётся только в форме создания ProjectMember/MemberTerms и больше не предзаполняется из Attempt. Миграция необратимо удаляет прежние значения ставки попытки; rollback восстанавливает только пустую колонку.

Производственному руководителю в overview дополнительно передаются описание, ответственный и дедлайн родительского Request как контекст доступных позиций, а также URL логотипа связанного клиента. Это не даёт доступа к странице Request, его редактированию, другим позициям или коммерческим данным клиента.
