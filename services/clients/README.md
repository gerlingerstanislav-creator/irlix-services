# Clients service

Первая рабочая версия backend-сервиса коммерческого контура IRLIX.

## Домен

Основная цепочка подключения специалиста: `Client -> Project -> ProjectMember -> MemberTerms`.

- при создании Client автоматически создаётся обязательный default Project с пустым `name`;
- `ProjectMember` хранит исторический факт участия специалиста в проекте;
- периоды `MemberTerms` могут иметь разрывы, но не могут пересекаться у одного специалиста в рамках одного Client;
- изменение ставки, загрузки, технологии или уровня оформляется новым `MemberTerms`;
- попытка подключения становится успешной только после явного создания `ProjectMember + MemberTerms` менеджером;
- Lead конвертируется в Client отдельным действием; Account Manager может быть назначен сразу или отдельным действием передачи после создания клиента;
- контакты являются самостоятельными M2M-сущностями для Lead/Client;
- у одного `ProjectMember` может быть любое количество текстовых фидбеков по работе специалиста на этом проекте.

## API первой версии

Базовый prefix на стенде: `/api/clients/`.

Реализованы:

- overview для UI;
- Clients и Projects;
- Leads, канбан, история, комментарии, контакты, юрлица и конвертация Lead -> Client — подробнее в `LEADS.md`;
- ContactPerson и связи;
- ProjectMember / MemberTerms;
- ProjectMemberFeedback: `GET /members/{member}/feedbacks` и `POST /members/{member}/feedbacks`;
- ClientRequest / Position / ConnectionAttempt;
- полный workflow запросов, позиций и попыток с обязательным CV, повторными интервью, планированием подключения и закрытием с причинами описан в `REQUESTS_POSITIONS_ATTEMPTS.md`;
- ReportingPeriod;
- карточка отчётного периода объединяет даты отправки и согласования ТШ и акта; строки ТШ ведут на управление Timesheets с фильтрами клиента и специалиста;
- `GET /absence-approvers?employee_id=&from=&to=` — read contract для Vacations: возвращает уникальных account managers и количество активных подключений сотрудника, чьи `MemberTerms` пересекаются с указанным периодом.

Все бизнес-endpoint'ы защищены общим Keycloak bearer middleware. `/health` доступен без токена.

## Ролевая модель контура клиентов

Запросы и позиции хранят состояния `Открыт` / `Закрыт` и закрываются менеджером явно. У открытой позиции с незакрытыми попытками отображается `В работе`. Закрытие блокируется попытками после этапа `Новая`; новые попытки автоматически закрываются неудачей с причиной `Запрос закрыт`. Подробности транзакций и миграции прежних статусов приведены в `REQUESTS_POSITIONS_ATTEMPTS.md`.

Проверка `tests/workflow_smoke.php` запускается при сборке backend image и проверяет workflow, атомарность закрытия, обязательный CV и границы производственного дерева через настоящий Laravel 12 с синтетическим Employees API. Для локального запуска нужны зависимости Laravel и PDO SQLite: `CLIENTS_TEST_AUTOLOAD=/path/to/vendor/autoload.php php tests/workflow_smoke.php`. SQLite проверяет транзакционность, но не PostgreSQL-блокировки параллельных запросов.

Clients владеет настраиваемой матрицей `role → permission → scope`, которая распространяется на Clients, Timesheets и будущие сервисы контура клиентов. Организационные роли вычисляются из Employees, специальные роли берутся со страницы «Роли». Scope: `own`, `team`, `all`; сервер является границей безопасности, а меню скрывает страницы без соответствующего `*.view`.

Роль `Руководитель производственного направления` назначается только сотруднику, указанному руководителем подразделения с признаком `is_production`. Его область производственных данных включает собственное производственное подразделение и всё дочернее дерево. Специалиста для попытки можно выбрать только из этого дерева. Доступ к страницам и действиям, включая запросы для Sales, определяется настраиваемой матрицей разрешений и не ограничивается дополнительным жёстким списком ролей.

Account Manager работает со своими клиентами, контактами, подключениями, отчётными периодами и ДДС. До передачи клиента Sales с разрешением `clients.manage` управляет своими клиентами и их воронкой; после назначения account manager Sales сохраняет просмотр, но редактирование выполняет Account. Руководитель аккаунтинга наследует права аккаунта и сейлза со scope не уже `team`; руководитель клиентской службы наследует права аккаунта со scope `all`; руководитель сейлз наследует права сейлза со scope не уже `team`. Сейлз не получает страницу «Клиенты». `platform-admin` всегда имеет все текущие и будущие разрешения со scope `all`; его строка неизменяема. Матрицу может менять только `platform-admin`, изменения пишутся в `client_contour_permission_audit`. Наследнику нельзя установить права уже базовой роли.

Экран «Настройки разрешений» расположен в нижней части меню Clients. Все ячейки ролей доступны для настройки; заблокирована неизменяемая колонка `platform-admin`, у которой всегда полный доступ, и ячейки `platform-tester` для действий Clients. Экран содержит только уже реализованные страницы и действия: добавление permission не создаёт новую бизнес-операцию. `GET /permissions/me` возвращает эффективные права текущего пользователя, `GET/PUT /permissions` управляют матрицей.

Для интерфейса и Timesheets используется справочник Employees `/api/clients-directory` с идентификатором, именем и подразделением без кадровых или зарплатных данных. Запросы и позиции редактируются из правых drawer-карточек; у попытки нет общего редактирования, а действия workflow дополнительно ограничиваются текущим статусом и permission/scope. Sales с настроенными `requests/positions/attempts.manage: own` имеет полный workflow для своих запросов, их позиций и попыток; контроллеры не вводят дополнительный список разрешённых ролей.

## Фидбеки по специалисту на проекте

Фидбек привязан именно к `ProjectMember`, то есть к конкретному специалисту на конкретном проекте.

- один ProjectMember может иметь 0..N фидбеков;
- содержимое фидбека — произвольный текст до 10 000 символов;
- фидбеки хранятся отдельными записями и не перезаписывают друг друга;
- сохраняются дата создания и username пользователя из Keycloak, если он присутствует в access token;
- в UI фидбеки отображаются в карточке участника проекта в обратном хронологическом порядке;
- там же доступно добавление нового фидбека;
- жизненный цикл фидбека следует `ProjectMember`: при административном удалении ProjectMember его фидбеки удаляются каскадно.

## Интеграции

- Employees — источник сотрудников; frontend Clients получает доступный аккаунт-менеджерам каталог через `/api/employees/clients-directory`.
- Vacations — двусторонняя read-интеграция без прямого доступа к БД: Clients читает `/api/vacations/calendar-absences`, а Vacations читает `/api/clients/absence-approvers` для формирования AM approval stage.
- Для Vacations активным считается подключение, у которого `member_terms.valid_from <= absence.to` и `valid_to IS NULL OR valid_to >= absence.from`. Если таких подключений нет, Clients возвращает пустой список AM, и Vacations пропускает AM stage.
- Timesheets — источник фактически внесённых часов для колонки `ТШ` и итогового подтверждения для колонки `Подтверждено` через внутренний API Clients.
- Reporting Periods — управляет этапами согласования, в том числе блокировкой редактирования ТШ после отправки клиенту.

## ДДС

Первая версия рассчитывает календарный план на frontend по периодам MemberTerms:

`рабочие дни РФ x hours_per_day - официальные отсутствия`.

Если внутри выбранного месяца менялись условия, один ProjectMember отображается несколькими строками по соответствующим периодам условий.

Колонка «Период условий» показывает полные даты MemberTerms, даже когда они выходят за выбранный месяц; открытый интервал заканчивается «по н.в.». Расчёт показателей при этом ограничен выбранным месяцем.

Экран ДДС загружает `/api/clients/cash-flow?month=YYYY-MM` и показывает календарные, фактические и подтверждённые часы и суммы для каждой версии MemberTerms. Фактические часы сопоставляются по специалисту, проекту и датам действия ставки; деньги рассчитываются по этой ставке. Экран получает справочник сотрудников через `clients-directory`, поэтому доступ к общему реестру Employees не требуется.

## Отчётные периоды

Период создаётся с клиентом и неизменяемыми датами. Его поля в карточке доступны только для чтения. Действие в меню карточки переводит период ровно на один следующий этап:

`Новый → ТШ на согласовании → ТШ согласованы → Акт на согласовании → Акт согласован → Счет оплачен`.

API `PATCH /reporting-periods/{id}` принимает следующий `status` и обязательную дату `date`, выбранную пользователем (по умолчанию в форме — сегодня). Даты пяти этапов хранятся отдельно: отправка ТШ, согласование ТШ, отправка акта, согласование акта, оплата. Переход вперёд разрешён только при наличии даты текущего этапа. Первый переход требует действующих заполненных ТШ и финального подтверждения каждого из них аккаунт-менеджером/уполномоченным руководителем: сервер сверяет сотрудника, проект и месяц каждой записи с подтверждениями Timesheets. В карточке перечислены все версии ставок клиента, пересекающиеся с периодом, включая версии без внесённых часов.

Руководитель клиентской службы, руководитель аккаунтинга и `platform-admin` могут откатить статус на один шаг; при откате дата покидаемого этапа очищается. Повторные откаты возвращают к `Новый`. Право проверяется по Employees `/access/me` и `/self`. `GET /reporting-period-lock?client_id=&work_date=&to=` сообщает Timesheets, заблокированы ли данные после отправки на согласование. `DELETE /reporting-periods/{id}` удаляет период после подтверждения в UI.

`ТШ` и `Подтверждено` загружаются через внутренний API Timesheets и не редактируются на экране ДДС.

## Внутренний каталог подключений для Timesheets

`GET /internal/timesheet-assignments` защищён отдельным `IRLIX_TIMESHEETS_INTEGRATION_TOKEN` в `X-Irlix-Timesheets-Token`. Он возвращает полную историческую выборку подключений одним SQL-запросом, без пользовательской фильтрации и коммерческих ставок: `{data:[{employee_id,employee_name,client_id,client_name,project_id,project_name,account_employee_id,valid_from,valid_to}], complete:true, count:N}`. Отсутствующий/неверный secret даёт 403. Endpoint предназначен только для серверной интеграции; browser `/api/overview` сохраняет обычные permissions/scope. Timesheets применяет собственные permissions к выдаче и использует каталог для фоновой синхронизации.

Ответ также содержит `locked_reporting_periods` (id, client_id, period_start, period_end, status, timesheets_sent_at), `locked_reporting_periods_complete=true` и `locked_reporting_periods_count`. Это полный серверный снимок периодов со статусом после «Новый», без ставок и денежных сумм. Он определяет обязательное финальное подтверждение и защиту отправленных ТШ в Timesheets, включая перенесённые периоды без известного автора согласования. После отката до «Новый» период исключается из снимка. Для отправки нового периода по-прежнему обязательны сохранённые финальные подтверждения всех действующих заполненных записей.

## Ограничение тестировщика платформы · 2026-10-08

`platform-tester` без `platform-admin` не имеет доступа ко всему сервису Clients. Явный запрет применяется независимо от организационных ролей и сохранённых разрешений матрицы: все разрешения, кроме `timesheets.*`, возвращаются как `allowed: false, scope: none`. Клиенты скрыты в общем launcher и дашборде; прямой `/clients/` возвращает пользователя на дашборд. Все бизнес API клиентов, логотипы, CV и управление матрицей возвращают 403. Недоступные ячейки тестировщика отображаются заблокированными; изменение через PUT возвращает 422. Администратор платформы, включая сочетание обеих ролей, сохраняет полный доступ.

Сохраняются GET `/permissions/me`, `/reporting-period-lock` и `/absence-approvers` — минимальные read-контракты для Timesheets и Vacations, без доступа к карточкам, коммерческим условиям и воронке клиентов. `timesheets.*` и существующие привилегии тестировщика в других сервисах сохраняются. Внутренний каталог подключений Timesheets по-прежнему защищён отдельным интеграционным токеном.
