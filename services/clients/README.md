# Clients service

Первая рабочая версия backend-сервиса коммерческого контура IRLIX.

## Домен

Основная цепочка подключения специалиста: `Client -> Project -> ProjectMember -> MemberTerms`.

- при создании Client автоматически создаётся обязательный default Project с пустым `name`;
- `ProjectMember` хранит исторический факт участия специалиста в проекте;
- периоды `MemberTerms` могут иметь разрывы, но не могут пересекаться у одного специалиста в рамках одного Client;
- изменение ставки, загрузки, технологии или уровня оформляется новым `MemberTerms`;
- попытка подключения становится успешной только после явного создания `ProjectMember + MemberTerms` менеджером;
- Lead конвертируется в Client отдельным действием и требует Account Manager;
- контакты являются самостоятельными M2M-сущностями для Lead/Client.

## API первой версии

Базовый prefix на стенде: `/api/clients/`.

Реализованы:

- overview для UI;
- Clients и Projects;
- Leads и конвертация Lead -> Client;
- ContactPerson и связи;
- ProjectMember / MemberTerms;
- ClientRequest / Position / ConnectionAttempt;
- ReportingPeriod.

Все бизнес-endpoint'ы защищены общим Keycloak bearer middleware. `/health` доступен без токена.

## Demo data

На текущем стенде вместе с миграциями устанавливается идемпотентный demo-набор данных для ручной отладки UI и бизнес-сценариев.

Он включает:

- несколько Clients из разных отраслей, default и обычные Projects;
- Leads во всех рабочих статусах, включая успех, отказ и `Клиент в игноре`;
- ContactPerson со связями как с Client, так и с Lead;
- Requests, Positions и ConnectionAttempts с активными, успешными и неуспешными сценариями;
- ProjectMember и MemberTerms с действующими, завершёнными, будущими периодами, сменой ставки и разрывом между периодами;
- ReportingPeriods в разных этапах workflow: от `Новый` до `Счет оплачен`.

Demo-данные имеют узнаваемые названия (`Demo ...`, а также фиксированный набор тестовых клиентов) и предназначены только для текущего стенда разработки.

## Интеграции

- Employees — источник сотрудников; frontend получает каталог через `/api/employees/employees`.
- Vacations — предоставляет минимальный read-model `/api/vacations/calendar-absences`; ДДС вычитает все созданные отсутствия выбранного периода независимо от их статуса.
- Timesheets — источник фактически внесённых часов. ДДС получает доступные текущему пользователю записи через `/api/timesheets/management?month=YYYY-MM` и сопоставляет их по `employee_id + project_id + work_date`.
- Reporting Periods — источник будущих подтверждённых клиентом часов и денег для колонок `Подтверждено`.

## ДДС

Календарный план рассчитывается на frontend по периодам MemberTerms:

`рабочие дни РФ x hours_per_day - официальные отсутствия`.

Если внутри выбранного месяца менялись условия, один ProjectMember отображается несколькими строками по соответствующим периодам условий.

Фактические показатели Timesheets уже подключены:

- `Часы / ТШ` — сумма фактически внесённых часов Timesheets по специалисту и проекту внутри конкретного периода MemberTerms;
- `ДС / ТШ` — `Часы / ТШ x hourly_rate` соответствующего MemberTerms;
- если ставка меняется внутри месяца, каждая запись Timesheets попадает в строку того периода условий, который действовал на дату записи;
- данные берутся с тем же permission/scope, который применяет экран `Управление` сервиса Timesheets.

Колонки `Подтверждено` пока не заполняются: их источником остаётся workflow ReportingPeriod после реализации фиксации согласованных с клиентом часов и сумм.
