# Vacations / Absences service

Vacations является source of truth для отсутствий сотрудников. Сервис не владеет сотрудниками и оргструктурой: employee identity, HR assignment, special roles, management hierarchy и permission/scope разрешаются через Employees. Активные клиентские подключения и account managers разрешаются через Clients API.

## Ролевая модель

Vacations различает три независимых понятия:

- **Кадровик** — специальная функциональная роль Employees `personnel-officer`; именно кадровики выполняют первичную и финальную кадровую проверку отпусков, имеют доступ к содержимому заявлений/вложений и могут вернуть незавершённую заявку в `planned`;
- **HR** — отдельная организационная функция/подразделение компании и не является синонимом кадровика;
- **HR направления** — конкретный HR, закреплённый за подразделением через `departments.hr_id`; эта связь остаётся частью оргструктуры и не даёт автоматически роль кадровика.

Кадровиков может быть несколько. Кадровый approval является role-based: любой сотрудник, который **сейчас** имеет `personnel-officer`, может выполнить активный кадровый этап. Снятие роли в Employees сразу лишает права выполнить такой этап, даже если employee id ранее попал в snapshot задачи.

`platform-admin` по платформенному правилу имеет полный scope и может выполнить любой активный этап approval за всех участников. Если на одном этапе есть несколько обязательных согласующих (например несколько account managers), одно действие `platform-admin` закрывает весь текущий этап.

В исторической схеме Vacations внутренние статусы `hr_review` / `hr_final_review` и `required_role=hr` сохранены ради совместимости данных. В бизнес-смысле это кадровые этапы и авторизуются только через `personnel-officer` (либо `platform-admin`). Directional HR в эти этапы не подставляется.

## Реализовано

Backend:

- производственный календарь РФ синхронизируется с публичным API isDayOff и сохраняется в PostgreSQL; worker заранее проверяет текущий год и два следующих, а уже загруженные годы доступны независимо от внешнего API;
- для следующего года с сентября по декабрь повторная проверка выполняется не чаще раза в 7 дней, в остальных случаях — не чаще раза в 30 дней; прошлые успешно загруженные годы не обновляются;

- Keycloak bearer authentication;
- изолированная PostgreSQL schema `vacations`;
- `Absence` для `paid_vacation`, `unpaid_vacation`, `sick_leave`, `maternity_leave`, `day_off`;
- type-specific validation и расчёт дней ежегодного оплачиваемого отпуска с исключением нерабочих праздничных дней РФ;
- запрет пересекающихся активных отсутствий;
- API занятых периодов для блокировки пересечений прямо в календаре создания;
- workflow `planned -> personnel primary -> account managers -> manager -> personnel final -> confirmed` для оплачиваемого/неоплачиваемого отпуска;
- Clients integration: уникальные account managers определяются по `member_terms`, которые пересекаются с периодом отсутствия;
- если на период нет ни одного активного подключения сотрудника в Clients, account-manager stage не создаётся и после первичного кадрового согласования workflow автоматически переходит к руководителю;
- сокращённые кадровые workflows для больничного, декрета и отгула;
- больничный и декрет можно создать с открытой датой окончания; до фактического закрытия они остаются `planned`;
- approval tasks, status history и audit log;
- approval progress отдаёт `approver_name`, разрешая `approver_employee_id` через Employees;
- manager scope на всё поддерево подразделения;
- руководитель может создать отсутствие сотруднику только внутри своего Employees scope;
- кадровик может создать `planned` отсутствие за любого сотрудника;
- manager fallback при подтверждённом пересекающемся отсутствии руководителя;
- возврат незавершённой заявки в `planned` с аннулированием текущего approval cycle;
- неизменяемость `confirmed` для обычных ролей;
- attachment layer: metadata в PostgreSQL, бинарные файлы в persistent storage volume;
- на текущем этапе к одному отсутствию допускается максимум один документ;
- содержимое документа доступно владельцу отсутствия и кадровику/admin; руководитель/HR видят только факт наличия документа;
- оплачиваемый/неоплачиваемый отпуск нельзя отправить на согласование без заявления;
- больничный/декрет нельзя отправить на итоговое подтверждение без закрытой даты окончания и подтверждающего документа;
- scoped registry по организационной зоне;
- scoped action history на базе `absence_audit_log`;
- server-side `available_actions`, `requires_my_action` и `approval_progress` для единого рабочего реестра.

Frontend:

1. **Мои отпуска** — создание, просмотр и управление собственными отсутствиями, документы, расчётный кадровый остаток и тот же визуальный approval progress, что в управлении;
2. **Отпуска подразделения** — календарь/список в доступном organizational scope; руководитель может создать отсутствие за сотрудника своей зоны;
3. **Управление отпусками** — единое рабочее окно реестра и согласований. Отдельная страница **«Согласования» удалена**;
4. **История действий** находится в нижнем системном блоке sidebar по паттерну Employees;
5. sidebar Vacations повторяет Employees: service launcher по клику на логотип, hover-подписи справа от иконок, одинаковый системный блок;
6. единая карточка отсутствия с документом, approval timeline, ФИО каждого согласующего и history;
7. единое контекстное меню `⋮` у каждой записи; согласовать, вернуть, предоставить и другие действия выполняются из него;
8. рабочие панели растягиваются до низа viewport и прокручивают таблицу/календарь внутри; контекстное меню телепортируется поверх scroll-контейнеров;
9. согласование и финальное предоставление выполняются без дополнительного browser-confirm;
10. создание отсутствия использует единый dropdown range calendar вместо двух отдельных date-полей;
11. уже занятые дни визуально заблокированы в range calendar; диапазон нельзя провести через существующее активное отсутствие;
12. ошибки создания, включая overlap, показываются внутри модального окна, а не фоновым alert основной страницы;
13. документ можно приложить сразу при создании отсутствия;
14. для собственного отсутствия в форме создания есть два сценария: **«Запланировать»** и **«Отправить на согласование»**; второй создаёт отсутствие, загружает документ и сразу выполняет submit;
15. в управлении отпусками фильтры имеют компактную высоту при прежнем размере шрифта;
16. 12 месячных карточек не используют горизонтальную прокрутку: на обычном ноутбуке помещаются в одну строку, на более узком экране переносятся;
17. выбор года в правом верхнем углу не имеет дополнительной внешней рамки/отступов, кнопка создания не переносит текст;
18. hover/focus на каждой точке approval progress показывает этап, ФИО согласующего и статус.

## Создание и документы

Обычный отпуск создаётся с обязательными датами начала и окончания. Документ можно приложить в том же модальном окне или позднее. Отправка оплачиваемого/неоплачиваемого отпуска на согласование доступна только после загрузки заявления.

В собственной форме создания доступны два независимых действия:

- **«Запланировать»** — сохранить `planned`;
- **«Отправить на согласование»** — выполнить create + upload документа + submit в одном пользовательском действии. Если обязательный документ отсутствует или open-ended больничный/декрет ещё не закрыт, submit недоступен, но сохранение `planned` разрешено.

Больничный и декрет поддерживают open-ended draft:

- обязательна дата начала;
- дата окончания при создании может отсутствовать;
- запись остаётся `planned`;
- сотрудник может создать такой больничный/декрет для себя;
- руководитель может создать такую запись за сотрудника в своём scope;
- после фактического закрытия сотрудник указывает конечную дату и прикладывает единственный подтверждающий документ;
- только после этого становится доступна отправка на итоговую кадровую проверку.

Максимум один документ на отсутствие — временное продуктовое ограничение текущей версии. Для замены старый документ нужно удалить и загрузить новый.

## Управление отпусками

Экран объединяет общий реестр и задачи согласования.

В верхней части:

- поиск;
- фильтр статуса;
- фильтр подразделения;
- фильтр типа отсутствия;
- переключатель **«Требуют моего действия»** с количеством доступных текущему пользователю approval tasks;
- компактный выбор года;
- создание отпуска за сотрудника для кадровика и для руководителя в его scope.

Фильтры имеют уменьшенную высоту controls без уменьшения размера шрифта.

Ниже отображаются 12 интерактивных карточек месяцев без горизонтального scroll. Клик по карточке включает/снимает быстрый фильтр этого месяца. Для каждого месяца рассчитываются:

- часы отсутствий;
- максимально возможное рабочее время текущей выборки из расчёта **8 часов × рабочие дни производственного календаря РФ**; если календарь выбранного будущего года ещё официально не опубликован и isDayOff его не отдаёт, UI временно использует обычную пятидневку до появления подтверждённых данных;
- процент `absence_hours / total_possible_hours`.

`rejected` и `cancelled` не включаются в часы отсутствий. Фильтр подразделения/поиск меняет состав сотрудников и, соответственно, знаменатель месячной статистики.

В строке отпуска справа отображается прогресс approval steps. Completed/pending/waiting этапы визуально различаются. Каждый approval task соответствует конкретному согласующему; при наведении на индикатор отображаются этап, ФИО и статус. Все разрешённые операции доступны через `⋮`, поэтому отдельный approvals inbox не нужен.

## Мои отпуска и расчётный остаток

До интеграции с 1С UI использует подтверждённый временный расчёт первой версии:

- базовый годовой лимит оплачиваемого отпуска — **28 дней**;
- из него вычитаются `entitlement_days` всех оплачиваемых отпусков года, кроме `rejected` / `cancelled`;
- остаток может быть отрицательным и не блокирует создание/отправку заявки;
- это именно расчётный показатель Vacations, а не юридически значимый остаток из 1С.

После подключения 1С источник кадрового остатка должен быть заменён без изменения workflow Vacations.

В колонке **«Документы»** при наличии вложения отображается ссылка на открытие карточки/документа; прочерк показывается только при отсутствии файла. В отдельной колонке согласования показывается тот же approval progress, что и на странице управления.

## Employees integration

Vacations использует Employees API для:

- текущего employee profile;
- ролей, permissions и scope;
- списка активных `personnel-officer`;
- directional HR отдельно от кадровиков;
- manager chain;
- проверки manager scope;
- минимального `vacations-directory` контракта для реестра/calendar/history;
- разрешения `approver_employee_id` в ФИО для отображения approval chain.

Прямого чтения таблиц Employees из runtime Vacations нет.

## Clients integration

Для оплачиваемого/неоплачиваемого отпуска Vacations вызывает Clients `GET /api/absence-approvers` с `employee_id`, `from`, `to`.

Clients является source of truth по подключениям к проектам и определяет:

- есть ли `member_terms`, пересекающиеся с датами отсутствия;
- список уникальных `clients.account_employee_id` по этим подключениям.

Если список пуст, AM approval stage полностью пропускается. Ошибка/недоступность Clients **не считается отсутствием подключения**: submit завершается ошибкой, чтобы не пропустить обязательное согласование из-за технического сбоя.

## Текущий workflow

Оплачиваемый и неоплачиваемый отпуск:

`planned -> кадровик primary -> [account managers, если есть активные подключения] -> manager -> кадровик final -> confirmed`.

Больничный и декрет:

`planned(open allowed) -> закрытие периода + документ -> кадровик final -> confirmed`.

Отгул:

`planned -> кадровик final -> confirmed`.

## API рабочего UI

- `GET /api/vacations/production-calendar?year=YYYY` — производственный календарь РФ из локальной БД, автоматически синхронизируемый с isDayOff;
- `GET /api/vacations/workspace` — текущий employee/access + scoped directory metadata;
- `GET /api/vacations/registry` — scoped absence registry с approval progress/actions и ФИО согласующих;
- `GET /api/vacations/history` — scoped action history;
- `GET /api/vacations/absences?year=YYYY` — собственные отсутствия, включая approval progress;
- `GET /api/vacations/absences/occupied` — активные занятые периоды текущего/доступного сотрудника для range calendar;
- `GET /api/vacations/absences/{id}/workspace` — единая карточка + approvals с ФИО/history/actions;
- `POST /api/vacations/absences/for-employee` — создание `planned` отсутствия руководителем в scope или кадровиком;
- `GET|POST /api/vacations/absences/{id}/attachments`;
- `GET /api/vacations/absences/{id}/attachments/{attachment}/download`;
- `DELETE /api/vacations/absences/{id}/attachments/{attachment}`.

## Demo seed стенда

`/opt/irlix-services/scripts/seed-vacations-demo.sh` создаёт идемпотентный набор тестовых отсутствий за сентябрь 2026 из актуальных сотрудников Employees. Seeder распределяет записи по доступным подразделениям, пропускает сотрудников с уже существующим пересечением и создаёт разные типы/статусы, history/audit и pending approval для workflow-статусов.

Маркер `vacations.demo_seed_runs` не позволяет применить этот seed повторно.

## Не завершено

- direct-confirm при создании отпуска кадровиком/admin (сейчас создаётся `planned`);
- admin override для изменения уже `confirmed`;
- перенос отпускных остатков между годами и интеграция юридически значимых кадровых остатков с 1С;
- RabbitMQ/outbox events Vacations;
- notifications;
- окончательный Timesheets read contract;
- полноценный acceptance suite для всех ролевых комбинаций.
