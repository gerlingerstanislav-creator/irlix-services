# Clients: сверка полей подключений и канонический перенос

Проверено 12.10.2026 по предоставленной оператором SQL-схеме `shema_clients.sql`.
Это сверка структуры выгрузки, а не заявление о проверке текущей production-БД.
Исходный dump и реальные строки не хранятся в Git. Реальный перенос требует нового Inspect/Dry run.

## `members → client_members`

| Legacy поле | Назначение и перенос |
|---|---|
| `id` | Собственный mapping `clients/members`, не копирование числового ID |
| `memberable_type` | `employee` — сотрудник; `subcontract` — отдельный партнёр; другие значения конфликт |
| `memberable_id` | Через users/Employees либо subcontracts/partner_specialists; ID разных типов не смешиваются |
| `client_id` | Владелец подключения; сверяется с клиентом проекта, если указаны оба поля |
| `project_id` | Реальный проект доказывает клиентскую принадлежность; при NULL проект не создаётся. История сохраняется в ProjectMember, даты назначения не выводятся из rates |
| `attached_by` | FK к legacy users: автор добавления, а не специалист. Аналога в новом ClientMember нет; приватная metadata с warning |
| `created_at`, `updated_at` | Исходные timestamps при создании; повторный перенос не меняет дату создания уже существующей строки |

`specialist_name` сотрудника берётся из surname/name/patronymic; отсутствие имени конфликт.
Партнёры сохраняют отдельную личность. `source_attempt_id` не выводится из совпадений имён/дат:
в исходном members ссылки на попытку нет.

## `rates → member_terms`

| Legacy поле | Назначение и перенос |
|---|---|
| `id` | Собственный mapping `clients/rates`; совместимые известные пересекающиеся/смежные интервалы объединяются с lineage каждого source ID, несовместимые и неизвестные пересечения требуют сверки |
| `member_id` | FK к members → `client_member_id`; проектные aliases одной личности/клиента ведут к одному подключению |
| `start_date`, `end_date` | `valid_from`, `valid_to`; NULL окончания означает открытый период |
| `workload` | `hours_per_day`, подтверждённые часы в день; диапазон 0–24, без округления сверх двух знаков |
| `technology_id` | Название из technologies → `technology`; исходный NULL сохраняется с warning, неизвестный непустой ID конфликт |
| `grade` | `level`; исходный NULL/пустое значение сохраняется NULL с warning |
| `rate` | Сумма отдельно от условий. При `clients_defer_rate_amounts=true` не читается как число: новая сумма NULL, существующая сумма сохраняется |
| `is_revision`, `reason` | Исходный признак и причина пересмотра остаются в приватной metadata с warning; фиктивные новые audit events не создаются |
| `created_at`, `updated_at` | Исходные timestamps при создании; дата создания существующей строки не переписывается |

С 12.10.2026 rates больше не исключается целиком. Сроки, загрузка, технология и грейд импортируются
даже без расшифрованной суммы. Все проверки ссылок, дат, точности и пересечений продолжают действовать.
Нулевую сумму вместо неизвестной не подставлять. Отдельная reporting_period_rate остаётся metadata-only.
После реализации проверенной расшифровки или получения проверенного числового экспорта можно отключить
`clients_defer_rate_amounts`; несовместимые/нечисловые суммы в этом режиме блокируют preflight.

Обычные бизнес-API по-прежнему требуют ставку, технологию и грейд для новых условий.
Nullable значения служат историческому импорту. ДДС и отчётные периоды возвращают NULL для денежных
показателей строки с неизвестной ставкой, сохраняя часы. Итог с любой такой строкой тоже NULL;
UI показывает «—», карточка условий — «Ставка неизвестна». Реальная ставка 0 остаётся числом 0.
Пустой ввод при редактировании ставки не преобразуется в ноль.

## `feedback → client_member_feedbacks`

Проверенный контракт источника: `id`, `member_id`, `content`, `date`, `rating`,
`interview_id`, `created_at`, `updated_at`. Иной набор полей блокируется до сверки.

| Legacy поле | Назначение и перенос |
|---|---|
| `id` | Собственный mapping `clients/feedback` с полным исходным payload |
| `member_id` | Через canonical mapping members → ClientMember; исходный реальный проект сохраняется в project_id |
| `content` | `text`, без потери текста |
| `date` | `occurred_on`, отдельно от timestamps |
| `rating` | Исходная строка без изменения шкалы или преобразования в число |
| `interview_id` | `legacy_interview_id`, исходный namespace, не FK на новый справочник |
| `created_at`, `updated_at` | Исходные nullable timestamps; NULL не заменяется временем импорта |

Автор в проверенной схеме отсутствует: `created_by_username=NULL`; ни attached_by
участника, ни выполняющий миграцию пользователь не считаются автором feedback.
Проектный feedback требует сохранённого доказательства исходной проектной связи.
Недатированные ProjectMember сохраняют только факт исторического участия;
ProjectAssignment без доказанных исходных дат не создаётся.
Повторный перенос feedback блокирует изменение исходного payload или целевой строки,
а не перезаписывает ручные исправления. Validate сверяет feedback и проектную историю.

## Существующие mappings после expand migration

Старые `members → project_members` перепривязываются к ClientMember только при
совпадении сохранённого source, прежнего target_payload и однозначной пары клиент–личность.
Старые `rates → member_terms` требуют сохранённого `member_term_lineage.original_payload`
и доказанного canonical owner. Изменённая или недоказанная история блокируется.
Прежние mappings сохраняются в `previous_mapping` и не теряются при повторных запусках.
Существующие ProjectMember и archived terms остаются на месте, новые дубликаты не создаются.

## Остальной актуальный контракт

- Клиенту не требуется проект. Импортируются только реальные проекты. Историческая принадлежность без доказанных дат хранится как evidence, не как выдуманный ProjectAssignment.
- Конвертированный лид с подтверждённой client_id переносится успешным; исходный иной статус сохраняется с warning.
- Legacy client_requests в предоставленной схеме имеет обязательную client_id и не имеет lead_id.
  Историческая принадлежность к лиду для таких строк не выдумывается. Если источник явно содержит lead_id,
  перенос сохраняет его и проверяет пару с converted_client_id; запросы, позиции и попытки не копируются.
- Повторный перенос не удаляет и не заменяет уже сохранённую исходную ссылку запроса на лид.
- Validate проверяет canonical и alias mappings условий/подключений, feedback, недатированную проектную историю и происхождение лидов/запросов.
- Новые назначения аккаунтов, временные замещения и история привлечения не создаются из неподтверждённых аналогий.

## Проверки

`schema_import_smoke.php`: отсутствие target writes при dry-run, полное ФИО/timestamps,
compatibility основной проект старой схемы, конвертация/происхождение, импорт всех версий условий без суммы, сохранение известной
ставки при повторе, nullable technology/grade, конфликты дат/ссылок и сверка Validate.
`unknown_rates_smoke.php`: неизвестная, нулевая и числовая ставки в ДДС/отчётном периоде; часы остаются доступны.

Обновление адаптера не пересчитывает старые отчёты и не запускает production-перенос автоматически.
После отдельного релиза применяются migrations Clients; затем оператор выполняет новый Dry run и повторный перенос Clients.

Канонические проверки: `canonical_clients_import_smoke.php` — один ClientMember, объединение совместимых интервалов, все aliases, отсутствие выдуманных проектов/назначений, доменный feedback с исходными NULL, source/target drift, rebase существующих mappings через lineage, повторные запуски и несовместимость неизвестных сумм.
