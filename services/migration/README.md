# Legacy Migration Service

Временный сервис переноса исторических данных из старых рабочих сервисов в IRLIX Services. Пока идёт миграция, сервис работает как закрытая административная панель. После завершения переноса runtime отключается, а код, mappings, runs, conflicts и отчёты остаются в репозитории/metadata для аудита и воспроизводимости.

## Принципы

- один migration-service, но независимый модуль на каждый бизнес-сервис;
- `employees`, `vacations`, `clients`, `timesheets` уже зарегистрированы; следующие модули добавляются без изменения ядра runner;
- каждый модуль можно `inspect`, `dry-run`, `migrate` и `validate` отдельно;
- mapping/conflicts/overrides/runs хранятся в приватной SQLite БД migration-service, а не в бизнес-схемах;
- API и background worker используют одну metadata DB в WAL-режиме;
- обычные business API и доменные side effects не вызываются при bulk import;
- неизвестные значения не угадываются: строка попадает в conflict report и пропускается.

## Metadata DB runtime

Служебная SQLite БД migration-service живёт только в приватном volume `/data`. Канонический путь задаётся отдельной переменной `MIGRATION_METADATA_DATABASE` и по умолчанию равен `/data/migration.sqlite`.

Migration Service не полагается на Laravel-default `database/database.sqlite`: service provider принудительно направляет default SQLite connection в `MIGRATION_METADATA_DATABASE`, API и worker используют один и тот же файл, а entrypoint создаёт файл и применяет migrations до запуска API.

Docker healthcheck обращается к `/api/migration/health`. Сервис считается healthy только если в metadata DB существуют обязательные таблицы `migration_runs`, `migration_connections`, `migration_run_events` и `migration_conflicts`. Это не позволяет выпустить контейнер в healthy-состоянии, если приложение случайно открыло пустую/не ту SQLite БД.

## Dashboard и доступ

В Dashboard migration-service отображается отдельной компактной карточкой рядом с Design System. Карточка и `/migration/` доступны только пользователю, у которого Employees `/access/me` возвращает специальную роль `platform-admin`.

Защита двухуровневая:

1. Portal скрывает карточку и страницу от остальных пользователей;
2. каждый `/api/migration/*` запрос независимо перепроверяет bearer token и роль через Employees.

Если Employees недоступен или роль `platform-admin` отсутствует, API работает fail-closed.

## Admin Console

Для каждого реализованного migration-модуля интерфейс показывает:

- параметры подключения к legacy PostgreSQL: host, port, database, user, password, SSL mode;
- `SSL mode` по умолчанию — `disable`; другой режим выбирается только если legacy PostgreSQL действительно требует TLS;
- признак, что пароль уже сохранён (сам пароль обратно в браузер никогда не отдаётся);
- отдельное подтверждение оператора, что используется выделенный read-only пользователь;
- кнопку проверки доступности сервера БД по TCP без PostgreSQL-аутентификации;
- кнопку проверки подключения и фактических PostgreSQL privileges;
- кнопки `Inspect`, `Dry run`, `Перенести`, `Validate`;
- текущий run, фазу, heartbeat, количество обработанных/mapped записей, warnings и conflicts;
- общую историю запусков;
- подробный event log, summary и список conflicts по выбранному run.

Форма подключения хранит пользовательский черновик независимо от фонового polling. Автообновление состояния migration-service не должно изменять или сбрасывать введённые host/port/database/user/password, выбранный SSL mode и read-only checkbox до явного сохранения или удаления подключения.

Любое пользовательское действие, которое ждёт ответ API (`Сохранить доступ`, TCP-проверка, проверка PostgreSQL-подключения, удаление доступа, постановка `Inspect`/`Dry run`/`Перенести`/`Validate` в очередь), переводит карточку модуля в явное pending-состояние: показывается индикатор ожидания и текст текущего действия, все поля и кнопки этого модуля временно блокируются, а повторный клик не создаёт второй запрос. Для фоновой операции блокировка продолжается после HTTP 202 до `completed`, `conflicts` или `failed` именно полученного run ID. Потеря связи не считается завершением: блокировка сохраняется, отображается повторная проверка статуса. Активные запуски опрашиваются каждую секунду, без активных — каждые 5 секунд. После перезагрузки страницы блокировка восстанавливается по серверному active_run. Сервер сериализует постановку задач через write-lock приватной SQLite metadata DB, запрещая параллельные запуски одного модуля даже из разных вкладок. Ручное `Обновить` аналогично блокируется и показывает собственный loading-state до завершения запроса.

`Проверить доступность сервера` использует введённые в текущую форму `host` и `port` и проверяет только возможность установить TCP-соединение. Эта операция не проверяет имя БД, логин, пароль, SSL negotiation или права PostgreSQL. Полная проверка выполняется отдельной кнопкой `Проверить подключение`.

Операции запускаются через background queue worker, поэтому браузерный HTTP-запрос не держится открытым и закрытие вкладки не останавливает перенос. Пока есть активный run, панель опрашивает состояние примерно раз в 2 секунды; в покое — реже.

Реальный `migrate` разрешается только если:

1. подключение сохранено;
2. live read-only verification прошёл успешно;
3. после этой проверки выполнен `Dry run`;
4. нет другого активного run этого сервиса;
5. platform-admin явно подтвердил реальный перенос.

## Хранение credentials

Legacy-пароли не пишутся в git, frontend storage или migration logs. Они шифруются отдельным `MigrationCredentialCipher` и сохраняются только в приватной metadata DB migration-service. API при первом health-запросе атомарно создаёт файл `/data/migration-credential.key` в общем приватном volume из постоянного `MIGRATION_APP_KEY`. API и worker читают этот файл при каждом шифровании и расшифровке; worker не может создать или заменить его. Laravel `Crypt`/`config('app.key')` не участвуют в новом формате. Новые payload имеют версионированный префикс `migration:v1:`.

`MIGRATION_APP_KEY` генерируется один раз на сервере при deploy, сохраняется в серверном `.env` и прокидывается в оба контейнера одновременно как `MIGRATION_APP_KEY` (а `APP_KEY` остаётся тем же значением для самого Laravel). `verify-migration.sh` проверяет обе переменные у API и worker против серверного `.env`, а затем проверяет расшифровку сохранённого ciphertext в каждом контейнере через общий файл ключа. После перехода со старого Laravel-Crypt формата оператор один раз повторно вводит пароль legacy-подключения; следующий save сохраняет его уже в `migration:v1`. Deploy сообщает о старом нечитаемом профиле, но допускает выпуск после проверки совпадения runtime ключей; новый формат обязан расшифровываться в обоих контейнерах.

Перед созданием run API проверяет доступность ключа и возвращает явную ошибку конфигурации, не оставляя ложный `failed` run «не удалось поставить задачу в очередь». `/migration/health` тоже требует доступного ключа в API-процессе. При каждом deploy, пока Migration Service запущен, скрипт сравнивает `APP_KEY` и `MIGRATION_APP_KEY` у обоих контейнеров с постоянным серверным ключом. Если у любого контейнера отсутствует ключ или контейнер отсутствует, API и worker пересоздаются вместе. При первом создании файла API допускает `APP_KEY` как совместимый источник, если отдельной переменной нет; после этого единственный источник нового cipher — файл в общем volume. Затем smoke запускает `php artisan migration:key-check` в обоих контейнерах; стенд считается проверенным только после этого. Значение ключа не выводится в логи.

При редактировании формы пустой password означает «оставить текущий пароль» только если сохранённое значение успешно расшифровывается. API сообщает `credential_status`, помечает нечитаемый профиль в панели и блокирует Verify/запуски до сохранения нового пароля. После save значение читается обратно из metadata DB и расшифровывается тем же cipher до ответа об успехе. Любое изменение параметров подключения сбрасывает статус verification, поэтому перед следующим запуском требуется повторная live-проверка.

После завершения всего проекта миграции credentials следует удалить из панели, runtime migration-service выключить, а ключ/volume архивировать или уничтожить согласно принятой политике хранения migration metadata.

## Критическое правило безопасности legacy DB

Migration-service никогда не должен иметь write-доступ к старым БД.

Для каждого legacy-сервиса DBA должен выдать отдельные credentials роли, которая имеет только минимально необходимое чтение. Migration-service сам не создаёт пользователей, не выполняет `GRANT/REVOKE` и не меняет настройки/схему старой БД.

Перед каждой операцией `LegacyReader` заново применяет сохранённый профиль подключения и проверяет его. Сохранённая отметка `verified` не заменяет live-check внутри run.

Приложение применяет несколько уровней защиты:

1. оператор обязан явно подтвердить использование read-only учётной записи;
2. соединение переводится в `default_transaction_read_only=on` только на уровне клиентской сессии;
3. каждый extraction query выполняется в отдельной PostgreSQL transaction с `SET TRANSACTION READ ONLY`;
4. установлены короткие `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`;
5. `LegacyReader` принимает только SQL, начинающийся с `SELECT`;
6. запрещены multiple statements, comments, locking SELECT, mutating keywords и известные side-effect PostgreSQL functions;
7. перед чтением проверяется, что роль не является `SUPERUSER`, не имеет `CREATEDB`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS`;
8. проверяется отсутствие `INSERT/UPDATE/DELETE/TRUNCATE/TRIGGER` на пользовательских таблицах;
9. проверяется отсутствие `CREATE` на базе/пользовательских схемах и `USAGE/UPDATE` на sequences.

Ожидаемый профиль legacy-пользователя — фактически SELECT-only. Если проверка блокируется, ответ должен показывать, какое условие ожидалось и какие запрещённые role attributes/privileges обнаружены у текущего PostgreSQL пользователя. Если не установлен UI-флаг `readonly_acknowledged`, права БД ещё не проверяются и ответ явно сообщает именно об этом.

Если любая проверка не проходит, операция блокируется. Обхода через `force` нет.

## CLI

CLI остаётся доступен для диагностики и аварийного администрирования. Он использует те же migration-модули и LegacyReader.

```bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.migration.yml \
  exec migration php artisan legacy:list
```

Inspect:

```bash
docker compose -f docker-compose.yml -f docker-compose.migration.yml \
  exec migration php artisan legacy:inspect employees
```

Dry-run:

```bash
docker compose -f docker-compose.yml -f docker-compose.migration.yml \
  exec migration php artisan legacy:migrate employees --dry-run
```

Реальный перенос и проверка:

```bash
docker compose -f docker-compose.yml -f docker-compose.migration.yml \
  exec migration php artisan legacy:migrate employees

docker compose -f docker-compose.yml -f docker-compose.migration.yml \
  exec migration php artisan legacy:validate employees
```

`vacations` запускается независимо теми же командами. На уровне данных Vacations ожидает, что соответствующие сотрудники уже существуют в новом Employees; Employees автоматически не запускается.

## Employees v1

Зарплаты исключены из текущего переноса: `salaries` не читается, SELECT на неё не требуется; `salary_history` не изменяется. Inspect, Dry run, Migrate и Validate не обрабатывают зарплаты. Ранее созданные mappings, ошибки/счётчики старых запусков и данные сохраняются для аудита. Новые запуски не показывают зарплатную таблицу и не создают её конфликтов. Проверенные точки отката по-прежнему сохраняют всю схему Employees, включая существующие зарплаты.

Переносятся/сопоставляются:

- departments (`yandex_id` -> alias -> normalized name);
- employees (login/email identity);
- department parent/manager/hr links после employee mapping;
- employment periods;
- employee access roles;
- current status/assignment history там, где её ещё нет.

`legal_entity`, employee-level `yandex_id` сохраняются в migration metadata, пока для них нет целевого доменного поля.

## Схемы от 07.10.2026

Vacations использует новый адаптер `VacationsV2Migration` для `users`, `vacations`, `approvers`, `changes`, `comments`, `attachments`, `business_dates`, `departments`, `activity_log`. Старые классы сохранены для аудита, но не зарегистрированы. Отсутствие связано с сотрудником через `vacations.user_id → users.id`; корпоративный login из email должен разрешиться однозначно в Employees, а существующий UUID mapping не должен ему противоречить. `from/to`, включительное число календарных дней, type/status переносятся в absences. Неизвестные значения и обратные диапазоны — ошибки. Working hours и неподтверждённая история сохраняются в приватных metadata. Согласующие переносятся в назначенную цепочку employee_review, документы скачиваются по старым ссылкам; подробности и ограничения ниже. Роли HR/AM/RN и даты решений не выдумываются.

Clients переносит клиентов, проекты, участников, условия/ставки, лиды с известным статусом, контакты/связи, юрлица, запросы/позиции/попытки и отчётные периоды. `users.external_key` сверяется с Employees mapping; login остаётся источником сопоставления. Для подключения без project_id создаётся стандартный default project соответствующего клиента. `rates.workload` — **часы в день**, подтверждено оператором; перенос 1:1 в `hours_per_day`, диапазон 0–24. Зашифрованная/нечисловая ставка, потеря точности, пересечение периодов, внешний member без подтверждённой личности, неизвестный результат закрытой попытки или коллизия существующей записи — конфликт. Вспомогательные справочники, json контактов, отзывы/заметки, поля юрлиц без нового аналога, files и polymorphic history сохраняются в metadata; они не считаются успешным импортом бизнес-строк.

Timesheets разрешает участника через уникальный login и единственное точное совпадение названия проекта/сотрудника в Clients (для default project — названия клиента). Совпадение числовых members.id между старыми базами не подтверждено оператором и не используется. Явный override `timesheets/members/legacy_id → target project_member_id` допускается только для того же сотрудника; неоднозначная/неизвестная строка project требует такого сопоставления. На стенде: `docker compose -f docker-compose.yml -f docker-compose.migration.yml exec migration php artisan migration:timesheets-member-map <legacy_member_id> <target_project_member_id>`, затем новый Dry run. Rate сопоставляется по участнику, точным датам и часам в день, а не по совпадению ID rate или названию проекта. Записи переносятся в `timesheet_entries` только внутри периода подключения, 0–24 часа и без округления сверх двух знаков. Дубликаты employee/project/date не складываются и не перезаписываются. Личные `time_records` без клиента/проекта, реплики календаря/отпусков, месячные confirmations без автора/времени подтверждения и per-entry `is_submitted` сохраняются в metadata с warning; они не превращаются в фиктивное финальное согласование или подтверждение всех проектов дня.

Перед реальной записью все строки проходят тот же полный preflight, включая прямые API/CLI вызовы; ошибка любого преобразования блокирует все target writes. Dry run выполняет те же преобразования с виртуальными IDs и не меняет target rows/mappings. Повторный импорт использует собственные mappings, существующие несопоставленные natural keys требуют явной reconciliation. Inspect показывает counts и фактические legacy enum values. Validate новых адаптеров проверяет полноту mappings, существование target rows, неизменность source payload и перенесённых target fields. Поля, сохранённые только как metadata, перечисляются в warning report.

## Добавление следующего сервиса

1. добавить legacy/target connection config;
2. создать класс в `app/Migration/Services`, реализующий `ServiceMigration`;
3. читать legacy только через `LegacyReader`;
4. зарегистрировать класс в `config/migration.php -> modules`;
5. добавить запись в `config/migration.php -> catalog`;
6. добавить safety/dry-run/validation cases и документацию;
7. никогда не добавлять общий `if ($service === ...)` в core runner.

Следующие ожидаемые модули: Recruitment/Specialists по мере получения схем старых БД.
## Проверить результат (Validate)

Операция не переносит и не исправляет данные. Employees сохраняет прежнюю проверку количества employees/departments. Vacations v2, Clients и Timesheets выполняют сверку mappings, текущего источника и целевых полей, описанную выше. Несовпадение даёт `conflicts`.

Проверка доступа worker основана на расшифровке сохранённого ciphertext (Laravel authenticated encryption), а не на сравнении fingerprint API и worker: только расшифровка проверяет рабочий ключ для конкретного сохранённого пароля. При каждом deploy `migration:credentials-check` выполняется отдельно в API и worker без подключения к legacy DB. Ошибки расшифровки отдельно указывают формат payload (migration:v1 либо Laravel Crypt). Секреты и ciphertext не возвращаются в UI.

## Права чтения legacy Employees

Роль подключения должна иметь `USAGE` на `public` и `SELECT` на `departments`, `employees`, `employments`, `employee_roles`, `users`, `subcontracts`, `comments` в старой БД `employee`. Кнопка «Проверить подключение» и safety-check перед каждым запуском проверяют весь этот набор и перечисляют недостающие права за один ответ. Права выдаёт DBA на legacy PostgreSQL; Migration Service не меняет GRANT/REVOKE. Не выдавать `INSERT`, `UPDATE`, `DELETE`, `CREATE` или права на sequences.

## Пульт переноса

Самостоятельный frontend: `apps/migration`, контейнер `migration-web` (8099), собственная сборка/CI и меню. Основная и единственная страница — пульт на `/migration/`; прежний интерфейс удалён. Старые ссылки `/migration/console[/]` автоматически переходят на основной адрес с сохранением параметров и hash после OIDC. Очередь Employees → Vacations, автоматические проверенные точки отката, Inspect/Dry run/Migrate/Validate, детализация таблиц и журнал. Формы сохраняют черновик и фокус при polling. API, безопасность checkpoint/restore и проверки описаны в [docs/MIGRATION.md](../../docs/MIGRATION.md#пульт-переноса).

## Подробности конфликтов периодов Employees

Ошибки и предупреждения по периодам работы сохраняют ограниченный контекст: ФИО, логин, legacy/target ID сотрудника, исходный период (ID, тип, начало, окончание) и незакрытые периоды новой БД. Даты показываются без преобразования часового пояса; дата-заглушка сохраняется как исходное значение, отдельно отмечается её трактовка как отсутствующего окончания.

Пульт предлагает «Сотрудник и периоды». GET `/api/migration/console/conflicts/{id}/details` доступен только `platform-admin`. Новые отчёты используют сохранённый контекст ошибки; существующие ошибки без контекста читают текущий источник через проверенный `LegacyReader` и target mapping, без повторного переноса и изменения отчёта. Текущие данные явно отделены от снимка на момент ошибки; отсутствие строки/сопоставления не трактуется как исправление. Чтение старых конфликтов блокируется при активном переносе/бэкапе и недоступности службы операций. Секреты, контакты и зарплаты в диагностический контекст не включаются.

## Приоритет старых данных Employees

Для сопоставленного сотрудника бизнес-поля карточки, включая дату трудоустройства и увольнения, обновляются по старой БД. Сопоставление использует сохранённый mapping, затем уникальное совпадение логина/рабочей почты без учёта регистра. Расхождение mapping с логином/почтой другого сотрудника остаётся `IDENTITY_COLLISION`. Пароли не читаются и не импортируются; существующие Keycloak ID, identity/onboarding status и дата создания целевого сотрудника сохраняются. Зарплаты по-прежнему исключены.

Периоды работы больше не пропускаются при наличии mapping. Существующий mapped или точно совпавший период сверяется с источником. Различающийся ручной незакрытый период заменяет даты начала/окончания и тип сотрудничества данными исходного незакрытого периода; если последний исходный период закрыт, ручной период закрывается его датой окончания. ID периода и локальные department/position сохраняются. Изменения фиксируются информационным событием `employment_period_updated` с предыдущими и применёнными значениями, без увеличения ошибок/предупреждений. Повторный перенос не создаёт дубликаты.

Несколько разных незакрытых периодов в самом источнике (`MULTIPLE_LEGACY_OPEN_PERIODS`), окончание раньше начала (`INVALID_EMPLOYMENT_DATES`) и неоднозначное/чужое сопоставление периодов (`EMPLOYMENT_MAPPING_COLLISION`) остаются конфликтами. Разные исходные интервалы не могут перезаписывать один и тот же целевой период. История прошлых ошибок сохраняется; новый результат появляется после нового запуска оператора. Dry run не изменяет целевые данные.

### Журнал с серверным фильтром

Ошибки таблицы ищутся во всём сохранённом отчёте, до пагинации. GET `/api/migration/console/runs/{run}/conflicts` поддерживает optional `severity`, `table`, `before` и возвращает страницу 200 сообщений, `total`, `cursor`, `more`. Алиасы entity/table разрешаются через `migration.table_entities`; авторизация сохраняется, отсутствующий запуск — 404, некорректные фильтры — 422. UI имеет независимые страницы фильтра, локальную загрузку/ошибку/повтор, защиту от запоздавшего ответа. Offline HTTP и browser regressions проверяют старые ошибки за новыми предупреждениями, пагинацию, переключение фильтра и сохранение draft/focus/caret.


### Повторный откат и объяснение ошибок

Точка отката остаётся доступной после восстановления. `restored` — информационная отметка, а не запрет повторного использования. Повторный откат требует прежнего подтверждения и проходит проверки контрольных сумм, состава схем, внешних FK, отсутствия активных операций и изменений другого сервиса после индивидуальной точки. Архив не изменяется при восстановлении.

В Vacations типы старой БД `paid`, `unpaid`, `maternity` соответствуют `paid_vacation`, `unpaid_vacation`, `maternity_leave`. Неизвестные значения остаются ошибками. Сопоставление сотрудника по корпоративному логину требует ровно одного совпадения: ошибки отдельно сообщают отсутствие сотрудника либо число совпадений и ID. Контекст ошибки содержит ID, email, тип и даты исходной записи, без паролей.

При ошибках пульт открывает фильтр «Ошибки», отключает автопрокрутку и показывает причину остановки и сводку ошибок независимо от страницы журнала. Проверенная таблица с ошибками имеет статус «Есть ошибки». Переход к истории выбирает сервис операции и сбрасывает фильтр таблицы. Запросы отчёта проверяют `operation_id`, чтобы повторно использованный после отката run ID не подменил старый отчёт новым. История операций сохраняется отдельно, но подробные отчёты хранятся в восстанавливаемой metadata SQLite: если отчёт утрачен, интерфейс явно сообщает об этом; восстановление старых подробностей не обещается.

История выбранного сервиса показывает его собственные операции и общие операции, которые затрагивали этот сервис (по `services` / этапам `runs`). Общий список доступен только во «Всех сервисах». При открытии общей операции из истории сервиса текущий сервис сохраняется.


### Итоги переноса и ручное сопоставление пользователей отпусков

Правая панель пульта переключается через общий UiTabs между «Итоги переноса» (по умолчанию) и «Журнал переноса». Итоги прокручиваются внутри панели и содержат причины остановки, сводку ошибок, счётчики и состояние до/во время/после запуска. Они больше не занимают место над обеими колонками. «Показать ошибки» и клики по счётчикам открывают журнал с соответствующим фильтром. Polling сохраняет вкладку, размер панелей, draft и фокус формы.

Подтверждённые соответствия Vacations: `sick → sick_leave`, `granted → confirmed`, `not_approved → rejected`, `approvers_definition → planned`, `on_approval → planned`. При выборе согласующих и ожидании согласования отпуск возвращается в «Запланирован»; старые согласования не превращаются в выдуманные новые этапы. Исходный статус сохраняется в metadata и аудите переноса. Сообщения неизвестных значений различают поля `type` и `status`.

Если логин пользователя отпусков отличается от текущего логина Employees, оператор открывает «Сопоставить сотрудника» в ошибке `users` журнала. Точный текущий логин проверяется, показываются ФИО, логин и ID, затем оператор подтверждает связь. GET `/api/migration/console/conflicts/{id}/employee-match?login=...` проверяет сотрудника; POST `.../employee-map` принимает проверенные `login`, `employee_id`, `source_fingerprint` и `confirmation=MAP USER <legacy_id>`. Доступ — существующие привилегированные роли Migration, без расширения прав. Неоднозначный/отсутствующий логин, противоречие UUID, старая ошибка, активный перенос/бэкап или недоступность ops блокируют сохранение.

Связь хранится приватно в `migration_overrides`: сервис `vacations`, entity `users`, конкретный legacy user ID → Employees ID. В note хранится fingerprint исходных email/UUID; изменения исходной личности требуют повторной проверки. Изменение текущего логина не ломает сохранённый Employees ID. Логины, пароли, Employees и Keycloak не меняются. Нельзя перепривязать уже импортированного пользователя к другому сотруднику без отката. Решение записывается в события отчёта с предыдущим и выбранным ID. Старые ошибки не редактируются; после сохранения требуется новый Dry run. При откате metadata сопоставления возвращаются к состоянию выбранной точки. Реальные соответствия не зашиваются в код, fixtures или документацию.


Технические ошибки ручного сопоставления показывают конкретный шаг: очередь, чтение исходного пользователя, поиск в Employees, проверка UUID или запись metadata. Ответ содержит `code`, `stage`, `diagnostic_id` и безопасный SQLSTATE при наличии. Ненайденный/неоднозначный логин остаётся ошибкой 422; активная операция — 409; технический сбой — 503. UI показывает шаг и код диагностики прямо в окне сопоставления. Серверный журнал по этому коду содержит только класс исключения, этап и SQLSTATE, без сообщения исключения, SQL, bindings, логинов или credentials. Регистр и обычные пробелы по краям игнорируются; похожие кириллические и латинские буквы автоматически не заменяются.


Release verification runs `migration:employee-query-check` in API and worker. It validates the exact Employees matching columns/functions and database permissions using an always-false WHERE condition, prints no employee data, never connects to legacy DB, then executes matching for one existing login without printing it, and emits only exception class, safe category and SQLSTATE on failure. PostgreSQL SQLSTATE is read from PDO errorInfo before the numeric driver exception code. No raw database error, SQL, bindings or credentials are printed.


Migration HTTP starts with `artisan serve --no-reload`: container TARGET_* and credential variables must be inherited by the child HTTP process. Laravel's default reloader strips non-passthrough variables when a .env exists, so CLI/worker may connect while HTTP cannot. The offline child-process regression reproduces stripping without the flag and validates preservation with it; CI also checks the production CMD. Credentials remain supplied through runtime environment, never copied into the image .env.

### Постоянное сопоставление логинов

Vacations хранит подтверждённые старый → новый login в отдельном томе `migration_identity`, доступном API/worker. Откаты business DB и metadata его не меняют. Текущий Employees ID определяется при каждом запуске: повторный импорт сотрудников с другими IDs поддерживается. Изменение нового логина требует обновления соответствия через окно сопоставления. `migration:identity-upgrade` сохраняет доступные прежние ручные решения; команда запускается проверкой стенда без вывода персональных данных. Том резервируется отдельно от точек бизнес-отката; подробности в `docs/MIGRATION.md`.

### Перенос документов и назначенной цепочки согласования Vacations

**Текущий режим:** перенос файлов временно отключён (`migration.vacation_documents_enabled=false`). `attachments` исключена из обязательных исходных таблиц, import/Dry run не проверяют ссылки и не скачивают/записывают файлы; итоговая validation не сверяет вложения. Код сохранён для будущего включения. Отпуска и согласующие продолжают переноситься. Уже сохранённые документы не удаляются; резервирование локальных файлов при создании точки отката сохраняется. Описанный ниже механизм документов действует только при включённом флаге.


Миграция добавляет старых согласующих в обычные `absence_approvals` нового сервиса: stage `employee_review` («Согласование сотрудниками»), конкретный Employees ID, без выдуманной роли HR/AM/RN. UUID согласующего разрешается через исходные users и их проверенное login-сопоставление; при отсутствии исходного user допускается подтверждённый Employees UUID mapping с существующим target. `order` становится sequence; одинаковый order — параллельная группа. `is_approved=true` становится approved, false — waiting (отказ из этого boolean не выводится). `acted_at`/acted_by остаются неизвестными. Текущий статус отсутствия сохраняет принятые aliases; `on_approval` и `approvers_definition` остаются planned. При явном submit такой цепочки активируется первая не завершённая sequence, затем следующие группы; все известные approved сохраняются. Последняя группа завершает обычный workflow статусом confirmed. Точные назначенные участники и platform-admin имеют существующее право согласования, роли остальных пользователей не расширяются. Возврат на доработку и редактирование planned сохраняют состав цепочки, но сбрасывают решения. В интерфейсе это обычная история/прогресс, отдельного исторического маршрута нет. Для обычных новых отпусков сохраняется HR → AM → руководитель → HR.

Вложения, связанные с Vacation по attachmentable_type/id, загружаются read-only по исходным HTTP/HTTPS URL. Поддерживаются Vacation/vacations и namespaced class Vacation. Остальные polymorphic objects сохраняются с warning и не прикрепляются к чужим отпускам. Все документы предварительно скачиваются во временные файлы до target writes; Dry run не пишет в target DB/хранилище. Реальный проход использует проверенные staged bytes и кладёт их в общий `vacations_files`, который Migration API/worker монтируют как `/vacation-files`, Vacations — `/app/storage/app/vacations`. Применяются лимит 10 МБ, timeout 30 секунд/соединение 5 секунд, максимум 5 переходов; каждый redirect снова проверяется и DNS адрес фиксируется для соединения. Loopback, link-local/metadata, userinfo и не-HTTP схемы запрещены. Частная сеть допускается только для legacy DB host или явно заданных `MIGRATION_LEGACY_FILE_HOSTS`; bearer tokens платформы в старое хранилище не передаются. HTTP ошибки, пустые/большие документы, HTML/JSON вместо файла блокируют preflight с ошибкой конкретного attachments ID. Исходные URL/имя и row остаются в приватной metadata, публичные CI логи их не содержат. При изменении уже перенесённого согласования/документа в новой системе повторный импорт отказывается его перезаписывать.

Имена новых и переносимых документов: `Заявление — <ФИО> — <тип> — <YYYY-MM-DD>_<YYYY-MM-DD> — <короткий ключ>.<расширение>`; для больничного/декрета/отгула — «Документ». Кириллица сохраняется, недопустимые символы/разделители заменяются, длина ограничена 255 UTF-8 bytes. 12 hex символов ключа предотвращают коллизии; для миграции ключ детерминирован источником/legacy attachment ID/URL, для загрузки — UUID. В хранилище и Content-Disposition используется одно читаемое имя. `source_original_name` хранит исходное имя, `external_url` — исходную ссылку импортированного файла; размер/MIME проверяются по скачанным bytes. Уже перенесённые основные отпуска можно дополнить повторным импортом без отката, если mappings сохранены и новых пользовательских изменений нет.

Новые точки пульта со scope vacations/all включают `vacations-files.tar.gz`, защищённый checksums и закрытым серверным каталогом. Restore восстанавливает bytes и metadata; перед запуском Vacations применяет текущие DB migrations, чтобы старые точки работали с новым кодом. Старые точки без архива документов не обещают восстановления потерянных файлов и не очищают существующий volume. Независимый справочник login-сопоставлений остаётся вне rollback. Clients в этой задаче не меняется. Comments/changes/activity_log/calendar продолжают храниться в metadata; недостоверные события и даты согласования не реконструируются.


### Clients: legacy-статусы, причины закрытия и диагностика подготовки · 2026-10-08

Старые коды лидов поддерживаются наряду с русскими статусами: `new → Новый лид`, `initial → Первичный контакт`, `clarification → Уточнение потребностей`, `ignore → Клиент в игноре`, `failed → Сделка закрыта - Отказ`. Другие неизвестные коды остаются конфликтами. Исходная запись сохраняется в приватной metadata.

`attempt_result → results.title` содержит также причины отказа, а не только успех/неудачу. Известные причины из действующего `RequestWorkflowController::FAILURE_REASONS` означают `Закрыт: неудача` и сохраняются в обычном `failure_reasons`; несколько причин одного отрицательного результата допустимы. Явные успех/неудача поддерживаются. Сочетание успеха и отказа и неизвестный title блокируют перенос. Отсутствующий результат обрабатывается по отдельному явному статусу попытки (см. временную политику ниже). Комментарий сохраняется отдельно; даты и причины не выдумываются.

Диагностика условий различает отсутствующую сумму, нечисловое значение, диапазон/точность, отсутствующий грейд и ссылку на справочник; указывается конкретное поле без исходной суммы или шифртекста. Нечисловое значение само по себе не доказывает шифрование. Ошибки зависимых строк Clients имеют `DEPENDENCY_BLOCKED` с таблицей, ID и причиной зависимости; `blocked_count` является подмножеством ошибок, а не дополнительным числом ошибок.

Dry run для адаптеров SchemaMigration считает `ready_count` и `processed_count`, но не `success_count`: проверенная строка не является импортированной. Повторная обработка и сохранение дополнительных полей той же строки в metadata не увеличивают число обработанных строк. Пульт показывает «Готово к переносу» и «Только metadata», счётчик готовых строк и зависимостей, до 40 групп предупреждений по таблице/коду/причине; полный журнал с ID и исходной metadata сохраняется. Старые отчёты не пересчитываются: для новых счётчиков нужен новый Dry run.

Ручное сопоставление пользователей доступно также для Clients через существующие `employee-match` / `employee-map`. Проверяются последний ошибочный Dry run, подтверждение, fingerprint email/external_key, уникальный текущий login Employees, UUID, отсутствие активных операций и запрет перепривязки уже импортированного user к другому Employees ID. Постоянные login-связи разделены по сервису и источнику; решение Clients не влияет на Vacations и переживает бизнес-откат. Внешние участники без проверенной личности остаются конфликтами; этот экран сопоставляет users, а не создаёт фиктивных сотрудников/подрядчиков.

Offline SQLite/HTTP regressions проверяют коды лидов, несколько причин отказа, неоднозначность, числовые поля, отсутствие target writes в Dry run, идемпотентность, точные счётчики, группировку предупреждений и изоляцию identity-связей Clients/Vacations.

### Clients: общий список логинов и второй разбор preflight

По решению пользователя Clients использует подтверждённый список Vacations для того же нормализованного старого корпоративного логина. Читается реестр текущего настроенного источника Vacations; legacy numeric user ID не переносится между сервисами. Собственное сопоставление Clients сохраняется отдельно. Если оба реестра указывают разные текущие логины, возникает `IDENTITY_ALIAS_COLLISION` с обоими значениями: ни одно не выбирается автоматически. Текущий login должен единственным образом разрешаться в Employees и согласовываться с UUID. Если уже импортированный users mapping указывает другой Employees ID, `IDENTITY_MAPPING_COLLISION` запрещает тихую перепривязку и требует проверки/отката Clients.

Дополнительные legacy статусы: `leads.active → Активные переговоры`, `leads.proposal_sent → КП отправлено`. `positions.under_consideration/waiting/no_candidates → Открыт`: позиция без closed_at остаётся открытой, а отображаемое «В работе» новый Clients вычисляет по попыткам; эти коды не создают выдуманных попыток или закрытий.

Закрытые попытки без attempt_result и явного терминального attempts.status восстанавливаются по согласованному правилу дат: заполненный started_at означает успех, иначе — неуспех на последнем достигнутом этапе. Сочетание явного успеха и отказа остаётся `AMBIGUOUS_ATTEMPT_RESULT` с названиями результатов. Нечисловая сумма с распознаваемой base64 JSON-структурой Laravel iv/value/mac имеет `ENCRYPTED_AMOUNT`; распознавание формата не расшифровывает и не доказывает валидность payload. Ключи, суммы и шифртекст не включаются в журнал. Остальные нечисловые значения сохраняют `NON_NUMERIC_AMOUNT`.

`EXTERNAL_MEMBER_UNRESOLVED` показывает исходные memberable_type/memberable_id без создания фиктивного сотрудника. `SOURCE_PERIOD_OVERLAP` показывает ID и границы обеих пересекающихся исходных записей; периоды не обрезаются и не объединяются автоматически. Эти подробности доступны только через приватный журнал с существующей авторизацией.

Открытые вопросы для завершения переноса: восстановление отсутствующих результатов попыток; доступ к старому ключу Clients или расшифрованному числовому экспорту; проверенные грейды/технологии отсутствующих ссылок; идентичности внешних участников; выбор корректных исходных записей пересекающихся периодов. До получения достоверных данных полный preflight блокирует Import и не изменяет target. После выпуска нужен новый Dry run; количество оставшихся ошибок заранее не обещается.

Синтетические offline regressions проверяют общий список при разных legacy ID, коллизию двух реестров, UUID, запрет перепривязки импортированного пользователя, дополнительные статусы, разделение отсутствующего/противоречивого исхода, распознавание encrypted payload и обе границы пересечения.

## Партнерский специалист · 2026-10-08

При добавлении подключения форма использует общий `UiSegmentedControl` «Сотрудник / Партнерский специалист». Первый вариант сохраняет дерево Employees; второй требует непустое ФИО до 255 символов. В создании попытки используется то же название и переключение; обязательный CV сохраняется.

Clients хранит партнерскую личность в `partner_specialists` с собственным ID и ФИО. ProjectMember ссылается ровно на одного сотрудника (`specialist_id`) либо партнера (`partner_specialist_id`), что защищено PostgreSQL CHECK/FK и отдельными уникальными связями с проектом. ID двух справочников никогда не смешиваются. Ручное добавление создает новую личность; совпадение ФИО не объединяет людей. Новые условия создаются через существующего участника; смена проекта сохраняет его личность.

Подключение из внешней попытки использует ее ФИО и сохраняет source_attempt_id; повторная операция по той же попытке использует существующего участника. Пересечение условий проверяется по типу и ID личности во всех проектах одного клиента. Неудачная операция откатывает также создание партнера. Права и scope остаются существующими members/manage и клиентскими ограничениями; карточка показывает «Партнерский специалист».

Партнер не получает учетную запись Employees, корпоративную авторизацию или отпуск. Каталог подключений для Timesheets включает только сотрудников: Timesheets сейчас оперирует employee_id и не поддерживает ввод часов партнеров. ДДС сохраняет календарный план партнера по условиям, а фактические/подтвержденные часы не подменяет часами сотрудника с таким же числовым ID. В отчётном периоде партнерская строка не ведёт на employee-фильтр Timesheets.

Migration переносит `subcontracts → partner_specialists` и `members.memberable_type=subcontract` через `memberable_id`. ФИО берется из full_name либо surname/name/patronymic. Повторный перенос использует исходный ID; одинаковые имена не являются ключом. Неизвестный тип, отсутствующая ссылка или ФИО блокируют полный preflight; сведения старой записи сохраняются приватно. Поддержка иных кодов/структуры старого справочника требует проверки нового Dry run, без угадывания личностей.

Проверки: `partner_members_smoke.php` входит в backend image checks; SQLite проверяет раздельные ID, одинаковые ФИО, условия, пересечения, транзакционный откат, подключение из попытки и смену проекта. PostgreSQL constraints применяются штатной миграцией. `timesheet_assignments_smoke.php` проверяет исключение партнеров из employee-каталога. Browser regression `apps/clients/tests/partner-members.browser.cjs` проверяет переключение формы, дерево сотрудников и partner payload на синтетических API; запускается на локальном preview с CLIENTS_PREVIEW, PLAYWRIGHT_MODULE и CHROMIUM_EXECUTABLE. Migration regression проверяет dry-run без записи, перенос партнеров и повторное использование mappings.


## Clients: временное исключение ставок и отдельный исход попытки · 2026-10-08

До получения APP_KEY старого Clients таблица `rates` исключена из доменного импорта целиком: условия подключения `member_terms`, их суммы, workload, грейды и технологии не создаются. `reporting_period_rate` также отложена. Предлагаемая ставка `attempts.rate` не импортируется; для новой попытки поле остаётся NULL, существующая ставка не стирается. Нулевые или выдуманные суммы не подставляются. Строки сохранены только в приватной migration metadata с явным предупреждением, без successful mappings. Активная политика находится в `migration.deferred_tables.clients`; старый путь импорта сохранён и протестирован для последующего возвращения после реализации проверенной расшифровки. Validate исключает отложенные таблицы из обязательной полноты и возвращает их отдельно в `deferred` с причиной и числом исходных строк.

Клиенты, проекты и участники импортируются, но условия и периоды подключений из rates пока отсутствуют. Поэтому исторический Timesheets, требующий точного совпадения условий Clients, для таких подключений нельзя переносить до возвращения условий. Уже перенесённые условия и ставки не удаляются этой политикой.

Статус попытки и результат/причина — разные поля. Явный legacy `attempts.status` (`success`/`Успех`/`Закрыт: успех`, `failure`/`failed`/`fail`/`Неуспех`/`Неудача`/`Закрыт: неуспех`/`Закрыт: неудача`) определяет финальный исход. Успех без результата сохраняет пустую причину; явная неудача без результата получает отдельную причину «Причина не указана в старом сервисе», включённую в каталог Clients. Недостающий closed_at не выдумывается. Известные старые результаты поддерживаются для источника без явного статуса; противоречие статуса и результата блокирует перенос. При отсутствии обоих используется согласованное правило дат только для закрытой попытки (closed_at заполнен). Inspect показывает `attempts.status` и имена доступных полей attempts; конфликт отдельно указывает, присутствует ли поле status.

Ненайденные технологии позиций остаются блокирующими до подтверждённого заполнения/сопоставления пользователем; исходный legacy ID виден в диагностике. Добавление технологии в новый Specialists само по себе не восстанавливает отсутствующую ссылку старого Clients. Пересекающиеся отчётные периоды не объединяются, не обрезаются и не отбрасываются: требуется решение по обеим записям с датами и статусами. Полный предварительный проход продолжает блокировать любые целевые записи при нерешённых коллизиях.


### Откат: окружение действующего контейнера и диагностика этапа

Одного image ID недостаточно: после restore нельзя заново собирать environment/сеть/тома из базового compose, который может отличаться от действующей выкладки. До остановки writers фиксируются настройки действующих сервисов; отдельный `php artisan migrate:status` проверяет их работоспособность. Затем migrations выполняются в контейнере того же образа с теми же environment, рабочим каталогом, пользователем, сетью и томами, без опубликованных портов и без pull/build. Environment передаётся через локальный временный файл 0600 и удаляется после команды; в журнал он не выводится. Отсутствующий контейнер, неоднозначная сеть или неподдерживаемый environment блокируют откат до остановки.

В `/snapshots/console/.restore-status.json` сохраняется последний этап и подтверждённость восстановления PostgreSQL, metadata и схем. Исход транзакции отмечается отдельно: `unmodified`, `unknown`, `rolled_back`, `committed`. Полный traceback записывается только в приватный `.restore-error.log` с режимом 0600. Console state возвращает allowlisted технические признаки без traceback/environment; сообщение неудачного отката называет этап. Перед остановкой ошибки проверки не выключают сервисы. Неизвестный исход транзакции или ошибка после COMMIT по-прежнему требует операторского восстановления, а не слепого запуска writers.

Unit regressions проверяют копирование действующего окружения, приватность tempfile/диагностики и отказ runtime-check до остановки. CI дополнительно поднимает отдельные синтетические Docker/PostgreSQL контейнеры: намеренно рассогласует базовый compose с действующим контейнером, проверяет snapshot, успешный и повторный restore, отказ несовместимого старого снимка без остановки и ошибку migrations после COMMIT с сохранением точного этапа. Этот тест использует только временные синтетические данные, не подключается к production и является частью обязательного `CI verified` при изменении migration-ops.


Откат Clients сохраняет Migration API для операционного пульта. Worker и соответствующие writers останавливаются; middleware по безопасному mirror `/ops/restore-status.json` закрывает доступ к восстанавливаемой SQLite и новые команды. Shared/exclusive metadata lock дожидается уже начавшихся запросов без блокирования single-process API. GET console/state сохраняет прежнюю авторизацию; health сообщает maintenance без чтения SQLite. UI во время maintenance опрашивает только ops state. При сомнительном COMMIT или частичном восстановлении данные остаются закрытыми до операторского восстановления.


### Clients: исход и этап попытки по датам

Если closed_at заполнен, а терминальный attempts.status и связанные attempt_result отсутствуют, заполненный started_at означает фактическое подключение и «Закрыт: успех». Без started_at переносится «Закрыт: неудача»: interviewed_at → closed_from_status «Интервью пройдено», иначе cv_sent_at → «CV отправлено», иначе «Новая». Для явной неудачи с started_at этап — «Ожидает подключения». Этап записывается для всех неуспешных попыток, в том числе с известными причинами. Причина без исходного результата — «Причина не указана в старом сервисе»; конкретный отказ не выдумывается. started_at сохраняется в connection_date.

Явные терминальные статусы и известные результаты имеют приоритет над восстановлением по датам. Их противоречия и неизвестные названия результатов не подавляются. Незакрытая попытка без терминального статуса остаётся активной, даже с started_at. interviewed_at используется как признак пройденного интервью; несуществующие записи интервью и история событий не создаются. Каждый восстановленный исход отмечается предупреждением INFERRED_ATTEMPT_OUTCOME с новым статусом, этапом и безопасной диагностикой исходных полей. Нужно повторить подготовку и Dry run; старые отчёты не пересчитываются.


### Исторические позиции без технологии

Пустой legacy positions.technology_id (NULL или пустая строка) переносится как positions.technology = NULL с предупреждением MISSING_POSITION_TECHNOLOGY. Связанные попытки не блокируются отсутствием технологии. Неизвестный непустой ID по-прежнему блокирует перенос: отсутствие справочной записи нельзя подменять отсутствием технологии. Новая БД допускает NULL для исторических позиций; обычные API создания/изменения технологии сохраняют обязательный выбор. Интерфейс показывает «Технология не указана» без добавления вымышленного значения в каталог Specialists. Пересечения reporting_periods остаются блокирующими и требуют отдельного решения по ID и диапазонам дат.
