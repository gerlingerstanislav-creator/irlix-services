# frontend — интерфейс и пользовательское взаимодействие

**Условия:** затронут внешний вид, маршрут, состояние формы/таблицы или взаимодействие. Designer как отдельный исполнитель нужен для нового/сложного UX или независимого визуального контроля, не автоматически для любого CSS.

**Источники:** целевой экран/компонент, критерии сценария, относящиеся контракты [FRONTEND](../../horizontal/FRONTEND.md), `packages/ui/README.md`, при необходимости дизайн-спецификация ideas. Не читать соседние сервисы ради случайного визуального образца.

**Действия:** найти существующий shared-компонент и проверить локальность изменения; использовать @irlix/ui, токены и принятую оболочку. Не создавать дубли базовых контролов. Для изменённого взаимодействия проверить loading/empty/error/success и отсутствие прав, клавиатуру/фокус и подходящие размеры экрана. Сохранить существующие eligibility и permissions. Не менять бизнес-смысл косметической правкой.

При новом UX сначала определить сценарий/состояния и сравнить значимые варианты, затем реализовать. При изменении shared UI подключить integration, обновить витрину/контракт и проверить потребителей согласно горизонтальному регламенту. Локальная раскладка не даёт права переопределять базовый вид общего компонента.

**Результат/evidence:** реально наблюдённый интерфейс в браузере/рендере, версия, viewport и затронутые состояния; сборка и релевантные тесты. Статический просмотр CSS не является визуальной проверкой. Если нужный визуальный контроль недоступен, это NOT TESTED; нельзя объявить визуальную приёмку пройденной.

**Границы:** не расширять дизайн-систему без обоснования повторяемого паттерна. Неясный пользовательский смысл → analysis; новые права/API → security/backend. Production не использовать как тестовую БД.
