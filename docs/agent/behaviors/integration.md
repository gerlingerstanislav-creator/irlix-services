# integration — зависимости и совместимость

**Условия:** межсервисный API/event, общий UI/auth, CI/runtime/инфраструктурный контракт или несколько непосредственно затронутых сервисов.

**Источники:** конкретный контракт и прямые потребители, [INTEGRATIONS](../../horizontal/INTEGRATIONS.md), относящиеся части архитектуры/CI/deployment. Не обходить весь граф сервисов рекурсивно.

**Действия:** определить владельца и потребителей, сравнить входы/выходы/permissions, совместимость версий и сценарии отказа. Для событий учесть повторную доставку, retry/dead-letter; для shared-компонента проверить затронутые приложения. Согласовать write scopes исполнителей и общий контракт до параллельной реализации.

Структурное изменение сервиса требует актуализации service map, catalog, registry/routes и проверки карты согласно горизонтальному регламенту. Не выдавать статическую карту за runtime health.

**Результат/evidence:** перечень реально затронутых границ, проверки контракта/потребителей, способ совместимого внедрения, версия и ограничения. Непроверенную соседнюю систему не помечать PASS.

**Границы:** существенное изменение подхода/контракта → analysis и согласование; данные → data, полномочия → security. При смысловом конфликте сохранить обе исходные версии и вынести конкретное решение, не выбирать ours/theirs автоматически.
