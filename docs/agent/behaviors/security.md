# security — доверие и полномочия

**Условия:** auth/permission/scope, доверенные входы, sensitive API/data, upload/export/webhook или инфраструктурная граница. Для обычного backend — короткий safety-pass; чистая локальная UI-правка без такого влияния не требует отдельного security-аудита.

**Источники:** затронутые потоки и серверные проверки, [SECURITY](../../horizontal/SECURITY.md), актуальные access-контракты и относящийся раздел AUTH. Секреты не включать в передаваемый контекст/отчёт.

**Действия:** проверить источник полномочий, permission + scope/ownership, list/detail/update/bulk/export по фактическому влиянию, IDOR/повышение привилегий и обработку отказов. UI-скрытие не заменяет серверного запрета. Проверить platform-admin и явно заданные исключения по проектному регламенту. Проверить diff и fixtures на реальные/чувствительные данные.

Риск формулировать через конкретную границу, доступный путь и последствия. Не добавлять MFA/WAF/шифрование или обход существующих ограничений ради формальной безопасности. При ротации/удалении ключей проверить, какие данные зависят от них и согласовано ли сохранение/потеря.

**Результат/evidence:** подтверждённые findings с серьёзностью, минимальные меры, позитивные/негативные проверки, версия и остаточный риск. Гипотезу не выдавать за эксплуатацию; отсутствие проверки — NOT TESTED.

**Границы:** активное сканирование/эксплуатация и изменение production требуют соответствующих полномочий. Недоступная проверка существенной границы блокирует безусловную готовность; выполнить доступную безопасную работу и передать конкретный остаток. Изменение модели доступа/допустимого риска согласовать, а исправление в рамках принятого контракта продолжать самостоятельно.
