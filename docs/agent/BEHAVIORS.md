# Каталог подключаемого поведения

Сначала оценка по [WORKFLOW](WORKFLOW.md), затем только необходимые модули. Это сочетаемые компетенции, не обязательная очередь ролей. Каждый модуль содержит условия, источники, действия, evidence и границы. Название роли без этих действий ничего не подтверждает.

| Модуль | Подключать по обнаруженным фактам | Требуемый результат |
|---|---|---|
| [analysis](behaviors/analysis.md) | Неясная цель/правило, новое поведение с неопределённостью, существенное решение, конфликт источников | Критерии, инварианты, проверенные предпосылки, варианты и нужные решения |
| [frontend](behaviors/frontend.md) | Изменение UI или пользовательского взаимодействия | Совместимый UI и фактическая визуальная/интерактивная проверка |
| [backend](behaviors/backend.md) | Изменение доменной логики, API, обработки ошибок/фоновых задач | Корректный контракт и проверка затронутого поведения |
| [data](behaviors/data.md) | Изменение хранения, SQL, ORM, схемы, импорта или истории | Инварианты, целостность, совместимость, безопасная миграция и сверка |
| [security](behaviors/security.md) | Изменение auth/permissions, trust boundary, sensitive data flow | Проверка серверных полномочий/границ и обоснованные негативные проверки |
| [integration](behaviors/integration.md) | Общий компонент, межсервисный контракт, инфраструктура или runtime-зависимость | Проверенные прямые потребители и совместимость |
| [verification](behaviors/verification.md) | Любой результат, который заявляется проверенным; глубина по влиянию | PASS/FAIL/NOT TESTED/N/A с версией, охватом и evidence |
| [delivery](behaviors/delivery.md) | Запись в Git, PR, CI, разрешённый выпуск | Достижение согласованной точки интеграции/выкладки |

Для обычного backend короткая проверка наличия auth/data границ обязательна; самостоятельный глубокий security-аудит нужен по найденному влиянию. Для нового поведения определить критерии до разработки, даже если отдельный аналитик не нужен. Для любого UI проверить затронутый вид/сценарий, даже если отдельный Designer не нужен.

Если задача не совпадает с примерами, применить тот же способ оценки, найти нужные компетенции и явно назвать отсутствующее знание. Не считать каталог исчерпывающим списком пользовательских задач. Предлагать новый модуль только при повторяемой доказанной потребности, после согласования изменения процесса.
