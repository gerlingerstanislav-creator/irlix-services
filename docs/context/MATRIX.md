# Матрица рабочих контекстов

**Не набор заранее загружаемых документов.** Контекст = `глобальные инварианты + выбранные технические компетенции (горизонтали) + один домен (вертикаль) + затронутый сценарий + только доказанные внешние контракты`.

## Правило выбора

1. Идентифицировать намерение задачи и точный сервис по URL/пути/сущности. Без чтения файлов можно получить структуру каталогов и заголовки.
2. Выбрать минимальный **набор горизонталей**: `frontend`, `backend`, `database`, `security`, `integration`, `qa`, `delivery`. Например, UI/CSS не выбирает database.
3. Найти **вертикаль** — `docs/context/<service>.md` и продуктовый раздел `ideas/company-internal-services-81-2.4/services/<service>/`. Не читать всю вертикаль.
4. Уточнить **сценарий/символ**. Читать только нужные заголовки/диапазоны, код функции, тесты. Для связанной сущности сначала открыть контракт, не весь соседний сервис.
5. Зафиксировать прочитанные материалы и обоснование каждого расширения в ходе выполнения сложной задачи; для Fast-правки отдельный отчёт о контексте не нужен.
6. Дополнительные методики, Skills, регламенты Git/CI/QA применяются по фактическому событию и текущим решениям; матрица не отменяет ни одной обязанности `AGENTS.md`.

## Логические горизонтали (не дублировать правила)

| Горизонталь | Источник истины / точка входа | Подключать когда |
|---|---|---|
| frontend | `docs/horizontal/FRONTEND.md`; `packages/ui/README.md` | UI, общие компоненты, router или визуальный контракт |
| backend | `docs/horizontal/BACKEND.md`; `docs/ARCHITECTURE.md` | доменная логика, Laravel/FastAPI, API |
| database | `docs/horizontal/DATABASE.md`, конкретные миграции и модели сервиса | изменение схемы, ORM, сохранение, SQL |
| security | `docs/horizontal/SECURITY.md`, `docs/AUTH.md` | auth, access, sensitive boundary; короткий safety-pass при backend |
| integration | `docs/horizontal/INTEGRATIONS.md` + конкретный endpoint/DTO/event | межсервисное взаимодействие |
| qa | `docs/QA.md`, точные тесты изменяемой функции | подбор тестов/регрессия/независимая проверка |
| governance | `docs/horizontal/GOVERNANCE.md` | неоднозначности, продуктовые требования, документация, критическая оценка |
| delivery | `docs/BRANCHING.md`, `docs/policies/GIT_RELEASE.md`, `docs/CI.md`, `docs/DEPLOYMENT.md` | Git, PR, CI, release, infra |

Канонические горизонтальные регламенты: `docs/horizontal/{FRONTEND,BACKEND,DATABASE,SECURITY,INTEGRATIONS,GOVERNANCE}.md`. Открывать только соответствующие разделы; прежний `docs/policies/ENGINEERING.md` — индекс совместимости со старыми ссылками.

## Вертикали

Текущие точечные указатели: `clients`, `timesheets`, `employees`, `migration` в `docs/context/`. Остальные домены используют прямые пути `apps/<service>/`, `services/<service>/` и сервисные документы в `ideas` с исключениями `Employees=apps/web`, `CV=services/cv-converter`; искать файлы перед чтением.

## Третья координата — сценарий

Сетка горизонталь × вертикаль **не создаёт файл для каждого пересечения**. Сценарий выбирает конкретную секцию внутри ячейки. В `MANIFEST.json` перечислены маршруты и условия загрузки, но не автоматические обязательные чтения. Любой manifest — навигация, не источник продуктовых требований и не точная спецификация БД.

### Проверочные трассы

| Изменение | Читать | Не читать |
|---|---|---|
| Ширина ячейки Timesheets | Fast; `apps/timesheets`: компонент и локальный тест; при shared-компоненте только его контракт `packages/ui` | ТЗ целиком, БД Timesheets, Clients/Vacations |
| Локальный API Clients | Standard; конкретный controller/request/model, бизнес-правило и тест; backend; security-pass | frontend всех сервисов и целиком `docs/ARCHITECTURE.md` |
| Clients ↔ Timesheets ↔ Migration | Deep; модель связи, time records, legacy mapping, конкретные интеграционные контракты, rollback/test | Recruitment, Finance, полные ТЗ не затронутых сервисов |

## Ограничения

- Путь в индексе указывает **где искать**, а не гарантирует существование модели/функции или актуальность бизнес-правила.
- Никакой автоматической загрузки всех горизонталей сервиса или всех разделов документов.
- Без перезаписи регламентов: рефакторинг канонических правил допустим только с таблицей соответствия и проверкой ссылок.
- Приватный `ideas` не цитировать дословно в публичной документации и CI.
