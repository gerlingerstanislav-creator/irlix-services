# Historical data migration

Исторические данные старых рабочих сервисов переносятся отдельным временным `services/migration`. Это контролируемое исключение из обычного запрета межсервисной записи: migration-service существует только на период cutover, получает target credentials отдельно по каждому новому сервису и после окончания миграции отключается.

## Архитектура

Реализованы четыре независимых источника: legacy Employees, Vacations v2, Clients и Timesheets. Migration Service читает их через LegacyReader и пишет только в соответствующие target schemas. Private SQLite хранит runs, mappings, overrides и conflicts. Очередь: Employees → Vacations → Clients → Timesheets; Timesheets зависит от mappings Employees и Clients.

Модули независимы и запускаются отдельно. Общий runner знает только контракт `ServiceMigration` и registry классов. Добавление следующего сервиса не должно менять существующие importers.

## Legacy connection diagnostics

Admin UI разделяет сетевую диагностику и полную проверку legacy PostgreSQL:

1. **Проверить доступность сервера** — выполняет TCP-проверку текущих `host:port` из формы. Она не требует сохранения формы и не проверяет логин, пароль, database или read-only права.
2. **Проверить подключение** — работает по сохранённому connection profile, подключается к PostgreSQL и выполняет полный safety-check роли через `LegacyReader`.

Для legacy-подключений SSL mode по умолчанию — `disable`. Оператор может явно выбрать другой режим, если конкретный legacy PostgreSQL требует TLS.

Поля connection form считаются пользовательским draft. Фоновый polling состояния migration-service не должен заменять введённые `host`, `port`, `database`, `username`, `password`, `sslmode` или read-only checkbox значениями с сервера. Draft очищается после успешного сохранения либо удаления подключения.

## Legacy DB safety invariant

Ни один migration module не получает raw Laravel connection к legacy DB. Единственная точка чтения — `LegacyReader`.

Обязательные invariants:

- только выделенный DB user без effective write privileges;
- явный operator acknowledgement read-only credentials;
- `default_transaction_read_only=on` на client session;
- каждый запрос в отдельной `READ ONLY` transaction;
- только fixed `SELECT` queries;
- hard statement timeout;
- elevated/superuser legacy role блокируется;
- отсутствие скрытого `force`/unsafe режима.

Полная safety-проверка учитывает не только прямые `GRANT` роли, но и эффективные PostgreSQL privileges, включая унаследованные через другие роли или `PUBLIC`. Поэтому пользователь, которому напрямую выдан только `SELECT`, всё равно может быть отклонён, если фактически имеет write/create/sequence privileges.

Migration-service никогда не выполняет schema migrations, DDL, cleanup, locks или data correction в legacy DB. Любая коррекция исходных данных выполняется отдельно владельцами legacy-системы, после чего migration запускается повторно.

## Cutover

Рекомендуемая последовательность для каждого сервиса:

1. проверить доступность legacy server;
2. проверить PostgreSQL connection и read-only safety;
3. `inspect`;
4. `dry-run`;
5. разобрать conflicts и при необходимости добавить explicit override;
6. test migration в очищенную/тестовую target среду;
7. `validate` + reconciliation;
8. production bulk migration;
9. legacy read-only window;
10. final delta (когда для конкретного сервиса будет реализован delta strategy);
11. final reconciliation;
12. отозвать target/legacy credentials migration-service и остановить его.

Код мигратора и private migration metadata не удаляются сразу после cutover: они нужны для аудита соответствий legacy_id -> target_id.
## Статусы фоновых операций

Если PHP не видит постоянный ключ миграции, API отклоняет запуск до создания run с явной ошибкой конфигурации. При отсутствии отдельной переменной `MIGRATION_APP_KEY` допускается только тот же постоянный `APP_KEY` контейнера; deploy проверяет его совпадение с ключом серверного `.env`. Каждый deploy со включённым Migration Service сверяет переменные у API и worker, при расхождении пересоздаёт оба контейнера и проверяет доступность ключа из PHP-процессов. Smoke запускается даже при выпуске другого сервиса, чтобы ошибку не обнаруживал первым оператор Dry run. Он проверяет расшифровку credentials нового формата в API и worker без подключения к legacy DB; старый Laravel Crypt профиль отмечается как требующий повторного сохранения пароля и не блокирует выпуск. Сравнение fingerprint между процессами не блокирует фоновые задачи.

Маршрут `/migration/` при обновлении страницы сначала показывает состояние авторизации, затем после проверки `platform-admin` открывает страницу миграции. Общий дашборд не должен появляться промежуточным кадром. Начально скрытые страницы и карточки остаются скрытыми независимо от CSS layout.

Кнопки и поля модуля блокируются от отправки запроса до финального ответа по конкретному run ID. HTTP 202 означает только очередь. Активная кнопка показывает loading, карточка — операцию, номер запуска и статус; при сбое polling блокировка сохраняется. Активные задачи обновляются каждую секунду, остальные — каждые 5 секунд. Сервер исключает гонку двух запусков одного сервиса с помощью SQLite write-lock.

`Validate` в UI называется «Проверить результат». Employees сохраняет прежнюю сверку количества employees/departments; новые адаптеры Vacations v2, Clients и Timesheets проверяют mappings, существование target rows, текущий source payload и перенесённые target fields. Данные не изменяются; сохранённые только в metadata поля не считаются импортированными.

Старое нечитаемое значение пароля не считается рабочим доступом: `/migration/state` показывает `credential_status`, интерфейс требует явно ввести и сохранить пароль, а Verify и создание run возвращают 409 до исправления. Сохранение подтверждается чтением шифртекста обратно из metadata DB и успешной расшифровкой в API.

Ключ нового формата хранится также в `/data/migration-credential.key` внутри приватного общего volume. Файл создаёт HTTP-процесс API атомарно при первом health-запросе; worker только читает его. Это исключает расхождение PHP process environment при сохранении и выполнении. Deploy проверяет расшифровку текущих payload в обоих контейнерах; при отказе выпуск не считается успешным. Файл сохраняется вместе с metadata DB и не должен удаляться при пересоздании контейнеров.

Для Employees legacy-роль должна иметь `USAGE` на схему `public` и `SELECT` на `departments`, `employees`, `employments`, `employee_roles`, `users`, `subcontracts`, `comments`. Для Vacations v2: `users`, `vacations`, `approvers`, `changes`, `comments`, `attachments`, `business_dates`, `departments`, `activity_log`. Полные allowlists Clients/Timesheets указаны в `config/migration.php`; jobs, failed_jobs, migrations и personal_access_tokens не читаются. `LegacyReader::assertSafe()` теперь до запуска чтения проверяет весь список и показывает недостающие таблицы/права одной диагностикой. DBA выдаёт минимальные права в исходной БД; migration-service не делает GRANT.

## Обратимый тест реального переноса Employees на стенде

Перед проверкой в действующем тестовом приложении отдельный CI шаг создаёт серверный снимок: архив схемы PostgreSQL `employees` и согласованную копию приватного volume Migration Service (SQLite mappings/runs и файл ключа). Снимок создаётся только при отсутствии активных migration runs; скрипт откажется, если другая схема имеет внешний ключ в `employees`. Дамп остаётся в закрытом каталоге `/opt/irlix-services/.ci/migration-test-snapshots/<CI run ID>` с правами доступа root; в GitHub artifacts он не загружается. Проверка CI должна завершиться успешно и вывести ID снимка **до** нажатия «Перенести».

На время теста publisher `employees-events` остановлен, чтобы события тестового импорта не ушли в RabbitMQ и другие сервисы. После решения оставить результат оператор запускает `docker compose -f docker-compose.yml -f docker-compose.migration.yml --env-file .env start employees-events` на стенде; откат запускает publisher самостоятельно. Не выполнять новый deploy, пока решение не принято: deploy может снова поднять остановленный контейнер.

Снимок создаётся отдельным CI шагом по явному запросу оператора, а не при каждом нажатии «Перенести». Для следующего теста нужен новый ID снимка и успешная проверка его восстановления.

В промежутке между снимком и решением о сохранении результата не редактировать Employees и не создавать сущности других сервисов со ссылками на новых сотрудников. Восстановление возвращает **всю схему Employees и всю metadata мигратора** к моменту снимка: оно удалит также любые другие изменения этих данных, сделанные позже. Текущий test stand на время снимка и восстановления кратко остановит Migration Service; при восстановлении останавливается и Employees API. Остальные схемы PostgreSQL не восстанавливаются. При обнаружении нового запуска миграции другого сервиса или внешних FK откат отказывается работать.

Ручной откат: GitHub Actions → **Restore Employees migration test snapshot** → Run workflow в `main`, указать числовой ID снимка и точное подтверждение `RESTORE EMPLOYEES`. Скрипт проверяет SHA-256 архивов, восстанавливает схему одной транзакцией PostgreSQL, затем SQLite metadata и перезапускает контейнеры. При ошибке восстановления сервисы остаются остановленными, исходный снимок сохраняется для восстановления оператором. Не удалять снимок до решения о сохранении результата.

### Снимок и откат в интерфейсе

Карточка Employees показывает доступные снимки и состояние операции. `platform-admin` нажимает «Создать снимок», ждёт статуса «Готово», выбирает точку отката и запускает перенос. Повторный запуск после завершившегося `failed` может использовать тот же снимок и сохранённые mappings. Для отката выбирается снимок и вводится точное подтверждение `RESTORE EMPLOYEES`; старые снимки не удаляются автоматически. Возврат к снимку удаляет все изменения Employees и metadata Migration Service после даты снимка, включая другие ручные изменения этих областей. При активном переносе снимок и откат запрещены.

Отдельный `migration-ops` контейнер принимает только команды создания и восстановления через приватный Unix-сокет. Только он имеет доступ к Docker socket и каталогу архивов; Migration API получает доступ лишь к Unix-сокету и проверяет `platform-admin` на каждом запросе. Операция асинхронна: временная остановка Migration API не обрывает процесс отката, после запуска страницы продолжают опрашивать состояние. Каталог архивов остаётся на сервере; данные и секреты не отправляются в браузер. При неуспешном восстановлении контейнеры остаются остановленными для ручного восстановления из архива. Ручной workflow GitHub Actions остаётся резервным способом.

## Пульт переноса

Единственный интерфейс — пульт переноса — доступен по `/migration/` только роли `platform-admin`. Frontend — самостоятельное приложение `apps/migration` и контейнер `migration-web`, не раздел Portal. Host nginx направляет `/migration/` в web на loopback 8099; API остаётся на 8098. Собственное меню содержит только «Пульт переноса». Прежняя страница полностью удалена; старые ссылки `/migration/console` и `/migration/console/` после OIDC переходят на `/migration/`, сохраняя параметры и hash. Дашборд доступен через общий переключатель сервисов. Он использует `UiAppShell` и компоненты `@irlix/ui`. Очередь реализованных модулей: Employees → Vacations → Clients → Timesheets. Будущие модули видны, но не запускаются.

«Перенести все» создаёт согласованную общую точку четырёх target schemas, затем отдельную точку перед каждым сервисом и последовательно выполняет Inspect → Dry run → Migrate → Validate. Перенос одного сервиса создаёт его точку и выполняет те же этапы. Любая ошибка останавливает очередь; продолжения после перезапуска ops нет. Validate новых адаптеров сверяет mappings и перенесённые поля.

Контрольные точки хранятся в `/snapshots/console/<scope>/<id>`: проверенный PostgreSQL dump, SQLite metadata и ключ credentials, checksums и manifest. На время снимка останавливаются соответствующие writers и Migration API/worker; источник legacy всегда read-only. Restore требует `RESTORE ALL`, `RESTORE EMPLOYEES` , `RESTORE VACATIONS`, `RESTORE CLIENTS` или `RESTORE TIMESHEETS`. Активные runs блокируют snapshot/restore. Откат одного сервиса запрещён, если после его точки переносился другой сервис. До остановки writers restore проверяется во временной БД поверх актуальной структуры выбранных схем. Ошибка репетиции отменяет откат без остановки и изменения целевых данных. После остановки отказ до записи БД или подтверждённый rollback транзакции запускает writers снова; неопределённый исход COMMIT и ошибки после восстановления БД оставляют writers остановленными для ручного восстановления. Общий откат восстанавливает все четыре схемы и metadata; история пульта в ops сохраняется отдельно, поэтому детали старых run после отката могут быть недоступны.

API: `GET /api/migration/console/state`, `POST .../start` (`scope`, `confirm:true`), `POST .../restore` (`scope`, `snapshot_id`, `confirmation`), `GET .../runs/{id}`, `GET .../runs/{id}/conflicts?before=<id>`. Глобальная reservation блокирует конкурентные запуски через совместимые legacy API. Host coordinator хранит последнюю операцию и последние 50 операций в `/ops/console.json`; команды строго ограничены сервисами и режимами.

Выбранный сервис указан в breadcrumbs. Блок этапов уплотнён: текст слева, действия справа. Верхние заголовки таблицы и журнала образуют общую строку одинаковой высоты; заголовки колонок обеих таблиц также выровнены и имеют высоту 30 px; пояснение таблицы находится справа от заголовка и целиком доступно в tooltip. По умолчанию таблица и журнал занимают равные половины. Вертикальный разделитель — линия шириной 1 px без отступов и обводки при наведении; невидимая зона захвата сохраняет удобство перетаскивания. Он изменяет их ширину мышью или стрелками клавиатуры (20–80%); Home/End выбирают границы, двойной щелчок возвращает 50/50. Polling не сбрасывает размер панелей. На mobile блоки располагаются последовательно, разделитель скрыт. Строки таблицы уплотнены без изменения шрифтов; фильтры журнала — компактные UiButton с aria-pressed, checkbox автопрокрутки выровнен по центру. Список сервисов не имеет обводок и закруглений; «Все сервисы» отделён дополнительным интервалом, надпись «Очередь переноса» удалена. У каждого пункта справа сверху шестерёнка настроек БД, под ней иконка дискеты «Бэкапы». Наведение и фокус выделяют только кнопку иконки; весь пункт подсвечивается при наведении на выбор сервиса. Для «Все сервисы» шестерёнка открывает выбор подключения; действия нереализованных модулей disabled. Сводка доступов в блоке этапов «Все сервисы» и надпись «Обновлено» с датой удалены во всех сервисах. Уведомления проверки/изменения подключения остаются только в UiDrawer настройки БД; polling сохраняет значения, DOM, focus и caret.

«Бэкапы» открывает UiDrawer выбранного сервиса, независимо от текущего выбора таблицы. В одном списке показаны снимки пульта и исторические снимки Employees/Vacations с источником, датой, ID и отметкой восстановления. Общие снимки находятся в «Все сервисы». Удаление требует отдельного подтверждения и физически удаляет архив на сервере. Возврат требует точной фразы RESTORE <SCOPE> и использует существующий API соответствующего типа снимка; восстановленные снимки доступны для повторного восстановления с теми же проверками. Глобальная активная операция переноса или snapshot/restore блокирует действия. Ошибки списка, удаления и возврата показываются только в соответствующем окне бэкапов. Новый DELETE /api/migration/console/snapshots/{scope}/{snapshot} требует platform-admin, allowlisted scope и numeric ID; ops сериализует его общим LOCK, проверяет активный legacy snapshot и удерживает SQLite BEGIN IMMEDIATE и файловый lock checkpoint-скрипта до конца удаления. Не удаляются архивы другого сервиса, история операций или metadata. Для старых снимков используются прежние endpoints /snapshots и /vacations/snapshots. GET console/state также возвращает snapshot_operation для блокировки и отображения операций исторического snapshot API.

Таблица показывает реальные total/read/success/error/warning counters по legacy-таблицам. Чтение вспомогательной таблицы не считается переносом; неизвестный total не превращается в выдуманный процент. Журнал объединяет события этапов выбранной операции и конфликты, имеет фильтры по severity, сервису и таблице, подгрузку старых сообщений.

Фоновое обновление выполняется без перекрытия запросов (1 секунда при работе, 5 секунд в ожидании). Оно обновляет состояние, а не черновик формы доступа. Значения, password, focus, caret и DOM-поля сохраняются; открытие формы явно загружает сохранённые параметры. Ошибка сети блокирует новые операции и повторяет проверку. Browser regression запускается при отсутствующем Portal и проверяет собственное меню, переход между интерфейсами, сохранность поля через несколько polling-ответов, блокировку повторного запуска, mobile layout и запрет для non-admin.

Проверки: `node --test apps/migration/tests/*.mjs`, browser fixture `apps/migration/tests/migration-console.browser.cjs`, `python -m unittest discover -s scripts/tests -v`, `php tests/console_smoke.php` внутри Laravel migration runtime. Snapshot/restore и импорт реальных БД требуют отдельной операторской проверки; тесты не запускают перенос production-данных.

## Самостоятельный frontend

`apps/migration` имеет собственные package/lock, Vite base `/migration/`, OIDC storage `irlix.migration.auth`, Dockerfile/nginx и CI component `migration-web`. Исходники и тесты обоих интерфейсов перенесены из Portal; Portal не содержит migration API calls, polling, форм, стилей или меню переноса. Общие зависимости — только `packages/ui` и `packages/auth`. Изменение Migration frontend собирает/выкатывает только его web image; изменение Dashboard — только Portal. При недоступном Portal Migration остаётся доступен; при недоступном Migration API web показывает ошибку и запрещает новые операции. Credentials/SQLite, worker, checkpoints и backend API при выделении frontend не меняются.



## Схемы от 07.10.2026

Vacations использует новый адаптер `VacationsV2Migration` для `users`, `vacations`, `approvers`, `changes`, `comments`, `attachments`, `business_dates`, `departments`, `activity_log`. Старые классы сохранены для аудита, но не зарегистрированы. Отсутствие связано с сотрудником через `vacations.user_id → users.id`; корпоративный login из email должен разрешиться однозначно в Employees, а существующий UUID mapping не должен ему противоречить. `from/to`, включительное число календарных дней, type/status переносятся в absences. Неизвестные значения и обратные диапазоны — ошибки. Working hours и неподтверждённая история сохраняются в приватных metadata. Согласующие переносятся в назначенную цепочку employee_review, документы скачиваются по старым ссылкам; подробности и ограничения ниже. Роли HR/AM/RN и даты решений не выдумываются.

Clients переносит клиентов, проекты, участников, условия/ставки, лиды с известным статусом, контакты/связи, юрлица, запросы/позиции/попытки и отчётные периоды. `users.external_key` сверяется с Employees mapping; login остаётся источником сопоставления. Для подключения без project_id создаётся стандартный default project соответствующего клиента. `rates.workload` — **часы в день**, подтверждено оператором; перенос 1:1 в `hours_per_day`, диапазон 0–24. Зашифрованная/нечисловая ставка, потеря точности, пересечение периодов, внешний member без подтверждённой личности, неизвестный результат закрытой попытки или коллизия существующей записи — конфликт. Вспомогательные справочники, json контактов, отзывы/заметки, поля юрлиц без нового аналога, files и polymorphic history сохраняются в metadata; они не считаются успешным импортом бизнес-строк.

Timesheets разрешает участника через уникальный login и единственное точное совпадение названия проекта/сотрудника в Clients (для default project — названия клиента). Совпадение числовых members.id между старыми базами не подтверждено оператором и не используется. Явный override `timesheets/members/legacy_id → target project_member_id` допускается только для того же сотрудника; неоднозначная/неизвестная строка project требует такого сопоставления. На стенде: `docker compose -f docker-compose.yml -f docker-compose.migration.yml exec migration php artisan migration:timesheets-member-map <legacy_member_id> <target_project_member_id>`, затем новый Dry run. Rate сопоставляется по участнику, точным датам и часам в день, а не по совпадению ID rate или названию проекта. Записи переносятся в `timesheet_entries` только внутри периода подключения, 0–24 часа и без округления сверх двух знаков. Дубликаты employee/project/date не складываются и не перезаписываются. Личные `time_records` без клиента/проекта, реплики календаря/отпусков, месячные confirmations без автора/времени подтверждения и per-entry `is_submitted` сохраняются в metadata с warning; они не превращаются в фиктивное финальное согласование или подтверждение всех проектов дня.

Перед реальной записью все строки проходят тот же полный preflight, включая прямые API/CLI вызовы; ошибка любого преобразования блокирует все target writes. Dry run выполняет те же преобразования с виртуальными IDs и не меняет target rows/mappings. Повторный импорт использует собственные mappings, существующие несопоставленные natural keys требуют явной reconciliation. Inspect показывает counts и фактические legacy enum values. Validate новых адаптеров проверяет полноту mappings, существование target rows, неизменность source payload и перенесённых target fields. Поля, сохранённые только как metadata, перечисляются в warning report.

### Employees: зарплаты вне текущего scope

Зарплаты исключены из Inspect/Dry run/Migrate/Validate. Таблица legacy `salaries` не читается и не входит в обязательные SELECT-права; целевая `salary_history` не изменяется. Старые mappings и отчёты запусков не удаляются, новые запуски не формируют зарплатных счётчиков/конфликтов. Снимки и откат сохраняют прежнюю полноту схемы Employees, включая существующие зарплаты. Следующие этапы отладки касаются сотрудников, подразделений, периодов работы, ролей и истории статусов/назначений.

## Employees: приоритет legacy при повторном переносе

Бизнес-поля уже существующих сотрудников обновляются из старого сервиса по сохранённому mapping либо логину/рабочей почте. Пароли и состояние корпоративной identity не переносятся; зарплаты остаются вне scope. Конфликт ручного незакрытого периода разрешается обновлением его дат и типа сотрудничества из legacy с сохранением целевого ID. Уже mapped периоды также сверяются при повторном запуске; изменения получают audit event с данными до/после. Закрытый последний период источника может закрыть ручной незакрытый период целевой БД. Непротиворечивость исходных дат и единственность незакрытого периода проверяются; несколько разных открытых периодов источника или чужой mapping остаются конфликтами. Ошибки прошлых запусков не удаляются. Проверки и выкладка не запускают реальный перенос.

## Фильтрация журнала до пагинации

Нажатие на ошибки/предупреждения таблицы или фильтр журнала запрашивает совпадающие conflicts с сервера, независимо от уже загруженных сообщений. GET `/api/migration/console/runs/{run}/conflicts` принимает необязательные `severity=error|warning`, `table` и `before`; без курсора возвращает первую страницу выбранного фильтра. Сервер применяет фильтры до лимита 200, учитывает соответствие entity_type исходной таблице и возвращает `items`, `total`, `cursor`, `more`. Существующие вызовы только с `before` совместимы. `total` — число сообщений, не число уникальных исходных строк.

В журнале видны загрузка, количество загруженных/найденных сообщений и отдельная пагинация выбранного фильтра. Ошибка чтения остаётся в журнале с повтором запроса и не выглядит как отсутствие ошибок. Ответ предыдущего фильтра не подменяет новый; polling не сбрасывает загруженные страницы при неизменном запуске, ввод, фокус и курсор в форме БД. События этапов из отчёта запуска продолжают отображаться с локальным фильтром; серверная пагинация относится к conflicts. Просмотр читает сохранённый отчёт, не запускает импорт и не требует доступности legacy БД.


### Повторный откат и объяснение ошибок

Точка отката остаётся доступной после восстановления. `restored` — информационная отметка, а не запрет повторного использования. Повторный откат требует прежнего подтверждения и проходит проверки контрольных сумм, состава схем, внешних FK, отсутствия активных операций и изменений другого сервиса после индивидуальной точки. Архив не изменяется при восстановлении.

В Vacations типы старой БД `paid`, `unpaid`, `maternity` соответствуют `paid_vacation`, `unpaid_vacation`, `maternity_leave`. Неизвестные значения остаются ошибками. Сопоставление сотрудника по корпоративному логину требует ровно одного совпадения: ошибки отдельно сообщают отсутствие сотрудника либо число совпадений и ID. Контекст ошибки содержит ID, email, тип и даты исходной записи, без паролей.

При ошибках пульт открывает фильтр «Ошибки», отключает автопрокрутку и показывает причину остановки и сводку ошибок независимо от страницы журнала. Проверенная таблица с ошибками имеет статус «Есть ошибки». Переход к истории выбирает сервис операции и сбрасывает фильтр таблицы. Запросы отчёта проверяют `operation_id`, чтобы повторно использованный после отката run ID не подменил старый отчёт новым. История операций сохраняется отдельно, но подробные отчёты хранятся в восстанавливаемой metadata SQLite: если отчёт утрачен, интерфейс явно сообщает об этом; восстановление старых подробностей не обещается.

История выбранного сервиса показывает его собственные операции и общие операции, которые затрагивали этот сервис (по `services` / этапам `runs`). Общий список доступен только во «Всех сервисах». При открытии общей операции из истории сервиса текущий сервис сохраняется.


### Итоги переноса и ручное сопоставление пользователей отпусков

Правая панель пульта переключается через общий UiTabs между «Итоги переноса» (по умолчанию) и «Журнал переноса». Итоги прокручиваются внутри панели и содержат причины остановки, сводку ошибок, счётчики и состояние до/во время/после запуска. Они больше не занимают место над обеими колонками. «Показать ошибки» и клики по счётчикам открывают журнал с соответствующим фильтром. Polling сохраняет вкладку, размер панелей, draft и фокус формы.

Подтверждённые соответствия Vacations: `sick → sick_leave`, `granted → confirmed`, `not_approved → rejected`, `approvers_definition → planned`, `on_approval → planned`. При выборе согласующих и ожидании согласования отпуск возвращается в «Запланирован»; старые согласования не превращаются в выдуманные новые этапы. Исходный статус сохраняется в metadata и аудите переноса. Сообщения неизвестных значений различают поля `type` и `status`.

Если логин пользователя отпусков отличается от текущего логина Employees, оператор открывает «Сопоставить сотрудника» в ошибке `users` журнала. Точный текущий логин проверяется, показываются ФИО, логин и ID, затем оператор подтверждает связь. GET `/api/migration/console/conflicts/{id}/employee-match?login=...` проверяет сотрудника; POST `.../employee-map` принимает проверенные `login`, `employee_id`, `source_fingerprint` и `confirmation=MAP USER <legacy_id>`. Доступ — существующие привилегированные роли Migration, без расширения прав. Неоднозначный/отсутствующий логин, противоречие UUID, старая ошибка, активный перенос/бэкап или недоступность ops блокируют сохранение.

Постоянное соответствие хранится приватно в отдельном томе `migration_identity`, файл `/identity/employee-logins.sqlite` (`MIGRATION_IDENTITY_DATABASE`). Ключ — сервис Vacations, fingerprint источника (host/port/database/schema, без credentials), нормализованный старый login (local-part email); значение — нормализованный текущий login Employees. API и worker разделяют этот том, migration-ops его не получает: ни откат Vacations, ни Employees, ни всей metadata не заменяет справочник. Каждый preflight заново разрешает текущий login в единственный Employees ID; отсутствие/неоднозначность блокирует перенос, но не удаляет решение. Смена числового ID после повторного импорта Employees допустима; смена текущего логина требует нового подтверждённого сопоставления через существующее окно ошибки. Смена домена email без смены local-part не сбрасывает связь. Проверка противоречия актуальному UUID mapping сохраняется. Сотрудники/логины/пароли/Keycloak не изменяются. Уже импортированного пользователя нельзя перепривязать к другому ID без отката его миграции. Fingerprint исходных email/UUID остаётся защитой preview → save, а не постоянным ключом. Решение и автор сохраняются в отдельном аудите справочника; события текущего отчёта по-прежнему откатываются вместе с metadata. `migration_overrides` остаётся совместимой записью текущего запуска, но не источником постоянной связи.

При выкладке `migration:identity-upgrade` переносит доступные прежние ручные решения в отдельный справочник только при совпадении исходного fingerprint/источника и наличии ранее подтверждённого target login с однозначным текущим сотрудником. Старые записи только с числовым ID автоматически не преобразуются: ID мог быть повторно использован после отката, поэтому требуется одно подтверждение в новом окне сопоставления. Уже сохранённые постоянные решения не перезаписываются. Утраченные ранее при откате решения восстановить автоматически нельзя. Справочник не содержит паролей, реальные соответствия никогда не попадают в Git/CI output. Для независимого резервирования остановить API/worker и сохранить том `migration_identity` в приватный серверный backup; восстановление этого тома — отдельная административная операция, не бизнес-откат. Не удалять том при повторном запуске сервиса.

Зависимые ошибки отпусков содержат причину нерешённого пользователя (`users.<id>`); период/тип и ID отпуска сохраняются в source context. Сохранение сопоставления требует нового Dry run; старые отчёты не редактируются.


Технические ошибки ручного сопоставления показывают конкретный шаг: очередь, чтение исходного пользователя, поиск в Employees, проверка UUID или запись metadata. Ответ содержит `code`, `stage`, `diagnostic_id` и безопасный SQLSTATE при наличии. Ненайденный/неоднозначный логин остаётся ошибкой 422; активная операция — 409; технический сбой — 503. UI показывает шаг и код диагностики прямо в окне сопоставления. Серверный журнал по этому коду содержит только класс исключения, этап и SQLSTATE, без сообщения исключения, SQL, bindings, логинов или credentials. Регистр и обычные пробелы по краям игнорируются; похожие кириллические и латинские буквы автоматически не заменяются.


Release verification runs `migration:employee-query-check` in API and worker. It validates the exact Employees matching columns/functions and database permissions using an always-false WHERE condition, prints no employee data, never connects to legacy DB, then executes matching for one existing login without printing it, and emits only exception class, safe category and SQLSTATE on failure. PostgreSQL SQLSTATE is read from PDO errorInfo before the numeric driver exception code. No raw database error, SQL, bindings or credentials are printed.


Migration HTTP starts with `artisan serve --no-reload`: container TARGET_* and credential variables must be inherited by the child HTTP process. Laravel's default reloader strips non-passthrough variables when a .env exists, so CLI/worker may connect while HTTP cannot. The offline child-process regression reproduces stripping without the flag and validates preservation with it; CI also checks the production CMD. Credentials remain supplied through runtime environment, never copied into the image .env.

### Перенос документов и назначенной цепочки согласования Vacations

**Текущий режим:** перенос файлов временно отключён (`migration.vacation_documents_enabled=false`). `attachments` исключена из обязательных исходных таблиц, import/Dry run не проверяют ссылки и не скачивают/записывают файлы; итоговая validation не сверяет вложения. Код сохранён для будущего включения. Отпуска и согласующие продолжают переноситься. Уже сохранённые документы не удаляются; резервирование локальных файлов при создании точки отката сохраняется. Описанный ниже механизм документов действует только при включённом флаге.


Миграция добавляет старых согласующих в обычные `absence_approvals` нового сервиса: stage `employee_review` («Согласование сотрудниками»), конкретный Employees ID, без выдуманной роли HR/AM/RN. UUID согласующего разрешается через исходные users и их проверенное login-сопоставление; при отсутствии исходного user допускается подтверждённый Employees UUID mapping с существующим target. `order` становится sequence; одинаковый order — параллельная группа. `is_approved=true` становится approved, false — waiting (отказ из этого boolean не выводится). `acted_at`/acted_by остаются неизвестными. Текущий статус отсутствия сохраняет принятые aliases; `on_approval` и `approvers_definition` остаются planned. При явном submit такой цепочки активируется первая не завершённая sequence, затем следующие группы; все известные approved сохраняются. Последняя группа завершает обычный workflow статусом confirmed. Точные назначенные участники и platform-admin имеют существующее право согласования, роли остальных пользователей не расширяются. Возврат на доработку и редактирование planned сохраняют состав цепочки, но сбрасывают решения. В интерфейсе это обычная история/прогресс, отдельного исторического маршрута нет. Для обычных новых отпусков сохраняется HR → AM → руководитель → HR.

Вложения, связанные с Vacation по attachmentable_type/id, загружаются read-only по исходным HTTP/HTTPS URL. Поддерживаются Vacation/vacations и namespaced class Vacation. Остальные polymorphic objects сохраняются с warning и не прикрепляются к чужим отпускам. Все документы предварительно скачиваются во временные файлы до target writes; Dry run не пишет в target DB/хранилище. Реальный проход использует проверенные staged bytes и кладёт их в общий `vacations_files`, который Migration API/worker монтируют как `/vacation-files`, Vacations — `/app/storage/app/vacations`. Применяются лимит 10 МБ, timeout 30 секунд/соединение 5 секунд, максимум 5 переходов; каждый redirect снова проверяется и DNS адрес фиксируется для соединения. Loopback, link-local/metadata, userinfo и не-HTTP схемы запрещены. Частная сеть допускается только для legacy DB host или явно заданных `MIGRATION_LEGACY_FILE_HOSTS`; bearer tokens платформы в старое хранилище не передаются. HTTP ошибки, пустые/большие документы, HTML/JSON вместо файла блокируют preflight с ошибкой конкретного attachments ID. Исходные URL/имя и row остаются в приватной metadata, публичные CI логи их не содержат. При изменении уже перенесённого согласования/документа в новой системе повторный импорт отказывается его перезаписывать.

Имена новых и переносимых документов: `Заявление — <ФИО> — <тип> — <YYYY-MM-DD>_<YYYY-MM-DD> — <короткий ключ>.<расширение>`; для больничного/декрета/отгула — «Документ». Кириллица сохраняется, недопустимые символы/разделители заменяются, длина ограничена 255 UTF-8 bytes. 12 hex символов ключа предотвращают коллизии; для миграции ключ детерминирован источником/legacy attachment ID/URL, для загрузки — UUID. В хранилище и Content-Disposition используется одно читаемое имя. `source_original_name` хранит исходное имя, `external_url` — исходную ссылку импортированного файла; размер/MIME проверяются по скачанным bytes. Уже перенесённые основные отпуска можно дополнить повторным импортом без отката, если mappings сохранены и новых пользовательских изменений нет.

Новые точки пульта со scope vacations/all включают `vacations-files.tar.gz`, защищённый checksums и закрытым серверным каталогом. Restore восстанавливает bytes и metadata; перед запуском Vacations применяет текущие DB migrations, чтобы старые точки работали с новым кодом. Старые точки без архива документов не обещают восстановления потерянных файлов и не очищают существующий volume. Независимый справочник login-сопоставлений остаётся вне rollback. Clients в этой задаче не меняется. Comments/changes/activity_log/calendar продолжают храниться в metadata; недостоверные события и даты согласования не реконструируются.


Точки отката Vacations/all читают и восстанавливают документы через общий `vacations_files`, смонтированный в migration-ops как `/vacation-files` (`MIGRATION_VACATIONS_FILES_PATH`). Docker inspect возвращает путь хоста, который нельзя использовать внутри контейнера; этот fallback сохраняется только для запуска скрипта непосредственно на хосте. Создание точки отката не зависит от legacy read-only подключения. Подсказка верхней панели не требует проверки БД без фактической ошибки.


### Clients: legacy-статусы, причины закрытия и диагностика подготовки · 2026-10-08

Старые коды лидов поддерживаются наряду с русскими статусами: `new → Новый лид`, `initial → Первичный контакт`, `clarification → Уточнение потребностей`, `ignore → Клиент в игноре`, `failed → Сделка закрыта - Отказ`. Другие неизвестные коды остаются конфликтами. Исходная запись сохраняется в приватной metadata.

`attempt_result → results.title` содержит также причины отказа, а не только успех/неудачу. Известные причины из действующего `RequestWorkflowController::FAILURE_REASONS` означают `Закрыт: неудача` и сохраняются в обычном `failure_reasons`; несколько причин одного отрицательного результата допустимы. Явные успех/неудача поддерживаются. Сочетание успеха и отказа и неизвестный title блокируют перенос. Отсутствующий результат обрабатывается по отдельному явному статусу попытки (см. временную политику ниже). Комментарий сохраняется отдельно; даты и причины не выдумываются.

Диагностика условий различает отсутствующую сумму, нечисловое значение, диапазон/точность, отсутствующий грейд и ссылку на справочник; указывается конкретное поле без исходной суммы или шифртекста. Нечисловое значение само по себе не доказывает шифрование. Ошибки зависимых строк Clients имеют `DEPENDENCY_BLOCKED` с таблицей, ID и причиной зависимости; `blocked_count` является подмножеством ошибок, а не дополнительным числом ошибок.

Dry run для адаптеров SchemaMigration считает `ready_count` и `processed_count`, но не `success_count`: проверенная строка не является импортированной. Повторная обработка и сохранение дополнительных полей той же строки в metadata не увеличивают число обработанных строк. Пульт показывает «Готово к переносу» и «Только metadata», счётчик готовых строк и зависимостей, до 40 групп предупреждений по таблице/коду/причине; полный журнал с ID и исходной metadata сохраняется. Старые отчёты не пересчитываются: для новых счётчиков нужен новый Dry run.

Ручное сопоставление пользователей доступно также для Clients через существующие `employee-match` / `employee-map`. Проверяются последний ошибочный Dry run, подтверждение, fingerprint email/external_key, уникальный текущий login Employees, UUID, отсутствие активных операций и запрет перепривязки уже импортированного user к другому Employees ID. Постоянные login-связи разделены по сервису и источнику; решение Clients не влияет на Vacations и переживает бизнес-откат. Внешние участники без проверенной личности остаются конфликтами; этот экран сопоставляет users, а не создаёт фиктивных сотрудников/подрядчиков.

Offline SQLite/HTTP regressions проверяют коды лидов, несколько причин отказа, неоднозначность, числовые поля, отсутствие target writes в Dry run, идемпотентность, точные счётчики, группировку предупреждений и изоляцию identity-связей Clients/Vacations.

### Clients: общий список логинов и второй разбор preflight

По решению пользователя Clients использует подтверждённый список Vacations для того же нормализованного старого корпоративного логина. Читается реестр текущего настроенного источника Vacations; legacy numeric user ID не переносится между сервисами. Собственное сопоставление Clients сохраняется отдельно. Если оба реестра указывают разные текущие логины, возникает `IDENTITY_ALIAS_COLLISION` с обоими значениями: ни одно не выбирается автоматически. Текущий login должен единственным образом разрешаться в Employees и согласовываться с UUID. Если уже импортированный users mapping указывает другой Employees ID, `IDENTITY_MAPPING_COLLISION` запрещает тихую перепривязку и требует проверки/отката Clients.

Дополнительные legacy статусы: `leads.active → Активные переговоры`, `leads.proposal_sent → КП отправлено`. `positions.under_consideration/waiting/no_candidates → Открыт`: позиция без closed_at остаётся открытой, а отображаемое «В работе» новый Clients вычисляет по попыткам; эти коды не создают выдуманных попыток или закрытий.

Закрытые попытки без attempt_result и явного терминального attempts.status восстанавливаются по согласованному правилу дат: заполненный started_at означает успех, иначе — неуспех на последнем достигнутом этапе. Сочетание явного успеха и отказа остаётся `AMBIGUOUS_ATTEMPT_RESULT` с названиями результатов. Нечисловая сумма с распознаваемой base64 JSON-структурой Laravel iv/value/mac имеет `ENCRYPTED_AMOUNT`; распознавание формата не расшифровывает и не доказывает валидность payload. Ключи, суммы и шифртекст не включаются в журнал. Остальные нечисловые значения сохраняют `NON_NUMERIC_AMOUNT`.

`EXTERNAL_MEMBER_UNRESOLVED` показывает исходные memberable_type/memberable_id без создания фиктивного сотрудника. `SOURCE_PERIOD_OVERLAP` показывает ID и границы обеих пересекающихся исходных записей; периоды не обрезаются и не объединяются автоматически. Эти подробности доступны только через приватный журнал с существующей авторизацией.

Открытые вопросы для завершения переноса: восстановление отсутствующих результатов попыток; доступ к старому ключу Clients или расшифрованному числовому экспорту; проверенные грейды/технологии отсутствующих ссылок; идентичности внешних участников; выбор корректных исходных записей пересекающихся периодов. До получения достоверных данных полный preflight блокирует Import и не изменяет target. После выпуска нужен новый Dry run; количество оставшихся ошибок заранее не обещается.

Синтетические offline regressions проверяют общий список при разных legacy ID, коллизию двух реестров, UUID, запрет перепривязки импортированного пользователя, дополнительные статусы, разделение отсутствующего/противоречивого исхода, распознавание encrypted payload и обе границы пересечения.

## Партнерский специалист · 2026-10-08

При добавлении подключения форма использует общий `UiSegmentedControl` «Сотрудник / Партнерский специалист». Первый вариант сохраняет дерево Employees; второй требует непустое ФИО до 255 символов. В создании попытки используется то же название и переключение; обязательный CV сохраняется.

Clients хранит партнерскую личность в `partner_specialists` с собственным ID и ФИО. ProjectMember ссылается ровно на одного сотрудника (`specialist_id`) либо партнера (`partner_specialist_id`), что защищено PostgreSQL CHECK/FK и отдельными уникальными связями с проектом. ID двух справочников никогда не смешиваются. Ручное добавление создает новую личность; совпадение ФИО не объединяет людей. Новые условия создаются через существующего участника; смена проекта сохраняет его личность.

Подключение из внешней попытки использует ее ФИО и сохраняет source_attempt_id; повторная операция по той же попытке использует существующего участника. Пересечение условий проверяется по типу и ID личности во всех проектах одного клиента. Неудачная операция откатывает также создание партнера. Права и scope остаются существующими members/manage и клиентскими ограничениями; карточка показывает «Партнерский специалист».

Партнер не получает учетную запись Employees, корпоративную авторизацию или отпуск. Каталог подключений для Timesheets включает только сотрудников: Timesheets сейчас оперирует employee_id и не поддерживает ввод часов партнеров. ДДС сохраняет календарный план партнера по условиям, а фактические/подтвержденные часы не подменяет часами сотрудника с таким же числовым ID. В отчётном периоде партнерская строка не ведёт на employee-фильтр Timesheets.

Migration переносит `subcontracts → partner_specialists` и `members.memberable_type=subcontract` через `memberable_id`. ФИО берется из full_name либо surname/name/patronymic. Повторный перенос использует исходный ID; одинаковые имена не являются ключом. Неизвестный тип, отсутствующая ссылка или ФИО блокируют полный preflight; сведения старой записи сохраняются приватно. Поддержка иных кодов/структуры старого справочника требует проверки нового Dry run, без угадывания личностей.

Проверки: `partner_members_smoke.php` входит в backend image checks; SQLite проверяет раздельные ID, одинаковые ФИО, условия, пересечения, транзакционный откат, подключение из попытки и смену проекта. PostgreSQL constraints применяются штатной миграцией. `timesheet_assignments_smoke.php` проверяет исключение партнеров из employee-каталога. Browser regression `apps/clients/tests/partner-members.browser.cjs` проверяет переключение формы, дерево сотрудников и partner payload на синтетических API; запускается на локальном preview с CLIENTS_PREVIEW, PLAYWRIGHT_MODULE и CHROMIUM_EXECUTABLE. Migration regression проверяет dry-run без записи, перенос партнеров и повторное использование mappings.


### Защита доступности при откате пульта

Перед остановкой сервисов выполняется репетиция `pg_restore --clean --single-transaction`: во временную БД загружается структура текущих выбранных схем, затем выбранный снимок. Это выявляет несовместимость старого снимка с новыми объектами (например, таблицей партнерских специалистов), сохраняя действующий стенд. Временная БД удаляется; снимок не изменяется. Такой снимок нельзя автоматически применять поверх новой схемы: требуется отдельный план совместимого восстановления.

При отказе до записи целевой БД сервисы запускаются снова. При ошибке `pg_restore` запуск разрешён только после подтверждённого завершения процесса с ошибкой и отката единой транзакции. Потеря связи с Docker не считается доказательством rollback: исход COMMIT может быть неизвестен. После успешного восстановления БД ошибка копирования metadata/документов или обновления схемы оставляет writers остановленными, чтобы исключить работу с несогласованными данными.

После восстановления всех выбранных схем выполняются актуальные Laravel migrations каждого сервиса (в том числе Clients), затем запускаются writers и Migration API/worker. Для migrations используется точный локальный image ID существующего контейнера, без build/pull и подмены образом из базового compose. Пульт различает отказ предварительной проверки, восстановление доступности без применения снимка и ситуацию, требующую оператора. Проверки: unit regression на несовместимость репетиции, подтверждённый abort, неизвестный исход транзакции, ошибку metadata и выбор точного образа. Реальные production-данные автоматически не откатываются тестами.


## Clients: временное исключение ставок и отдельный исход попытки · 2026-10-08

До получения APP_KEY старого Clients таблица `rates` исключена из доменного импорта целиком: условия подключения `member_terms`, их суммы, workload, грейды и технологии не создаются. `reporting_period_rate` также отложена. Предлагаемая ставка `attempts.rate` не импортируется; для новой попытки поле остаётся NULL, существующая ставка не стирается. Нулевые или выдуманные суммы не подставляются. Строки сохранены только в приватной migration metadata с явным предупреждением, без successful mappings. Активная политика находится в `migration.deferred_tables.clients`; старый путь импорта сохранён и протестирован для последующего возвращения после реализации проверенной расшифровки. Validate исключает отложенные таблицы из обязательной полноты и возвращает их отдельно в `deferred` с причиной и числом исходных строк.

Клиенты, проекты и участники импортируются, но условия и периоды подключений из rates пока отсутствуют. Поэтому исторический Timesheets, требующий точного совпадения условий Clients, для таких подключений нельзя переносить до возвращения условий. Уже перенесённые условия и ставки не удаляются этой политикой.

Статус попытки и результат/причина — разные поля. Явный legacy `attempts.status` (`success`/`Успех`/`Закрыт: успех`, `failure`/`failed`/`fail`/`Неуспех`/`Неудача`/`Закрыт: неуспех`/`Закрыт: неудача`) определяет финальный исход. Успех без результата сохраняет пустую причину; явная неудача без результата получает отдельную причину «Причина не указана в старом сервисе», включённую в каталог Clients. Недостающий closed_at не выдумывается. Известные старые результаты поддерживаются для источника без явного статуса; противоречие статуса и результата блокирует перенос. При отсутствии обоих используется согласованное правило дат только для закрытой попытки (closed_at заполнен). Inspect показывает `attempts.status` и имена доступных полей attempts; конфликт отдельно указывает, присутствует ли поле status.

Ненайденные технологии позиций остаются блокирующими до подтверждённого заполнения/сопоставления пользователем; исходный legacy ID виден в диагностике. Добавление технологии в новый Specialists само по себе не восстанавливает отсутствующую ссылку старого Clients. Пересекающиеся отчётные периоды не объединяются, не обрезаются и не отбрасываются: требуется решение по обеим записям с датами и статусами. Полный предварительный проход продолжает блокировать любые целевые записи при нерешённых коллизиях.


### Откат: окружение действующего контейнера и диагностика этапа

Одного image ID недостаточно: после restore нельзя заново собирать environment/сеть/тома из базового compose, который может отличаться от действующей выкладки. До остановки writers фиксируются настройки действующих сервисов; отдельный `php artisan migrate:status` проверяет их работоспособность. Затем migrations выполняются в контейнере того же образа с теми же environment, рабочим каталогом, пользователем, сетью и томами, без опубликованных портов и без pull/build. Environment передаётся через локальный временный файл 0600 и удаляется после команды; в журнал он не выводится. Отсутствующий контейнер, неоднозначная сеть или неподдерживаемый environment блокируют откат до остановки.

В `/snapshots/console/.restore-status.json` сохраняется последний этап и подтверждённость восстановления PostgreSQL, metadata и схем. Исход транзакции отмечается отдельно: `unmodified`, `unknown`, `rolled_back`, `committed`. Полный traceback записывается только в приватный `.restore-error.log` с режимом 0600. Console state возвращает allowlisted технические признаки без traceback/environment; сообщение неудачного отката называет этап. Перед остановкой ошибки проверки не выключают сервисы. Неизвестный исход транзакции или ошибка после COMMIT по-прежнему требует операторского восстановления, а не слепого запуска writers.

Unit regressions проверяют копирование действующего окружения, приватность tempfile/диагностики и отказ runtime-check до остановки. CI дополнительно поднимает отдельные синтетические Docker/PostgreSQL контейнеры: намеренно рассогласует базовый compose с действующим контейнером, проверяет snapshot, успешный и повторный restore, отказ несовместимого старого снимка без остановки и ошибку migrations после COMMIT с сохранением точного этапа. Этот тест использует только временные синтетические данные, не подключается к production и является частью обязательного `CI verified` при изменении migration-ops.


При откате Clients Migration API больше не выключается вместе с worker. Пульт читает состояние операции через ops без SQLite; интерфейс сначала обновляет этот статус и при maintenance не запрашивает заменяемый журнал. Middleware временно закрывает все metadata endpoints и новые команды, сохраняя GET console/state с прежней авторизацией и operational health. Общая файловая блокировка в `/ops/migration-metadata.lock` дожидается завершения уже начавшихся metadata-запросов перед восстановлением; новые запросы не блокируют процесс API, а получают явный maintenance 503. Схема Clients и worker по-прежнему останавливаются на время восстановления. При неопределённом исходе COMMIT или несогласованности metadata middleware продолжает защищать журнал до операторского восстановления. Полные traceback и environment не передаются в UI.


### Диагностика отсутствующих технологий Clients

Название технологии читается из legacy `technologies.title` по `positions.technology_id` (и `rates.technology_id`, когда перенос ставок включён). `MISSING_REFERENCE` содержит в видимом сообщении исходное поле, ID позиции/условий и ID отсутствующей технологии. Пустой technology_id обозначается отдельно. Если строки справочника нет, название не выдумывается: сообщение явно указывает, что оно недоступно. Контекст сохраняет reference_table, reference_id и source_id. Наличие строки с таким ID в подключённой исходной базе требует проверки чтения справочника, а не создания нового названия.


### Подтверждённые технологии и диагностика исхода попыток

Для позиций `clients_technology_names` содержит подтверждённый оператором список legacy ID → название. Он применяется только если запись отсутствует в legacy technologies; существующее название источника имеет приоритет. Hidden-технологии не исключаются, родители не подменяют дочерние технологии. UUID и связи с подразделениями в этот список не включаются. Попытка хранит только position_id, не собственную technology. NULL и неизвестные ID остаются конфликтами.

Inspect Clients записывает в журнал все фактически прочитанные колонки attempts, число присутствующих и заполненных значений (false и 0 считаются заполненными). В ошибках исхода закрытой попытки доступны «Исходные поля попытки»: все названия полей, признак заполнения, тип, безопасные значения статуса/исхода/дат/ID и число/названия связанных results. Прочие значения, включая суммы, шифртекст и персональные поля, скрываются, факт заполнения остаётся доступен. Данные относятся к моменту запуска. Для закрытых попыток без явного исхода и связанных результатов оператор согласовал восстановление по датам; противоречивые и неизвестные результаты остаются блокирующими. Повторить подготовку для нового отчёта; старые отчёты не пересчитываются.

Справочник выбора принадлежит Specialists; подтверждённый список в Migration — только legacy ID → имя для восстановления позиций. Specialists дополняет и синхронизирует дерево отдельной миграцией, Clients читает его через существующий API /api/specialists/catalog. Legacy 1С нормализуется к каталожному 1C.


### Clients: исход и этап попытки по датам

Если closed_at заполнен, а терминальный attempts.status и связанные attempt_result отсутствуют, заполненный started_at означает фактическое подключение и «Закрыт: успех». Без started_at переносится «Закрыт: неудача»: interviewed_at → closed_from_status «Интервью пройдено», иначе cv_sent_at → «CV отправлено», иначе «Новая». Для явной неудачи с started_at этап — «Ожидает подключения». Этап записывается для всех неуспешных попыток, в том числе с известными причинами. Причина без исходного результата — «Причина не указана в старом сервисе»; конкретный отказ не выдумывается. started_at сохраняется в connection_date.

Явные терминальные статусы и известные результаты имеют приоритет над восстановлением по датам. Их противоречия и неизвестные названия результатов не подавляются. Незакрытая попытка без терминального статуса остаётся активной, даже с started_at. interviewed_at используется как признак пройденного интервью; несуществующие записи интервью и история событий не создаются. Каждый восстановленный исход отмечается предупреждением INFERRED_ATTEMPT_OUTCOME с новым статусом, этапом и безопасной диагностикой исходных полей. Нужно повторить подготовку и Dry run; старые отчёты не пересчитываются.


### Исторические позиции без технологии

Пустой legacy positions.technology_id (NULL или пустая строка) переносится как positions.technology = NULL с предупреждением MISSING_POSITION_TECHNOLOGY. Связанные попытки не блокируются отсутствием технологии. Неизвестный непустой ID по-прежнему блокирует перенос: отсутствие справочной записи нельзя подменять отсутствием технологии. Новая БД допускает NULL для исторических позиций; обычные API создания/изменения технологии сохраняют обязательный выбор. Интерфейс показывает «Технология не указана» без добавления вымышленного значения в каталог Specialists. Пересечения reporting_periods остаются блокирующими и требуют отдельного решения по ID и диапазонам дат.


### Соседние месячные отчётные периоды

Для частичного наложения соседних месячных периодов одного клиента применяется согласованное выравнивание границ: если предыдущий период имеет полный месячный диапазон (начало + 1 месяц − 1 день = окончание), а следующий заканчивается ровно через месяц после предыдущего, начало следующего переносится на следующий день после окончания предыдущего. Его окончание, статусы, значения и связи не меняются. Требуется ровно один подходящий предыдущий период; результат затем проходит обычную проверку всех пересечений. Правило не зависит от порядка чтения строк. Оригинал сохраняется в приватной metadata, коррекция видна в предупреждении ALIGNED_MONTHLY_REPORTING_PERIOD. Произвольные пересечения и одинаковые диапазоны не объединяются и не удаляются.

SOURCE_PERIOD_OVERLAP для отчётных периодов содержит ID клиента и безопасные поля обеих записей с признаками заполненности и числом связей reporting_period_rate. Суммы и прочие чувствительные поля скрыты. В UI есть «Сравнить исходные периоды», даты диапазонов показаны как ДД.ММ.ГГГГ. Данные отражают новый запуск подготовки; старые отчёты не меняются.


### Выбранный оператором отчётный период

Конфигурация migration.clients_preferred_reporting_period_ids задаёт явно согласованные канонические legacy ID. Только при точном совпадении client_id/from/to и ровно одном выбранном периоде остальные исходные записи сопоставляются с его целевым ID. Каноническая запись импортируется первой независимо от порядка чтения. Её статусы/значения сохраняются; остальные записи остаются в приватной metadata как aliases, получают REPORTING_PERIOD_ALIAS и не создают второй доменный период. Исходные ссылки на оба legacy ID разрешаются в один target. Ставки остаются отложенными.

Ранее перенесённый отдельно дубликат не удаляется автоматически: несовпадение его mapping с каноническим target даёт REPORTING_PERIOD_ALIAS_COLLISION. Отличающиеся клиенты/даты и несколько выбранных периодов одного диапазона остаются конфликтами. Validate проверяет исходные данные, канонические записи, общие target ID и явно разрешённые aliases; произвольное совпадение mappings не считается допустимым.

## Права на сервис миграций

Доступ к пульту, истории, настройкам подключений, переносу и точкам отката разрешён только роли `platform-admin`, проверяемой через Employees `/access/me`. Роль `platform-tester`, в том числе вместе с организационными ролями, доступа не даёт: API возвращает 403, сервис скрыт в Dashboard, левом меню и переключателе сервисов. Если у пользователя обе платформенные роли, доступ администратора сохраняется. Публичные health probes остаются доступны мониторингу.


## Диагностика каждой попытки отката

Новая попытка получает отдельный `diagnostic_id` (32 hex символа). Пульт показывает этап остановки, безопасный код и причину, ID точки, подтверждённый исход PostgreSQL (`unmodified`, `rolled_back`, `unknown`, `committed`), завершённость metadata и обновления схемы. Ошибки операций со снимками показываются отдельно от Inspect/Dry run/Migrate/Validate: отсутствие конфликтов в последнем Validate не означает успешный откат.

Кнопка «Скачать диагностику» сохраняет безопасный JSON для передачи разработчику; DevTools и открытие API вручную не требуются. Диагностика console-отката сохраняется в истории самой операции и не подменяется следующим откатом той же точки. Старые точки Employees/Vacations получают такую же диагностику; прежние ошибки без отчёта явно помечаются как недиагностированные.

Полный stdout/stderr неудачных команд и цепочка исключений сохраняются только на сервере, в `/snapshots/diagnostics/<diagnostic_id>.log` (0600). Каталог приватный; путь на host: `/opt/irlix-services/.ci/migration-test-snapshots/diagnostics/`. Отдельный `<diagnostic_id>.json` хранит безопасные поля этапа. Логи разных попыток не перезаписывают друг друга. В публичную причину не копируются SQL, строки таблиц, environment, пароли или исходный traceback. Доступ к пульту остаётся только у platform-admin; скачать полный технический лог через API нельзя. Если запись лога не удалась, это явно показывается и не изменяет исход транзакции.

Отслеживаются и ранние отказы проверки metadata volume/FK, и несовместимость старой схемы, и ошибки после COMMIT. При повторе одной точки сбрасываются признаки предыдущего восстановления. В случае подтверждённого rollback и запуска сервисов сохраняется исходный `failed_stage=database`, а не только заключительный этап `start`. Правила остановки writers, preflight и операторского восстановления не меняются; диагностика сама не исправляет несовместимый снимок и не запускает повторный откат.
