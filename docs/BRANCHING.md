# Правило создания и интеграции рабочих веток

## Единственная база разработки

**Все новые рабочие ветки** (`feature/*`, `fix/*`, `chore/*`, `tmp/*` и любые другие) создаются **только от актуального `origin/development`**. Ветка `main` не используется как источник новых задач, даже когда она совпадает с `development`. Это распространяется на всех разработчиков, ChatGPT, параллельные чаты и автоматизацию.

Перед созданием ветки необходимо получить текущую вершину `development`:

```bash
git fetch origin development
git switch -c feature/short-description origin/development
```

В интерфейсе GitHub явно выбрать `development` как source при создании ветки. Стандартная ветка репозитория может оставаться `main` — это не разрешение ответвляться от неё.

## Интеграция и релиз

1. Изменения рабочей ветки возвращаются **только в актуальный `development`**; PR должен иметь `base: development`, а не `main`.
2. Перед интеграцией повторно сверить `origin/development`, итоговый diff и конфликты. Сохранять независимые изменения других чатов и не делать force-push общих веток.
3. `main` обновляется **только накопительным fast-forward релизом всего проверенного `development`** по прямой команде пользователя; никакого feature-PR, cherry-pick или hotfix напрямую в `main`.
4. Если ветка уже создана от `main` или устаревшей базы, не вливать её как есть: сначала перенести полезную работу на новую ветку от актуального `development`, проверить результат и только потом интегрировать. Для общей опубликованной ветки не переписывать историю.
5. Архивные и восстановительные refs — не рабочие ветки и не используются как база новой разработки.

Правило создания веток организационное: GitHub не может надёжно восстановить источник нажатия «Create branch» по одному Git-графу, особенно когда `main` и `development` имеют один SHA. Защита `main` обязательными checks действует дополнительно и не заменяет данное правило.
