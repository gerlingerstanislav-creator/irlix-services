# Scoped context policy

Цель этого правила — не загружать в рабочий контекст документацию и детали всех сервисов платформы для каждой задачи.

## Базовый принцип

Перед началом любой задачи сначала определить её scope: какие сервисы, платформенные компоненты и интеграции она реально затрагивает.

По умолчанию рабочий контекст состоит из трёх слоёв:

1. **Глобальный минимум проекта** — читается всегда.
2. **Документация и код затрагиваемого сервиса/сервисов** — читаются только файлы и разделы, необходимые для задачи; весь сервис заранее не загружается.
3. **Связанные сервисы и платформенные компоненты** — подключаются только когда задача действительно затрагивает соответствующую интеграцию или общий контракт.

Запрещено заранее загружать полную документацию всех сервисов «на всякий случай».

## Глобальный минимум

Для любой задачи достаточно начать с:

- `AGENTS.md`;
- этот документ (`docs/CONTEXT_SCOPE.md`);
- релевантного раздела `docs/ARCHITECTURE.md`, если задача затрагивает архитектуру или межсервисные контракты;
- `docs/DEVELOPMENT.md`, если задача требует локальной разработки/проверок;
- `docs/DEPLOYMENT.md`, только если задача касается CI/CD, инфраструктуры или выкладки;
- общих продуктовых решений из `ideas/company-internal-services-*/DECISIONS.md` и `DOCUMENTATION.md` только в части, необходимой для текущей задачи.

Не нужно читать все глобальные документы полностью, если задача не зависит от их содержания.

Список документов в README или индексе не является обязательным пакетом чтения. Полнота документации означает возможность найти нужную информацию, а не необходимость загрузить всё сразу.

## Контекст конкретного сервиса

Если задача относится к одному бизнес-сервису, основной контекст ограничивается:

- `apps/<service>/` — его frontend, если есть;
- `services/<service>/` — его backend, если есть;
- документацией этого сервиса рядом с кодом;
- `ideas/company-internal-services-*/services/<service>/` — продуктовым ТЗ и связанными артефактами.

Документация остальных сервисов не загружается, пока не появляется конкретная зависимость.

Пути не всегда совпадают с названием сервиса:

| Сервис | Frontend | Backend | Продуктовое ТЗ в `ideas/company-internal-services-*/` |
|---|---|---|---|
| Employees | `apps/web/` | `services/employees/` | `services/employees/` |
| CV | `apps/cv/` | `services/cv-converter/` | `services/cv/` |
| Dashboard | `apps/portal/` | только используемые endpoints Platform Core | только раздел текущего сценария Dashboard |
| Migration | раздел Migration в `apps/portal/src/main.js` | `services/migration/` | только документы текущего переноса; реализация — `docs/MIGRATION.md` |

Для остальных сервисов сначала найти их каталог по имени. Общие `packages/ui` и `packages/auth` читаются только в части используемого компонента или контракта.

## Прямые зависимости

Карта ниже нужна для навигации, а не для автоматической загрузки всего соседнего сервиса.

| Scope задачи | Возможные прямые зависимости |
|---|---|
| Employees | Keycloak/LDAP, RabbitMQ, Platform Core |
| Vacations | Employees; Clients только для подключений и согласующих account managers |
| Clients | Employees, Vacations, Timesheets (только сценарии отчётности/ТШ) |
| Timesheets | Employees, Clients, Vacations |
| Specialists | Employees |
| Recruitment | Employees; Specialists только когда сценарий явно затрагивает передачу/развитие специалиста |
| CV | auth и shared UI; Clients/Recruitment не подключаются ради будущих интеграций |
| Migration | только контракт целевого Employees/Vacations и схема legacy-источника текущего переноса |
| Dashboard / Portal | service catalog, auth, shared UI; бизнес-сервисы только для конкретного виджета/ссылки |
| Design System / shared UI | затрагиваемые frontend-приложения только для проверки совместимости |
| Auth / permissions | Keycloak, `packages/auth`, соответствующие сервисы, в которых меняются permission/scope |
| CI/CD / infrastructure | только сервисы, затронутые изменением deployment/runtime-контракта |

Наличие зависимости в таблице **не означает**, что её документацию нужно читать целиком. Например, при изменении отображения отсутствий в Timesheets достаточно контракта Vacations, который поставляет отсутствие; внутренние правила согласования отпусков в контекст не нужны.

## Когда расширять scope

Расширить контекст можно только при одной из причин:

- меняется API/event contract между сервисами;
- меняется permission/scope, который используется несколькими сервисами;
- задача меняет shared UI/auth/service catalog;
- требуется понять источник данных или бизнес-правило соседнего сервиса;
- тест или ошибка фактически проходит через несколько сервисов;
- изменение инфраструктуры влияет на runtime нескольких сервисов.

При расширении scope сначала читать минимальный контракт/документ интеграции. Полный контекст соседнего сервиса подключать только если минимального контракта недостаточно.

Зависимости не обходятся рекурсивно: если Timesheets использует Clients, это не требует чтения всех зависимостей Clients. Сначала ищется конкретный endpoint, DTO, событие или permission; читается его описание и, при необходимости, реализация. Если этого недостаточно, следует кратко обозначить причину расширения контекста.

Поиск путей и точечных ссылок (`rg --files`, `rg -n` по нужному символу/контракту) допустим. Пакетное чтение всех README, ТЗ, исходников или историй всех сервисов запрещено для задачи одного сервиса. История чатов используется только для отсутствующего решения по текущей задаче; она не заменяет актуальную документацию.

Примеры границ чтения:

| Задача | Необходимый контекст |
|---|---|
| Изменить ширину ячеек Timesheets | UI Timesheets и используемые стили/компоненты; backend соседей не нужен |
| Изменить запрет ТШ вне подключения | Timesheets и конкретный контракт периодов подключений Clients |
| Изменить renderer CV | CV renderer, схема CV и его тесты; Employees/Clients/Recruitment не нужны |
| Исправить меню одного сервиса | его пункты меню и используемый компонент `packages/ui`; другие приложения только при проверке изменённого общего компонента |

## Новые чаты и параллельная работа

При старте нового чата/рабочего контекста не восстанавливать историю всего проекта из предыдущих обсуждений.

Алгоритм:

1. определить сервисы из запроса пользователя;
2. прочитать глобальный минимум;
3. найти и прочитать относящиеся к задаче разделы документации этих сервисов;
4. проверить их текущий код и состояние веток;
5. добавить соседний сервис в scope только при обнаруженной интеграционной необходимости;
6. зафиксировать новые подтверждённые решения в документации, чтобы следующий контекст не зависел от истории чата.

Если пользователь говорит «работаем с Timesheets», это **не** является основанием читать Recruitment, Specialists, Vacations и Clients целиком. Vacations/Clients/Employees подключаются только в объёме конкретной зависимости текущей задачи.

## Исключения

Полный проектный контекст допустим для задач уровня:

- системный архитектурный аудит;
- сквозной security-аудит;
- глобальная миграция design system/auth;
- изменение общей модели permissions;
- реорганизация монорепозитория;
- CI/CD или инфраструктурное изменение, затрагивающее все сервисы;
- явная просьба пользователя изучить или проверить систему целиком.

Во всех остальных случаях используется минимально достаточный scope.
