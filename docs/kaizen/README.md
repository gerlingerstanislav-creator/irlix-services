# Межсессионная история проблем (Kaizen signals)

Этот каталог — **долговременная память о подтверждённых наблюдениях**, позволяющая замечать повторения между Chat/Work-сессиями. Он не является бэклогом, реестром идей, перечнем всех багов, статистикой надёжности или заменой GitHub/GitLab Issues. Задачи и решения об их выполнении живут только в действующем issue tracker; продуктовые требования — в приватном `ideas`.

## Организация

- **Один файл на класс проблемы**: `docs/kaizen/signals/<scope>--<fingerprint>.md` (например, `auth--missing-negative-permission-check.md`). Имя определяется областью и наблюдаемым признаком, **а не неподтверждённой причиной**.
- Файлы содержат **факты, даты, отдельные эпизоды, evidence и результат анализа**. Один и тот же CI retry, сообщения об одном инциденте или несколько комментариев к одному PR **не являются несколькими независимыми проявлениями**.
- Шаблон: [SIGNAL_TEMPLATE.md](SIGNAL_TEMPLATE.md). Не создавать пустые файлы сигналов, не делать отдельный индекс/реестр с дублированными статусами. Новый случай находить по пути/scope/ключевым словам; при совпадении **дополнять существующую запись**, а не плодить новую.
- **Сохранять и первое значимое проявление**, даже когда системная причина ещё не подтверждена: иначе следующий чат не обнаружит второе. Не записывать каждую мелкую опечатку, обычный unit-test FAIL или успешно исправленную локальную мелочь без признаков повторной стоимости/риска.
- В файл попадают не предложения «на будущее», а проверяемая история. Неподтверждённые объяснения явно обозначать гипотезами. Несогласованные/отложенные предложения **не** превращать в требования, Issues или скрытую работу; можно оставить факт проблемы без плана внедрения.

## Протокол PM между чатами

**В начале задачи** после определения scope: прочитать список файлов `docs/kaizen/signals/`, открыть только записи затронутого сервиса и общего контракта (auth/CI/QA, если относится к задаче); дополнить актуальными связанными PR/Issues/CI при необходимости. **Не** перечитывать весь каталог на каждую задачу. Если каталог пуст, отсутствие записей не означает, что исторических проблем не было. Не ссылаться на недоступные истории чатов как на проверенные источники.

**При появлении значимого события:** определить наблюдаемый признак, проверить совпадение с имеющимся файлом; добавить один эпизод с датой, фактическим результатом и ссылкой на доступное долговременное доказательство (Issue, PR, commit, CI run, тест/отчёт). Если ссылка на разговор недоступна, отметить факт как «сообщение владельца; независимое подтверждение отсутствует» и по возможности приложить проверяемый артефакт. Не выдумывать прогоны тестов, даты или количество повторов.

**Перед завершением задачи:** убедиться, что значимый обнаруженный сигнал записан **в Git и доступен другим чатам**, а не остался только в переписке/незамёрженной ветке. Обычно вести запись в отдельной docs-only feature-ветке с PR в `development` (чтобы не интегрировать незавершённый продуктовый код); соблюсти стандартные проверки. Если запись пока только в PR, **явно** назвать её недоступной в общей `development`-истории и дать ссылку; не заявлять сохранение межсессионной истории до merge.

**После появления нового независимого эпизода:** сопоставить его с прежними и применить порог из [основного регламента](../CONTINUOUS_IMPROVEMENT.md); PM предлагает улучшение самостоятельно при обоснованном сигнале. Повторение отражается в истории даже если владелец ранее отложил инициативу, но **не** даёт автоматического разрешения возобновить работу или повторно навязывать предложение без существенных новых фактов.

**Когда мера внедрена:** хранить ссылку на её PR/тест; следующий сопоставимый случай проверяет эффект. Не объявлять улучшение эффективным без наблюдения или доказательного теста. Историю не удалять при закрытии Issue: она нужна для будущих повторов.

## Ограничения безопасности и конкуренции

`irlix-services` публичный: **не записывать** персональные, коммерчески закрытые данные, секреты, реальные payload, содержимое приватного `ideas` и пользовательские переписки. Использовать обезличенное описание и разрешённые ссылки на артефакты; если даже обезличенный факт раскрывает чувствительное, хранить подробности только в приватном `ideas`, а в публичном Git — безопасный указатель без подробностей либо не публиковать сигнал. Доступ к приватному `ideas` нельзя предполагать.

Разные чаты могут одновременно встретить тот же сигнал: перед записью перечитать текущую `development`, проверить схожие файлы/PR, не перетирать чужие обновления и не force-push. Для параллельных изменений отдельные ветки и PR по общим Git-правилам. История переносится с кодом и документацией в целевой корпоративный GitLab при cutover без изменения смысла; **единственный активный issue tracker** выбирается по действующей политике.

История обновляется только когда ассистент фактически выполняет задачу с доступом на запись; это **не непрерывный фоновый мониторинг** и не автоматическое чтение всех чатов.
