# AuthZ V2: проверяемый переход к согласованной новой модели

**Статус на 29.10.2026:** код AuthZ V2 уже входит в production, но это **не означает активацию локальных матриц**. Глобальный Keycloak/JWT-контур и синхронизация связанных учётных записей подтверждены предыдущим deploy smoke; состояние семи `IRLIX_*_LOCAL_AUTHZ_ENABLED` нужно читать из фактических запущенных контейнеров, а не из Compose defaults. Read-only отчёт `scripts/authz/inspect_runtime.py` запускается в production verification, перечисляет только безопасные статусы и агрегаты; пока отчёт и ролевые E2E не получены, локальный cutover не принят. За identity отвечает Employees → подписанные роли Keycloak, за бизнес-разрешения — **каждый сервис отдельно**. Мультикомпанийности нет.

## Решение владельца 29.10.2026: закончить новую авторизацию, без постоянного legacy-contour

Приоритет — сделать самостоятельные persisted бизнес-матрицы сервисов
реальным источником разрешений, а не держать бесконечный параллельный
режим старой авторизации. Не требуется отдельный TEST-контур.
Проверка identity через Employees по текущему сотруднику, назначенным
ролям и сервисному admission остаётся обязательной: это новая утверждённая
архитектура, а не legacy grant. Секреты и рабочие данные не выходят
из production. После проверки новых маршрутов планируется
последовательная production-активация.

**Timesheets:** после одноразового импорта существующих бизнес-grants/deny
из Clients чтение и проверка разрешений идут только из собственной
`timesheets_role_permissions`. Runtime-запрос к Clients
`/permissions/me` больше не нужен для определения права на действия
Timesheets. Это также устраняет 503 у Timesheets при недоступности
старой Clients матрицы; Clients остаётся поставщиком бизнес-данных о
клиентских подключениях там, где они требуются для scope. Employees
`access/me` продолжает проверять идентификатор, отозванные роли и
`services.timesheets` на каждом защищённом запросе.

**Finance:** новые бизнес-разрешения читаются из собственной
`finance_role_permissions`, а не пересекаются с устаревшими
`Employees.permissions.finance.*` при каждом запросе. Согласованное
текущее Employees `services.finance` и проверка актуальных подписанных
ролей остаются обязательными. Перед включением Finance V2 приватный
экспорт только старых `employee_permission_rules` с
`enabled=false` по `finance.*` переносит явные ролевые запреты через
Employees → Finance сервисные процессы в матрицу Finance. Seeded grants
при необходимости становятся explicit deny; ранее редактированные
администратором V2-записи импорт не переписывает и аварийно
останавливается при конфликте. Импорт имеет постоянную отметку успешного
прохождения `IRLIX_FINANCE_V2_DENIAL_IMPORT_DONE` и не повторяется
при последующих релизах. После миграции изменения бизнес-прав Finance
выполняются в интерфейсе/сервисе Finance.

**Важно:** указанное изменение само по себе не включает
`IRLIX_TIMESHEETS_LOCAL_AUTHZ_ENABLED`; это отдельная production-операция.
Доказательства ролей и объектного scope не подменяются количеством строк
матрицы. Отказ от старой runtime-системы не даёт права неявно назначить
новые привилегии или раскрывать чувствительные объекты.

## Решение владельца 29.10.2026: импорт действующих доступов

Повторное бизнес-утверждение старых прав **не требуется**. Стартовая политика
V2 должна автоматически наследовать реально действующие старые разрешения,
запреты, индивидуальные ручные исключения и ограничения на конкретные объекты.
Это более позднее решение заменяет прежнюю оговорку о необязательной parity
**именно для первоначального переноса**. Дальнейшее расширение прав остаётся
отдельным продуктовым решением. Техническое доказательство отсутствия
эскалации и потери доступа всё равно обязательно.

Источники для переноса различны: Employees `employee_permission_rules`,
`access/me`, Clients `client_contour_permissions`, локальные legacy-gates
и маршруты backend каждого сервиса. Само наличие `service:*` не даёт право
автоматически перенести все действия с `scope=all`. Непереносимые
индивидуальные исключения/прямые объектные связи требуют безопасного
технического преобразования, а не нового утверждения владельцем.

Текущий обратимый этап охватывает **семь** сервисов: Finance, Equipment,
Clients, Timesheets, Vacations, Specialists и Recruitment. Clients копирует
реальные сохранённые legacy-строки вместе с явными `denied` без перезаписи
администраторских правок. Timesheets импортирует управленческие разрешения
из Clients через приватный in-memory service-to-service экспорт, включая
партнёрские часы и финальное утверждение; на каждом запросе старые
effective права и scope остаются верхней границей. Finance пересекает
новую матрицу с текущими персональными Employees permissions.
Все сервисы проверяют актуальный Employees service-entry.
Vacations хранит old own/team/all для сотрудников, руководителей, HR и
кадровиков: доступ к содержимому документов только сотруднику и кадровику.
У Specialists редактировать каталог, как и раньше, может только
platform-admin; общий head-шаблон не предоставляет это действие.

Условием **активации локального V2** остаются реальные подписанные
положительные и отрицательные role/object E2E, подтверждение переноса
пользовательских исключений и проверенный откат. Стартовые
`IRLIX_*_LOCAL_AUTHZ_ENABLED` по-прежнему выключены.
Резервные копии сохраняются только на защищённом production-хосте;
данные матриц и их аудит не публикуются в GitHub Actions.


## Требования к допуску

1. Собрать **полный** подписанный identity-контракт для каждого связанного с Keycloak сотрудника: один `employee-id`, актуальные `org:*` по всей иерархии, отдельные `head:*` по явным manager assignments и `special:*` по явным назначениям. Отозванные privileges и сменённые подразделения не могут оставаться действующими до истечения JWT. Доказать issuer, audience/client, signature, exp и защиту platform-admin (включая MFA и журнал), а не только наличие realm roles.
2. Для каждого сервиса сохранить backup действующей матрицы и ручных назначений **в защищённом окружении**, запретить передачу ФИО, ставок, документов, зарплат и других реальных данных в публичный GitHub или логи workflow. Не переносить `allowed=false` как явный запрет, если в legacy это означало «не назначено».
3. Сформировать проверяемую матрицу сценариев **целевой V2-политики**, отдельно для чтения, записи, администрирования и просмотра содержимого конфиденциальных объектов. Для первоначальной миграции неизменённые старые права являются эталоном: сверять allow/deny и own/team/all по каждому действующему бизнес-сценарию. Любое намеренное изменение должно быть отдельно зафиксировано; повышение доступа без такого решения запрещено.
4. Проверить V2 на **уровне объектов**: свои, текущих подчинённых, чужих, уволенных, старые периоды, изменённую цепочку менеджеров, кадровые документы, зарплаты, офферы и ставки. Проверять независимо требуемые allow и deny, не выводя эталон из прежней системы. Реальные персональные данные не передавать в публичный GitHub.
5. Отдельно проверить отрицательные сценарии: отсутствующий grant, явный deny, комбинации ролей, после отзыва admin/personnel-officer, подмена/preview токена, другой `employee-id`, недоступность Employees/Keycloak, чужой resource и отказ в 403 без утечки содержимого.
6. **Необязательно:** для диагностики неожиданных изменений можно использовать `php scripts/authz/compare_effective_grants.php /private/path/pair.json` в защищённой среде. `parity=false` не является автоматическим отказом, если изменение подтверждено целевой политикой. Реальные идентификаторы нельзя публиковать; для optional-сверки используются непрозрачные HMAC-ID, которые не выгружаются в artifacts.
7. Подтвердить отрицательные сквозные сценарии с реальными **подписанными** JWT и backend: пользователь не видит чужой файл даже по прямому URL; исчезновение меню не принимается за проверку; просмотр без управления и отдельные бизнес-ограничения (назначение approver, lock, статус и сроки) остаются обязательны.
8. Интегрировать ветку из свежей `development`, пройти exact-SHA CI/QA, Finance, Keycloak integration, browser smoke. Отсутствующий или отменённый workflow означает `NOT TESTED`, не `PASS`.

## Порядок переключения

- Заполнять новую persisted матрицу **только** явно подтверждёнными полномочиями. Пустая матрица = default deny, не автонастройка глобальных ролей `org:irlix` или `service:*`.
- Клиентские подключения и сотрудники в Clients, рабочие часы в Timesheets, финансовый ledger в Finance, отсутствия и кадровые документы в Vacations, кандидаты в Recruitment — остаются у своих доменных сервисов. Из других сервисов разрешается использовать доверенные идентификаторы/связи, но не прямые SQL-запросы к чужим таблицам.
- Переключать **по одному сервису**, с датой, ответственным, подтверждёнными ролями и списком обязательных положительных/отрицательных проверок. Перед включением все маршруты сервиса, включая вложения и approvals, должны применять объектный scope и бизнес-инварианты; недостающие правила не компенсируются старыми `service:*`.
- После включения повторить согласованные сценарии просмотра, изменения и отказов; продублировать аудит административных действий. Хранить закрытую запись результата внутри защищённого окружения (не в публичном репозитории).
- При возникновении эскалации, несогласованного изменения прав, массового 403/503 или missing role выполнить откат **только затронутого флага**, не восстанавливая старую матрицу поверх новых ручных настроек. Подтвердить восстановление существующих бизнес-сценариев. По умолчанию все `IRLIX_*_LOCAL_AUTHZ_ENABLED=false`.

## Выявленная проблема первоначального переноса (29.10.2026)

В production у Timesheets после миграции всего три локальные V2-строки. Миграция личного права добавляет `timesheets.mine.manage`, но не `timesheets.mine.view`. Поскольку V2 middleware требует `timesheets.mine.view` для GET `/api/workspace`, необходима отдельная сверка действующего разрешения из Clients и безопасное восполнение с сохранением явных запретов до активации. Три строки сами по себе не подтверждают полноту управленческих прав.

### Проверка первоисточника Timesheets перед исправлением

Read-only runtime-аудит дополнительно считывает агрегаты **старой** матрицы
`client_contour_permissions`: разрешённые и явно запрещённые legacy-роли
по `timesheets.mine.view`, управлению, аналитике и аудиту, а также булево
состояние `employee / timesheets.mine.view / own`. Имена сотрудников,
идентификаторы объектов, содержимое матрицы, секреты и персональные данные
не публикуются. Это различает два случая:

- Старое личное разрешение существует, но не импортировано: восстановить
  исключительно его текущий `allowed/scope/denied` через существующий
  безопасный Clients → Timesheets экспорт/импорт, не создавая новых grants.
- Старое разрешение отсутствует или запрещено: никакого автоматического
  `org:irlix` grant; сначала разобраться в фактически действующей политике
  доступа (в том числе отсутствии права на личный workspace).

Ни этот аудит, ни число заполненных строк не означает приёмку AuthZ V2.
Реальные role/object E2E и проверка отката остаются обязательны.

### Проверено по production legacy backend — 29.10.2026

Аудит `[authz-v2-readiness]` на production подтвердил: исходное
`employee/timesheets.mine.view` в Clients отсутствует, явных запретов
этого действия в матрице нет, а в Timesheets V2 оно не было импортировано.
Тем не менее **старый** маршрут `GET /api/workspace` пропускал пользователя
при наличии Employees `services.timesheets`, не требуя этой записи матрицы,
и возвращал только собственные записи сотрудника.

Импортёр Clients → Timesheets теперь в точном случае **отсутствующей**
исторической ячейки `employee/timesheets.mine.view` восстанавливает
`org:irlix → timesheets.mine.view: own`, не меняя старый Employees
service-entry и не расширяя доступ к чужим данным. Если исходная запись
существует (в том числе `allowed=false` или `denied=true`), fallback не
используется; она переносится/сохраняется в соответствии с прежней матрицей.
Существующие V2 записи не перезаписываются. Реальная SQLite-интеграция
проверяет повторный импорт и отрицательный сценарий явного запрета.
После релиза нужен **новый** runtime-аудит, подтверждающий отсутствие
критического пропуска. Это не заменяет подписанные E2E и испытание rollback.

### Дополнительный обнаруженный разрыв effective-проверки (29.10.2026)

При ревизии полного запроса в режиме Timesheets V2 обнаружено, что
`TimesheetsRoleAuthorization::restrictToLegacy` повторно сужал
`timesheets.mine.view` по пустой исторической ячейке Clients,
аннулируя добавленный при импорте `own` grant. Значит наличие новой
строки в production-счётчике само по себе **не** доказывало доступность
`GET /api/workspace` после переключения.

Исправление использует согласованный исторический факт: Clients возвращает
Timesheets отдельное минимальное булево свидетельство, что исходная
`employee/timesheets.mine.view` ячейка **отсутствовала**, а ни одна
действующая legacy-функциональная роль сотрудника не содержит явного
`denied=true` для этого действия. Timesheets применяет его только
если реально выдан собственный V2 grant и текущий Employees service-entry
разрешает Timesheets; максимум области данных в этом fallback — `own`.
Существующий old `allowed=false` или `denied=true` не может быть
подменён отсутствующей записью. Маркер не заменяет отдельные grants
управления, аналитики, партнёрских часов и права на чужие объекты.

Этот change-set требуется подтвердить точным CI и signed JWT / объектными
E2E в защищённом окружении. Пока они не пройдены, переключение запрещено.

## Оставшиеся доказательства

- Покрытие проверками согласованной V2-политики для типовых, составных и отозванных ролей, включая отрицательные объектные сценарии.
- Законченность `own/team/all` **для всех** маршрутов Vacations и непрозрачная работа с содержимым кадровых документов.
- Подтверждённая доступность реальных ролей, права администратора, rollback и приёмка отдельных сервисов. Один зелёный synthetic smoke недостаточен.

**Никакой массовой активации локальных матриц без обязательных backup, изолированных role/object E2E и отдельной приёмки по каждому сервису.** Само обновление кода или успешный smoke не является таким подтверждением.

## Защищённый production preflight (операционный этап, без переключения)

Однократный opt-in `[authz-preflight]` на коммите production-релиза через
существующий `CI` запускает `scripts/authz/production_preflight.py` через SSH.
Штатные релизы без маркера этот шаг не выполняют; новая отдельная workflow
не создаётся. Скрипт сначала проверяет фактические работающие контейнеры,
синхронизацию Keycloak, непустые V2-матрицы и обязательные permissions, а
также **отключённые** локальные флаги всех семи сервисов.

Для каждого сервиса создаётся новая root-only копия его матрицы и аудита на
production-хосте с использованием `backup_local_matrices.py`. Затем архив
восстанавливается в отдельную случайно именованную временную базу PostgreSQL,
проверяется количество строк матрицы и временная база удаляется даже при
неуспешной проверке. Скрипт не пишет в рабочие матрицы и не меняет флаги.
В GitHub Actions допускаются только статусы PASS/FAIL по сервисам, без
идентификаторов сотрудников, содержания матриц и путей архивов.
Закрытый минимальный receipt сохраняется в `/opt/irlix-authz-backups/`.

**Значение PASS:** защищённая копия и восстановление конкретной матрицы
технически подтверждены. Это **не** тест подписанных JWT/объектного scope,
не упражнение отката рабочего флага и не приёмка cutover. До отдельных
подтверждений таких сценариев 0/7 сервисов следует оставлять на legacy.
Если исходные/восстановленные количества расходятся, текущие флаги уже
включены или не подтверждён Keycloak — preflight прекращается без активации.

### Паритет Clients → Vacations: календарь специалистов

В legacy сотрудники с разрешённым входом в Clients могли обращаться к двум GET-маршрутам
Vacations — `api/client-service-calendar` и `api/client-service-absence-alerts` — даже
когда `services.vacations` выключен. Первоначальный V2 entitlement требовал
вход в Vacations и нарушал этот действующий контракт.

V2 сохраняет альтернативу `services.clients` только для этих двух GET.
При этом отдельное локальное `vacations.client-calendar.view`, текущая проверенная
роль сотрудника, принадлежность клиентской службе и для общего календаря
независимое разрешение Clients `specialists.view=all` остаются обязательными.
Доступ к workspace, документам, изменению отсутствий и другим маршрутам
через Clients-only не предоставляется. Негативные проверки добавлены,
но production signed role/object E2E по-прежнему обязателен.

## Финальная production-активация без отдельного TEST-контура

При явно разрешённом production release SHA с маркером
`[authz-v2-cutover]` существующий CI после deploy и browser smoke
запускает `scripts/authz/activate_local_v2.py`. Временно поддерживать
параллельную старую систему бизнес-прав после успешного включения не
требуется: семь `IRLIX_*_LOCAL_AUTHZ_ENABLED` хранятся в защищённой
серверной `.env`, сами backend используют собственные V2 матрицы.

Перед переключением скрипт проверяет работающую Keycloak/JWT-синхронизацию,
все семь таблиц V2 и критические grants, закрытые копии и успешный
`pg_restore`-прогон, а также одноразовое преобразование явных Finance
deny. Каждый backend пересоздаётся отдельно с `--no-build --no-deps`,
после чего проверяются **реальный container env**, доступность health и
отказ HTTP 401 по прямому API без JWT. После всех семи переключений
запускаются штатные `verify-stand`, `verify-timesheets` и release smoke.
Если этап не прошёл, все флаги, изменённые именно текущим запуском,
откатываются по одному с повторной health/deny проверкой, без изменений
данных или Keycloak.

Указанная автоматическая проверка не доказывает положительные реальные
role/object-сценарии каждого сотрудника (такие сценарии без тестовых
учётных данных остаются `NOT TESTED`), поэтому её нельзя выдавать за
универсальное доказательство корректности назначений. Но она позволяет
осуществить запрошенный переход на рабочей системе, **без создания
нового окружения** и без постоянной зависимости новых бизнес-прав
от старых runtime-матриц.
