# AuthZ V2: проверяемый переход к согласованной новой модели

**Статус:** подготовка в PR #709, не считать включённым в production. Ответственный за схему ролей: Employees → подписанные роли Keycloak. За бизнес-разрешения отвечает **каждый сервис отдельно**. Мультикомпанийности нет.

## Требования к допуску

1. Собрать **полный** подписанный identity-контракт для каждого связанного с Keycloak сотрудника: один `employee-id`, актуальные `org:*` по всей иерархии, отдельные `head:*` по явным manager assignments и `special:*` по явным назначениям. Отозванные privileges и сменённые подразделения не могут оставаться действующими до истечения JWT. Доказать issuer, audience/client, signature, exp и защиту platform-admin (включая MFA и журнал), а не только наличие realm roles.
2. Для каждого сервиса сохранить backup действующей матрицы и ручных назначений **в защищённом окружении**, запретить передачу ФИО, ставок, документов, зарплат и других реальных данных в публичный GitHub или логи workflow. Не переносить `allowed=false` как явный запрет, если в legacy это означало «не назначено».
3. Сформировать проверяемую матрицу сценариев **целевой V2-политики**, отдельно для чтения, записи, администрирования и просмотра содержимого конфиденциальных объектов. Модели old/new могут различаться намеренно: обязательного совпадения действующих effective grants со старыми нет.
4. Проверить V2 на **уровне объектов**: свои, текущих подчинённых, чужих, уволенных, старые периоды, изменённую цепочку менеджеров, кадровые документы, зарплаты, офферы и ставки. Проверять независимо требуемые allow и deny, не выводя эталон из прежней системы. Реальные персональные данные не передавать в публичный GitHub.
5. Отдельно проверить отрицательные сценарии: отсутствующий grant, явный deny, комбинации ролей, после отзыва admin/personnel-officer, подмена/preview токена, другой `employee-id`, недоступность Employees/Keycloak, чужой resource и отказ в 403 без утечки содержимого.
6. **Необязательно:** для диагностики неожиданных изменений можно использовать `php scripts/authz/compare_effective_grants.php /private/path/pair.json` в защищённой среде. `parity=false` не является автоматическим отказом, если изменение подтверждено целевой политикой. Реальные идентификаторы нельзя публиковать; для optional-сверки используются непрозрачные HMAC-ID, которые не выгружаются в artifacts.
7. Подтвердить отрицательные сквозные сценарии с реальными **подписанными** JWT и backend: пользователь не видит чужой файл даже по прямому URL; исчезновение меню не принимается за проверку; просмотр без управления и отдельные бизнес-ограничения (назначение approver, lock, статус и сроки) остаются обязательны.
8. Интегрировать ветку из свежей `development`, пройти exact-SHA CI/QA, Finance, Keycloak integration, browser smoke. Отсутствующий или отменённый workflow означает `NOT TESTED`, не `PASS`.

## Порядок переключения

- Заполнять новую persisted матрицу **только** явно подтверждёнными полномочиями. Пустая матрица = default deny, не автонастройка глобальных ролей `org:irlix` или `service:*`.
- Клиентские подключения и сотрудники в Clients, рабочие часы в Timesheets, финансовый ledger в Finance, отсутствия и кадровые документы в Vacations, кандидаты в Recruitment — остаются у своих доменных сервисов. Из других сервисов разрешается использовать доверенные идентификаторы/связи, но не прямые SQL-запросы к чужим таблицам.
- Переключать **по одному сервису**, с датой, ответственным, подтверждёнными ролями и списком обязательных положительных/отрицательных проверок. Перед включением все маршруты сервиса, включая вложения и approvals, должны применять объектный scope и бизнес-инварианты; недостающие правила не компенсируются старыми `service:*`.
- После включения повторить согласованные сценарии просмотра, изменения и отказов; продублировать аудит административных действий. Хранить закрытую запись результата внутри защищённого окружения (не в публичном репозитории).
- При возникновении эскалации, несогласованного изменения прав, массового 403/503 или missing role выполнить откат **только затронутого флага**, не восстанавливая старую матрицу поверх новых ручных настроек. Подтвердить восстановление существующих бизнес-сценариев. По умолчанию все `IRLIX_*_LOCAL_AUTHZ_ENABLED=false`.

## Оставшиеся доказательства

- Покрытие проверками согласованной V2-политики для типовых, составных и отозванных ролей, включая отрицательные объектные сценарии.
- Законченность `own/team/all` **для всех** маршрутов Vacations и непрозрачная работа с содержимым кадровых документов.
- Подтверждённая доступность реальных ролей, права администратора, rollback и приёмка отдельных сервисов. Один зелёный synthetic smoke недостаточен.

**Никакой production-выпуск без отдельного явного разрешения владельца.**
