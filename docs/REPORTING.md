# Результат и следующий шаг

Каждое сообщение владельцу — первичное понимание/план, промежуточный статус, ответ на вопрос, блокер и финальный результат — заканчивается ясным блоком о действиях владельца. Подробный итог нужен только при достижении конечной точки или реальном блокере; не отправляй полный отчёт после каждого чтения или коммита. Метки компетенций и таймеры не нужны.

## Последний блок любого сообщения

- **Что требуется от тебя:** назови конкретное решение, доступ или действие владельца. Если сейчас ничего не требуется, напиши ровно «Действий не требуется». Не перекладывай проверки и доступные действия агента на владельца.
- **Следующий шаг:** если задача ещё не достигла согласованной конечной точки, назови конкретное продолжение и статус: «продолжаю сейчас», «жду результат запущенной проверки», «ожидаю твоего решения/доступа» или «в этой сессии исполнение прекращено; для возобновления нужна новая команда». Не обещай фоновую работу после завершения сессии. При законченной задаче строка о следующем шаге не обязательна.

Этот блок ставь **последним**. Сообщение о статусе не отменяет исходный запрос. «Действий не требуется» неуместно, когда без решения владельца нельзя выполнить зависимую часть. Явная команда остановиться прекращает действия немедленно: кратко подтверди остановку и обозначь фактический остаток без дополнительных записей.

## Формат итогового ответа

1. **Что реализовано** — подтверждённый результат по согласованному объёму, 1–5 смысловых пунктов. Для исследования/аудита — что установлено. Неполный результат обозначить прямо.
2. **Сборка и деплой** — отдельная компактная строка на затронутый Git-репозиторий: точная ветка → состояние → фактические QA/CI/build/deploy/smoke → SHA → PR/Actions. Элементы через «·»; для нескольких репозиториев отдельные строки. В read-only задаче достаточно проверенного ref/SHA и «изменений нет», без выдуманной рабочей ветки/запусков.
3. Для production-релиза непосредственно под техническими строками — **«В релиз вошли»**, вертикальный нумерованный список всех смысловых изменений прежний→новый production SHA, включая другие задачи, инструкции и инфраструктуру. При незавершённой выкладке — «Кандидат на релиз», не опубликованный состав.
4. **Что требуется от тебя** и, если задача не завершена, **Следующий шаг** — последние строки ответа по правилу выше. Не прячь нужное решение посреди отчёта.

## Значение статусов

- Рабочая ветка / draft PR: работа не интегрирована; PR сам по себе не означает готовность.
- development: разработка интегрирована; после обязательных проверок согласованная задача разработки завершена, production не подразумевается.
- main: ref перемещён; production подтверждён только после успешных обязательных deployment/smoke. Неудачный/неполный deploy указывать прямо.
- PASS/FAIL/NOT TESTED/N/A — отдельно по фактическим проверкам. Не выдавать synthetic browser tests за real-API E2E или самопроверку за независимый QA.

Полнота, продолжение и принятие результата определяются [WORKFLOW](agent/WORKFLOW.md), Git-интеграция — [BRANCHING](BRANCHING.md) и [GIT_RELEASE](policies/GIT_RELEASE.md). Термины tracker labels и checkpoint различаются явно в [STATE](agent/STATE.md); не закрывать Issue как production-tested по одному development merge.

Подтверждённый Kaizen-сигнал/предложение можно кратко включить в эти блоки; отдельная обязательная секция не нужна. Предложение, согласование, внедрение и проверка эффекта — разные состояния. Доказательства и checkpoint должны быть доступны по ссылкам без публикации приватного содержимого.
