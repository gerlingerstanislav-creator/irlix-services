# Результат работы

Итог сообщает подтверждённое состояние задачи. Промежуточные сообщения по [WORKFLOW](agent/WORKFLOW.md) не являются финалом и не требуют полного шаблона. Метки компетенций, таймеры и отчёт после каждого коммита не обязательны.

## Формат итогового ответа

1. **Что реализовано** — результат по согласованному объёму, 1–5 смысловых пунктов. Для исследования/аудита — что установлено. Неполный результат явно обозначить и назвать остаток.
2. **Что требуется от тебя** — только действительно необходимое решение/доступ/действие, иначе «Действий не требуется». Не перекладывать доступные исполнителю проверки на владельца.
3. **Сборка и деплой** — внизу отдельная компактная строка на затронутый Git-репозиторий: точная ветка → состояние → фактические QA/CI/build/deploy/smoke → SHA → PR/Actions. Элементы через `·`; для нескольких репозиториев отдельные строки списка. В read-only задаче достаточно проверенного ref/SHA и «изменений нет», без выдуманной рабочей ветки/запусков.

При production-релизе непосредственно под строками — **«В релиз вошли»**, вертикальный нумерованный список всех смысловых изменений прежний→новый production SHA, включая другие задачи, инструкции и инфраструктуру. При незавершённой выкладке — «Кандидат на релиз», не опубликованный состав. Не дублировать Git-статус верхним бейджем или второй таблицей.

## Значение статусов

- Рабочая ветка / draft PR: работа не интегрирована; PR сам по себе не означает готовность.
- development: разработка интегрирована; после обязательных проверок согласованная задача разработки завершена, production не подразумевается.
- main: ref перемещён; production подтверждён только после успешных обязательных deployment/smoke. Неудачный/неполный deploy указывать прямо.
- PASS/FAIL/NOT TESTED/N/A — отдельно по фактическим проверкам. Не выдавать synthetic browser tests за real-API E2E или самопроверку за независимый QA.

Полнота, продолжение и принятие результата определяются [WORKFLOW](agent/WORKFLOW.md), Git-интеграция — [BRANCHING](BRANCHING.md) и [GIT_RELEASE](policies/GIT_RELEASE.md). Термины tracker labels и checkpoint различаются явно в [STATE](agent/STATE.md); не закрывать Issue как production-tested по одному development merge.

Подтверждённый Kaizen-сигнал/предложение можно кратко включить в эти блоки; отдельная обязательная секция не нужна. Предложение, согласование, внедрение и проверка эффекта — разные состояния. Доказательства и checkpoint должны быть доступны по ссылкам без публикации приватного содержимого.
