# Professional ChatGPT Skills ↔ роли Irlix Services

Этот регламент связывает **установленные пользователем профессиональные ChatGPT Skills** с существующими ролями команды. Skills — универсальные методики и инструментарий. Они **не заменяют** инструкции проекта, не запускают AI самостоятельно и не создают дополнительные контексты.

## Матрица

| Роль Irlix Services | Название профессионального Skill | Использовать для |
|---|---|---|
| `Analyst` | **Senior Business & System Analyst** | requirements engineering, permissions, BPMN/UML, criteria, impact analysis |
| `Designer` | **Senior Product UI/UX Designer** | UX, взаимодействия, таблицы и формы, адаптивность, визуальная проверка |
| `Developer` — PHP/Laravel backend | **Senior PHP / Laravel Backend Engineer** | Laravel, SQL, API, безопасность, тесты, backend review |
| `Developer` — JavaScript/Vue frontend | **Senior JavaScript / Vue Frontend Engineer** | Vue 3, TypeScript, компоненты, доступность, frontend tests |
| `QA` | **Senior QA Engineer** | тест-дизайн, негативные случаи, API/UI/E2E, permissions, регрессии и баг-репорты |
| `DatabaseEngineer` | **Senior Database Engineer** | прагматичная нормализация, ключи, целостность, SQL и safe migrations |
| `SecurityEngineer` | **Senior Application Security Engineer** | risk-based AppSec, auth/permission+scope, API, чувствительные данные |

PM по-прежнему координирует задачи и читает `.github/agents/PM.agent.md`. У `PlatformEngineer` и `ProductAdvisor` **нет обязательной пары Skill**: не подменять их искусственно одним из семи. Если это помогает узкой технической подзадаче, PM может назначить подходящую компетенцию, не меняя роль/полномочия агента.

Для full-stack задач `Developer:<service>` применяет **оба** профессиональных Skill к соответствующим частям кода. При реальном разделении на независимые Vue/Laravel subagents PM назначает каждому **свой** профиль и непересекающийся `write_scope`.

## Переносимые Skill bundles в репозитории

После подтверждённого импорта оригинальных пользовательских ZIP-файлов полный состав навыков хранится в `skills/<slug>/SKILL.md`, а ссылки и вспомогательные ресурсы — в соседних `references/`, `assets/`, `scripts/`, `tests/`, `examples/`. К пяти архивным навыкам добавлены два созданных в репозитории; фактическое наличие проверяется по `SKILL.md` и `MANIFEST.json`. Всего семь slug:

- `skills/senior-business-system-analyst/`;
- `skills/senior-product-uiux-designer/`;
- `skills/senior-php-laravel-backend-engineer/`;
- `skills/senior-javascript-vue-frontend-engineer/`;
- `skills/senior-qa-engineer/`;
- `skills/senior-database-engineer/`;
- `skills/senior-application-security-engineer/`.

**Статус источника определять по файлам, а не по этому документу:** если нужный `SKILL.md` ещё отсутствует в Git, не утверждать, что архив импортирован или прочитан. Инструкция и безопасный импорт целых ZIP: [skills/README.md](../skills/README.md), `scripts/skills/import.py`; после импорта проверять `python scripts/skills/validate.py`.

Если Skills доступны в репозитории, рабочая роль **предпочитает репозиторный Skill** в качестве переносимой, фиксированной версии. Персональный установленный Skill можно использовать дополнительно, если его версия доступна; конфликтующие правила эскалировать PM. Репозиторные инструкции `.github/agents/` и продуктовые ТЗ `ideas` неизменно выше в приоритете.

## Порядок выбора и приоритетов

1. `AGENTS.md` → `docs/CONTEXT_SCOPE.md` → относящиеся к задаче `docs/policies/`, `.github/agents/<Role>.agent.md` → только нужные ТЗ приватного `ideas` и исходники.
2. Определи **фактическую роль** и необходимую технологическую специализацию. Найди соответствующий установленный Skill по **точному названию** из таблицы.
3. Если среда **реально позволяет** прочитать/активировать Skill — используй его инструкции и применимые supporting files для работы роли. Не пытайся загрузить все семь Skills на любую задачу.
4. При противоречии между универсальными правилами Skill и реальными требованиями проекта **приоритет у утверждённых ТЗ, инвариантов безопасности, репозиторных архитектурных/CI правил и действующих контрактов**. Существенные противоречия передай PM, а не молча отменяй правила.
5. В отчёте роли PM получит имя **действительно использованного** Skill либо явное `Skill not available in this session`; не утверждать, что Skill прочитан/исполнен, если виден только его заголовок или его нет в текущем окружении.

## Обычный Chat

Сохраняется **один ассистент и один общий контекст**. Во время проходов Analyst / Designer / Developer / QA использовать Skill соответствующего этапа, **если он доступен в этой Chat-сессии**. Ролевые метки не создают независимых агентов. Не требовать от владельца повторного выбора всех Skills при каждом обращении; если конкретный Skill недоступен, использовать самодостаточные правила соответствующей роли в репозитории и при необходимости сообщить об ограничении. Не имитировать использование недоступного Skill.

## ChatGPT Work

PM выполняет план и **явно делегирует** затронутые роли, если subagents доступны в текущей Work-сессии. Каждому реальному subagent передаёт **его профиль из репозитория и точное имя нужного установленного Skill**. Subagent проверяет доступность Skill **в своём окружении** и только тогда применяет его. Доступность Skills в личном Chat пользователя **не гарантирует**, что тот же Skill можно читать из Work subagent. PM сохраняет результат проверки и не выдаёт назначение названия за факт запуска или чтения Skill.

Аналитик, дизайнер при аудите, QA и PlatformEngineer получают свои изолированные scope согласно `docs/AGENT_CONTEXT_PROTOCOL.md`; Skill — методика, а не повод передавать переписку или скрытые рассуждения другого агента. QA не получает внутренние выводы Developer даже при использовании общего набора профессиональных Skills.

## Самодостаточность и переносимость

**Источники истины по Irlix Services остаются в двух репозиториях:** `irlix-services` (код, инструкции, общие правила) и `ideas` (приватные продуктовые требования). Персональные ChatGPT Skills могут быть недоступны новому разработчику или другой сессии, поэтому **выполнение проекта не должно зависеть от знания их внутреннего содержания**. Репозиторные профили должны оставаться полноценными и достаточными как fallback. Полный набор Skills можно публиковать только после проверки содержимого и осознанного экспорта владельцем; приватные бизнес-данные из `ideas` по-прежнему не копируются в публичный Git.

Если установленные Skills недоступны текущему исполнителю, он **продолжает по репозиторным инструкциям** и отмечает ограничение; не блокирует реализацию, если методика Skill не содержит незаменимых для конкретной задачи процедур. Чтобы проверить интеграцию, запусти небольшую задачу и попроси PM назвать фактически доступные и использованные Skills в результатах, без выдуманного статуса.

**Граница возможного:** этот файл и `.github/agents/` настраивают **маршрутизацию инструкций**, но не устанавливают/включают ChatGPT Skills, не привязывают их к аккаунтам Work subagents на уровне платформы и не вызывают модель из GitHub Actions.
