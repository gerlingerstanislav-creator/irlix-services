# Контексты агентов

В ChatGPT Work координатор PM передаёт каждому делегированному агенту только утверждённые требования, необходимые файлы и результаты предыдущих этапов.

В обычном Chat роли выполняются одним ассистентом без технической изоляции контекстов.

## Матрица передаваемого контекста в Work

| Роль | Получает | Возвращает | Не получает как основание |
|---|---|---|---|
| **PM** | Запрос владельца, утверждённые решения, статусы и итоговые артефакты | Узкие поручения, исправления, итоговые отчёты | Полную историю одной роли для рассылки другим |
| **Analyst** | Цель, нужные разделы `ideas`, бизнес-правила и контракты | Согласованные критерии, переходы, права, вопросы | Гипотезы Developer как установленные требования |
| **DatabaseEngineer** | Затронутые таблицы, инварианты, реальные объёмы и миграции | Модель и trade-offs, integrity/index/migration findings | Ненужные чужие данные |
| **SecurityEngineer** | Затронутые trust boundaries, access-контракты и diff | Минимальные фиксы, severity, evidence/negative tests | Секреты/ПДн, заявления автора вместо проверок |
| **Designer** | Пользовательские сценарии, UI-критерии, дизайн-систему | UX/UI-контракт, состояния, a11y, responsive | Технические черновики реализации |
| **Developer:<service>** | Утверждённые ТЗ, UX/API-контракты, test design; при FAIL — баг-репорты | Код, PR/SHA, тесты, измеримые результаты, риски | Черновики и весь рабочий контекст Analyst/QA/Designer |
| **QA до разработки** | Оригинальные требования, acceptance criteria, матрицу ролей и состояний | Тест-дизайн с негативными, граничными, ролевыми сценариями | План Developer вместо ожидаемого поведения |
| **QA после разработки** | Требования, код/diff/PR, точный SHA, тесты и CI | PASS/FAIL/NOT TESTED, дефекты с evidence, покрытие | Самооценку, обоснования и догадки Developer как доказательство |
| **PlatformEngineer** | Архитектуру, auth/shared/API-контракты, diff | Контрактные риски и проверяемые заключения | Ненужные продуктовые детали и объяснения автора вместо проверок |
| **ProductAdvisor** | Цель и разрешённые ограничения, только по запросу | Предложения с рисками, фактами и допущениями | Секреты и приватные детали без необходимости |

Аудит **Analyst** по готовой реализации проводится по исходным критериям, фактическому поведению и diff, а не по ожиданиям Developer. Визуальный аудит **Designer** — по принятому UI-контракту и реально наблюдаемым рендерам/скриншотам, без авторских объяснений. Для этих аудитов PM по возможности использует **новый контекст или отдельного проверяющего**. QA всегда отдельный от Developer в Work.

Общий GitHub не обеспечивает строгую техническую изоляцию: коммиты, PR и логи могут раскрывать чужие выводы. Если независимость фактически нарушена, не заявлять «слепую проверку».

## Передача результатов через PM

PM выдаёт отдельной роли `task_id`, `role`, `phase`, `scope`, `source_sha`, утверждённые источники, `acceptance_criteria`, минимум необходимых `input_artifacts`, `read_scope`, `write_scope`, `forbidden_scope`, `requested_model`, `requested_reasoning_effort`, ожидаемый отчёт и зависимости. При повышении относительно профиля по умолчанию из `docs/AI_TEAM.md` добавляется `escalation_reason`. Для аудита запрещается менять бизнес-реализацию.

Роль возвращает PM: `task_id`, `role`, `phase`, `source_sha`, `status` (PASS/FAIL/BLOCKED/NOT_TESTED), подтверждённые средой `actual_model` и `actual_reasoning_effort` либо значение `unverified`/`unavailable`, проверяемые выводы, ссылки на факты, файлы, блокеры и следующий шаг. Запрошенную конфигурацию нельзя выдавать за фактически применённую без подтверждения. **PM передаёт другой роли краткий handoff из утверждённых решений и проверяемых фактов, а не полную рабочую переписку.** При FAIL Developer получает конкретные воспроизводимые дефекты; не весь контекст QA. Аргументация и доказательства сохраняются — запрещена лишь необоснованная передача чужих рабочих гипотез.

При параллельных Vue и Laravel subagents PM назначает общий утверждённый API-контракт и разные write scopes. Нельзя поручать нескольким агентам одновременную запись в одни файлы. Приватные `ideas` остаются закрытыми; без доступа отмечать NEEDS_INFO, без публикации секретов/ТЗ в открытом PR.

## Видимые отметки работы

В ходе существенных переходов и при блокерах показывай пользователю **короткие сообщения о ходе этапов, а не скрытые рассуждения**:

- `[PM]` — scope, распределение работы, ожидание, интеграция.
- `[Аналитик]` — согласованные требования, противоречия.
- `[БД]` — scoped data design и безопасная миграция (только при необходимости).
- `[Дизайнер]` — UI-контракт, наблюдаемые несоответствия.
- `[Разработчик]` — изменения, тесты, PR и SHA.
- `[Platform]` — контракты и инфраструктурные проверки.
- `[Безопасность]` — scoped AppSec и реальные негативные проверки (только при необходимости).
- `[QA]` — реально выполненные проверки, PASS/FAIL/NOT TESTED.

В **Work** состояние `назначен / выполняется / завершён / блокирован` показывается только если подтверждено механизмом делегирования. В **Chat** те же метки обозначают последовательные этапы одного ассистента и **не** подразумевают независимые контексты. Не выдавать поручение за выполненную работу. Для мелких задач достаточно одной-двух отметок, не создавать шум. Этапы и фактические статусы отражаются без обязательных оценок сроков и таймеров.
