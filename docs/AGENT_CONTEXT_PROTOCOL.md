# Контексты агентов

В ChatGPT Work координатор PM передаёт каждому делегированному агенту только утверждённые требования, необходимые файлы и результаты предыдущих этапов.

В обычном Chat роли выполняются одним ассистентом без технической изоляции контекстов.

## Матрица передаваемого контекста в Work

| Роль | Получает | Возвращает | Не получает как основание |
|---|---|---|---|
| **PM** | Запрос владельца, утверждённые решения, статусы и итоговые артефакты | Узкие поручения, исправления, итоговые отчёты | Полную историю одной роли для рассылки другим |
| **Analyst** | Цель, нужные разделы `ideas`, бизнес-правила и контракты | Согласованные критерии, переходы, права, вопросы | Гипотезы Developer как установленные требования |
| **Designer** | Пользовательские сценарии, UI-критерии, дизайн-систему | UX/UI-контракт, состояния, a11y, responsive | Технические черновики реализации |
| **Developer:<service>** | Утверждённые ТЗ, UX/API-контракты, test design; при FAIL — баг-репорты | Код, PR/SHA, тесты, измеримые результаты, риски | Черновики и весь рабочий контекст Analyst/QA/Designer |
| **QA до разработки** | Оригинальные требования, acceptance criteria, матрицу ролей и состояний | Тест-дизайн с негативными, граничными, ролевыми сценариями | План Developer вместо ожидаемого поведения |
| **QA после разработки** | Требования, код/diff/PR, точный SHA, тесты и CI | PASS/FAIL/NOT TESTED, дефекты с evidence, покрытие | Самооценку, обоснования и догадки Developer как доказательство |
| **PlatformEngineer** | Архитектуру, auth/shared/API-контракты, diff | Контрактные риски и проверяемые заключения | Ненужные продуктовые детали и объяснения автора вместо проверок |
| **ProductAdvisor** | Цель и разрешённые ограничения, только по запросу | Предложения с рисками, фактами и допущениями | Секреты и приватные детали без необходимости |

Аудит **Analyst** по готовой реализации проводится по исходным критериям, фактическому поведению и diff, а не по ожиданиям Developer. Визуальный аудит **Designer** — по принятому UI-контракту и реально наблюдаемым рендерам/скриншотам, без авторских объяснений. Для этих аудитов PM по возможности использует **новый контекст или отдельного проверяющего**. QA всегда отдельный от Developer в Work.

Общий GitHub не обеспечивает строгую техническую изоляцию: коммиты, PR и логи могут раскрывать чужие выводы. Если независимость фактически нарушена, не заявлять «слепую проверку».
