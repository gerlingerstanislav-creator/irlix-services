# Dashboard — каталог и действия сотрудника

## Цель и границы

`apps/portal/` остаётся главной страницей платформы (`/`) и содержит общее левое меню с разделами **Дашборд** и **Задачи** (`/tasks/`). Ресурсный монитор, карта сервисов и перенос данных сюда не входят — см. `docs/SYSTEM_FRONTEND.md`.

Компактный каталог выводит доступные сервисы горизонтальными плитками высотой около 64px. Состав, группы, ссылки и lifecycle metadata сохраняются в `packages/ui/src/serviceCatalog.js`; стадии Product lifecycle не показываются сотрудникам на плитках, но не удаляются из источника. Сам Dashboard остаётся первым пунктом левого меню; одноимённая плитка на текущей странице не дублируется. Поддерживается поиск, адаптивность и клавиатурная навигация. Неизвестные/отсутствующие entitlements не расширяют доступ.

## Действия и API

Доменные сервисы самостоятельно решают, какие действия являются актуальными; Dashboard не выводит их из сырых бизнес-таблиц. Первые источники:

- `GET /api/vacations/attention`: собственные плановые отпуска/отсутствия в пределах 45 дней и ещё не закрытые согласования текущего исполнителя, используя фильтрацию и scope `ApprovalController::index`;
- `GET /api/timesheets/attention`: незаполненные рабочие дни/незавершённое подтверждение за прошлый месяц и текущий начиная с 25-го числа; согласования руководителя по разрешённым подключениям только через effective Clients permissions + Timesheets scope.

Единый формат `{ data: [{ id, title, detail, kind, due_at, href }] }`, где `kind` — `attention` (требует действия) либо `upcoming` (предстоит), `due_at` — дата YYYY-MM-DD или null, `href` — внутренняя абсолютная ссылка. Идентификатор стабилен в пределах источника. Пользователь видит только разрешённые через Employees `data.services` источники; каждый API отдельно проводит authenticated/scope checks.

Сводка на Dashboard выводит первые пять задач; `/tasks/` — все, с фильтром. Сначала сортируются требующие действия, затем ближайший срок. Каждая задача — ссылка в соответствующий бизнес-сервис. После изменения состояния следующая выборка удаляет завершённые задачи; автообновление не чаще одного раза в минуту, без постоянного сохранения промежуточного состояния.

Ошибка одного источника **не превращается в «задач нет»**: интерфейс явно сообщает о неполных данных. Отсутствие permission исключает запрос к источнику. Задачи не агрегируются через прямое чтение чужих схем БД.

## Границы первой итерации

Не реализованы push-уведомления, snooze, подтверждение/завершение действий из Dashboard, полная шина событий для новых сервисов. При добавлении источника требуется: собственный доменный API, permission/scope тесты, отрицательные кейсы, корректные ссылки в конкретную запись, регистрация источника в `attentionModel.js`. Для рабочего календаря Timesheets сейчас используется проверка будних дней и подтверждённых отсутствий, а не отдельный сложный SLA планировщик; алгоритм требует валидации на реальных сценариях и возможного расширения производственным календарём.

## Проверки

1. Сотрудник видит только своё и доступные ему сервисы; РН — только согласования своего разрешённого scope; посторонний руководитель не видит чужих записей.
2. Ошибки Employees и источников не раскрывают данных.
3. Просроченные/ближайшие задачи группируются, завершённые уходят после обновления; дубликаты ключей внутри одного источника не допускаются.
4. Перейти по задаче можно прямым URL после входа в систему; Back/Forward и поиск не теряют навигацию.
5. Desktop 1300px, tablet, mobile и focus-visible; Dashboard по-прежнему доступен из левого меню.
