# Контроль переноса

## Назначение и границы

«Контроль переноса» — **единственный frontend Migration** для переноса, контроля,
сопоставления источников и операций со снимками. Устаревший интерфейс удалён;
его backend orchestration, строгая последовательность Inspect → Dry run →
Migrate → Validate, архивы, mappings, блокировки и API сохраняются. Частичный
перенос допускается только явно подтверждённой control-операцией.

Канонический маршрут System — `/system/migration/control/`. Старый
`/system/migration/` перенаправляется туда с сохранением параметров.
Для standalone аналогично: `/migration/control/`, а старые
`/migration/`, `/migration/console/` и `?view=control` нормализуются
после OIDC. В меню остаётся только «Контроль переноса»; второй экран
не загружается. Другие бизнес-сервисы не меняются.

Изменения этой задачи ограничены Migration: его приложением, backend, ops,
скриптами, тестами и документацией. **Нельзя переделывать Employees, Vacations,
Clients, Timesheets, другие сервисы или shared UI без отдельного прямого поручения
владельца.** Если для данных нет целевой возможности, результат — видимый
`deferred`/`unmapped` и отдельное предложение изменения целевого сервиса.

Текущая эксплуатационная предпосылка: пользователи ещё не редактируют целевые
сервисы. Это не отменяет проверки ссылок, дублей и согласованности mappings.
Релиз кода не запускает перенос автоматически. Legacy подключается только для
чтения. Управление и отчёты доступны только `platform-admin`.

Этот документ фиксирует согласованные требования и контракт реализации.
Чек-лист ниже — условия приёмки, **не утверждение о пройденном тестировании**.
Фактические PASS/FAIL и проверки конкретного SHA фиксируются отдельным отчётом QA.

## Дерево переноса и детализация

Экран организован как **одна табличная иерархия**: весь перенос → сервис → исходная
сущность/таблица. Все уровни занимают строки единой таблицы со строго общими колонками:
объект, статус, обработано/всего, без результата, ошибки, предупреждения,
полнота и действия. Раскрытие сервиса вставляет строки его сущностей непосредственно
под ним без сдвига показателей между колонками. На узких экранах прокручивается
таблица, а не вся страница; первый столбец и заголовки остаются видимыми. Верхняя строка содержит статус операции, полноту
доказательств, ожидаемые строки без результата и счётчики диагностических
событий. Строка сервиса содержит статус, обработано/всего (при наличии
достоверных чисел), полноту доказательств, ошибки/предупреждения и кнопку
**«Запустить перенос»**. При раскрытии сервиса строки сущностей показывают
назначение переноса (expected/excluded/undocumented), обработано/всего,
без результата и проблемы. Сырые данные полей и диагностики не загромождают
дерево.

Настройки видимости **отдельны для каждого сервиса**: у сущности есть
«Скрыть», а при наличии скрытых строк появляется кнопка
«Показать скрытые (N)». Она открывает отдельный список скрытых в
выбранной операции сущностей и позволяет вернуть одну строку или сразу все.
При отсутствии скрытых строк кнопка не занимает место в таблице. Список сохранён в
localStorage браузера по паре `service:legacy_table`, не по ID операции:
выбор версии, автоматическое обновление и перезагрузка страницы не
сбрасывают исключения. Настройка не передаётся в API и не меняет
исходную миграцию, архивы, полномочия или факт успешности этапов.
Если сущность исчезла в старой версии, она не показывается в её списке
скрытых, но настройка остаётся для версии, где сущность есть.

**Показатели сервиса по видимым сущностям** (обработано/всего,
без результата, количество групп и ошибок/предупреждений)
пересчитываются после исключения строк. Общая строка операции
также исключает их из счётчиков видимых ошибок и строк без результата.
Суммы не используются вместо неподтверждённых данных: если исход
или total любой видимой сущности неизвестен, не рисовать ложное
нулевое значение или прогресс. Процент и полоска показываются
при известных `processed` и положительном `total`; если они
отсутствуют — явно показывается отсутствие данных. Диагностические группы без достоверной привязки к таблице либо к
сервису остаются видимыми при фильтрации. Исключать разрешено только
группы сущности, реально скрытой в текущем дереве выбранной операции.
Если количество диагностических событий отсутствует или некорректно,
соответствующая сводка явно показывает «Неизвестно», а не 0.
Статус
фактической операции, подтверждения этапов и архивный отчёт при
скрытии строк **не меняются**. Текст в таблице и боковых
`UiDrawer` одинаковой гарнитуры Onest и размера из UI-токенов,
без изменения других сервисов и базовых компонентов.

Любой кликабельный показатель открывает `UiDrawer`: общий контекст
операции, сервис с причиной и этапами, сущность с outcome, поля
или ошибки/предупреждения. Количество ошибок — количество
диагностических событий, **не** уникальных source rows. Сначала можно
показать агрегированные группы; подробные элементы из полного
авторизованного JSON подгружаются **только по запросу**, без искусственного
лимита на три примера. Если полный список недоступен, это явно показано.

Выбор исторической операции полностью переключает дерево, диагностические
окна, stage/run и архив на **выбранный ID**; незавершённая загрузка предыдущей
версии не подменяет текущий отчёт. Запуск отдельного сервиса использует
существующий `POST /control/start` с `scope=<service>`: новая операция
не создаёт snapshot автоматически, не переписывает историческую версию
и не запускает остальные сервисы. Перед импортом требуется отдельно созданная совместимая ручная точка сервиса или общая точка. До начала записи backend проверяет её наличие. Кнопка блокируется при недоступной
связи, active worker или другой операции; перед записью требуется
отдельное подтверждение с объяснением риска частичной записи.
Неисполненный/неподтверждённый этап остаётся неизвестным, а не нулевым.

Верхняя часть экрана — **одна плотная строка**: заголовок «Контроль
переноса», компактный селектор текущей/исторической операции шириной до
280 px, кнопка «Новый перенос», небольшой прелоадер при ожидании backend,
кнопка остановки при активной операции и действие «Отчёт» (копирование готового безопасного текста).
Кнопка скачивания JSON убрана; внутренний JSON endpoint оставлен для проверок и техподдержки. Прелоадер находится именно внутри этой строки, не
создаёт отдельного вертикального блока и не скрывает предыдущие
доказательства при недоступном API. Лишние верхние отступы удалены.
Старой страницы и перехода на неё больше нет. В верхней строке также
расположена кнопка «Снимки». В каждой **строке сервиса** таблицы находится
шестерёнка «Настройки подключения»; она открывает форму для этого
сервиса без общего селектора. Форма сохраняет ручные read-only этапы Inspect и Dry run, проверку подключения и Clients APP_KEY. Из диагностики доступны подтверждаемое сопоставление legacy users → Employees и read-only подробности конфликтов периодов работы; записи разрешаются только при отсутствии активного переноса. При отсутствии операций показывается
стартовая таблица четырёх сервисов с действиями настройки.
На мобильном экране элементы строки переносятся, не создавая
горизонтального скролла страницы; селектор сохраняет поиск и полные
подписи в выпадающем списке.
Описание механизма, повторяющиеся строки статуса, пояснения про нули и
сырой диагностический текст удалены из основного экрана; объяснения,
этапы, подробности и доказательства остаются в соответствующих `UiDrawer`.
При активной операции кратко показан исполняемый сервис/этап. В таблице
дефис означает отсутствие подтверждённого показателя, а не ноль;
общий processed нельзя суммировать по нескольким этапам.
Кнопка «Запустить перенос» присутствует только у строк сервисов,
фиксирует конкретный сервис в диалоге подтверждения и не меняет
историческую операцию.

## Отчёт HTTP 500, настройки и блокировка нового запуска

При сбое агрегатора полного диагностического отчёта (`/control/operations/{id}/report`)
frontend не должен терять строку операции, настройки подключений и
возможность просмотра истории. Для обычного чтения интерфейс
использует отдельный host-side read-only `/control/operations/{id}/summary`.
На стороне `migration-ops` он исключает массивы сырых событий и
диагностических элементов **до** передачи в Laravel. Полный JSON сохраняется на сервере и доступен по защищённому API для технической диагностики, но **не предлагается оператору как отдельная загрузка**. Публичная кнопка «Отчёт» копирует текст с этапом, категорией, исходом и диагностическими признаками отказа.

Если `summary` не может быть построена, `migration-ops` возвращает
строго обозначенную degraded-сводку: ID и состояние операции из
сохранённого `operation.json`, `report_degraded=true`,
`REPORT_AGGREGATION_UNAVAILABLE`, `archive_complete=false`.
Она **не подтверждает** успех этапов или нулевое число ошибок;
исходные доказательства не переписываются. Исключения в журналах
публикуются только как класс без текста, содержащего приватные сведения.
Непредвиденный отказ full report возвращает безопасный HTTP 503 JSON
вместо необработанного HTTP 500. Настоящая причина прежних 500
устанавливается только по защищённым runtime-логам.

В таблице Control **все четыре** сервиса имеют доступные шестерёнки
настройки **сразу после названия**, без горизонтального скролла,
независимо от загрузки/сбоя JSON, выбора частичного historical scope
или свёрнутого корня. Сервисы вне выбранной операции помечены
«Не входит в выбранную операцию» и **не включаются** в её
агрегированные результаты. Изменения профилей всё так же запрещены
во время активного worker; только просмотр разрешён.

Кнопка «Новый перенос» не разблокируется при отсутствии отчёта или
просто по таймауту. Она подчиняется подтверждённому
`operation/console_operation/snapshot_operation/restore_status/active_runs`
и выводит конкретную причину блокировки (включая ID активной операции).
Автоматическое завершение старого worker, обнуление состояния, удаление
run, перезапуск или откат **не выполняются**. Если флаг активности
устарел, необходимо отдельно подтвердить исход на сервере.

## Недоступность Migration API и восстановление связи

Обновление состояния Migration Control никогда не оставляет неподвижный экран в
ожидании зависшего backend. Начальная загрузка показывает `UiLoader` из
`@irlix/ui`; если очередной запрос занимает больше ~900 мс, появляется
индикатор ожидания ответа. При 502/503, сетевой ошибке или таймауте последний
полученный отчёт остаётся доступным как **неподтверждённый**, а прелоадер
с сообщением об автоматической перепроверке показывается до восстановления
связи. **Чтение текущего состояния не ждёт полного диагностического JSON**:
его запрос выполняется независимо и ограничен частотой для неизменного
активного этапа (приблизительно раз в 30 секунд); на переходах между
этапами и при завершении он обновляется вне очереди опроса состояния.
Отдельный медленный или неуспешный отчёт не переводит успешный опрос
состояния в «API недоступен». Повторное чтение состояния выполняется
примерно раз в 1,5 секунды при активном переносе, 5 секунд в покое
и 2 секунды при ошибке связи, без перекрытия предыдущих запросов
состояния. Восстановление связи автоматически скрывает индикатор;
при смене исторической операции запоздавший ответ не должен подменять
выбранный архив.

Ошибки опроса, загрузки отчёта и подтверждения операции показываются
в **фиксированном уведомлении вне потока разметки**, которое не сдвигает
таблицу и тулбар вверх-вниз при повторных запросах. Место для небольшого
прелоадера в тулбаре постоянно зарезервировано. Новый перенос запрещён,
пока текущий worker не подтверждён как завершённый. **Запрос остановки
разрешён даже при ошибке чтения состояния**, если ранее известна активная
операция: оператор может отправить его независимо от опроса, без запуска
нового переноса. HTTP 202 означает лишь принятие и сохранение запроса.
Текущий этап и уже выполненные записи не прерываются и не откатываются;
приёма запроса недостаточно, чтобы считать операцию остановленной.
Если остановку нельзя подтвердить ответом API, интерфейс сохраняет
неизвестный статус и позволяет повторить запрос с тем же ID после проверки.

В standalone Migration до проверки доступа отображается `UiLoader`.
Сетевые/5xx ошибки сервиса проверки доступа повторяются автоматически с
ограниченным по времени запросом; подтверждённый отказ 401/403 и отсутствие
роли `platform-admin` не маскируются бесконечным спиннером. В старом
пульте первичная загрузка, замедленный ответ и повторная попытка используют
тот же компонент; legacy запросы ограничены таймаутами, включая получение
состояния, чтобы polling мог продолжаться. Детальный отчёт через `UiDrawer`
также имеет явный таймаут, не блокирует страницу.

Прелоадер показывает **ожидание доступа к backend**, а не успех миграции,
завершение записи или восстановление из бэкапа. Остановка и rollback не
выполняются автоматически. Ошибки экспорта отчёта вроде
`REPORT_EXPORT_COMMAND_FAILED` требуют закрытых логов `migration-ops`:
статус завершённого dry-run и наличие snapshot сами по себе не подтверждают
архив доказательств или возможность продолжить запись.

## Операции и результаты

Статус операции и полнота данных — разные характеристики. Успешное завершение
этапов само по себе не доказывает полный перенос всех исходных столбцов.

| Состояние | Значение для оператора |
|---|---|
| `queued` | Очередь зарезервирована, выполнение ещё не началось |
| `running` | Выполняется текущий этап; показаны сервис и фаза |
| `completed` | Запланированные этапы завершены; полнота оценивается по отчёту |
| `partial` | Есть выполненная работа и неперенесённые данные либо незавершённые сервисы |
| `failed` | Выполнение не удалось; причина и исход записей требуют отдельной оценки |
| `cancelled` | Запрос оператора исполнен на безопасной границе этапов |
| `interrupted` | Процесс ops прерван; исход активного этапа не доказан |

Запрос остановки содержит ID операции и непустую причину. Он не убивает worker
посреди записи: текущий этап завершается, затем новые этапы не запускаются.
До этой границы интерфейс показывает «остановка запрошена», а не «отменено».
Остановка, ошибка и перезапуск ops не являются автоматическим откатом.

История должна сохранять операцию, инициатора, время, выполненные этапы,
неисполненные этапы, причины остановки и ссылки на отчёты. Архив control хранится
отдельно от восстанавливаемых migration metadata. Числовой `run_id` после restore
может переиспользоваться: идентичность отчёта обязательно связана с операцией.
Недоступный старый отчёт обозначается как недоступный, без подстановки нового run.

## Инвентаризация и судьба данных

Inspect control получает перечень пользовательских таблиц и столбцов из catalog
источника, а не только из списка таблиц адаптера. Пустые, неизвестные и недоступные
таблицы остаются видимыми. Доступность, время наблюдения и полнота исследования
указываются явно. Неизвестное количество — `null`, а не ноль.

Для каждой исходной таблицы дополнительно фиксируется **намерение переноса**,
полученное только из явных правил полей: `expected` (есть проверенные доменные
mapping-правила), `excluded` (все описанные поля сознательно отнесены к
metadata/deferred/excluded) либо `undocumented` (решение неполное или отсутствует).
`expected` не означает, что каждая строка обязана создать отдельную target-запись:
конфликты, ссылки, алиасы и строковые проверки учитываются отдельно. Пустая таблица
или нулевые outcome-счётчики сами по себе никогда не превращают её в `excluded`.
Общий `unprocessed_rows` сохраняется как технический итог источника, но отчёт обязан отдельно показывать `expected_unprocessed_rows`, `excluded_unprocessed_rows` и `undocumented_unprocessed_rows`. Сознательно исключённые строки сами по себе не делают semantic coverage неполным; неописанные решения, deferred/unknown, ошибки и незавершённый ожидаемый перенос — делают.


Для каждого обнаруженного столбца показываются тип, статистика заполнения,
правило адаптера и судьба:

| Судьба | Что подтверждает |
|---|---|
| `direct` | Есть явное правило копирования в указанное целевое поле |
| `transformed` | Есть явное преобразование с описанным правилом |
| `reference` | Значение разрешается через mapping или проверенное соответствие |
| `metadata_only` | Источник сохранён для аудита; доменная сущность не импортирована |
| `deferred` | Перенос этой части явно отложен с причиной |
| `unmapped` | Проверенного правила нет; данные не объявляются перенесёнными |
| `excluded` | Явное обоснованное исключение, если оно предусмотрено реестром |

Правило поля описывает возможность адаптера, но не доказывает запись конкретной
строки. Источники значений статусов/типов включают PostgreSQL enum и явно
определяемые кодовые столбцы; значения перечисляются со счётчиками и NULL.
Неизвестное значение не получает выдуманный target-аналог.

Ограничения: наблюдения выполняются отдельными read-only запросами, не являются
единым замороженным снимком legacy и могут различаться при изменении источника.
Таймаут, отказ доступа или неподдерживаемый тип показываются как неполнота.
Список кодовых столбцов зависит от реестра и правил обнаружения; неизвестный
столбец нельзя считать покрытым только потому, что его имя похоже на целевое.
Неполный реестр правил консервативно оставляет поле `unmapped`, даже если другой
участок адаптера фактически использует его: это требует сверки, а не догадки UI.

Подтверждение полноты требует инвентаризации и сохранённого результата записи
для каждого сервиса выбранной области. Незавершённый или неархивированный этап,
а также отсутствующий сервис не могут давать `semantic_complete=true`.
Наличие одного `archive_key` недостаточно: файл этапа должен существовать и
соответствовать operation/run/service/mode. `failed_unique > 0` также всегда
запрещает `semantic_complete=true`, даже при `unprocessed=0`.
Живые счётчики не считаются сохранённым архивом.

## Прогресс и диагностика

Показываются общий и сервисный прогресс, фаза, уникальные обработанные строки,
известный объём и свежесть состояния. Неизвестный объём не превращается в процент.
Повторные ошибки одной строки не увеличивают число обработанных сущностей.

Нужно различать чтение, готовность Dry run, доменную запись, сопоставление ссылки,
проверку target, metadata-only, deferred, unmapped, blocked и unprocessed.
Суммы полей и суммы строк — разные измерения; их нельзя складывать в общий
«процент импорта». Например, разрешение users к существующему Employees — ссылка,
а не создание сотрудника. Сохранение source payload в metadata не равно импорту.

Диагностика группируется по корневой причине и сервису с полным числом случаев.
Таблица и severity должны сохраняться в деталях, чтобы одинаковые коды разных
контекстов не скрывали последствия. Копируемый диагностический текст по каждому
сервису содержит точный подтверждённый этап (либо явно «неизвестен»), статус,
run ID, состояние записи, затронутые сущности, причину, последствия и полноту
доказательств: архив этапа, инвентарь, diagnostics и outcome записи. Неизвестный
исход не превращается в ноль, `not_started` или rollback. Полный JSON отчёта
остаётся отдельным download и формируется сервером из всего отчёта,
без перелистывания 200-строчных страниц в браузере. Группировка не заменяет
отдельные случаи и не должна ограничиваться первыми 40 группами.

Экспорт предназначен для администрирования и может содержать чувствительные
диагностические сведения. Публичные Git, PR и CI не являются местом для отчётов
реального переноса. Credentials, APP_KEY, ciphertext, private traceback и
необработанные source payload не должны попадать в текст для чата и экспорт.

## Повторы и безопасность

Новый запуск допускается поверх частичного результата; обязательного
автоматического rollback нет. Перед запуском проверяются отсутствие активного
worker, доступное read-only подключение и контрольная точка. Предыдущий отчёт
остаётся историческим: новая проверка не переписывает его результат.

Неизвестные поля и статусы отражаются как неперенесённые данные. В control
безопасные независимые строки могут продолжать обработку, а зависимости от
неперенесённой строки получают `dependency_blocked`. Это не разрешение писать
небезопасные значения. Неоднозначная identity, отсутствующий target по mapping,
нарушение FK, конфликт natural key и опасные пересечения периодов блокируют
соответствующие записи. Неопределённый исход живого worker блокирует новый запуск.

Повтор использует сохранённые target IDs и обновляет только предусмотренный
адаптером payload. Отсутствующие в новом источнике строки не удаляются автоматически.
Employees предшествует Vacations и Clients; Timesheets зависит от Employees и
Clients. После повторного изменения зависимого набора нужна новая проверка
потребителей; старое успешное Validate не доказывает актуальность после повтора.

**Известная граница безопасности:** target commit и сохранение mapping в SQLite
не составляют одну транзакцию. Сбой между ними может оставить target без mapping.
Кроме того, защита natural key в общем `write()` действует только когда адаптер
передал явный unique key; не все записи имеют такой ключ. Поэтому отсутствие
mapping не доказывает отсутствие ранее записанной сущности. Нельзя обещать
безусловную идемпотентность, автоматически сопоставлять по похожему имени или
молча создавать дубль. Такой случай требует диагностики и явной сверки.

## Откат

Контрольная точка — возможность восстановления, а не доказательство выполненного
отката. История должна различать `not_requested`, `in_progress`, `proven`,
`partial`, `unknown` и `failed`. Доказанный результат требует подтверждения всех
частей scope: целевой БД, metadata и документов, когда они входят в снимок.
Один успешный subprocess или существующий архив этого не доказывает.

После частичного restore или неопределённого COMMIT состояние явно остаётся
partial/unknown. Оператор руководствуется restore diagnostics и не считает
данные исходными по одному статусу операции. Существующие safeguards restore
и подтверждения `RESTORE <SCOPE>` не ослабляются новым интерфейсом.

Новые снимки включают контрольные количества и отпечатки строк/последовательностей,
metadata, ключа и дерева документов. После восстановления выполняется независимая
сверка до возобновления записи и проверка после обновления схемы. Старые снимки без
этих данных остаются доступными, но не получают расширенное подтверждение.
История control и ранее подтверждённый реестр соответствий корпоративных логинов
намеренно сохраняются вне бизнес-отката; подтверждение относится к составу снимка.

При восстановлении Employees или всех сервисов временно останавливается также
зависимость проверки прав Employees. В этот период authenticated state/report могут
быть недоступны: интерфейс сохраняет последнее состояние с явной отметкой отсутствия
связи. Проверка прав остаётся закрытой при отказе зависимости, без кэша разрешений.
После запуска Employees состояние и доказательства перечитываются автоматически.

## Контракт control API

PHP публикует авторизованный proxy `/api/migration/control/*`; ops endpoints
являются внутренними. Названия приведены относительно внутреннего ops API.

| Метод и путь | Контракт |
|---|---|
| `GET /control/state` | `operation`, `history`, `snapshots`, `restore_status`, `console_history`; может дополнительно включать текущую `console_operation` для общей блокировки |
| `GET /control/operations/{id}/report` | `operation`, `runs`, `root_cause_groups`, `chat_summary`; инвентаризация и архивные события могут дополнять объект |
| `POST /control/start` | `scope`: реализованный сервис или `all`; `confirm: true`; создаёт операцию **без снимков**; требует совместимую вручную созданную точку для каждого сервиса или `all` |
| `POST /control/snapshot` | отдельное ручное создание контрольной точки `scope` | 
| `POST /control/restore` | отдельный откат к выбранной `snapshot_id` с `RESTORE <SCOPE>`; не запускает перенос |
| `POST /control/cancel` | `operation_id`, непустая `reason` до 500 символов; запрашивает остановку между этапами |

Старые `/console/*` не включают tolerant mode автоматически. Оба интерфейса
используют общую reservation/блокировку: одновременный запуск legacy API и control
пульта запрещён. При недоступности ops действия блокируются, повторная запись
«наугад» не выполняется. Ошибки авторизации — 401/403, неподходящие параметры —
422, занятый контур — 409; окончательные коды проверяются по proxy-контракту.


### Повторяющаяся ошибка экспорта после Clients dry-run

Два наблюдаемых запуска (21 октября 2026 г., 21:01 и 21:31 UTC)
завершили Clients dry-run, но не сохранили доказательный JSON:
`REPORT_EXPORT_COMMAND_FAILED` и `missing_archive_key`. До исходной
ошибки PHP источник не доказан: это **не** подтверждение успеха проверки,
не причина запускать импорт снова и не доказательство отката.

При ненулевом коде `migration:control-report` CLI выдаёт только
`CONTROL_REPORT_FAILURE|<PHP exception class>|<numeric code>|<filename>|<line>`,
без исходного текста исключения (он мог содержать SQL, source values,
DSN и персональные сведения). Координатор заносит исключительно
проверенную по строгому шаблону категорию, номер строки и exit code в
приватный архив/операторскую сводку. `exit=137` без такого маркера
дополнительно помечается как SIGKILL с рекомендацией проверить лимиты
памяти; это не является доказательством OOM. Сырой stdout/stderr команды
не возвращается через API, не сохраняется в operator report и не
публикуется в GitHub Actions.

Для снижения пикового потребления памяти экспорт использует
потоковое чтение SQL-строк конфликтов, событий и инвентаризации без
промежуточной материализации всех коллекций. Все исходные записи
диагностики по-прежнему включаются в итоговый неизменяемый JSON;
предельного лимита выборки нет.

Повторный dry-run или миграция не запускаются выпуском кода.
Точный PHP category/line при новой попытке либо защищённые
runtime-логи предыдущего запуска необходимы для подтверждения
первопричины. Исторические отчёты не переписываются.

### Ошибки экспорта архивов

Worker со статусом `completed` не доказывает, что архив этапа сохранён. Если файл отсутствует, сервис нельзя объявлять успешно завершённым; отчёт должен показывать точный этап, ID запуска и отсутствие подтверждения. В новом запуске ошибка экспорта сохраняет публичный код категории (timeout, invalid JSON, command failure, I/O failure, identity mismatch или write failure). Полные технические детали остаются в защищённых журналах. Ошибка dry-run до migrate позволяет говорить о незапущенной записи данного сервиса, но не об откате ранее перенесённых данных. Старые архивные отчёты неизменяемы.

### Ручные контрольные точки и давность записи (22.10.2026)

Создание точки больше не является шагом `/control/start`: оператор запускает `POST /control/snapshot` отдельно. В строке «Весь перенос» и в каждой строке сервиса доступны «Создать точку» и «Откат к точке» с ограничениями доступа платформенного администратора. Восстановление требует выбора совместимой точки и подтверждения `RESTORE ALL` или `RESTORE <SERVICE>`. Никогда не запускается автоматически по кнопке переноса.

`GET /control/state` публикует `last_migrations`: дату последней архивированной стадии **записи** `migrate` по сервису. Источником служит доказательство, привязанное к `operation_id` и `run_id`, а не сухая дата Dry run, создание снимка либо успешность операции в целом. Возраст больше **24 часов** отображается красным; когда архивных доказательств нет, интерфейс показывает «Нет подтверждённой записи» без выдуманной даты. Для общей строки берётся самая старая подтверждённая дата всех четырёх сервисов; если хотя бы один неизвестен, статус общий не подтверждается. Отметка о прошлой записи не доказывает актуальное состояние после restore.

Для следующего сбоя экспорта (в частности, Timesheets `dry-run`, `exit=255`) операторский «Отчёт» дополнительно содержит: компонент `migration:control-report via docker exec`, operation/run ID, exit code, наличие и безопасный fingerprint PHP-маркера, классификацию Docker/PHP, статус сохранения закрытого server-side лога. Вывод subprocess может содержать персональные данные и сохраняется только на защищённом хосте (`/ops/control-reports/<operation>/private/export-<run>.log`, 0600); наружу не возвращается. `exit=255` без PHP-маркера означает отказ транспорта/контейнера на этапе экспорта, **но не доказывает окончательную первопричину** — нужно проверять Docker и worker. Новая попытка переносов релизом не запускается.

### Плотность таблицы и диагностика исторических отказов (22.10.2026)

Таблица «Контроль переноса» занимает **оставшуюся доступную высоту** внутри System/Migration, а не ограничивается `max-height: calc(100vh - 215px)` с высотой по содержимому. Прокручивается только внутренний контейнер таблицы; заголовок закреплён. Столбцы стали компактнее: действия работы с переносом, отметка времени последней записи — в колонке «Действия», а создание и восстановление точек отката — **в отдельной девятой колонке «Точки отката»**. Для строк сущностей предусмотрена пустая ячейка девятой колонки, чтобы сетка оставалась выровненной.

По подтверждённому сбою `#1792639810384241` / `timesheets dry-run #186`: стадия dry-run завершилась `conflicts`, но экспорт доказательств через `docker exec` завершился `exit=255` без PHP-маркера. Из имеющейся публичной диагностики **нельзя** установить, вызван ли сбой отказом OCI/Docker, памятью, состоянием контейнера или ошибкой экспортирующего процесса. Код не должен объявлять `exit=255` самостоятельным доказательством недоступности контейнера.

Операторский защищённый endpoint `GET /control/operations/{id}/summary` теперь **дополняет** ранее сохранённый текст «Отчёта» распознанным безопасным кодом из хостового файла `/ops/control-reports/<operation>/private/export-<run>.log` (0600): OCI exec failure, Docker daemon unavailable, container not running/not found, transport disconnect, memory exhaustion, host process limit, disk full, PHP fatal или `UNCLASSIFIED_EXPORT_EXIT`. Исходный текст stderr/stdout, команды с аргументами, имена клиентов, пути БД, SQL, DSN и персональные данные никогда не возвращаются. Оригинальный неизменяемый архив операции остаётся неизменным; новое обогащение является отдельной read-only операторской сводкой, применимой и к историческому `run #186`. При следующем отказе фиксируется также ограниченный снимок состояния Docker (`running/exited/restarting`, OOMKilled, exit code), если `docker inspect` доступен. Никакой повторный перенос/снимок/откат код диагностики не инициирует.

### Timesheets dry-run: устранение переполнения памяти экспортёра (22.10.2026)

Инцидент `#1792641786136053`, Timesheets `dry-run #190`: worker зарегистрировал `conflicts`, но при `migration:control-report` экспорт завершился `exit=255`. Защищённый журнал классифицирован `MEMORY_EXHAUSTION_EVIDENCE`. Это **сбой формирования диагностического архива**, не доказательство ошибки переноса данных; `migrate` не запускался. Конкретная таблица/строка исходных конфликтов неизвестна, поскольку старая попытка не успела сохранить доказательства.

Экспортёр ранее накапливал в памяти все подробные diagnostic `items` (десятки тысяч предупреждений Timesheets), одновременно группируя их в несколько массивов. Теперь `migration:control-report` возвращает точные `diagnostics.occurrences`, `items_total`, `groups`, `affected_rows`, outcomes, но содержит не более **256** подробных `items`, при этом `items_complete=false` явно помечает, что inline-представление — выборка, а не полный источник доказательств.

Координатор в таком случае **обязательно** запускает независимую команду `migration:control-report-items`: она читает конфликты cursor-ом и выдаёт безопасные диагностические записи построчно. Stdout записывается сразу в приватный временный JSONL-файл на хосте (не через `capture_output` и без полной загрузки в память), затем проверяются `operation_id`, `run_id`, количество строк, завершающий маркер и SHA-256. Только после доказанного завершения файл публикуется в `/ops/control-reports/<operation>/runs/<archive>.items.ndjson` (0600), а его metadata (`key/count/sha256`) включается в **неизменяемый** основной архив этапа. Если подробный архив недоступен или счётчики/идентичность не совпали, продолжение переноса блокируется. История, группы причин и общее количество сохраняются; подробные записи не отбрасываются и не попадают в публичный операторский ответ целиком. В UI отображаются компактные группы и ограниченная выборка; полный массив остаётся в проверенном закрытом хостовом архиве.

Сокращена дополнительная память на индексацию dependency roots: они формируются только для действительно связанных строк отдельным cursor-проходом. Без изменения правил `dry-run`, маппинга исходных сущностей, норм часов, снимков и откатов. Исправление устраняет обнаруженный профиль памяти, но фактическое наличие бизнес-конфликтов Timesheets выясняется по следующему запуску; их пока нельзя объявить разрешёнными.

### Timesheets: пакетная обработка больших таблиц (22.10.2026)

Причина повторяющихся проблем: общий `SchemaMigration::extract()` материализовал полную таблицу legacy `timesheets` (десятки тысяч строк) до начала доменных проверок, затем `validate()` повторял полный запрос. С учётом промежуточных сопоставлений и диагностик это приводило к высоким пикам памяти, а per-row отчёт дополнительно мог переполнять память (см. раздел про OOM экспортёра).

Новая реализация поддерживает **отложенные исходные таблицы** в общем слое `SchemaMigration`. Пока это применяется только к `timesheets.timesheets`; справочники `users`, `members`, `rates` и таблицы исторических подтверждений/отсутствий пока сохраняют существующий путь. Для фактов Timesheets используется чтение `SELECT * FROM public.timesheets WHERE id > :last AND id <= :highWater ORDER BY id LIMIT 1000` с read-only транзакцией на **каждую страницу**. Размер конфигурируется `migration.timesheets_batch_size` с пределами 100–2000; по умолчанию 1000. Первоначальные `COUNT(*)` и `MAX(id)` определяют границы; каждая полная итерация проверяет число строк, а последовательные проходы — SHA-256 содержимого **каждой** страницы. При расхождении импорт прерывается, а не корректирует исходные строки автоматически.

**Целостность между стадиями:** для `ControlMode` после завершённого `dry-run` каждого пакета сохраняются границы `first_source_id/last_source_id`, число строк и SHA-256 в таблице `migration_batch_progress`. Перед `migrate` пакеты сравниваются с контрольными значениями **только из completed dry-run той же контрольной операции**; чужой или старый dry-run не допускается. Эта проверка происходит на предварительном чтении до начала целевой записи, затем пакеты повторно сверяются по мере обработки. `validate` также читает источник порциями и проверяет исходный отпечаток в режиме ControlMode. Чтение справочников и бизнес-правила часов остаются прежними: совокупные часы одного сотрудника за день проверяются **между страницами**, включая посторонние существующие записи; целевой индекс и сопоставления защищают от дублирования на повторном запуске.

**Прогресс:** каждая фактически обработанная страница регистрируется в `migration_batch_progress` с принадлежностью к `run_id`, диапазоном ключей, числом строк и SHA-256. `state=processed` означает окончание обработки диапазона, **не** успешный импорт каждой строки и не окончательное бизнес-согласование. Если worker аварийно завершился внутри пакета, текущий пакет остаётся незавершённым; повторный запуск использует идемпотентные сопоставления/intent-журнал, а не безусловно пропускает старые страницы. **Быстрое возобновление непосредственно с последнего подтверждённого пакета без повторной валидации предыдущих пакетов пока не реализовано:** такой пропуск небезопасен без сверки исходного содержимого, целевых часов, уникальных ключей и всех предупреждений. Решение о его включении требует отдельного полного регрессионного покрытия. Не утверждать, что уже реализовано ускоренное возобновление.

Согласованность источника **не является межзапросным PostgreSQL snapshot**: `COUNT/MAX` и страницы читаются разными read-only транзакциями. Система обнаруживает изменения между проходами, но для юридически/финансово точного production cutover требуется приостановить изменения в legacy Timesheets либо обеспечить проверяемый неизменяемый снимок источника. Ни создание target snapshot, ни автоматический rollback эта доработка не включает.

QA: интеграция с 30 синтетическими исходными строками в нескольких страницах, dry-run без записи, повторный идемпотентный импорт, проверка источника между проходами и потоковое чтение 100 000 синтетических строк с ограниченным ростом памяти. Требуется терминальный PASS тестов точного коммита и production-валидация перед признанием задачи завершённой.

## Хранение точек отката — управляемый лимит (22.10.2026)

В System → Контроль переноса → Снимки доступна настройка «Хранить последних точек отката на контур» (целое число 1–20, по умолчанию **2**). Политика едина для пяти независимых областей: Employees, Vacations, Clients, Timesheets и All; отдельный выбор контура ниже не меняет общее значение. Конфигурация сохраняется в закрытом host volume Migration Operations `/ops/snapshot-retention.json`, переживает перезапуски и восстановление SQLite.

После подтверждённого изменения лимита сервер **немедленно** пытается удалить все более старые проверенные консольные точки каждого контура; новые успешные снимки также запускают очистку, при старте migration-ops после безопасного развёртывания применяется дефолт 2, а регулярный host maintenance применяет **ту же** политику. Удаление необратимо; UI отдельно подтверждает его и сообщает число удалённых точек. Проверка не полагается на один frontend: endpoint доступен только `platform-admin`, разрешает диапазон 1–20 и отклоняет операцию при активном coordinator/worker/restore; во время чистки используются общий exclusive snapshot lock и SQLite write lock.

Неверифицированные/неизвестные каталоги, симлинки, файлы с неожиданной структурой и точки, помеченные вручную `.keep`, **не удаляются** — они отражаются в числе пропусков. Статус `restored` сам по себе не удерживает старый snapshot: неизменяемое доказательство восстановления остаётся в защищённой истории операций. Старые отдельные (legacy) Employees/Vacations snapshots не входят в эту политику; их удаление остаётся отдельной ручной операцией. При недоступности статуса worker или повреждённой политике очистка запрещена (fail closed); отсутствие файла настройки интерпретируется как дефолт 2.

### Timesheets: отложенные внешние специалисты и список неперенесённых members (2026-10-22)

По решению владельца подтверждённые внешние участники исторической Timesheets не импортируются в текущую employee-only модель. Явные `memberable_type` (`subcontract`, `contractor`, `external`, `partner`) получают `EXTERNAL_SPECIALIST_DEFERRED` (`warning`); то же правило применяется к принадлежащим им `rates` и исходным `timesheets`. Все три уровня сохраняют исходную строку в приватной migration conflict metadata, получают отдельный `deferred` в источниковых outcomes и не создают mappings/часы в целевой БД. При наличии ранее подтверждённого mapping по исключаемой строке операция **блокируется** как identity collision; неизвестные типы не исключаются по догадке. Остальные внутренние ошибки не исчезают автоматически. Повторный импорт внешних специалистов потребует отдельной новой реализации и сверки.

В таблице Timesheets выводится постоянная пометка о наличии внешних участников в отчёте и действие «Неперенесённые members». `GET /api/migration/console/runs/{run}/unresolved-members?operation_id=<operation>&page=1` читает старые `members` только через `LegacyReader`, сравнивает с подтверждёнными mappings, по 100 строк возвращает исходный ID, тип и ID внешней связи, проект, состояние и причину. Поле ФИО заполняется только доступными именами из `members`, уникальным UUID-сопоставлением `members.employee_id → legacy users.employee_id`, либо подтверждённым UUID/login-маршрутом к Employees; совпадения случайных числовых ID из разных legacy БД не используются. Невозможность доказать ФИО честно указывается в UI. Ответ — **текущее** состояние и может не совпасть с архивной операцией.

Маршрут доступен только `platform-admin`, требует связанного `operation_id` (защита от повторно использованных run IDs после отката), `Cache-Control: no-store` и не добавляет персональные данные к безопасному скачиваемому операторскому отчёту. Проверка не меняет source/target, не запускает перенос, не создаёт снимок и не обходит blocking conflicts.
