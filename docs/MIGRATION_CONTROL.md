# Контроль переноса

## Назначение и границы

«Контроль переноса» — отдельная страница Migration для наблюдения за переносом,
анализа неперенесённых данных и повторного запуска после частичного результата.
Существующий пульт остаётся самостоятельным интерфейсом. Его API и строгая
последовательность Inspect → Dry run → Migrate → Validate сохраняются.
Допуск частичного переноса включается только новой операцией control.

Рабочие маршруты разведены: `/system/migration/` открывает старый пульт,
`/system/migration/control/` — новый контроль. Это две страницы внутри общей
оболочки System, а не вкладки одного экрана. Самостоятельная сборка сохраняет
аналогичную пару `/migration/` и `/migration/control/`; прежний query
`?view=control` нормализуется в отдельный URL. Другие бизнес-сервисы не меняются.

Изменения этой задачи ограничены Migration: его приложением, backend, ops,
скриптами, тестами и документацией. **Нельзя переделывать Employees, Vacations,
Clients, Timesheets, другие сервисы или shared UI без отдельного прямого поручения
владельца.** Если для данных нет целевой возможности, результат — видимый
`deferred`/`unmapped` и отдельное предложение изменения целевого сервиса.

Текущая эксплуатационная предпосылка: пользователи ещё не редактируют целевые
сервисы. Это не отменяет проверки ссылок, дублей и согласованности mappings.
Релиз кода не запускает перенос автоматически. Legacy подключается только для
чтения. Управление и отчёты доступны только `platform-admin`.

Этот документ фиксирует согласованные требования и контракт реализации.
Чек-лист ниже — условия приёмки, **не утверждение о пройденном тестировании**.
Фактические PASS/FAIL и проверки конкретного SHA фиксируются отдельным отчётом QA.

## Дерево переноса и детализация

Экран организован как **одна табличная иерархия**: весь перенос → сервис → исходная
сущность/таблица. Все уровни занимают строки единой таблицы со строго общими колонками:
объект, статус, обработано/всего, без результата, ошибки, предупреждения,
полнота и действия. Раскрытие сервиса вставляет строки его сущностей непосредственно
под ним без сдвига показателей между колонками. На узких экранах прокручивается
таблица, а не вся страница; первый столбец и заголовки остаются видимыми. Верхняя строка содержит статус операции, полноту
доказательств, ожидаемые строки без результата и счётчики диагностических
событий. Строка сервиса содержит статус, обработано/всего (при наличии
достоверных чисел), полноту доказательств, ошибки/предупреждения и кнопку
**«Запустить перенос»**. При раскрытии сервиса строки сущностей показывают
назначение переноса (expected/excluded/undocumented), обработано/всего,
без результата и проблемы. Сырые данные полей и диагностики не загромождают
дерево.

Настройки видимости **отдельны для каждого сервиса**: у сущности есть
«Скрыть», а при наличии скрытых строк появляется кнопка
«Показать скрытые (N)». Она открывает отдельный список скрытых в
выбранной операции сущностей и позволяет вернуть одну строку или сразу все.
При отсутствии скрытых строк кнопка не занимает место в таблице. Список сохранён в
localStorage браузера по паре `service:legacy_table`, не по ID операции:
выбор версии, автоматическое обновление и перезагрузка страницы не
сбрасывают исключения. Настройка не передаётся в API и не меняет
исходную миграцию, архивы, полномочия или факт успешности этапов.
Если сущность исчезла в старой версии, она не показывается в её списке
скрытых, но настройка остаётся для версии, где сущность есть.

**Показатели сервиса по видимым сущностям** (обработано/всего,
без результата, количество групп и ошибок/предупреждений)
пересчитываются после исключения строк. Общая строка операции
также исключает их из счётчиков видимых ошибок и строк без результата.
Суммы не используются вместо неподтверждённых данных: если исход
или total любой видимой сущности неизвестен, не рисовать ложное
нулевое значение или прогресс. Процент и полоска показываются
при известных `processed` и положительном `total`; если они
отсутствуют — явно показывается отсутствие данных. Диагностические группы без достоверной привязки к таблице либо к
сервису остаются видимыми при фильтрации. Исключать разрешено только
группы сущности, реально скрытой в текущем дереве выбранной операции.
Если количество диагностических событий отсутствует или некорректно,
соответствующая сводка явно показывает «Неизвестно», а не 0.
Статус
фактической операции, подтверждения этапов и архивный отчёт при
скрытии строк **не меняются**. Текст в таблице и боковых
`UiDrawer` одинаковой гарнитуры Onest и размера из UI-токенов,
без изменения других сервисов и базовых компонентов.

Любой кликабельный показатель открывает `UiDrawer`: общий контекст
операции, сервис с причиной и этапами, сущность с outcome, поля
или ошибки/предупреждения. Количество ошибок — количество
диагностических событий, **не** уникальных source rows. Сначала можно
показать агрегированные группы; подробные элементы из полного
авторизованного JSON подгружаются **только по запросу**, без искусственного
лимита на три примера. Если полный список недоступен, это явно показано.

Выбор исторической операции полностью переключает дерево, диагностические
окна, stage/run и архив на **выбранный ID**; незавершённая загрузка предыдущей
версии не подменяет текущий отчёт. Запуск отдельного сервиса использует
существующий `POST /control/start` с `scope=<service>`: новая операция
создаёт собственный snapshot, не переписывает историческую версию
и не запускает остальные сервисы. Кнопка блокируется при недоступной
связи, active worker или другой операции; перед записью требуется
отдельное подтверждение с объяснением риска частичной записи.
Неисполненный/неподтверждённый этап остаётся неизвестным, а не нулевым.

Верхняя часть экрана — **одна плотная строка**: заголовок «Контроль
переноса», компактный селектор текущей/исторической операции шириной до
280 px, кнопка «Новый перенос», небольшой прелоадер при ожидании backend,
кнопка остановки при активной операции и действия «Диагностика» и
«JSON-отчёт». Прелоадер находится именно внутри этой строки, не
создаёт отдельного вертикального блока и не скрывает предыдущие
доказательства при недоступном API. Лишние верхние отступы удалены.
Ссылка «Открыть пульт переноса» в шапке отсутствует: старый пульт
остался доступен через штатную боковую навигацию и собственный URL.
На мобильном экране элементы строки переносятся, не создавая
горизонтального скролла страницы; селектор сохраняет поиск и полные
подписи в выпадающем списке.
Описание механизма, повторяющиеся строки статуса, пояснения про нули и
сырой диагностический текст удалены из основного экрана; объяснения,
этапы, подробности и доказательства остаются в соответствующих `UiDrawer`.
При активной операции кратко показан исполняемый сервис/этап. В таблице
дефис означает отсутствие подтверждённого показателя, а не ноль;
общий processed нельзя суммировать по нескольким этапам.
Кнопка «Запустить перенос» присутствует только у строк сервисов,
фиксирует конкретный сервис в диалоге подтверждения и не меняет
историческую операцию.

## Недоступность Migration API и восстановление связи

Обновление состояния Migration Control никогда не оставляет неподвижный экран в
ожидании зависшего backend. Начальная загрузка показывает `UiLoader` из
`@irlix/ui`; если очередной запрос занимает больше ~900 мс, появляется
индикатор ожидания ответа. При 502/503, сетевой ошибке или таймауте последний
полученный отчёт остаётся доступным как **неподтверждённый**, а прелоадер
с сообщением об автоматической перепроверке показывается до восстановления
связи. Новые операции и отмена недоступны, пока состояние worker не
подтверждено. Повторное чтение состояния выполняется примерно раз в 2 секунды
без перекрытия предыдущих запросов. Восстановление связи автоматически
скрывает индикатор и актуализирует отчёт; при смене исторической операции
запоздавший ответ не должен подменять выбранный архив.

В standalone Migration до проверки доступа отображается `UiLoader`.
Сетевые/5xx ошибки сервиса проверки доступа повторяются автоматически с
ограниченным по времени запросом; подтверждённый отказ 401/403 и отсутствие
роли `platform-admin` не маскируются бесконечным спиннером. В старом
пульте первичная загрузка, замедленный ответ и повторная попытка используют
тот же компонент; legacy запросы ограничены таймаутами, включая получение
состояния, чтобы polling мог продолжаться. Детальный отчёт через `UiDrawer`
также имеет явный таймаут, не блокирует страницу.

Прелоадер показывает **ожидание доступа к backend**, а не успех миграции,
завершение записи или восстановление из бэкапа. Остановка и rollback не
выполняются автоматически. Ошибки экспорта отчёта вроде
`REPORT_EXPORT_COMMAND_FAILED` требуют закрытых логов `migration-ops`:
статус завершённого dry-run и наличие snapshot сами по себе не подтверждают
архив доказательств или возможность продолжить запись.

## Операции и результаты

Статус операции и полнота данных — разные характеристики. Успешное завершение
этапов само по себе не доказывает полный перенос всех исходных столбцов.

| Состояние | Значение для оператора |
|---|---|
| `queued` | Очередь зарезервирована, выполнение ещё не началось |
| `running` | Выполняется текущий этап; показаны сервис и фаза |
| `completed` | Запланированные этапы завершены; полнота оценивается по отчёту |
| `partial` | Есть выполненная работа и неперенесённые данные либо незавершённые сервисы |
| `failed` | Выполнение не удалось; причина и исход записей требуют отдельной оценки |
| `cancelled` | Запрос оператора исполнен на безопасной границе этапов |
| `interrupted` | Процесс ops прерван; исход активного этапа не доказан |

Запрос остановки содержит ID операции и непустую причину. Он не убивает worker
посреди записи: текущий этап завершается, затем новые этапы не запускаются.
До этой границы интерфейс показывает «остановка запрошена», а не «отменено».
Остановка, ошибка и перезапуск ops не являются автоматическим откатом.

История должна сохранять операцию, инициатора, время, выполненные этапы,
неисполненные этапы, причины остановки и ссылки на отчёты. Архив control хранится
отдельно от восстанавливаемых migration metadata. Числовой `run_id` после restore
может переиспользоваться: идентичность отчёта обязательно связана с операцией.
Недоступный старый отчёт обозначается как недоступный, без подстановки нового run.

## Инвентаризация и судьба данных

Inspect control получает перечень пользовательских таблиц и столбцов из catalog
источника, а не только из списка таблиц адаптера. Пустые, неизвестные и недоступные
таблицы остаются видимыми. Доступность, время наблюдения и полнота исследования
указываются явно. Неизвестное количество — `null`, а не ноль.

Для каждой исходной таблицы дополнительно фиксируется **намерение переноса**,
полученное только из явных правил полей: `expected` (есть проверенные доменные
mapping-правила), `excluded` (все описанные поля сознательно отнесены к
metadata/deferred/excluded) либо `undocumented` (решение неполное или отсутствует).
`expected` не означает, что каждая строка обязана создать отдельную target-запись:
конфликты, ссылки, алиасы и строковые проверки учитываются отдельно. Пустая таблица
или нулевые outcome-счётчики сами по себе никогда не превращают её в `excluded`.
Общий `unprocessed_rows` сохраняется как технический итог источника, но отчёт обязан отдельно показывать `expected_unprocessed_rows`, `excluded_unprocessed_rows` и `undocumented_unprocessed_rows`. Сознательно исключённые строки сами по себе не делают semantic coverage неполным; неописанные решения, deferred/unknown, ошибки и незавершённый ожидаемый перенос — делают.


Для каждого обнаруженного столбца показываются тип, статистика заполнения,
правило адаптера и судьба:

| Судьба | Что подтверждает |
|---|---|
| `direct` | Есть явное правило копирования в указанное целевое поле |
| `transformed` | Есть явное преобразование с описанным правилом |
| `reference` | Значение разрешается через mapping или проверенное соответствие |
| `metadata_only` | Источник сохранён для аудита; доменная сущность не импортирована |
| `deferred` | Перенос этой части явно отложен с причиной |
| `unmapped` | Проверенного правила нет; данные не объявляются перенесёнными |
| `excluded` | Явное обоснованное исключение, если оно предусмотрено реестром |

Правило поля описывает возможность адаптера, но не доказывает запись конкретной
строки. Источники значений статусов/типов включают PostgreSQL enum и явно
определяемые кодовые столбцы; значения перечисляются со счётчиками и NULL.
Неизвестное значение не получает выдуманный target-аналог.

Ограничения: наблюдения выполняются отдельными read-only запросами, не являются
единым замороженным снимком legacy и могут различаться при изменении источника.
Таймаут, отказ доступа или неподдерживаемый тип показываются как неполнота.
Список кодовых столбцов зависит от реестра и правил обнаружения; неизвестный
столбец нельзя считать покрытым только потому, что его имя похоже на целевое.
Неполный реестр правил консервативно оставляет поле `unmapped`, даже если другой
участок адаптера фактически использует его: это требует сверки, а не догадки UI.

Подтверждение полноты требует инвентаризации и сохранённого результата записи
для каждого сервиса выбранной области. Незавершённый или неархивированный этап,
а также отсутствующий сервис не могут давать `semantic_complete=true`.
Наличие одного `archive_key` недостаточно: файл этапа должен существовать и
соответствовать operation/run/service/mode. `failed_unique > 0` также всегда
запрещает `semantic_complete=true`, даже при `unprocessed=0`.
Живые счётчики не считаются сохранённым архивом.

## Прогресс и диагностика

Показываются общий и сервисный прогресс, фаза, уникальные обработанные строки,
известный объём и свежесть состояния. Неизвестный объём не превращается в процент.
Повторные ошибки одной строки не увеличивают число обработанных сущностей.

Нужно различать чтение, готовность Dry run, доменную запись, сопоставление ссылки,
проверку target, metadata-only, deferred, unmapped, blocked и unprocessed.
Суммы полей и суммы строк — разные измерения; их нельзя складывать в общий
«процент импорта». Например, разрешение users к существующему Employees — ссылка,
а не создание сотрудника. Сохранение source payload в metadata не равно импорту.

Диагностика группируется по корневой причине и сервису с полным числом случаев.
Таблица и severity должны сохраняться в деталях, чтобы одинаковые коды разных
контекстов не скрывали последствия. Копируемый диагностический текст по каждому
сервису содержит точный подтверждённый этап (либо явно «неизвестен»), статус,
run ID, состояние записи, затронутые сущности, причину, последствия и полноту
доказательств: архив этапа, инвентарь, diagnostics и outcome записи. Неизвестный
исход не превращается в ноль, `not_started` или rollback. Полный JSON отчёта
остаётся отдельным download и формируется сервером из всего отчёта,
без перелистывания 200-строчных страниц в браузере. Группировка не заменяет
отдельные случаи и не должна ограничиваться первыми 40 группами.

Экспорт предназначен для администрирования и может содержать чувствительные
диагностические сведения. Публичные Git, PR и CI не являются местом для отчётов
реального переноса. Credentials, APP_KEY, ciphertext, private traceback и
необработанные source payload не должны попадать в текст для чата и экспорт.

## Повторы и безопасность

Новый запуск допускается поверх частичного результата; обязательного
автоматического rollback нет. Перед запуском проверяются отсутствие активного
worker, доступное read-only подключение и контрольная точка. Предыдущий отчёт
остаётся историческим: новая проверка не переписывает его результат.

Неизвестные поля и статусы отражаются как неперенесённые данные. В control
безопасные независимые строки могут продолжать обработку, а зависимости от
неперенесённой строки получают `dependency_blocked`. Это не разрешение писать
небезопасные значения. Неоднозначная identity, отсутствующий target по mapping,
нарушение FK, конфликт natural key и опасные пересечения периодов блокируют
соответствующие записи. Неопределённый исход живого worker блокирует новый запуск.

Повтор использует сохранённые target IDs и обновляет только предусмотренный
адаптером payload. Отсутствующие в новом источнике строки не удаляются автоматически.
Employees предшествует Vacations и Clients; Timesheets зависит от Employees и
Clients. После повторного изменения зависимого набора нужна новая проверка
потребителей; старое успешное Validate не доказывает актуальность после повтора.

**Известная граница безопасности:** target commit и сохранение mapping в SQLite
не составляют одну транзакцию. Сбой между ними может оставить target без mapping.
Кроме того, защита natural key в общем `write()` действует только когда адаптер
передал явный unique key; не все записи имеют такой ключ. Поэтому отсутствие
mapping не доказывает отсутствие ранее записанной сущности. Нельзя обещать
безусловную идемпотентность, автоматически сопоставлять по похожему имени или
молча создавать дубль. Такой случай требует диагностики и явной сверки.

## Откат

Контрольная точка — возможность восстановления, а не доказательство выполненного
отката. История должна различать `not_requested`, `in_progress`, `proven`,
`partial`, `unknown` и `failed`. Доказанный результат требует подтверждения всех
частей scope: целевой БД, metadata и документов, когда они входят в снимок.
Один успешный subprocess или существующий архив этого не доказывает.

После частичного restore или неопределённого COMMIT состояние явно остаётся
partial/unknown. Оператор руководствуется restore diagnostics и не считает
данные исходными по одному статусу операции. Существующие safeguards restore
и подтверждения `RESTORE <SCOPE>` не ослабляются новым интерфейсом.

Новые снимки включают контрольные количества и отпечатки строк/последовательностей,
metadata, ключа и дерева документов. После восстановления выполняется независимая
сверка до возобновления записи и проверка после обновления схемы. Старые снимки без
этих данных остаются доступными, но не получают расширенное подтверждение.
История control и ранее подтверждённый реестр соответствий корпоративных логинов
намеренно сохраняются вне бизнес-отката; подтверждение относится к составу снимка.

При восстановлении Employees или всех сервисов временно останавливается также
зависимость проверки прав Employees. В этот период authenticated state/report могут
быть недоступны: интерфейс сохраняет последнее состояние с явной отметкой отсутствия
связи. Проверка прав остаётся закрытой при отказе зависимости, без кэша разрешений.
После запуска Employees состояние и доказательства перечитываются автоматически.

## Контракт control API

PHP публикует авторизованный proxy `/api/migration/control/*`; ops endpoints
являются внутренними. Названия приведены относительно внутреннего ops API.

| Метод и путь | Контракт |
|---|---|
| `GET /control/state` | `operation`, `history`, `snapshots`, `restore_status`, `console_history`; может дополнительно включать текущую `console_operation` для общей блокировки |
| `GET /control/operations/{id}/report` | `operation`, `runs`, `root_cause_groups`, `chat_summary`; инвентаризация и архивные события могут дополнять объект |
| `POST /control/start` | `scope`: реализованный сервис или `all`; `confirm: true`; создаёт отдельную control-операцию |
| `POST /control/cancel` | `operation_id`, непустая `reason` до 500 символов; запрашивает остановку между этапами |

Старые `/console/*` не включают tolerant mode автоматически. Оба интерфейса
используют общую reservation/блокировку: одновременный запуск старого и нового
пульта запрещён. При недоступности ops действия блокируются, повторная запись
«наугад» не выполняется. Ошибки авторизации — 401/403, неподходящие параметры —
422, занятый контур — 409; окончательные коды проверяются по proxy-контракту.


### Повторяющаяся ошибка экспорта после Clients dry-run

Два наблюдаемых запуска (21 октября 2026 г., 21:01 и 21:31 UTC)
завершили Clients dry-run, но не сохранили доказательный JSON:
`REPORT_EXPORT_COMMAND_FAILED` и `missing_archive_key`. До исходной
ошибки PHP источник не доказан: это **не** подтверждение успеха проверки,
не причина запускать импорт снова и не доказательство отката.

При ненулевом коде `migration:control-report` CLI выдаёт только
`CONTROL_REPORT_FAILURE|<PHP exception class>|<numeric code>|<filename>|<line>`,
без исходного текста исключения (он мог содержать SQL, source values,
DSN и персональные сведения). Координатор заносит исключительно
проверенную по строгому шаблону категорию, номер строки и exit code в
приватный архив/операторскую сводку. `exit=137` без такого маркера
дополнительно помечается как SIGKILL с рекомендацией проверить лимиты
памяти; это не является доказательством OOM. Сырой stdout/stderr команды
не возвращается через API, не сохраняется в operator report и не
публикуется в GitHub Actions.

Для снижения пикового потребления памяти экспорт использует
потоковое чтение SQL-строк конфликтов, событий и инвентаризации без
промежуточной материализации всех коллекций. Все исходные записи
диагностики по-прежнему включаются в итоговый неизменяемый JSON;
предельного лимита выборки нет.

Повторный dry-run или миграция не запускаются выпуском кода.
Точный PHP category/line при новой попытке либо защищённые
runtime-логи предыдущего запуска необходимы для подтверждения
первопричины. Исторические отчёты не переписываются.

### Ошибки экспорта архивов

Worker со статусом `completed` не доказывает, что архив этапа сохранён. Если файл отсутствует, сервис нельзя объявлять успешно завершённым; отчёт должен показывать точный этап, ID запуска и отсутствие подтверждения. В новом запуске ошибка экспорта сохраняет публичный код категории (timeout, invalid JSON, command failure, I/O failure, identity mismatch или write failure). Полные технические детали остаются в защищённых журналах. Ошибка dry-run до migrate позволяет говорить о незапущенной записи данного сервиса, но не об откате ранее перенесённых данных. Старые архивные отчёты неизменяемы.

## QA evidence

PR QA для Migration запускает безопасный coordinator-suite `scripts/tests/test_migration_control.py` вместе с frontend contracts/browser checks. Он проверяет archive completeness, `failed_unique`, mid-write failure и multi-service continuation без подключения к реальным API/DB и без изменения production-данных.

## Проверяемый чек-лист приёмки

- [ ] Отдельная страница `/system/migration/control/` работает; `/system/migration/` остаётся старым пультом с прежней строгой семантикой.
- [ ] Non-admin не получает state, отчёт или управление; секреты не экспортируются.
- [ ] Видны таблицы вне required_tables, пустые таблицы, все catalog-столбцы и отказы доступа.
- [ ] Неизвестные поля и статусы показаны с неполнотой; metadata не считается импортом.
- [ ] Progress разделяет обработку, запись, ссылки и проверку, не удваивает строки.
- [ ] Более 200 конфликтов и более 40 групп полностью доступны в download.
- [ ] Диагностический текст содержит этап/сервис/сущности/причину/последствия/полноту доказательств; полный JSON доступен без загрузки всех страниц ошибок в браузер.
- [ ] История и отчёт переживают restart/restore и переиспользование run_id.
- [ ] Cancel сохраняет причину и исполняется между этапами, без ложного rollback.
- [ ] Безопасные строки control переносятся при локальных unknown-data конфликтах.
- [ ] Повтор поверх partial разрешён, IDs сохранены; integrity hazards не обходятся.
- [ ] Сбой между target commit и mapping выявлен либо честно обозначен как неизвестный исход.
- [ ] Rollback proven/partial/unknown определён по доказательствам всех частей scope.
- [ ] Другие сервисы и shared UI не изменены; недостающие возможности явно отложены.
