# BACKEND — IRLIX Services

Канонический горизонтальный регламент. Подключать для backend-сценария через `docs/context/MATRIX.md`; не загружать остальные горизонтали без необходимости.

## Правила разработки

- Пока проект является монорепозиторием.
- Каждый backend-сервис имеет собственную доменную границу, API и жизненный цикл.
- Employees является source of truth для сотрудников и оргструктуры.

## Архитектура Laravel (обязательно для нового кода)

- `routes/*.php` регистрируют маршруты и middleware, но не реализуют бизнес-сценарии. Простые служебные health endpoints могут быть исключением.
- `app/Http/Controllers`: преобразование HTTP-запроса в вызов use case/service, разрешения уровня HTTP и формирование ответа. Не размещать доменные алгоритмы, транзакции или SQL.
- `app/Http/Requests`: валидация сложных входных контрактов; при переносе legacy-обработчиков сохранять прежний порядок authorization vs validation и статус-коды.
- `app/Http/Resources`: явные внешние API-контракты, скрытие внутренних и чувствительных полей. Для простых стабильных ответов допустима ручная сериализация.
- `app/Models`: Eloquent-модели собственных таблиц с точными именами, ключами, casts и локальными relations; scopes и простые инварианты сущности допустимы. Модели не управляют сквозными бизнес-процессами.
- `app/Services` либо `app/Application`: бизнес-сценарии, проверки инвариантов, транзакции, координация моделей и интеграций. Группировать по бизнес-возможностям, избегая гигантских God services.
- `app/Policies` или выделенные authorizers: permission + scope и запрет небезопасных переходов; серверная проверка обязательна независимо от UI.
- Межсервисные клиенты и адаптеры размещаются отдельно (`Integrations`, `Infrastructure` или текущий однозначный адаптер). Никаких Eloquent-relations к таблицам других сервисов.

## Выбор инструментов

- По умолчанию все штатные запросы к своим бизнес-сущностям — через Eloquent: `Model::query()`, local relations, eager loading, `whereHas`, `upsert`, `chunkById` и т. п.
- В контроллерах, route closures и обычных бизнес-сервисах `DB::table()` не используется.
- `DB::transaction()` допускается в сервисах как управление транзакцией. При конкурирующих записях учитывать constraints, uniqueness, блокировки и идемпотентность.
- Низкоуровневый Query Builder, SQL, schema/DDL разрешены только там, где Eloquent мешает необходимой производительности или функциональности (массовая миграция, большие агрегаты, узкоспециализированные отчёты). Исключение изолировать в инфраструктурном адаптере и документировать причину, сценарий, тесты и риски.
- **Не** вводить Repository, DTO, interface, Action, event или отдельный класс автоматически для каждого CRUD. Обоснование — реальная сложность сценария, внешний контракт либо необходимость замены реализации.
- Не делать Eloquent-модели сквозным публичным JSON-контрактом: при необходимости использовать API Resources с явным allowlist полей.
- Для RabbitMQ учитывать at-least-once доставку, retries и идемпотентность; критичные события публикации связывать с commit (transactional outbox).
- Перед рефакторингом сохранить API/permission/error semantics и покрыть критические сценарии регрессионными тестами. Проверять N+1, пагинацию, блокировки, `cursor/chunk/upsert` и стоимость массовой гидрации моделей.

## Переход существующих сервисов

Для legacy-кода допускается поэтапная миграция. **Новые** backend-сценарии обязаны следовать стандарту, но наличие ещё не переделанных файлов не считается основанием нарушать его дальше. Любой затронутый вертикальный срез переводится целиком: route → controller → service → model, включая проверки доступа, tests и контрактные последствия. Нельзя механически заменить `DB::table` на Eloquent без пересмотра ответственности классов. Старые таблицы/миграции не переписывать ради рефакторинга.

Пилот: `services/employees` — модуль специальных ролей, матрица разрешений и чтение прав на входе. Ограничение среза документировано в `services/employees/ARCHITECTURE_REFACTOR.md`. Расширение на весь Employees и другие сервисы требует отдельных регрессионных шагов; не объявлять весь сервис мигрированным по итогам одного среза.
