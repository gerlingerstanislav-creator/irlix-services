# BACKEND — IRLIX Services

Канонический горизонтальный регламент. Для backend-задачи выбирать соответствующую горизонталь через `docs/context/MATRIX.md`; не загружать несвязанные сервисы. Обязательное короткое правило в `AGENTS.md` ссылается на этот документ.

## Правила разработки

- Монорепозиторий состоит из независимых backend-сервисов со своими бизнес-границами, API и жизненным циклом.
- Employees — источник истины для сотрудников и организационной структуры.
- **Нормы ниже обязательны для Laravel-сервисов.** Для FastAPI и других стеков сохраняются требования к границам, ответственности, безопасности, контрактам и тестам, но не навязывается Laravel/Eloquent.

## Архитектура Laravel — обязательный контракт

Для **нового бизнес-сценария и затронутого legacy-среза** ответственность распределяется так:

| Слой | Обязанности | Запрещено |
|---|---|---|
| `routes/*.php` | Регистрация endpoint → Controller, middleware и ограничений маршрута | Closure с бизнес-обработчиком, SQL, обращения к данным и правила согласования |
| `app/Http/Controllers` | HTTP boundary: authentication/authorization, валидация или FormRequest, mapping параметров, выбор use case, код статуса и формат ответа | Бизнес-алгоритм, транзакции, ORM/SQL-запросы, обход scope или интеграционные workflow |
| `app/Services` либо `app/Application` | Use cases, инварианты, state transitions, координация моделей, read projections, транзакции и внешние зависимости | SQL/Query Builder `DB::table()` в обычном сценарии, неявное расширение прав, прямые чтения чужих схем |
| `app/Models` | Отдельная Eloquent-модель каждой **самостоятельной собственной бизнес-сущности**, ключи, casts, timestamps, локальные relations, scopes, простые инварианты сущности; простые pivot-таблицы допустимо использовать через relations без отдельной модели | HTTP, сквозная оркестрация, сетевые вызовы, relations к чужому сервису |
| `app/Policies` / authorizers | Серверные проверки **permission + resource/organizational scope** и условий перехода; переиспользуемая логика, когда нужна | Доверять только скрытию кнопок во frontend |

`FormRequest` использовать при существенном входном контракте, `Resource`/явный serializer — для устойчивого/чувствительного выхода. Это **не** требование создавать файл для каждого запроса. Простой health/check может остаться служебным endpoint без отдельного use case при отсутствии бизнес-логики и SQL в маршруте. Простой CRUD без бизнес-операций не требует искусственной иерархии сервисов: достаточно небольшого application/read-сервиса для доступа к данным, контроллер остаётся тонким. Это не разрешение переносить Eloquent-запросы обратно в контроллер.

## ORM, транзакции и интеграции

- Обычные операции со своими сущностями: `Model::query()`, relations, eager loading, scoped queries, `whereHas`, `upsert`, `chunkById` — в сервисном/read-model слое. **Простая замена `DB::table` на `Model::query()` внутри контроллера не считается рефакторингом.**
- `DB::transaction()` допустима **в сервисе/use case**, а не в маршруте или HTTP-контроллере. Для важных переходов обеспечить atomicity DB, ограничения уникальности, идемпотентность, гонки/lock и безопасный retry; транзакция БД **не охватывает** HTTP, RabbitMQ или файловое хранилище.
- Keycloak, Employees, Clients, Platform Core, Finance и прочие внешние зависимости доступны через явный API/client/adapter, а не через join/foreign key/Eloquent relation к чужим таблицам. На границе предусмотреть timeout, запрет утечки секретов, сбои, повторы и компенсирующие операции/outbox, где необходимы.
- Локальная связь через `belongsTo/hasMany` допустима только в пределах собственной схемы и bounded context. Внешний ID — scalar reference; проверить у владельца его существование/право доступа через контракт.
- `DB::table()`, raw SQL и прямой Query Builder — **исключение** только в выделенном инфраструктурном/миграционном адаптере (массовый импорт, DDL, performance-critical агрегаты), с измерением либо конкретным техническим обоснованием, отдельными тестами, явными границами и ссылкой на документированное решение. `DB::transaction()` и инфраструктурные миграции сами по себе не нарушают стандарт.
- Не создавать Repository pattern, интерфейс, DTO, Action, event или отдельный класс для каждой CRUD-операции «ради архитектуры». Разделять сервисы по бизнес-возможности и сложности, не выращивать God Service. Повторно используемый query scope/read-model сервис оправдан общим безопасным контрактом.
- RabbitMQ — at-least-once, retries и идемпотентность; критичная публикация события через transactional outbox. Не отправлять внешнее событие как будто транзакция уже зафиксирована, пока commit не подтверждён.

## Сохранение контрактов при рефакторинге

**Рефакторинг структуры ≠ изменение продукта или схемы.** По умолчанию необходимо сохранить:

- URL/методы, status codes, структуру JSON, значения null, сортировки, фильтры, пагинацию, сообщения ошибок, порядок authentication/authorization/validation;
- ограничения ролей, `permission + scope`, приватные поля и запрет self-approval; не делать `toArray()` на всей модели как публичный API;
- state machine, бизнес-периоды, историю, уведомления, аудит, downstream events, порядок побочных эффектов и поведение при сбоях;
- исходную PostgreSQL-схему и уже применённые миграции: **не** добавлять DDL/очистку данных просто ради перехода на ORM.

Внимание: возврат Eloquent models вместо `DB::table()->get()` может **изменить** JSON datetime/timezone, casts, числовые типы, поля, null и сериализацию JSONB. Проверять contract snapshots и выбирать `Resource`, explicit projection или `getRawOriginal()` **осознанно**, не механически. При выборе raw-полей проверить JSONB/денежные типы и ожидаемый формат; для денежной арифметики не использовать float без согласованной точности.

## Legacy-миграция и критерии готовности

- Прежде чем менять крупный сервис, прочитать актуальные код и относящееся ТЗ в `ideas`, перечислить endpoints, модели и исторические инварианты. Анализировать затронутые пересечения с соседями, но не загружать все сервисы.
- Старый код вне scope может оставаться временно. **Новый сценарий** и **изменяемый вертикальный срез** следуют этому стандарту. Не требовать бессмысленного переписывания всего сервиса ради небольшой независимой правки; если срез нельзя безопасно завершить целиком — выделить миграцию в самостоятельную проверяемую задачу.
- В рамках среза выполнить маршрут → контроллер → бизнес-/read-сервис → модель; при необходимости policies, adapters и workers. Удалять дублирование и сохранять границы, а не просто переименовывать классы.
- Обязательная проверка перед PR/слиянием: PHP lint, unit/domain state transitions, API/JSON/status regression, negative permission+scope, DB-транзакции и concurrency, внешние сбои/retry, аудит/outbox, performance/N+1 там, где затронуто. Если тест недоступен (нет реального PostgreSQL/Keycloak/TEST) — указать **NOT TESTED**, не выдавать SQLite/static CI за E2E PASS.
- Для новых/значительно изменённых Laravel-сценариев добавить проверку архитектурных границ в тесты сервиса: отсутствие business route closures, `DB::table()` и транзакций в controllers, наличие моделей и сохранность API. Локальные gates должны охватывать изменённые файлы; **не блокировать CI чужим legacy-кодом**, пока он не включён в согласованный scope.
- До объединения обновить технические документы сервиса и продуктовые контракты в `ideas`, если они действительно изменились. Для чистого технического рефакторинга достаточно технического decision/описания в `irlix-services`; не дублировать приватное ТЗ в публичном кодовом репозитории.
- Исключение из стандарта при существенной причине: указать **где, зачем, измеримое основание, владелец, тесты и как/когда убрать исключение** в сервисной документации или ADR. Не использовать «так было раньше» как основание.

## Реализованные примеры

- `services/employees`: кадровый реестр, оргструктура, ФОТ, Keycloak, аудит и фоновые обработчики. См. [технический разбор](../../services/employees/ARCHITECTURE_REFACTOR.md).
- `services/vacations`: доменные правила сохранены, Eloquent + `AbsenceService` / read services / attachment + purge services. См. [технический разбор](../../services/vacations/ARCHITECTURE_REFACTOR.md).

Примеры показывают **принятую структуру**, но не гарантируют, что каждый исторический файл уже совершенен или что все E2E роли/конкурентные сценарии были проверены. Отдельное продуктовое обоснование находится в приватном ADR `ideas/company-internal-services-81-2.4/architecture/ADR_LARAVEL_APPLICATION_LAYERS_2026_10_24.md`.
