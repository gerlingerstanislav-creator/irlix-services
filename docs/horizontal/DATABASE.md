# DATABASE — IRLIX Services

Канонический горизонтальный регламент. Подключать для изменений ORM/хранения через `docs/context/MATRIX.md`.

## Правила разработки

- Прямое чтение или изменение таблиц другого сервиса запрещено.
- На первом этапе допускается одна физическая PostgreSQL, но каждый сервис владеет своей schema и работает через отдельного DB user.
- Обычные запросы к своим бизнес-сущностям выполняются через Eloquent-модели, описанные в `app/Models`. Статические `DB::table()` в маршрутах и контроллерах не допускаются.
- Внутрисервисные связи описываются Eloquent relations. Межсервисные идентификаторы остаются scalar references, интеграция — через API/события. Eloquent relation через границу сервиса запрещена.
- Схема меняется новыми версионированными миграциями, без правки ранее применённых миграций. Рефакторинг без изменения хранения не должен добавлять DDL.
- Ограничения уникальности, FK внутри сервиса, check constraints и конкурентная целостность обеспечиваются базой, а не только Eloquent-проверками.
- Транзакции `DB::transaction()` допустимы на уровне сервисов. Для больших выгрузок и миграций разрешены обоснованные и изолированные инфраструктурные batch/SQL-операции с bounded memory, progress и retry.
- Индексы, N+1, eager loading, количество запросов и memory impact должны проверяться для затронутых сценариев. Не загружать весь набор Eloquent-объектов ради массовой записи.
- `DB::table()` в обычном HTTP/бизнес-коде, ORM в контроллерах и `DB::transaction()` в контроллерах не допускаются; низкоуровневый SQL — только в изолированном Infrastructure/Migration-коде с обоснованием и проверкой.
- При переходе `DB::table()` → Eloquent контролировать serialization/casts/datetime/null и API snapshot, не менять DDL и исторические миграции автоматически. DB-транзакция не гарантирует атомарность сетевых запросов, RabbitMQ и файлового хранилища; предусматривать outbox/idempotency/compensation по необходимости.
- Для новых/изменённых бизнес-срезов проверять ограничение `permission + scope`, конкурентную целостность и доступность API при отказе соседнего сервиса.
- Точные обязанности слоёв, допустимые исключения и условия обновления legacy приведены в [Backend](BACKEND.md#архитектура-laravel--обязательный-контракт).
