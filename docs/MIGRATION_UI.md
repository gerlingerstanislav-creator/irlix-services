# Migration UI — пульт переноса

## Основная страница

Единственный интерфейс переноса открывается сразу по `/migration/`. В левом меню остаётся «Пульт переноса»; прежняя страница «Текущий интерфейс», её разметка, стили, polling и вкладочные скрипты полностью удалены. Старые ссылки `/migration/console` и `/migration/console/` после обработки OIDC автоматически заменяются на `/migration/` с сохранением query-параметров и hash, включая выбранный сервис.

Frontend находится в `apps/migration`, собственный image/container `migration-web`. Portal не содержит экранов или polling мигратора. Оболочка и компоненты — общие `UiAppShell` и `@irlix/ui`; Dashboard выбирается через общий launcher. Доступ проверяется через authenticated Employees access API и общую функцию `isPlatformAdminAccess`; ошибка проверки не открывает интерфейс.

`src/main.js` отвечает только за авторизацию и запуск `MigrationConsole.vue`; состояние и композиция пульта находятся в `MigrationConsole.vue`, `migration-console-model.js` и `migration-console.css`. Polling сохраняет черновики, DOM, фокус и положение курсора. Настройка подключения и её уведомления показываются в отдельном окне; архивы и действия с ними — в окне «Бэкапы». Исторические снимки Employees/Vacations остаются доступны через существующие API.

## Компактная компоновка пульта

Выбранный сервис указан в breadcrumbs. Блок этапов уплотнён: текст слева, действия справа. Верхние заголовки таблицы и журнала образуют общую строку одинаковой высоты; заголовки колонок обеих таблиц также выровнены и имеют высоту 30 px; пояснение таблицы находится справа от заголовка и целиком доступно в tooltip. По умолчанию таблица и журнал занимают равные половины. Вертикальный разделитель — линия шириной 1 px без отступов и обводки при наведении; невидимая зона захвата сохраняет удобство перетаскивания. Он изменяет их ширину мышью или стрелками клавиатуры (20–80%); Home/End выбирают границы, двойной щелчок возвращает 50/50. Polling не сбрасывает размер панелей. На mobile блоки располагаются последовательно, разделитель скрыт. Строки таблицы уплотнены без изменения шрифтов; счётчики объединены в одну колонку «Успешно / Ошибки / Предупр.» с тремя значениями через `/`. Ошибки и предупреждения остаются кликабельными фильтрами журнала. Все колонки таблицы переноса, кроме первой, выровнены по горизонтальному центру, включая заголовки и состояния; фильтры журнала — компактные UiButton с aria-pressed, checkbox автопрокрутки выровнен по центру. Список сервисов не имеет обводок и закруглений; «Все сервисы» отделён дополнительным интервалом, надпись «Очередь переноса» удалена. У каждого пункта справа сверху шестерёнка настроек БД, под ней иконка дискеты «Бэкапы». Наведение и фокус выделяют только кнопку иконки; весь пункт подсвечивается при наведении на выбор сервиса. Для «Все сервисы» шестерёнка открывает выбор подключения; действия нереализованных модулей disabled. Сводка доступов в блоке этапов «Все сервисы» и надпись «Обновлено» с датой удалены во всех сервисах. Уведомления проверки/изменения подключения остаются только в UiDrawer настройки БД; polling сохраняет значения, DOM, focus и caret.

«Бэкапы» открывает UiDrawer выбранного сервиса, независимо от текущего выбора таблицы. В одном списке показаны снимки пульта и исторические снимки Employees/Vacations с источником, датой, ID и отметкой восстановления. Общие снимки находятся в «Все сервисы». Удаление требует отдельного подтверждения и физически удаляет архив на сервере. Возврат требует точной фразы RESTORE <SCOPE> и использует существующий API соответствующего типа снимка; восстановленные снимки доступны для повторного восстановления с теми же проверками. Глобальная активная операция переноса или snapshot/restore блокирует действия. Ошибки списка, удаления и возврата показываются только в соответствующем окне бэкапов. Новый DELETE /api/migration/console/snapshots/{scope}/{snapshot} требует platform-admin, allowlisted scope и numeric ID; ops сериализует его общим LOCK, проверяет активный legacy snapshot и удерживает SQLite BEGIN IMMEDIATE и файловый lock checkpoint-скрипта до конца удаления. Не удаляются архивы другого сервиса, история операций или metadata. Для старых снимков используются прежние endpoints /snapshots и /vacations/snapshots. GET console/state также возвращает snapshot_operation для блокировки и отображения операций исторического snapshot API.


## Создание точки из окна бэкапов

В UiDrawer «Бэкапы» каждого реализованного сервиса и «Все сервисы» есть UiButton «Создать точку отката». POST /api/migration/console/snapshot принимает scope окна, не активной таблицы. Он требует platform-admin и отсутствие активных операций; legacy credentials/verification не требуются, импорт не запускается. Окно остаётся открытым; polling добавляет проверенную точку, показывает готовность/ошибку и сохраняет фокус/draft. Кнопка заблокирована на время задачи, загрузки списка и потери связи.

Clients/Timesheets имеют собственные подключения и snapshots; «Все сервисы» охватывает Employees, Vacations, Clients и Timesheets. На время consistent checkpoint останавливаются writers выбранной схемы (включая Employees events и Vacations calendar-sync), Migration API/worker. Старые глобальные checkpoints из двух схем видны и доступны для удаления, но восстановление через новый глобальный контур запрещено: требуется новая точка из четырёх схем. API/server проверяют состав manifest независимо от disabled в UI. Снимки отдельных старых Employees/Vacations продолжают использовать собственные legacy endpoints.

Во время создания точки отката API временно останавливается для согласованности снимка. Окно бэкапов и подтверждение переноса заранее объясняют ожидаемые 502/503. При подтверждённой активной операции snapshot (включая первый checkpoint очереди переноса) такие ответы показываются нейтральным статусом ожидаемой паузы, повторная проверка связи продолжается, действия остаются заблокированными. Окончательный результат не объявляется до успешного ответа API. Ошибки иных типов/вне создания снимка остаются обычными ошибками; поля форм и настройки интерфейса не сбрасываются.

### Сотрудник и периоды в журнале

Для конфликтов Employees/employment журнал показывает ФИО и логин из сохранённого контекста и кнопку «Сотрудник и периоды». Общий `UiDrawer` показывает ID сотрудника в обеих БД и таблицу исходного периода / незакрытых целевых периодов с типом сотрудничества и датами. Снимок новых ошибок помечен как сохранённый при возникновении ошибки; для старых ошибок используются текущие read-only данные, которые могли измениться после запуска. Ошибки чтения остаются в этом окне. Просмотр не повторяет импорт и не исправляет конфликт; фоновые опросы не обновляют открытые подробности.

## Фильтрация журнала до пагинации

Нажатие на ошибки/предупреждения таблицы или фильтр журнала запрашивает совпадающие conflicts с сервера, независимо от уже загруженных сообщений. GET `/api/migration/console/runs/{run}/conflicts` принимает необязательные `severity=error|warning`, `table` и `before`; без курсора возвращает первую страницу выбранного фильтра. Сервер применяет фильтры до лимита 200, учитывает соответствие entity_type исходной таблице и возвращает `items`, `total`, `cursor`, `more`. Существующие вызовы только с `before` совместимы. `total` — число сообщений, не число уникальных исходных строк.

В журнале видны загрузка, количество загруженных/найденных сообщений и отдельная пагинация выбранного фильтра. Ошибка чтения остаётся в журнале с повтором запроса и не выглядит как отсутствие ошибок. Ответ предыдущего фильтра не подменяет новый; polling не сбрасывает загруженные страницы при неизменном запуске, ввод, фокус и курсор в форме БД. События этапов из отчёта запуска продолжают отображаться с локальным фильтром; серверная пагинация относится к conflicts. Просмотр читает сохранённый отчёт, не запускает импорт и не требует доступности legacy БД.


### Повторный откат и объяснение ошибок

Точка отката остаётся доступной после восстановления. `restored` — информационная отметка, а не запрет повторного использования. Повторный откат требует прежнего подтверждения и проходит проверки контрольных сумм, состава схем, внешних FK, отсутствия активных операций и изменений другого сервиса после индивидуальной точки. Архив не изменяется при восстановлении.

В Vacations типы старой БД `paid`, `unpaid`, `maternity` соответствуют `paid_vacation`, `unpaid_vacation`, `maternity_leave`. Неизвестные значения остаются ошибками. Сопоставление сотрудника по корпоративному логину требует ровно одного совпадения: ошибки отдельно сообщают отсутствие сотрудника либо число совпадений и ID. Контекст ошибки содержит ID, email, тип и даты исходной записи, без паролей.

При ошибках пульт открывает фильтр «Ошибки», отключает автопрокрутку и показывает причину остановки и сводку ошибок независимо от страницы журнала. Проверенная таблица с ошибками имеет статус «Есть ошибки». Переход к истории выбирает сервис операции и сбрасывает фильтр таблицы. Запросы отчёта проверяют `operation_id`, чтобы повторно использованный после отката run ID не подменил старый отчёт новым. История операций сохраняется отдельно, но подробные отчёты хранятся в восстанавливаемой metadata SQLite: если отчёт утрачен, интерфейс явно сообщает об этом; восстановление старых подробностей не обещается.

История выбранного сервиса показывает его собственные операции и общие операции, которые затрагивали этот сервис (по `services` / этапам `runs`). Общий список доступен только во «Всех сервисах». При открытии общей операции из истории сервиса текущий сервис сохраняется.


### Итоги переноса и ручное сопоставление пользователей отпусков

Правая панель пульта переключается через общий UiTabs между «Итоги переноса» (по умолчанию) и «Журнал переноса». Итоги прокручиваются внутри панели и содержат причины остановки, сводку ошибок, счётчики и состояние до/во время/после запуска. Они больше не занимают место над обеими колонками. «Показать ошибки» и клики по счётчикам открывают журнал с соответствующим фильтром. Polling сохраняет вкладку, размер панелей, draft и фокус формы.

Подтверждённые соответствия Vacations: `sick → sick_leave`, `granted → confirmed`, `not_approved → rejected`, `approvers_definition → planned`, `on_approval → planned`. При выборе согласующих и ожидании согласования отпуск возвращается в «Запланирован»; старые согласования не превращаются в выдуманные новые этапы. Исходный статус сохраняется в metadata и аудите переноса. Сообщения неизвестных значений различают поля `type` и `status`.

Если логин пользователя отпусков отличается от текущего логина Employees, оператор открывает «Сопоставить сотрудника» в ошибке `users` журнала. Точный текущий логин проверяется, показываются ФИО, логин и ID, затем оператор подтверждает связь. GET `/api/migration/console/conflicts/{id}/employee-match?login=...` проверяет сотрудника; POST `.../employee-map` принимает проверенные `login`, `employee_id`, `source_fingerprint` и `confirmation=MAP USER <legacy_id>`. Доступ — существующие привилегированные роли Migration, без расширения прав. Неоднозначный/отсутствующий логин, противоречие UUID, старая ошибка, активный перенос/бэкап или недоступность ops блокируют сохранение.

Связь хранится приватно в `migration_overrides`: сервис `vacations`, entity `users`, конкретный legacy user ID → Employees ID. В note хранится fingerprint исходных email/UUID; изменения исходной личности требуют повторной проверки. Изменение текущего логина не ломает сохранённый Employees ID. Логины, пароли, Employees и Keycloak не меняются. Нельзя перепривязать уже импортированного пользователя к другому сотруднику без отката. Решение записывается в события отчёта с предыдущим и выбранным ID. Старые ошибки не редактируются; после сохранения требуется новый Dry run. При откате metadata сопоставления возвращаются к состоянию выбранной точки. Реальные соответствия не зашиваются в код, fixtures или документацию.
