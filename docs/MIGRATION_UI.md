# Migration Service UI

Этот документ фиксирует UI-контракт административной страницы `/migration/`. Бизнес- и safety-правила Migration Service описаны в `docs/MIGRATION.md`.

## Карточки сервисов

Каждый migration module отображается отдельной карточкой на всю доступную ширину рабочей области. Две карточки одного ряда не используются: оператор должен видеть параметры, операции и события одного сервиса без сжатия содержимого.

Для каждого реализованного migration module содержимое карточки разделяется общим компонентом `UiTabs` на три вкладки:

1. **Перенос данных** — `Inspect`, `Dry run`, запуск реального переноса, «Проверить результат», состояние последнего run и журнал событий этого сервиса.
2. **Откат переноса данных** — создание резервной точки перед переносом, выбор доступного снимка, откат к выбранному снимку и удаление ненужной точки отката. Удаление физически удаляет архив snapshot на сервере, требует `platform-admin` и запрещено во время активной миграции или операции snapshot/restore. Если snapshot/restore для конкретного сервиса ещё не реализован backend-ом, вкладка остаётся видимой и показывает явное состояние «не поддерживается».
3. **Доступ к БД** — параметры legacy PostgreSQL, read-only acknowledgement, сохранение/удаление credentials, проверка доступности сервера и полная проверка подключения/прав.

Статус подключения, активного run и ожидания ответа сервера остаётся в заголовке карточки и виден независимо от выбранной вкладки.

Выбранная вкладка хранится отдельно для каждого migration module и не должна сбрасываться из-за фонового polling/re-render страницы.

## Vacations

Для Vacations вкладка «Откат переноса данных» реализована отдельно от Employees, но с тем же операторским сценарием: создать снимок, дождаться готовности, выбрать точку, при необходимости восстановить или удалить её.

Снимок Vacations содержит схему PostgreSQL `vacations` и согласованную копию metadata Migration Service. Схема Employees в этот снимок не входит и при откате Vacations не восстанавливается. Для подтверждения восстановления используется точная фраза `RESTORE VACATIONS`.

Реальный перенос Vacations серверно требует наличия готовой невосстановленной точки отката. Поэтому отсутствие снимка нельзя обойти прямым API-вызовом мимо интерфейса.

## Реализация

- базовая разметка migration module формируется в `apps/migration/src/main.js`;
- общая вкладочная композиция и существующий Employees rollback находятся в `apps/migration/src/migration-tabs-base.js`;
- `apps/migration/src/migration-tabs.js` подключает общую вкладочную композицию и service-specific расширения;
- управление точками отката Vacations находится в `apps/migration/src/migration-vacations-snapshots.js`;
- вкладки используют `UiTabs` из `@irlix/ui`, локальный аналог tabs не создаётся;
- snapshot-файлами управляет только изолированный `migration-ops`; browser и Migration API не получают прямой доступ к каталогу архивов;
- перемещение существующих DOM-блоков не меняет permissions или migration run lifecycle.

## Самостоятельный сервис

Frontend находится в `apps/migration`, собственный image/container `migration-web`. Оба интерфейса используют меню Migration: «Текущий интерфейс» и «Пульт переноса»; Dashboard выбирается через общий launcher. Portal не содержит экранов или polling мигратора. Оболочка и компоненты остаются общими `@irlix/ui`; параметры доступа в пульте отделены от данных polling и сохраняют value/focus/caret.

## Компактная компоновка пульта

Выбранный сервис указан в breadcrumbs. Блок этапов уплотнён: текст слева, действия справа. Верхние заголовки таблицы и журнала образуют общую строку одинаковой высоты; заголовки колонок обеих таблиц также выровнены и имеют высоту 30 px; пояснение таблицы находится справа от заголовка и целиком доступно в tooltip. По умолчанию таблица и журнал занимают равные половины. Вертикальный разделитель — линия шириной 1 px без отступов и обводки при наведении; невидимая зона захвата сохраняет удобство перетаскивания. Он изменяет их ширину мышью или стрелками клавиатуры (20–80%); Home/End выбирают границы, двойной щелчок возвращает 50/50. Polling не сбрасывает размер панелей. На mobile блоки располагаются последовательно, разделитель скрыт. Строки таблицы уплотнены без изменения шрифтов; счётчики объединены в одну колонку «Успешно / Ошибки / Предупр.» с тремя значениями через `/`. Ошибки и предупреждения остаются кликабельными фильтрами журнала. Все колонки таблицы переноса, кроме первой, выровнены по горизонтальному центру, включая заголовки и состояния; фильтры журнала — компактные UiButton с aria-pressed, checkbox автопрокрутки выровнен по центру. Список сервисов не имеет обводок и закруглений; «Все сервисы» отделён дополнительным интервалом, надпись «Очередь переноса» удалена. У каждого пункта справа сверху шестерёнка настроек БД, под ней иконка дискеты «Бэкапы». Наведение и фокус выделяют только кнопку иконки; весь пункт подсвечивается при наведении на выбор сервиса. Для «Все сервисы» шестерёнка открывает выбор подключения; действия нереализованных модулей disabled. Сводка доступов в блоке этапов «Все сервисы» и надпись «Обновлено» с датой удалены во всех сервисах. Уведомления проверки/изменения подключения остаются только в UiDrawer настройки БД; polling сохраняет значения, DOM, focus и caret.

«Бэкапы» открывает UiDrawer выбранного сервиса, независимо от текущего выбора таблицы. В одном списке показаны снимки пульта и прежнего интерфейса с источником, датой, ID и отметкой восстановления. Общие снимки находятся в «Все сервисы». Удаление требует отдельного подтверждения и физически удаляет архив на сервере. Возврат требует точной фразы RESTORE <SCOPE> и использует существующий API соответствующего типа снимка; уже восстановленные снимки нельзя восстановить повторно. Глобальная активная операция переноса или snapshot/restore блокирует действия. Ошибки списка, удаления и возврата показываются только в соответствующем окне бэкапов. Новый DELETE /api/migration/console/snapshots/{scope}/{snapshot} требует platform-admin, allowlisted scope и numeric ID; ops сериализует его общим LOCK, проверяет активный legacy snapshot и удерживает SQLite BEGIN IMMEDIATE и файловый lock checkpoint-скрипта до конца удаления. Не удаляются архивы другого сервиса, история операций или metadata. Для старых снимков используются прежние endpoints /snapshots и /vacations/snapshots. GET console/state также возвращает snapshot_operation для блокировки и отображения операций прежнего интерфейса.


## Создание точки из окна бэкапов

В UiDrawer «Бэкапы» каждого реализованного сервиса и «Все сервисы» есть UiButton «Создать точку отката». POST /api/migration/console/snapshot принимает scope окна, не активной таблицы. Он требует platform-admin и отсутствие активных операций; legacy credentials/verification не требуются, импорт не запускается. Окно остаётся открытым; polling добавляет проверенную точку, показывает готовность/ошибку и сохраняет фокус/draft. Кнопка заблокирована на время задачи, загрузки списка и потери связи.

Clients/Timesheets имеют собственные подключения и snapshots; «Все сервисы» охватывает Employees, Vacations, Clients и Timesheets. На время consistent checkpoint останавливаются writers выбранной схемы (включая Employees events и Vacations calendar-sync), Migration API/worker. Старые глобальные checkpoints из двух схем видны и доступны для удаления, но восстановление через новый глобальный контур запрещено: требуется новая точка из четырёх схем. API/server проверяют состав manifest независимо от disabled в UI. Снимки отдельных старых Employees/Vacations продолжают использовать собственные legacy endpoints.

Во время создания точки отката API временно останавливается для согласованности снимка. Окно бэкапов и подтверждение переноса заранее объясняют ожидаемые 502/503. При подтверждённой активной операции snapshot (включая первый checkpoint очереди переноса) такие ответы показываются нейтральным статусом ожидаемой паузы, повторная проверка связи продолжается, действия остаются заблокированными. Окончательный результат не объявляется до успешного ответа API. Ошибки иных типов/вне создания снимка остаются обычными ошибками; поля форм и настройки интерфейса не сбрасываются.

### Сотрудник и периоды в журнале

Для конфликтов Employees/employment журнал показывает ФИО и логин из сохранённого контекста и кнопку «Сотрудник и периоды». Общий `UiDrawer` показывает ID сотрудника в обеих БД и таблицу исходного периода / незакрытых целевых периодов с типом сотрудничества и датами. Снимок новых ошибок помечен как сохранённый при возникновении ошибки; для старых ошибок используются текущие read-only данные, которые могли измениться после запуска. Ошибки чтения остаются в этом окне. Просмотр не повторяет импорт и не исправляет конфликт; фоновые опросы не обновляют открытые подробности.
