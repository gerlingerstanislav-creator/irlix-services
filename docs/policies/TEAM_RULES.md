# Обязательные правила исполнения задач AI-командой

Обязательный регламент из корневого `AGENTS.md`; также см. `docs/AI_TEAM.md` и `docs/AGENT_CONTEXT_PROTOCOL.md`.

## Режим команды ChatGPT Chat / ChatGPT Work

Подробный обязательный регламент: [docs/AI_TEAM.md](docs/AI_TEAM.md). **Передача контекста и видимые отметки этапов:** [docs/AGENT_CONTEXT_PROTOCOL.md](docs/AGENT_CONTEXT_PROTOCOL.md). В Work каждый subagent получает только относящиеся к его роли утверждённые материалы; PM передаёт между ролями результаты и доказательства, а не полную историю или чужие рабочие гипотезы. Независимые аудиты Analyst, Designer, QA и PlatformEngineer не основываются на объяснениях автора реализации. В Chat метки `[PM]`, `[Аналитик]`, `[Дизайнер]`, `[Разработчик]`, `[Platform]`, `[QA]` обозначают проходы одного ассистента, не отдельные контексты. Называть стадией только фактически выполняемый этап; скрытые рассуждения не публиковать. **Режим выбирается по фактическому ChatGPT-интерфейсу, в котором пользователь ставит задачу; не путать последовательные роли Chat с независимыми subagents Work.**

- **Обычный Chat:** один ассистент в одном контексте выполняет PM → Analyst → Designer (при UI) → Developer:<service> → PlatformEngineer (при shared) → критический QA-проход → исправления → PM. **Не** утверждать независимости AI QA или запуска фоновых AI-агентов. Разные пользовательские чаты могут работать параллельно через **разные feature-ветки** от актуальной `development`.
- **ChatGPT Work (если в данной сессии доступны subagents):** PM — **корневой координатор** Work; он обязан **явно создавать отдельных subagents** для каждой задействованной роли: Analyst, Developer:<service>, QA, Designer (если есть UI), PlatformEngineer (если изменяются общие контракты), ProductAdvisor (только по запросу). Назначать им ограниченный отдельный контекст; не отправлять весь поток размышлений других агентов. Обязательное действие PM — **дождаться результата** каждого зависимого этапа, контролировать активные задачи и поручить повторную реализацию при FAIL. Разрешать параллельную работу только по независимым направлениям и исключать одновременную запись в одни файлы.
- В Work **QA — отдельный агент с собственным контекстом**, получает бизнес-критерии из `ideas`, код/diff/PR, итоговый SHA и реальные результаты тестов, **не** получает объяснения разработчика о правильности реализации как источник истины. QA проектирует негативные, граничные, ролевые и регрессионные сценарии; при дефектах PM даёт Developer исправление и ждёт новый QA по новому SHA.
- **Ограничение доступности:** Work subagents поддерживаются только там, где эта возможность реально доступна в текущем аккаунте/сессии. Если средств делегирования нет, PM сообщает пользователю об ограничении и **не имитирует** отдельных агентов или независимый QA. Последовательный режим Chat — только как явно обозначенная альтернатива, по согласованию.
- `.github/agents/*.agent.md` — профили с разными инструкциями для реальных subagents Work либо последовательных проходов Chat, но сами эти файлы никого не запускают. Профессиональные Skills при их наличии дают методику роли; источники истины остаются в актуальных репозиториях.
- Workflow `.github/workflows/ai-team.yml` выдаёт только детерминированную маршрутизацию по PR, а не AI-review или запуск Work subagents. **GitHub CI** проверяет существующие тесты, сохраняет доказательства, не присылает сам сообщения в чат и не заменяет полноценную бизнес-приёмку. Проверки не выполнялись → `NOT TESTED`. При FAIL ответственный активный исполнитель исправляет код и повторяет проверки.
- В обоих режимах: сначала `AGENTS.md` и `docs/CONTEXT_SCOPE.md`, дальше только релевантные ТЗ `ideas`, код сервиса и прямые контракты; изолированная feature-ветка от свежей `development`, PR в `development`, ожидание `CI verified` и `Development release candidate` для итогового SHA. Не изменять `main` / production без явной команды владельца; не разглашать закрытый `ideas` в публичном PR.

### Code Review Rules

- Не нарушать backend ownership: другой сервис используется через его API/контракт, не прямым доступом к таблицам.
- Для изменения permission/scope, переходов и периодов подключений требовать позитивные, негативные и ролевые тесты. Не утверждать выполнение непроведённых тестов.
- Для shared UI требовать `packages/ui`, актуальную витрину и проверки потребителей; без browser/screenshot evidence визуальная приёмка остаётся `NOT TESTED`.

## Поэтапный прогресс реализации

- При каждой реализации до начала изменений показать пользователю все этапы работы в таблице: этап, статус и время в формате **прогноз / факт**, например `25 мин / 30 мин`.
- Для незавершённого этапа вместо факта показывать `—`; явно отмечать текущий этап. После завершения сразу обновлять статус и фактически затраченное время, измеренное по времени начала и окончания работ. Приблизительное время отмечать `≈`.
- Обновлять прогресс при завершении этапов и существенных изменениях плана; итоговый отчёт должен содержать завершённые этапы и их фактическое время. Время ожидания согласования пользователя не включать в длительность реализации.
- Если выявлена новая обязательная работа, добавить её в план и обновить прогноз. Не выдавать прогноз за фактическую длительность.
