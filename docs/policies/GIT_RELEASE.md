# Git, CI/CD, защита изменений и накопительный релиз

Обязательный регламент из корневого `AGENTS.md`; также см. `docs/BRANCHING.md`, `docs/CI.md` и `docs/DEPLOYMENT.md`.

## Единый формат итогового отчёта

Обязателен общий шаблон [`docs/REPORTING.md`](../REPORTING.md) для всех задач и исполнителей:

1. **Что реализовано** — кратко по функциональным блокам.
2. **Что требуется от тебя** — только действия/решения владельца либо «Действий не требуется».
3. **Сборка и деплой** — **одной компактной строкой в самом низу**: точная ветка и состояние изменений всегда; результаты фактически выполненных CI/QA/сборки/merge/deploy/smoke, SHA, PR и Actions — по наличию. Разделять элементы символом `·`, статусы делать короткими; не превращать это в отдельные пункты или таблицу. Не выносить статус ветки в шапку. Для production **после строки** обязательно идёт нумерованный список «В релиз вошли». Детальные правила и примеры — в `docs/REPORTING.md`.

После production-релиза в нижнем блоке обязателен подраздел **«В релиз вошли»**:
1. **Сервис или область:** краткое название и суть доработки.
2. **Следующий сервис или область:** краткое название и суть доработки.
3. Далее — все остальные фактически выпущенные изменения.

- «В релиз вошли» — **вертикальный нумерованный список**, одна смысловая доработка на строку, не таблица и не абзац.
- Список составлять по сравнению прежнего и нового production SHA и охватывать **весь накопительный релиз**, включая задачи других чатов, изменения документации, Skills, CI и инфраструктуры.
- Не заявлять PASS для непроверенных стадий. Push в `main` без завершённых production CI/deploy/smoke не является подтверждённым выпуском. При ошибке показывать отдельный статус `deploy failed` / `NOT TESTED`, а не успешный `main`.
- Правило едино для всех будущих чатов и исполнителей.

## Обязательное ожидание итогов CI/CD

- После любого push, merge, релиза или другого действия, запускающего GitHub Actions, **не завершать задачу, пока не получен терминальный результат всех относящихся к ней проверок** для точного итогового SHA. Статусы `queued`, `pending` и `in_progress` не являются успешным завершением.
- При производственном релизе дождаться не только CI ветки `development`, но и production CI, deployment и итоговых smoke/health-проверок. Перевод `main` на нужный SHA сам по себе не означает успешную выкладку.
- Если проверки завершились неуспешно, изучить причины, внести исправление по обычному процессу и дождаться результата повторного CI. Не объявлять релиз успешным до подтверждения фактической выкладки.
- В итоговом сообщении указывать результат проверок, SHA, ссылку на workflow и отдельно статус production. Если внешняя система делает завершение недоступным, честно обозначить блокер и не выдавать незавершённую работу за выполненную.

## Git и CI/CD — накопительные релизы

- **Постоянные ветки:** `development` — интеграционная ветка, `main` — точное состояние production-релиза. Исторический снимок `archive/development-before-cumulative-release-2026-10-08` хранится только для восстановления старой работы.
- **Любая задача:** сначала актуальная `development` (напрямую или через временную feature-ветку), затем общий CI. По умолчанию задача **не** выкатывается в production. Не задавать вопрос «сразу в прод?» перед каждым изменением; прямое указание пользователя на релиз — отдельное действие.
- **Накопление:** коммиты разных задач остаются в `development` до явной команды на выпуск. Не готовую к совместному релизу или рискованную реализацию нельзя интегрировать в `development`: оставить в изолированной feature-ветке до готовности либо закрыть безопасным feature flag (по согласованию). Разработчику запрещено автоматически выкатывать законченный логический блок после его CI.
- **Запрет промежуточных интеграций:** промежуточные результаты одной задачи (готовый экран, отдельный сценарий, технический этап, успешная сборка) **не переносить в `development`**. До полного выполнения согласованной задачи, проверок и обновления релевантной документации работа остаётся в отдельной feature/fix-ветке. Исключение — явное решение владельца, что текущий объём «пока достаточно»/согласован завершённый сокращённый этап: фиксировать границы завершённого и оставшееся, проверить безопасную интеграцию. Молчание, промежуточный отчёт и зелёный CI не означают согласование.
- **«Катим сразу в прод» / «выкатывай в прод»:** это разрешение выпустить **всё** текущее проверенное состояние `development`, включая независимые изменения других чатов. Выборочная публикация задачи, cherry-pick, squash/rebase, отдельная release-ветка и перенос одной только feature-ветки в `main` запрещены.
- **Единый порядок для всех чатов:** по команде «кати в прод» без повторного подтверждения самостоятельно проверить актуальный `development`, дождаться завершения `CI verified` и `Development release candidate` для его SHA, при ошибке изучить и по возможности исправить причину и заново дождаться CI. Затем безопасно продвинуть весь проверенный `development` в `main` и дождаться штатного автоматического production CI, deploy и smoke-проверок. Очередь или продолжающийся CI — не причина завершать задачу отказом. Итоговый ответ — только о завершении релиза либо о конкретном непреодолимом препятствии. Не добавлять отдельную систему релизов, GitHub Issues или новые workflow: действующий CI/CD уже выполняет сборку и развёртывание.
- **GitHub-доступ проверять по операциям, а не по догадкам:** прочитать репозиторий ≠ проверить Actions ≠ иметь право записи. Перед заявлением «нет доступов» обнаружить доступные GitHub-инструменты и проверить требуемое действие: `get_repo` (permissions), `fetch` GitHub Actions runs, `fetch_workflow_run_jobs` (CI по SHA), `compare_commits` (безопасность переноса), `update_ref` с `expected_sha` (fast-forward). Название `Cumulative production release` — не обязательный инструмент: обычный проверенный перенос SHA из `development` в `main` сам запускает штатный prod CI. **Запрещено делать вывод «не могу проверить CI / нет права деплоя» только потому, что не найден отдельный workflow-dispatch или специфичный инструмент.** При неудаче одной операции найти другое разрешённое действие и проверить реальный ответ API. Pending/queued/cancelled на устаревшем SHA не равны отказу в доступе; проверять именно последний SHA `development`. Лишь подтверждённый отказ доступа на нужную операцию или полное отсутствие разрешённых альтернатив — объективный блокер. Повторного участия пользователя не требовать без такого факта. Обязательный практический алгоритм: `docs/GITHUB_ACCESS.md`.
- **Команда «кати в прод» — задача на результат, а не запрос инструкции/статуса:** она уже является окончательным разрешением на релиз **всего** `development`. Не спрашивать повторного подтверждения, не возвращать пользователю отказ «CI не подтверждён / проверка ещё не завершена» и не перекладывать на него ожидание или ручной запуск. Самостоятельно проверить актуальный состав `main..development`, зафиксировать SHA, дождаться завершения **обоих обязательных checks** — `CI verified` и `Development release candidate` — для точного SHA (queued/in_progress/missing сразу после push означает **ждать**, а не отказ). Если CI завершился ошибкой, изучить логи, исправить причины в `development`, снова пройти проверки и продолжить **по той же команде пользователя**. Если вершина `development` изменилась в ходе ожидания, заново проверить полный накопленный состав и дождаться проверок нового SHA, не выкатывать устаревший. Не публиковать коммит с проваленными проверками и не обходить защиту `main`; при объективном блокере, который нельзя исправить без пользователя, сообщить точную причину и необходимое действие.
- **Перед переносом:** показать краткий состав всех накопленных изменений и риски; выполнить fast-forward только после успешных проверок текущего SHA. После переноса дождаться и проверить production CI/deploy/smoke, при проблеме заняться исправлением. Не считать задачу завершённой лишь после push в `main` или запуска CI; конечный ответ должен явно говорить, развернуто ли на стенде. Если изменений нет, проверить актуальный production-run и честно сообщить, что новый deploy не требовался.
- **Продвижение:** `main` продвигается **только fast-forward до проверенного SHA `development`**; перед операцией `main` обязан быть предком `development`. Push/update `main` напрямую для функциональных исправлений, cherry-pick, merge-коммит, squash, force-push и reset `main` запрещены. При аварийной ошибке исправление тоже сначала попадает в `development`; выпуск включает весь накопленный набор. Не откатывать production через откат ref: создавать и проверять revert в `development`, затем продвигать `main`.
- **CI:** push `development` проверяет проект и публикует проверенные images, **без деплоя**. Push `main` вызывает CI/deploy на production. Дополнительная проверка `main` гарантирует, что опубликованный SHA существует в истории `development`; без неё деплой не выполняется. Ручной workflow `Cumulative production release` **дожидается** завершения CI и обязательной проверки кандидата для текущего `development` (до 90 минут) и затем делает fast-forward `main`; если запись `main` сделана встроенным `GITHUB_TOKEN`, workflow отдельно запускает production CI через workflow_dispatch (такая запись сама по себе не инициирует другие workflows).
- **Тестовый стенд:** после предоставления отдельной инфраструктуры/секретов `development` будет автоматически выкатываться на TEST. До её настройки `development` не должна обращаться к production SSH/БД/volume или запускать деплой.
- **Защита в GitHub без дополнительного приложения:** GitHub ruleset для `main` требует два успешных check runs **на точном SHA**: `CI verified` и `Development release candidate` (ожидаемый источник — GitHub Actions). Второй check создаётся отдельным workflow **только на push в `development`**, так что произвольный новый commit напрямую в `main` будет отклонён до его проверки в `development`. Required checks настроить без bypass; `Restrict updates` и `Require a pull request` **не включать**, поскольку они заблокируют fast-forward release с текущим `GITHUB_TOKEN`. Это SHA-проверка, **не** ограничение субъекта: пользователь с правом push технически способен вручную продвинуть `main` на уже проверенный SHA `development`. Только явная команда пользователя разрешает такой выпуск организационно. Документация и ручные шаги: `docs/CI.md`.
- **После релиза:** проверить результат main CI, deploy и smoke; если ошибка — зафиксировать статус, не считать релиз успешным. `main` всегда остаётся предком `development`. Релиз одного и того же SHA повторно не создавать.
- **Локальные/временные ветки:** допускаются для незавершённой или параллельной работы; удалять их только после безопасной интеграции. Существующие правила по registry, адресным image builds и secrets из `docs/CI.md` остаются обязательны.
- **Коммиты:** разделять независимые задачи, проверять чужие параллельные изменения, не выполнять force-push и не отменять запущенный production deploy. При изменении CI/deploy поддерживать `docs/CI.md`, `docs/DEPLOYMENT.md` и `ideas/.../operations/CI.md` актуальными.

## Параллельная разработка и защита изменений

- **Разрешение конфликтов происходит в рабочей ветке до интеграции в `development`:** получить свежий `origin/development`, в своей feature/fix-ветке влить `origin/development` обычным `git merge` (для уже опубликованных совместных веток — без rebase/force-push), разрешить конфликты с сохранением смысла обеих изменений, запустить проверки и только затем объединить готовую ветку в обновлённый `development`. Если `development` изменился снова — повторить синхронизацию и проверку. Нельзя откатывать или перетирать независимые изменения другого чата, механически выбирать только `ours`/`theirs`. При неразрешимом смысловом конфликте собрать обе версии и конкретно описать противоречие, не теряя код. Подробности: `docs/BRANCHING.md`.

Проект разрабатывается многопоточно: одновременно могут выполняться независимые задачи в разных чатах или рабочих контекстах. Любую работу с репозиторием нужно вести с предположением, что после последнего чтения ветки другой поток уже мог внести изменения.

- Перед началом изменений и повторно непосредственно перед записью, commit, merge или разрешением конфликта необходимо получить актуальное состояние целевой ветки и проверить, не появились ли параллельные изменения в затрагиваемых файлах.
- Запрещено записывать целый файл поверх более новой версии, используя устаревший снимок. Свои изменения нужно переносить на актуальную версию файла, сохраняя чужие независимые доработки.
- Запрещены `force push`, принудительный reset общей ветки, переписывание общей истории и другие действия, способные удалить уже опубликованные коммиты, если это явно не согласовано отдельно.
- При merge/rebase/cherry-pick конфликт нельзя разрешать механическим выбором только одной стороны (`ours`/`theirs`), если обе стороны содержат функциональные изменения. Нужно объединить независимые изменения и убедиться, что результат сохраняет поведение обеих задач.
- Если параллельные изменения затрагивают одну и ту же бизнес-логику и их нельзя безопасно совместить автоматически, конфликт считается смысловым: нельзя молча отбрасывать одну реализацию. Нужно сохранить обе исходные версии до принятия решения и явно зафиксировать конфликт.
- Перед переносом `development` в `main` необходимо учитывать актуальный `main`, а не состояние `main` на момент начала задачи. Интеграция не должна откатывать изменения, которые попали в `main` из других параллельных задач.
- После интеграции необходимо проверить итоговый diff/историю: изменения текущей задачи присутствуют, а параллельные изменения других задач не исчезли.
- Удалять временную ветку другого потока только потому, что она не `main`/`development`, запрещено. Сначала необходимо убедиться, что работа завершена или полностью интегрирована; правило двух постоянных веток не должно приводить к потере активной параллельной работы.
