# Политика задач и GitHub Issues

Обязательный регламент из корневого `AGENTS.md`; единый источник backlog и статусов.

## Единый реестр задач

- **Единственный актуальный бэклог — GitHub Issues репозитория `irlix-services`**: https://github.com/gerlingerstanislav-creator/irlix-services/issues . Никаких параллельных списков текущих задач в `irlix-services` и `ideas` не вести.
- **Issues — только память о незавершённых, отложенных и запланированных доработках или дефектах, к которым необходимо вернуться.** Не создавать Issue автоматически по каждому обращению, замечанию, багу, PR или изменению. Если задача выполняется сразу в текущем диалоге и доводится до результата, Issue не требуется; достаточно обновления кода и итоговой документации по обычным правилам.
- Из сообщений владельца продукта, пользователей и QA переносить в Issues только то, что решено **сохранить на будущее** или не удалось завершить сейчас. Перед созданием проверять дубли, код, ТЗ и существующие Issues. Если в ходе текущей работы осталась незакрытая часть, создать или актуализировать Issue только на этот остаток. Если пользователь явно просит «добавь в идеи/бэклог», сохранить как `Идея`/`Бэклог` даже без немедленной реализации. Спорные предложения не считать утверждёнными; при необходимости уточнить до переноса в работу.
- Стадии (отдельные метки Issues): `Идея` — не утверждено; `Бэклог` — принято к реализации; `TODO` — текущий/следующий этап; `Done` — **выложено в production**; `Tested` — **QA проверил в production**. При отрицательном QA или повторной регрессии возвращать в `TODO` с объяснением в комментарии. Нельзя считать merge/CI/стенд достаточными для `Done`.
- В каждой Issue сохранять сервис, тип (bug/feature/improvement/tech-debt), приоритет P0–P3, источник, ожидаемое поведение, критерии приёмки, взаимосвязанные задачи и ссылки на релиз/QA при наличии.
- Названия Issues должны соответствовать схеме **`[Статус] [Сервис] [Тип] [Приоритет] Краткое действие`**. Статус берётся из пяти стадий выше; сервис — устойчивый короткий идентификатор (например `Employees`, `Vacations`, `Clients`, `DesignSystem`, `Platform`, `Migration`, `CI-CD`); тип: `Bug`, `Feature`, `Improvement`, `TechDebt`, `QA`, `Test`; приоритет `P0`–`P3`. При смене стадии или приоритета одновременно обновлять заголовок. Не переименовывать Pull Requests по этому правилу. Любая проверка на стенде не заменяет `Tested` на production. Без подтверждения не приписывать задаче статус продакшен-релиза или успешной проверки.
- `ideas` хранит только актуальную итоговую продуктовую документацию и согласованные решения; изменения бизнес-правил по принятым задачам отражать в соответствующем ТЗ, но **не вести там список задач или их статусы**.
