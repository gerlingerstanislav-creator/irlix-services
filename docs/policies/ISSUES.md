# Политика задач и GitHub Issues

Обязательный регламент из корневого `AGENTS.md`. До подтверждённого переноса на корпоративный GitLab (#408) единственный актуальный реестр незавершённых задач — [GitHub Issues irlix-services](https://github.com/gerlingerstanislav-creator/irlix-services/issues). `ideas` хранит согласованные продуктовые решения и ТЗ, а не копию backlog. После GitLab cutover правила и таксономию меток переносим без смены смысла, а рабочие ссылки обновляем.

## Когда создавать Issue

- Issue — **только обязательство вернуться** к реально незавершённому дефекту/утверждённой задаче, сохранённой идее или согласованной отложенной работе. Не создавать автоматически на каждое замечание, правку, баг-фикс, PR, релиз или успешный QA.
- Сначала проверить актуальный код, ТЗ, существующие Issues, PR и родительский поток. Если запрос можно закончить в текущей задаче, отдельная Issue не нужна. Неподтверждённый дефект не выдавать за воспроизведённый; добавить его к существующему QA-пакету, если это лишь сценарий проверки.
- Несколько комментариев из одного Excel, интервью, чата или отчёта **сначала группировать по одной пользовательской проблеме/сценарию**, а не создавать одну Issue на строку. После пилота дробить только утверждённые **независимо завершаемые** реализации; уже выполненное закрывать со ссылкой на проверку.
- Будущие продуктовые направления допустимы как одна `stage:idea` / `stage:backlog` Issue, если владелец велел сохранить. Не создавать десятки непроверенных технических подзадач и не считать такую идею текущим обязательством разработки.
- Перед закрытием писать причину (completed, duplicate, not planned) и ссылку на родительскую или заменяющую задачу. Никакого «выполнено в production» без подтверждения.

## Labels — единственный источник классификации

**Названия Issues — короткое понятное действие без префиксов** `[Статус] [Сервис] [Тип] [Приоритет]`. Ранее использовавшиеся префиксы убраны: категория и порядок определяются настоящими GitHub Labels. Не дублировать метки заголовком или вручную редактируемыми таблицами статусов.

| Группа | Метки | Правило |
|---|---|---|
| Стадия | `stage:idea`, `stage:backlog`, `stage:todo`, `stage:done`, `stage:tested` | **Ровно одна**. Идея — не утверждена; backlog — принято, но не очередь текущей работы; todo — текущая/ближайшая; done — код доказанно в production; tested — QA доказанно проверил в production. |
| Приоритет | `priority:P0` … `priority:P3` | **Ровно одна**: P0 — безопасность/потеря данных/непроходимый критический gate; P1 — основной бизнес-сценарий; P2 — локальные улучшения; P3 — косметика/долгосрочные идеи. Учитывать реальный риск и ближайший gate, а не громкость формулировки. |
| Размер | `size:S`, `size:M`, `size:L`, `size:XL` | **Ровно одна** после triage. S — точечная проверка/правка, M — ограниченный сценарий, L — крупный модуль/объём QA, XL — межсервисная или многопроходная работа. Это **относительная сложность**, не сроки и не story points. |
| Тип | `type:bug`, `type:feature`, `type:improvement`, `type:tech-debt`, `type:qa`, `type:test` | **Ровно одна**. QA-гипотезу не классифицировать как доказанный bug. |
| Сервис | `service:<slug>` | Один или несколько только **непосредственно затронутых** сервисов (`clients`, `finance`, `migration`, `vacations`, `timesheets`, `platform`, `ci-cd`, `design-system` и др.). Не метить всю платформу за любую косвенную зависимость. |
| Этап запуска | `gate:R0` … `gate:R5` | Необязательно, может быть несколько: **принадлежность к этапу**, не автоматический блокер. Жёсткие блокировки оформляются связями ниже. |
| Особые потоки | `kind:program`, `track:1c` | Только когда полезно: программа перехода #429, параллельное обследование/импорт 1С #436/#437. Не плодить индивидуальные метки для каждой идеи. |

Стадия и GitHub `open/closed` — разные измерения. `stage:done` допускает открытую Issue до production QA; после доказанного `stage:tested` её закрываем как completed. При отказе от реализации или дубле закрываем с `not_planned/duplicate` и объяснением, **не** проставляя `done/tested`. При провале QA вернуть в `stage:todo`, описать регрессию. `development` и зелёный CI **не** являются `stage:done`.

У каждой активной задачи одновременно должны существовать stage, priority, size, type, service. При изменении значения сначала убрать старую метку **той же группы**; не накапливать `priority:P1` и `priority:P2` вместе. Для временной неподготовленной идеи допустима первоначальная оценка размера S/M/L/XL с пометкой «предварительно». Не вводить оценки в днях/часах.

## Связи Issues: программа, подзадачи, зависимости

- **Parent / Sub-issue:** целостная программа или независимый большой deliverable — родитель, дочерняя Issue — самостоятельный проверяемый результат. Не дробить задачу только ради дерева. У дочерней может быть один родитель; вложенность мелких QA-кейсов обычно лишняя.
- **Blocked by / Blocking:** только **жёсткая** зависимость, когда без завершения другой Issue нельзя закончить эту. Направление обязательно: «#432 блокируется #431». Не использовать для простой последовательности обсуждений или косметики; избегать циклов.
- **Related:** тематическая связь, общий контракт или гипотеза без необходимости ждать завершения. Похожие Issues сначала проверять на дубль — `related` не повод хранить дубли вечно.
- Когда доступно редактирование нативных GitHub Sub-issues/Dependencies, **они предпочтительны**, текстовые ссылки дополняют контекст. Подключённый GitHub API текущего AI-контекста на дату аудита 21.10.2026 позволяет **читать**, но не создавать native Sub-issues/Dependencies. Пока используем в теле Issue секцию `### Связи и зависимости`: «Входит в», «Блокируется задачами», «Блокирует / следующий шаг», «Связанные». Это **взаимные кликабельные ссылки**, а не якобы настроенные native relations. После появления write-доступа переносим в нативные поля без создания дубликатов и удаляем избыточность.
- Для связи с кодом PR указывает `Closes #N` / `Fixes #N` **только если** релизная политика допускает авто-закрытие при merge; по умолчанию в cumulative release используем `Refs #N` и закрываем по доказанному production QA. Автоматическое закрытие при merge в `development` не должно создавать фиктивный `Done`.
- Перед созданием/изменением дочерней задачи обновлять родителя и проверять отсутствие конфликтов между графом и обязательными gates. Ручные чекбоксы с отдельными «статусами выполнения» не вести: единственный источник статуса — Issue и её labels.

## Короткий шаблон Issue

1. **Проблема/результат** и почему это не закрывается текущим PR.
2. **Источник/подтверждение:** ТЗ, пользователь, QA, SHA/окружение/воспроизведение для бага, без личных/финансовых данных.
3. **Ожидаемое поведение и критерии приёмки** (включая роли/scope, негативные сценарии и границы, если применимо).
4. **Ссылки/зависимости:** parent, blocked by, related, PR/release/QA, если есть.
5. **Метки:** stage, priority, size, type, service, опционально gate/track.

Допускается короткая Issue в 5–10 строк, если контекст и критерии уже есть по ссылке в актуальном ТЗ. Не создавать отдельную Issue только ради заполнения шаблона.

## Триаж без ритуалов

По событию (релиз, пилот, крупная миграция, серия замечаний) проверить связанные задачи: закрыть доказанное, снять дубли, проверить блокировки, приоритет, stage и новый scope. Для повседневной работы достаточно основных фильтров [P0/P1](https://github.com/gerlingerstanislav-creator/irlix-services/issues?q=is%3Aissue+is%3Aopen+label%3A%22priority%3AP1%22) и [R0](https://github.com/gerlingerstanislav-creator/irlix-services/issues?q=is%3Aissue+is%3Aopen+label%3A%22gate%3AR0%22); GitHub search можно комбинировать по другим `label:` и `is:open`. Никаких обязательных спринтов, оценки времени или issue на каждую микроправку.

Долгосрочные идеи сохраняются с `stage:idea`/`stage:backlog` и `priority:P3`, но не загромождают ближайшую очередь. До GitLab cutover source of truth — GitHub Issues; после cutover — единственный активный бэклог GitLab, GitHub остаётся зеркалом кода, не вторым трекером.
