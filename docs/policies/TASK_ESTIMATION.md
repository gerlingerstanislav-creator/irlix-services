# Прогнозы и фактическая длительность задач

Цель: за 20–30 завершённых задач накопить **сопоставимые наблюдения**, чтобы оценивать типичные сроки, а не угадывать минуты. Правило распространяется на **Chat** и **Work**. Отчёты остаются в GitHub PR, не создаём отдельные Issues по каждой задаче.

## Термины

- **Прогноз**: интервал времени (например, 20–50 мин), известный **до выполнения**; указывать сервисы, тип задачи, неопределённость/риски. После начала нельзя незаметно перезаписать начальный прогноз; изменения фиксировать отдельно с причиной.
- **Время роли**: сумма подтверждённых отрезков START→STOP **конкретного исполнителя/прохода**, по часам. Это **elapsed time** агента, а не измеренное CPU-время или количество токенов. В Chat роли — этапы **одного** ассистента; в Work — отдельные subagents. Работа разных Work-агентов может идти **параллельно**; сумму их времен нельзя выдавать за общую длительность задачи.
- **PR lead time**: от `created_at` PR до `merged_at` — *календарное время* вместе с ожиданием и CI. Это **не** чистая длительность разработки; работа до PR не включена.
- **Ожидание CI/пользователя**: отмечать отдельно, если есть достоверные границы интервала. Не включать в время роли, если агент в это время не выполнял полезную работу.
- **Не измерено**: нет обеих временных отметок — никаких выдуманных `≈ 10 мин`. Закрытый START без STOP показывать `измерение не завершено`.

## Минимальные действия в каждой задаче

1. **[PM] До выполнения:** указать прогноз-диапазон и этапы в сообщении пользователю; при открытии PR можно сохранить исходный прогноз в описание PR в виде текстового поля `Прогноз: 20–50 мин`. Никаких лишних Issues.
2. **При каждом реальном переходе роли:** если PR уже открыт и есть доступ к GitHub комментариям, PM пишет короткий START и STOP каждой роли (или каждому Work-subagent). Для работы до PR фиксирует собственный таймер/подтверждённые метки Work и переносит итоги в PR после открытия. Не считать одно сообщение дважды. Не отправлять лишние комментарии без возможности записи.
3. **[PM] В конце:** вывести таблицу **каждой участвовавшей роли** с фактическим интервалом или `не измерено`; отметить повторные циклы QA/исправлений, если они были, статус QA и PR SHA. Суммарно показывать отдельно **сумму времени ролей** и **календарное время** (если доступны); не складывать параллельные роли ради прогноза календарного срока.
4. **Масштабирование:** после 20–30 работ анализировать медианы по типу задачи, сервису, объёму diff, числу QA-повторов и неопределённости. Сперва прогнозировать диапазонами; сравнивать исходный прогноз с фактами. Учитывать незавершённые интервалы и отсутствующие метки как пропуски, а не нули.

## Формат временных отметок GitHub PR

В отдельном комментарии PR добавлять:

```text
<!-- irlix-time-event-v1 -->
role: QA
action: start
segment: qa-review-1
```

При завершении — тот же `role` и `segment`, но `action: stop`. `segment` различает повторные проходы и параллельных агентов одной роли. Роли: `PM`, `Analyst`, `Designer`, `Developer` (или `Developer:clients` и т. п.), `QA`, `PlatformEngineer`, `ProductAdvisor`.

Время берётся **только из серверных `created_at` GitHub**, а не из текста комментария. В расчёт попадают записи от владельца/доверенных участников репозитория. Нельзя отправлять события задним числом и выдавать их за прошлое время; для прошлой работы возможна лишь проверяемая отдельная фиксация с явно указанным источником. Если START/STOP не были отмечены, факт = `не измерено`.

GitHub Action `PR task timing` автоматически обновляет **один** PR-комментарий `<!-- irlix-time-summary-v1 -->`: времена подтверждённых пар, открытые сегменты, отсутствующие измерения и календарный интервал PR. Само создание PR или CI **не запускает AI**. При необходимости событие START/STOP может публиковать главный Work PM через GitHub-инструменты. В обычном Chat это фактический таймер **этапов**, а не разных физических агентов.

## Финальный ответ PM — обязательный формат

| Роль | Время | Метод |
|---|---:|---|
| PM | 5 мин или не измерено | GitHub START→STOP / Work task telemetry / — |
| Analyst | 7 мин или не измерено | ... |
| Developer | 19 мин или не измерено | ... |
| QA | 8 мин или не измерено | ... |

Указывать только реально задействованные роли, а если процесс предполагает роль, но проход не состоялся — отдельно сказать `NOT TESTED`. **Всегда** отражать роль и время в отчёте, даже когда значение неизвестно. В Work предпочтительно брать реальные временные отметки инструментов исполнения. Не объявлять это точным временем активного мышления модели; это время выполнения задачи/этапа по наблюдаемому таймеру.

Прогнозные этапы в таблице на старте и обновления по факту остаются обязательны. Если время измерялось только по GitHub PR, явно указать, что работа **до PR не измерена**. Источник данных и ограничение точности важнее искусственной точности до минуты.

**Ограничение прав GitHub Actions:** в данном репозитории стандартный GITHUB_TOKEN может возвращать 403 при POST/PATCH PR комментариев. Поэтому основным гарантированным выходом workflow считаются job summary и артефакт `task-timing-*` (`task-timing.md` и `task-timing.json`, хранение 90 дней); комментарий создаётся только когда права это позволяют. Исходные START/STOP от доверенных авторов PR остаются в истории комментариев GitHub. Артефакт не является бессрочным хранилищем — для долговременной аналитики используем PR timeline или экспорт.
