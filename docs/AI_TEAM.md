# AI-команда Irlix Services — два режима: ChatGPT Chat и ChatGPT Work

## Принцип

Обязательный общий для обеих схем [протокол контекстов и handoff](AGENT_CONTEXT_PROTOCOL.md): матрица входных данных каждой роли, границы независимого аудита Analyst/Designer/QA/PlatformEngineer, отчёты PM и видимые метки `[PM]`, `[Аналитик]`, `[Дизайнер]`, `[Разработчик]`, `[Platform]`, `[QA]`. В Work реальные subagents получают минимально необходимый контекст, а не полную переписку соседей; PM пересылает только утверждённые артефакты и проверяемые результаты. В обычном Chat те же метки означают лишь последовательные проходы одного общего контекста.

Одна и та же задача ведётся по **разным правилам в зависимости от режима ChatGPT**. Обе схемы используют подключённый GitHub, действующие проверки, приватные продуктовые ТЗ `ideas` и общие правила `AGENTS.md` + `docs/CONTEXT_SCOPE.md`.

| | Обычный Chat | ChatGPT Work с доступными subagents |
|---|---|---|
| Координация | Ассистент как PM в одном чате | PM — главный агент/координатор Work |
| Аналитик, дизайнер, разработчик, QA | Последовательные проходы **одного контекста** | **Отдельные делегированные subagents с собственными контекстами** по каждой задействованной роли |
| Ожидание и передача результата | Следующий проход того же чата | PM запускает, отслеживает, **ждёт результат**, при FAIL повторно назначает работу |
| Независимый QA | Критическая самопроверка, не независимый AI | Отдельный QA-контекст, НЕ получает рассуждения разработчика |
| Код / ветки / CI | GitHub + отдельная feature-ветка | Те же правила GitHub + один владелец записи каждого файла |
| OpenAI API, Codex, дополнительный VPS | Не требуются | Не требуются для subagents Work, если возможность доступна аккаунту |

**Важно:** `AGENTS.md`, этот документ и `.github/agents/*.agent.md` — **инструкции**, а не механизм запуска. Работающие subagents появляются только когда **сам ChatGPT Work действительно предоставляет возможность делегирования**. По актуальной документации OpenAI Work может запускать subagents у подходящих аккаунтов; на обычных уровнях интеллекта запрос на делегирование должен быть явным. Подключение и права в Work должны быть настроены пользователем. Никакой GitHub Actions не вызывает AI автоматически. Не выдавать предполагаемые запуски за реальные.

## Подключение профессиональных ChatGPT Skills

Обязательная [матрица профессиональных Skills по ролям](AGENT_SKILLS.md) определяет, какой установленный универсальный Skill применяется Analyst, Designer, Developer (Laravel и/или Vue) и QA. PM назначает **точное имя Skill**, каждый исполнитель проверяет его доступность **в собственной сессии**. Skills не являются LLM-агентами и не запускают subagents; **если Skill недоступен**, применяются полноценные репозиторные инструкции, без ложных заявлений, будто его прочитали. Приоритет у проектных ТЗ и контрактов, а не универсальных советов Skill. Не передавать Skills в качестве обходного канала чужого контекста.

## Режим A: обычный Chat — оставить существующий процесс

PM → Analyst → Designer (если UI) → Developer:<service> → PlatformEngineer (если общие контракты) → QA → исправления → PM. Все этапы **в одном чате и одном контексте**; не заявлять независимых LLM-агентов.

Для каждого задания: определить scope, изучить нужные бизнес-правила `ideas`, соблюдать `@irlix/ui` для интерфейсов, изменить код и тесты в отдельной ветке от свежей `development`, открыть PR, дождаться QA и конечного CI. При ошибках исправить код и проверить повторно. Пользователю достаточно обычного запроса в текущем чате. Разные чаты могут вести независимые задачи в отдельных ветках.

## Режим B: ChatGPT Work — PM-оркестратор и отдельные subagents

**Триггер:** пользователь запускает задачу именно в Work; при доступности Work subagent tools PM **явно делегирует** каждую затронутую роль в отдельный контекст. Не имитировать делегирование последовательными переключениями «масок» в основном чате.

### Роли и ограничения

| Роль | Когда создаётся отдельный subagent | Вход → выход |
|---|---|---|
| PM (главный Work-агент) | Всегда, как корневая сессия; **не** дополнительный subagent | Задача → назначения, контроль, интеграция и итог |
| Analyst | Каждая задача с требованиями, бизнес-логикой или изменением поведения | ТЗ нужного сервиса → критерии приёмки, состояния, permission + scope, неопределённости |
| Designer | Любые UI/UX изменения | Дизайн-система и UX-сценарии → спецификация и визуальные замечания |
| Developer:<service> | Каждый затронутый сервис | Утверждённые критерии + контракты → код, тесты, PR; при необходимости отдельные Vue- и Laravel-направления |
| PlatformEngineer | Shared/auth/permissions, БД-инфраструктура, CI, межсервисные контракты | Архитектура и ограничения → оценка рисков, интерфейсы и проверки |
| QA | Любая реализация или аудит; **обязательно отдельный агент от Developer** | Исходные критерии + PR diff + SHA + CI → независимый QA-отчёт PASS/FAIL/NOT TESTED |
| ProductAdvisor | **Только** по явному запросу владельца | Предложения; неавторизованные новые требования в работу не брать |

Допускается параллельно запускать **независимые читающие задачи** (например, анализ прямых контрактов и UX), но зависимые этапы выполняются **после** необходимых результатов. Не создавай одновременно конкурирующих писателей одних файлов, даже если каждый subagent имеет отдельный контекст. При необходимости два разработчика работают на разных путях и с заранее определённым контрактом; PM единолично интегрирует результат.

### Исполняемый протокол PM в Work

1. **Старт / обнаружение возможности.** Прочитай `AGENTS.md`, `docs/CONTEXT_SCOPE.md` и этот документ. Убедись, что текущий режим — Work и **реально доступны средства запуска subagents**. Скажи, какие роли будешь запускать. В Work при обычных уровнях интеллекта используй **явный запрос/вызов** делегирования; одних markdown-профилей недостаточно.
2. **План и контексты.** Определи затронутые сервисы, GitHub branch / PR, риски пересечения файлов. Каждому subagent передай только минимально нужные пути, конкретную задачу, входные артефакты, полномочия и формат результата. Для роли используй инструкции `.github/agents/<Role>.agent.md` и подходящие профессиональные Skills, если установлены. Не прокидывай историю размышлений других ролей.
3. **Анализ и тест-дизайн.** Запусти Analyst, затем отдельный QA subagent для **первичных негативных, граничных, ролевых и регрессионных сценариев до разработки**. При UI параллельно можно дать Designer исследовать существующие паттерны. PM утрясает противоречия до передачи в разработку; спорные бизнес-решения подтверждает владелец.
4. **Реализация.** Запусти Developer:<service> для затронутых сервисов; при сквозных контрактах подключи PlatformEngineer. Разработчик получает требования и внешний контракт, а не полный чат. Создать ветку только от актуальной development; разграничить write-ownership. Не отдавать QA полномочия менять бизнес-реализацию.
5. **Ожидание и надзор.** PM отслеживает реальные статусы делегированных задач (ожидание, выполнение, блокер, завершение), по необходимости уточняет задачу, **ждёт обязательные ответы**. Нельзя объявлять роль выполненной по факту отправки задания или подменять её результат своим предположением.
6. **Независимая проверка.** Отдельному QA subagent предоставить требования `ideas`, acceptance matrix, diff/PR, exact SHA, артефакты тестов; **не предоставлять rationale, черновики и самопроверку Developer как доказательство корректности**. QA сам определяет негативные, security/permission, граничные и интеграционные проверки; различает PASS, FAIL, NOT TESTED. Designer при UI проверяет реальное визуальное evidence, PlatformEngineer проверяет пересечения контрактов.
7. **Цикл замечаний.** FAIL с воспроизведением → PM передаёт конкретный defect Developer → ждёт исправления и повторного CI → **снова назначает QA** на новый SHA. При повторяющемся FAIL / блокере PM сообщает о проблеме, не выдавая её за успех. Нет TEST — не заявлять real-API/Keycloak E2E.
8. **Интеграция и отчёт.** PM перепроверяет свежую development, разрешает конфликты веток, открывает/доводит PR только в development, дожидается обязательного CI на точном SHA после merge. Сообщает активные/завершённые роли, найденные дефекты, результаты QA/CI, PR, SHA, пробелы покрытия, отдельно статус production.

**Формат результата каждой роли** (передаётся PM, а не в публичный GitHub):
- `role`, `scope`, `source_sha`, `status: PASS | FAIL | BLOCKED | NOT_TESTED`;
- входные ссылки и проверенные требования;
- фактические действия и доказательства / тестовые результаты;
- конкретные замечания с серьёзностью и affected files, незакрытые вопросы;
- изменённые файлы/ветка (если разрешена запись), что делать PM дальше.

### Независимость QA

Отдельный Work subagent QA сохраняет **свой контекст** и должен независимо вывести ожидаемое поведение из `ideas`, а не из объяснений реализации. Автотесты — проверка определённых свойств, а не автоматически полная продуктовая приёмка. Если независимый QA subagent не был реально запущен, статус **«независимый AI QA: NOT TESTED»** (даже при зелёном CI).

### Недоступность subagents в Work

Если у текущей сессии нет инструментов делегирования, **сообщи об ограничении прямо и до создания впечатления, что роли запущены**. Не называй последовательные проходы одним агентом «отдельными контекстами». Предложи либо воспользоваться обычным режимом Chat по правилу A, либо запускать отдельные Work-чаты с ручным разделением и передачей результатов через PR. **Не переключай режим без согласия пользователя**. Документ не включает эту функцию в настройках аккаунта сам по себе.

## Общие правила, действующие для обоих режимов

- Единый бэклог незакрытых вопросов — GitHub Issues, только по `AGENTS.md`. `ideas` — утверждённые актуальные ТЗ, не список задач.
- `irlix-services` публичный, `ideas` приватный. Права доступа к приватному ideas у subagent могут зависеть от доступных в Work инструментов. При недоступности фиксировать `NEEDS_INFO`, не угадывать требования. Не публиковать закрытые ТЗ, персональные, коммерческие данные и секреты в публичный PR, отчёты CI и fixtures.
- Для каждого чата/задачи отдельная feature-ветка из свежей `development`, никакого прямого коммита в `main`. При параллельных задачах внимательно согласовывать shared UI/auth/infra, не затирать изменения.
- `.github/workflows/ai-team.yml` **не запускает AI**: он пишет детерминированный комментарий с затронутыми сервисами/ролями. GitHub QA/CI проверяет только реальные автоматические сценарии и создаёт артефакты; в чат не поступают push-уведомления без отдельной интеграции.
- Нет независимого TEST — Playwright smoke использует локальный Chromium и синтетические API. `PASS`, `FAIL`, `NOT TESTED` указывать по факту. После изменений QA и docs обновлять по необходимости.
- Production только по **прямой команде владельца** и по существующему проверенному процессу release `development → main`. Режим Work или запуск subagent сам по себе **не разрешает релиз**.

## Как запускать Work

Открой ChatGPT **Work** в проекте Irlix Services, предоставь доступ к `irlix-services` и разрешённый доступ к приватному `ideas`; задай задачу с явной инструкцией:

> Работай по AGENTS.md и docs/AI_TEAM.md из irlix-services в режиме Work. Явно запусти отдельные subagents Analyst, QA, Developer:<service> и, если требуется, Designer и PlatformEngineer. PM — координатор. Каждому дай отдельный контекст, дождись результатов, передавай ошибки разработчику и повторяй независимый QA. Никакого production без моего указания. Если subagents недоступны, сообщи сразу, не имитируй их.

В обычном **Chat** специальный запуск не нужен: действует последовательный режим A.

Справка OpenAI о доступности и запуске subagents в Work: https://learn.chatgpt.com/docs/agent-configuration/subagents
