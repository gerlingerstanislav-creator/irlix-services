# Организация работы Irlix Services — ChatGPT + GitHub, без внешнего AI-исполнителя

## Решение

Для текущего этапа проекта используем **обычные чаты ChatGPT, подключённый GitHub и существующие GitHub Actions**. Никакого Codex, OpenAI API, отдельного AI-биллинга, постоянно запущенных LLM-агентов или TEST-стенда для этого процесса не требуется.

**Один чат — одна последовательная рабочая сессия со сменой профессиональных ролей**, а не команда независимо работающих процессов. Один и тот же ассистент последовательно анализирует требования, проектирует UX при необходимости, реализует изменения, проверяет результат как QA, исправляет обнаруженные дефекты и подводит итог как PM. Это не настоящая независимая экспертиза нескольких моделей: следует сохранять критичность, но нельзя выдавать внутреннюю перепроверку за подтверждённую независимую приёмку.

**Разные чаты** могут одновременно вести независимые задачи, каждый со своим контекстом и feature-веткой от актуальной `development`. Общая точка синхронизации — репозиторий и точный SHA. Наличие нескольких чатов не создаёт непрерывного фонового процесса после завершения ответа: очередную работу ассистент не выполняет сам по себе.

## Роли — последовательные этапы выполнения

| Роль | Действие в одном чате | Выход |
|---|---|---|
| PM | Определяет задачу, затронутые сервисы, границы, зависимости, следит за исправлениями и результатом CI | Однозначный объём задачи и финальный статус |
| Analyst | Сверяет требования с утверждённой бизнес-логикой приватного `ideas`, выявляет противоречия; обновляет продуктовую документацию | Критерии приёмки, согласованные изменения ТЗ |
| Designer (для UI) | Использует существующую дизайн-систему, проектирует новые паттерны; позднее критично перепроверяет интерфейс | UX-решение и результат визуального контроля |
| Developer:<service> | Реализует frontend + backend **только затронутого сервиса**, добавляет тесты, обновляет техническую документацию | Код в отдельной feature-ветке / PR |
| PlatformEngineer (при необходимости) | Контролирует общие библиотеки, permissions/auth, межсервисные контракты, миграции, CI/CD | Совместимые интеграции и общие компоненты |
| QA | Запускает и читает реальные результаты автоматических проверок, сверяет код с критериями, исследует граничные/негативные сценарии; фиксирует ограничения покрытия | PASS / FAIL / NOT TESTED по фактическим данным |
| ProductAdvisor | Предлагает необязательные улучшения только по запросу; не вводит требования самостоятельно | Предложения, требующие решения владельца |

Профили `.github/agents/*.agent.md` — справочники ответственности этих этапов. Их наличие **не запускает отдельных AI-исполнителей** и не создаёт сообщения между ними.

## Обязательный алгоритм каждого чата

1. **PM / scoping:** прочитать `AGENTS.md` и `docs/CONTEXT_SCOPE.md`; найти фактический сервис и необходимые прямые зависимости. Не загружать все сервисы в контекст.
2. **Analyst:** выбрать относящиеся к задаче ТЗ `ideas/company-internal-services-*/`; сверить цель, права `permission + scope`, переходы, критерии приёмки. Не угадывать новые бизнес-правила. Частные данные и ТЗ не публиковать в публичный PR.
3. **Designer (если есть UI):** сверить `packages/ui/README.md`, компоненты, токены, адаптивность и доступность; если нужен общий компонент, обновить его, витрину и дизайн-документацию, проверить потребителей.
4. **Developer:<service>:** от свежей `development` создать **отдельную** feature-ветку для задачи; изменить только нужный сервис и контрактных соседей; добавить тесты и документацию. Для сквозной задачи явно указать владельца интеграции.
5. **QA-проход:** независимо от уверенности в реализации критично сверить diff с критериями, запустить доступные локальные проверки и/или PR QA CI, проанализировать результаты, повторить при ошибках. Вести раздельные `PASS`, `FAIL`, `NOT TESTED`; без TEST-стенда нельзя объявлять полноценные real-API/Keycloak E2E или визуальные проверки, которые фактически не проводились.
6. **PM / интеграция:** перед merge сверить новую вершину `development`; при расхождениях влить её в свою ветку, сохранить чужие изменения, повторить проверки, открыть/обновить PR в `development`. После merge дождаться `CI verified` и `Development release candidate` **на точном конечном SHA**. При FAIL — исправлять в рамках задачи, не называть работу завершённой.
7. **Итог в чат:** что изменено; PR/commit SHA; что реально проверено и что остаётся `NOT TESTED`; статус `development` и отдельно production. Не создавай Issues по каждому изменению: сохраняй только незавершённые, отложенные или запланированные работы по `AGENTS.md`.

Роли могут объединяться в одном этапе для маленьких задач; не нужно искусственно создавать дополнительные ожидания или семь последовательных сообщений. Но требования, тестирование и документация не должны исчезнуть только потому, что исполнитель один.

## Что действительно происходит автоматически в GitHub

- `.github/workflows/ai-team.yml` выполняет **только детерминированную маршрутизацию**: по списку изменённых файлов выводит `Developer:<service>` и потенциально относящиеся роли; публикует короткий комментарий в PR. Ни одна модель не вызывается.
- GitHub Actions CI/QA проверяет имеющиеся Node/contract, PHP syntax и synthetic Chromium/Playwright сценарии. Ошибки препятствуют успешному `CI verified`.
- Если проверка провалилась, **GitHub сам не вызывает AI для исправлений**: активный чат/PM должен прочитать лог, исправить ошибку и повторно запустить проверки через новый push.
- GitHub Actions работает независимо от текущего чата. **Этот чат не получает вебхуки/события автоматически** и после своего завершения не продолжает работу незаметно для пользователя.

## Параллельные чаты и защита друг от друга

- Разные задачи — разные feature-ветки, все из свежей `development`. Не писать напрямую в `main`. Вести интеграцию через PR в `development`.
- Перед каждым изменением общих файлов и перед merge заново проверять вершину `development`; нельзя перезаписывать правки другого чата старой копией файла. Содержательные конфликты требуют отдельного решения.
- Если два чата меняют `packages/ui`, permissions, навигацию или общий CI, второй пересматривает изменения и повторно выполняет проверки после совмещения.
- Общее состояние готовности определяется **только GitHub CI для конечного SHA**, а не сообщением из другого чата.
- `main` и production меняются исключительно по явной команде владельца с накопительным выпуском всего проверенного `development`.

## Приватность и текущие ограничения

`irlix-services` публичный, `ideas` приватный. Не копировать приватные ТЗ, данные сотрудников/клиентов, финансовые сведения или секреты в PR, тестовые фикстуры и публичные комментарии. Правила читать только через разрешённый приватный доступ текущего рабочего чата.

Пока нет TEST-стенда, браузерные тесты запускаются локально со **синтетическими API**, не на реальных данных. Визуальная и бизнес-приёмка возможна только в пределах действительно выполненных проверок.

**Для владельца:** никаких подключений Codex, настроек AI Team variable или создания платного API-ключа не требуется. Новые задачи можно просто ставить в отдельных чатах Irlix Services.
