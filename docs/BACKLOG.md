# Бэклог IRLIX Services

**Единый реестр задач — [GitHub Issues](https://github.com/gerlingerstanislav-creator/irlix-services/issues).** Этот файл описывает правила ведения бэклога, а не дублирует задачи. GitHub Projects можно подключить как канбан-представление тех же Issues.

## Что заводим в задачи

- `bug` — ошибка существующей функциональности.
- `feature` — новая пользовательская возможность.
- `improvement` — доработка существующего поведения или UX.
- `tech-debt` — технический долг и инфраструктурные улучшения.

Для каждой задачи указывать **сервис**, **приоритет** (`P0` критический, `P1` высокий, `P2` обычный, `P3` низкий), описание текущего и ожидаемого поведения, критерии приёмки и ссылку на ТЗ/решение при наличии.

## Статусы

`Backlog` → `Ready` → `In Progress` → `Review` → `Done`.

Статусы можно отображать в GitHub Projects. Закрытый Issue означает выполненную или отменённую задачу с зафиксированной причиной, но **не автоматически выкладку в production**.

## Первичная инвентаризация (кандидаты, не заведённые Issues)

Перед созданием задач необходимо проверить код и уже существующие исправления, чтобы не плодить дубликаты:

1. **Migration / Clients:** оценить полноту и корректность переноса legacy-данных, составить перечень расхождений.
2. **Migration / Vacations:** проверить перенос заявлений и восстановление согласующих; отдельно проработать файлы и ссылки на скачивание.
3. **Timesheets:** провести регрессию подтверждений, редактирования и отображения отметок после последних доработок.
4. **Platform:** сверить текущие permissions и доступы с ТЗ.
5. **CV Converter:** оценить задачи следующих итераций (OCR, legacy .doc, клиентские шаблоны, интеграции) и определить приоритет.

Это **не подтверждённый список дефектов** и не замена полноценной инвентаризации ТЗ.
