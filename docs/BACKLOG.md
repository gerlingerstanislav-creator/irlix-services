# Бэклог IRLIX Services

**Единый реестр задач — [GitHub Issues](https://github.com/gerlingerstanislav-creator/irlix-services/issues).** Этот файл описывает правила ведения бэклога, а не дублирует задачи. GitHub Projects можно подключить как канбан-представление тех же Issues.

## Что заводим в задачи

- `bug` — ошибка существующей функциональности.
- `feature` — новая пользовательская возможность.
- `improvement` — доработка существующего поведения или UX.
- `tech-debt` — технический долг и инфраструктурные улучшения.

Для каждой задачи указывать **сервис**, **приоритет** (`P0` критический, `P1` высокий, `P2` обычный, `P3` низкий), описание текущего и ожидаемого поведения, критерии приёмки и ссылку на ТЗ/решение при наличии.

## Статусы

`Backlog` → `Ready` → `In Progress` → `Review` → `Done`.

Статусы можно отображать в GitHub Projects. Закрытый Issue означает выполненную или отменённую задачу с зафиксированной причиной, но **не автоматически выкладку в production**.

## Первичная инвентаризация (кандидаты, не заведённые Issues)

Перед созданием задач необходимо проверить код и уже существующие исправления, чтобы не плодить дубликаты:

1. **Migration / Clients:** оценить полноту и корректность переноса legacy-данных, составить перечень расхождений.
2. **Migration / Vacations:** проверить перенос заявлений и восстановление согласующих; отдельно проработать файлы и ссылки на скачивание.
3. **Timesheets:** провести регрессию подтверждений, редактирования и отображения отметок после последних доработок.
4. **Platform:** сверить текущие permissions и доступы с ТЗ.
5. **CV Converter:** оценить задачи следующих итераций (OCR, legacy .doc, клиентские шаблоны, интеграции) и определить приоритет.

Это **не подтверждённый список дефектов** и не замена полноценной инвентаризации ТЗ.

### Решения по вопросам Vacations (09.10.2026)

Пользователь утвердил следующие правила после QA-триажа. Документированные ранее правила сохраняются, пока явно не изменены.

1. **Руководитель:** организационная структура не предполагает произвольного выбора из нескольких руководителей. Назначение брать из детерминированной цепочки Employees; предусмотренный manager fallback при подтверждённом отсутствии руководителя сохраняется. Различия назначений из QA расследовать как вопрос данных/алгоритма, не вводя дополнительный бизнес-выбор.
2. **Праздники:** можно оформлять оплачиваемый отпуск целиком на праздничный день/дни, даже если списание равно 0; не блокировать такое отсутствие.
3. **Задние даты:** оформление отсутствия задним числом разрешено. Убрать необоснованное ограничение UI и обеспечить одинаковое правило API/UI; специфические требования к подтверждающим документам сохраняются.
4. **Больничные:** отдельный максимальный лимит длительности не вводится.
5. **Редактирование за сотрудника:** кадровику и руководителю разрешено **в определённых случаях**. Какие это типы, состояния, поля и scope — требует отдельного уточнения перед расширением прав; существующие ограничения не отменять до спецификации.
6. **Отзыв:** автор может отозвать своё отсутствие до окончательного подтверждения. Отзыв возвращает отсутствие к стартовому состоянию (`planned`) и обнуляет решения текущего цикла согласования, с аудитом.
7. **Открытый декрет:** сохраняется защита от пересечения отсутствий; поддерживается корректировка открытого периода и последующее закрытие по фактической дате. Не трактовать неопределённую дату конца как выдуманную конечную дату.
8. **«Отклонить»:** отдельное действие согласующего с **обязательным комментарием для специалиста**. Не переводит отсутствие в терминальный статус `rejected`: возвращает его на стартовый этап (`planned`) с сохранением комментария в истории и доступностью автору; решения предыдущего цикла аннулируются. Развести его с текущим действием «Вернуть на доработку» на уровне интерфейса и аудита; не трактовать как безвозвратный отказ.

**К проверке реализации:** приоритет восстановления цепочки руководителя; UI/API задних дат; корректность пересечений с открытым декретом; права автора на отзыв; новая операция отклонения и авторизация по всем типам согласующих. **Единственный незакрытый продуктовый вопрос:** точные «определённые случаи» редактирования за сотрудника (п. 5).
