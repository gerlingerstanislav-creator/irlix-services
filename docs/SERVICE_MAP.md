# Карта сервисов System — источник истины и синхронизация

## Где находится и кому доступна

- `/system/service-map/` — карта в административном System, **только `platform-admin`**. Старый `/service-map/` перенаправляется туда. UI: `apps/portal/src/ServiceMap.vue`, используемый `apps/system/src/main.js`.
- Данные диаграммы: `apps/portal/src/serviceMapData.js`; интерактивный инспектор, контуры Frontend / Backend / Infra, зависимости.
- Единственный источник **публичного frontend-каталога и URL**: `packages/ui/src/serviceCatalog.js`. Карта импортирует его; наборы backend, infrastructure, принадлежность доменам и подтверждённые зависимости задаются явно.
- Дополнительные источники для сверки: `infra/ci/services.json` (фактически собираемые компоненты), `infra/nginx/irlix-services.conf` (маршруты), Compose и реальные API/контракты.
- Продуктовая спецификация: приватный `ideas/company-internal-services-*/services/system/README.md`.

Карта представляет **логические зависимости**, а не мониторинг сетевых соединений, текущее состояние контейнеров, SLA или RBAC доступ. Не публиковать в ней секреты, IP, непубличные сведения или необоснованные связи.

## Актуальная топология

`System` — отдельный frontend (`/system/`): ресурсный монитор, карта, миграции. Единый `Migration Control` (`/system/migration/control/`) встроен в System и использует Migration API; прежний `/system/migration/` служит совместимым перенаправлением, а не отдельной страницей. Управление подключениями выполняется через шестерёнку напротив сервиса в таблице Control; операции со снимками — через кнопку «Снимки». Отдельной публичной frontend-карточки нет. Исторический образ `migration-web` ещё присутствует в registry, но запросы на `/migration/` перенаправляются в System.

`migration` API и `migration-ops` являются отдельными backend-компонентами; `resource-monitor` — отдельный фоновый collector **без HTTP listener**, собирает Docker/host metrics в приватное хранилище; Platform Core читает snapshots read-only. Dashboard обращается к Employees (effective permissions) и к Vacations/Timesheets attention API.

Dashboard (`/`) относится к горизонтальному контуру **«Сотрудники»** вместе с Employees и Vacations; это соответствует группе `employees` в общем каталоге. Контур «Платформа» содержит отдельную административную «Систему» и инфраструктурные компоненты, но не Dashboard. При переносе компонента между контурами его логические API-связи сохраняются, если сами интеграции не менялись.

Неактивные или планируемые frontend (`available:false`) не считаются развёрнутыми и отсутствуют на карте, даже если остаются в продуктовом каталоге. Модули с `showInLauncher:false` также не отображаются как самостоятельные frontend-приложения.

**Finance (новый контур):** frontend `/finance/`, backend `/api/finance/`, отдельная схема PostgreSQL `finance`; доверенные связи read-only к Employees (зарплатные условия/роли), Clients (периоды, ставки и документы) и Timesheets (фактически отработанные и подтверждённые часы). Пользовательские финансовые операции не изменяют записи соседних сервисов напрямую; изменение платёжного статуса Clients разрешено только защищённым контрактом. Настройки и секреты хранятся на сервере, а не в графе. Host nginx направляет Finance API на loopback `127.0.0.1:8104`, Finance frontend — на `127.0.0.1:8103`; порт `127.0.0.1:8102` остаётся за System. Эти host-порты изолированы; логические узлы и связи карты не меняются.

**Brandbook:** `/brandbook/` — самостоятельный статический frontend в контуре «Платформа». Пока опубликованы только сведения из открытых источников. Нет API и рёбер к бизнес-сервисам; отсутствующие оригиналы не подменяются сгенерированными фирменными активами. Контейнер `brandbook` слушает loopback `127.0.0.1:8105`, host nginx проксирует `/brandbook/`. Статус: In development.

**Design System:** `/design-system/` — публичная витрина с синтетическими примерами, доступная без входа. Она не инициализирует OIDC и не обращается к защищённым API, включая открытие launcher. Пункт каталога помечен `public`; launcher самой витрины показывает только Design System, без закрытых сервисов и фиктивного аккаунта. Авторизация API остальных сервисов сохраняется. У витрины нет runtime-рёбер к Employees или Keycloak; логическая принадлежность контуру «Платформа» не меняется.

**Изменение 21.10.2026 — Keycloak JWT:** отдельный компонент `employees-authorization-sync` (без HTTP listener) получает роли/оргструктуру из Employees и синхронизирует управляемые realm roles в Keycloak. Он работает как фоновый процесс общего образа `irlix-employees`; бизнес-сервисы в JWT-режиме локально проверяют токен, глобальный доступ и локальную матрицу. Включение режима требует успешной сверки и production smoke.

## Обязательный шаг в Definition of Done для всех сервисов

При **любом изменении структуры сервиса** (создание, удаление, переименование, перенос frontend или backend, смена URL и redirect, принадлежности контуру, зависимости от API, фоновой задачи или хранилища), в **том же PR**:

1. Сверить `serviceCatalog.js`, `infra/ci/services.json`, host nginx и действующие API/Compose-связи.
2. Синхронизировать `domainContours`, `nodes`, `links`, `serviceDescriptions` и инфраструктурные узлы в `serviceMapData.js`. Новые frontend-имя и URL подтягиваются из единого каталога автоматически, но назначение в контур и **рёбра** всё равно требуют ревью.
3. При изменении смысла или UX карты обновить этот документ, `docs/SYSTEM_FRONTEND.md`, архитектуру и приватную спецификацию System в `ideas`.
4. Проверить доступность пути, группировку, инспектор, направленные связи и то, что статический граф не выдается за мониторинг.
5. Пройти `apps/portal/tests/resources.test.js`, затем QA/CI итогового SHA. Без обновлённой карты и зелёного контракта структурную доработку не считать завершённой.

Тест сверяет опубликованные frontend с каталогом и registry (с явным исключением исторического `migration-web`), URL и уникальность узлов, состав доменов и концов рёбер, ключевые зависимости System, Migration, Resource Monitor. `apps/portal/Dockerfile` включает копирование `infra/ci/services.json` во временный build-контейнер: contract test выполняется и в локальном QA, и при Docker build; отсутствие файла должно быть ошибкой, а не пропуском проверки. При изменении `packages/ui/` QA уже выбирает Portal; изменения `infra/ci/services.json` и `infra/nginx/irlix-services.conf` теперь тоже выбирают Portal через `scripts/qa/plan.mjs`.

**Ограничение:** ни контракт, ни CI не могут вывести из исходников все новые бизнес-вызовы. Разработчик/аналитик/QA проверяют фактические логические связи каждого затронутого сервиса; неизвестные связи не придумывают и не рисуют.
